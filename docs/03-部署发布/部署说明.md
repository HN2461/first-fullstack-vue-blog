# 已上线站点的日常部署

在 Windows 项目根目录使用 PowerShell 7 运行发布脚本。新服务器需要先装好 Nginx、MongoDB、Node.js、PM2，建立站点、生产配置和永久文件目录，再使用本文更新。首次安装、域名备案、证书续期和分层排错见[从开发到上线详细教程](个人全栈博客系统从开发到上线超级详细教程.md)。

## 1. 按此次改动选目标

| 此次改动 | 在项目根目录执行 | 脚本的主要动作 |
| --- | --- | --- |
| Vue 页面、样式、静态资源 | `pwsh -File scripts\deploy-release.ps1 -Target frontend` | 构建前端、检查编码、验证新包的入口和静态文件，然后切换前端目录。MongoDB 和 PM2 无需操作。 |
| API、后端业务、随包交付的后端脚本或测试 | `pwsh -File scripts\deploy-release.ps1 -Target backend` | 运行后端测试和编码检查，备份 MongoDB、后端及配置，安装生产依赖，校验 Nginx 并重载 PM2。 |
| 前端、后端都有变更 | `pwsh -File scripts\deploy-release.ps1 -Target full` | 执行两端检查，分别备份、替换并验证两端应用。 |
| 仅维护仓库说明或本地开发资料 | 提交并推送 Git | 只有进入前端产物或后端白名单的文件才会随应用发布。 |
| 只编辑文章正文或分类等运营信息 | 按文章维护流程发布或回写 | 普通代码发布包不包含 `output`。既有文章按稳定身份做三方对比，新文章从后台导入为草稿。见[文章本地仓库同步流程](../02-开发指南/文章本地仓库同步流程.md)。 |

## 2. 发布前核对

1. 用 `git status --short`、`git diff --cached --stat` 和 `git diff --cached --check` 核对本次提交，按变更范围检查数据模型、枚举、权限和关联。发布脚本从本地工作区取文件；如有其他人的代码改动，使用本次已测试提交的独立干净工作区发布。
2. 本机准备好 Node.js、前后端各自的锁文件依赖、能运行 Paramiko 的 Python。首次配置可把 `scripts/deploy.local.example.ps1` 复制为 `scripts/deploy.local.ps1`，按示例在本机填写 SSH 连接信息。已有私有配置可继续使用。生产 `backend/.env` 留在服务器。
3. 若更换服务器、调整文件路径或迁移文章附件，核对生产 `UPLOAD_DIR`、历史文章 `OLD_NOTES_DIR` 与文件实际位置。公开文件、`uploads-private`、`work-journal-private` 和仍被引用的旧文章资源应位于可持续保留的位置。位于待替换后端目录中的历史文件须先专项备份并恢复可读路径，防止文章相对图片失效。见[统一文件资源接入与维护](../02-开发指南/统一文件资源接入与维护.md)。
4. 进入上表对应目标的发布流程。`-BackendTestFiles` 可以指定覆盖本次后端改动的测试文件，默认执行完整后端测试。`-SkipChecks -SkipPackage` 仅用于已完成等价验证并明确复用同一份产物的发布。

普通 backend/full 发布执行 `mongodump`，数据库迁移、回填与历史种子同步各有独立入口。`-RunDatabaseTasks` 会执行脚本中整组任务，并备份公开上传、私有资源和历史工作日志目录。仅当本次需要这组任务且已核对范围时使用。反馈菜单与索引有单独的 `-RunFeedbackMigration`，重置书签和清理题库历史也有独立开关。程序启动本身仍执行既有 RBAC 和节假日初始化。见[数据库发布与迁移流程](数据库发布与迁移流程.md)。

## 3. 如何判断发布成功

脚本自动生成 `release/frontend-dist.zip` 或 `release/backend-release.zip`。后端白名单包含 `package.json`、锁文件、PM2 配置、`src`、测试及配套说明。服务器独立保存生产 `.env` 和永久上传目录。增加后端根目录运行依赖时同步核对[打包白名单](../../scripts/package-release.ps1)。

- **看脚本结果。** 前端发布先运行 Vitest 和 Vite 构建。记下输出的 `RELEASE_DIR`。远程阶段完成会打印 `DONE_RELEASE_DIR`，随后本机检查公网首页和 `/api/health`。后端发布另检查 `/api/ready` 是否能在两秒内连通 MongoDB。最后写入 `/www/personal-blog/runtime/release-meta.json`，其 `releaseId`、`target`、`lastSuccessfulReleaseAt` 对应本次发布。发布时间为 UTC。
- **看实际站点。** 在 PowerShell 中执行下面两条只读检查。第一条应返回 200，第二条应返回健康响应。发布前端时可再检查首页引用的新 JS/CSS 能返回；后端问题可登录服务器检查 `pm2 status` 与 `pm2 logs personal-blog-api --lines 120 --nostream`。

~~~powershell
curl.exe -fsS -o NUL -w "%{http_code}" https://haonan.online/
curl.exe -fsS https://haonan.online/api/health
~~~

- **按改动核验业务。** 文章相关改动抽查一篇既有公开文章的详情、封面、正文图片及附件。涉及私有资源时，以具有和缺少相应权限的账号分别核对读取结果。文章同步需保留写前备份，写后再次比对作用范围、内容和运营字段。项目记录部署后可在后台“项目记录台账”导入当天文件。

## 4. 发布失败或需要回退

远程脚本在后端切换至本机健康检查阶段、前端目录切换阶段分别有程序回退处理。公网检查和成功时间写入是后续步骤。在这些步骤失败时先查已运行的版本、域名和服务日志，全量发布也可能已有一个目标切换成功。保留本次输出的 `RELEASE_DIR` 以便按目标恢复。

| 本次要恢复的对象 | 在本次服务器备份目录中核对 |
| --- | --- |
| 前端 | `frontend-before/index.html` 和同目录的 `assets/` |
| 后端和配置 | `backend-before/`、`backend.env.before-release`、`personal-blog.nginx.before-release.conf` |
| 数据库 | backend/full 发布的 `mongodb-before/personal_fullstack_blog/` |
| 原件与绑定 | 文件迁移时的同一恢复点数据库、公开上传、私有上传和历史工作日志备份，及对应核验清单 |

每次发布使用对应发布标识的 `release-*` 目录保存回退材料。公网验收和成功时间记录完成后，脚本按前端、后端分别保留最近两次成功发布的回退目录，完整发布同时计入两类。仅清理有成功标记且材料结构匹配的旧目录，历史未标记副本、专项备份和独立数据恢复点按各自流程管理。程序故障先恢复对应应用。确认数据库数据损坏时才按专项流程恢复，并先保全恢复点以来的新数据。程序回退操作见[首次部署教程第 19 章](个人全栈博客系统从开发到上线超级详细教程.md#19-回滚)，数据库和文件恢复见[数据库发布与迁移流程](数据库发布与迁移流程.md)。

## 5. 配套备份、隔离演练与异机核验

恢复点包含站点 MongoDB、`uploads`、`uploads-private`、`work-journal-private`。生产 `.env` 及业务密钥由服务器独立保管。完整业务恢复需要保留该配置。程序回退、配套备份、历史专项归档各有独立目录。

1. 开发机执行 `python -B scripts/recovery/key.py`。将其生成的公开证书 `backups/recovery/recipient.pem` 和仓库里的 `scripts/recovery/install.sh`、`snapshot.py` 放到服务器独立运维目录。开发机的 `%LOCALAPPDATA%\PersonalBlogRecovery\key.dpapi` 由该 Windows 用户的 DPAPI 保护。迁移开发机或重装系统前，先完成密钥迁移并验证既有归档可解密。
2. 在包含上述三个文件的服务器目录执行 `bash install.sh recipient.pem`，安装 `personal-blog-recovery.timer`。每天北京时间 04:15 开始备份。在服务器执行 `python3 /www/personal-blog/runtime/recovery/snapshot.py daily` 可立即进行完整流程。用 `systemctl list-timers personal-blog-recovery.timer` 查看下次运行，用 `journalctl -u personal-blog-recovery.service` 查看失败与重试。
3. 每次先比较复制前后数据库内容及原件清单，遇到并发修改则放弃候选点。隔离演练使用独立 Linux 网络命名空间及临时 MongoDB 实例，验证归档摘要、文件逐项摘要、集合、文章正文以及公开和私有附件抽样。成功后在 `/www/personal-blog/backups/recovery-points/point-…/` 生成 `verified.json`，加密副本名为 `data.cms`。手工单独建点、演练和加密分别使用 `snapshot.py create`、`snapshot.py verify point-…`、`snapshot.py seal point-…`。
4. 开发机通过已验证主机密钥的 OpenSSH 别名执行 `python -B scripts/recovery/pull.py --sftp 用户@主机`，也可用 `python -B scripts/recovery/pull.py --source 目录` 读取经已验证来源复制的密文、摘要与演练报告。可附加 `--point point-…` 选择日期，默认取最近成功点。归档使用 OpenSSL CMS AES-256-CBC，兼容服务器的 OpenSSL 1.1.1。接收端流式解密并比对可靠来源的 SHA-256，通过后才保存密文、摘要和报告。开发机恢复在线后可补取仍在保留期内的点。
5. 用 `snapshot.py prune` 预览到期的配套恢复点，`snapshot.py prune --apply` 执行。每日任务在新点完成演练和加密后轮转，服务器最多保留两个通过演练的完整恢复点，优先选择最近两个不同日期。上一个恢复点保留原始归档，再次取回时可用 `seal` 重新加密。程序回退目录按第 4 节轮转，历史专项资料需根据用途和恢复核验结果单独清理。
