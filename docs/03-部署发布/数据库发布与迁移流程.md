# 数据库发布与迁移流程

## 发布前决定是否需要写库

| 变更 | 处理方式 |
| --- | --- |
| 纯前端 | 使用 `-Target frontend`，发布流程跳过 MongoDB。 |
| 后端代码、查询、兼容的可选字段或展示逻辑 | backend/full 发布会备份当前 MongoDB，按新旧数据分别验证读取。 |
| 字段改名、旧枚举失效、必填字段、唯一索引、菜单授权或文章与资源关联变化 | 核对旧数据，设计有明确筛选条件的一次性迁移，先预览、再备份、再写入。 |
| 已上线文章改正文、封面或线上运营字段回写 | 按文章身份及上次确认基线比对、同步和验证。见[文章本地仓库同步流程](../02-开发指南/文章本地仓库同步流程.md)。 |

比较当前运行的代码提交与要发布的提交。重点查看 `backend/src/modules/**/{models,services,validators}`、`backend/src/scripts` 和 `backend/src/constants`。下面的 PowerShell 命令可在本机使用，发布提交使用已审阅的 `HEAD`。

~~~powershell
$previousRelease = Read-Host '输入当前线上代码的 Git 提交号'
git diff $previousRelease HEAD -- backend/src/modules backend/src/scripts backend/src/constants
~~~

## 备份与预览

1. 在目标数据库所在环境以迁移脚本的默认 dry-run 列出影响数量、对象范围、冲突和预计动作。涉及新增唯一索引时先核查重复值。新脚本放入 `backend/src/scripts`，显式 `--apply` 才执行写入。
2. 记录当前代码版本、数据库名、备份目录与核验范围。backend/full 发布输出的 `RELEASE_DIR` 中有 `mongodb-before/personal_fullstack_blog/`。纯前端发布生成的目录只包含前端恢复材料。需要单独备份时，在服务器按下面的命令建立独立目录。
3. 对会改动文件、媒体归属或引用的操作，暂停相关写入，保全同一恢复点的 MongoDB、`uploads`、`uploads-private`、`work-journal-private` 及生产实际配置的其他永久文件根。核对文件数量、路径和摘要，再恢复写入。资源迁移细节见[统一文件资源接入与维护](../02-开发指南/统一文件资源接入与维护.md)。

~~~bash
(
  set -eu
  umask 077
  BACKUP_DIR="/www/personal-blog/backups/db-migration-$(date +%Y%m%d-%H%M%S)"
  mkdir "$BACKUP_DIR"
  mongodump --uri="mongodb://127.0.0.1:27017/personal_fullstack_blog" --out="$BACKUP_DIR/mongodb-before"
  test -s "$BACKUP_DIR/mongodb-before/personal_fullstack_blog/articles.bson"
  printf '保存此次恢复点 %s\n' "$BACKUP_DIR"
)
~~~

## 执行与验证

使用本次审阅的具体脚本和预览时相同的筛选参数。`deploy-release.ps1 -RunDatabaseTasks` 会执行发布脚本中列出的整组索引、种子和历史回填，包括文章正文图片绑定以及工作日志凭证迁移。如果只需单项迁移，可在目标后端目录运行对应脚本。意见反馈的专用入口是 `-RunFeedbackMigration`。

写入后再次运行相同范围的 dry-run，应只剩可解释的跳过项或零项待写入。比对重要集合数量，并按影响范围验证身份和引用。例如，修改文章分类时核对原文章 ID、slug、分类和详情；修改文件关联时核对附件、封面、正文链接、相同文件的其他业务引用及私有访问。数据量相同也可能存在错绑，优先核对本次命中的对象。

在服务器查看接口健康和错误日志：

~~~bash
curl -fsS http://127.0.0.1:3001/api/health
pm2 logs personal-blog-api --lines 120 --nostream
~~~

## 代码回退与数据库恢复

发布失败时先核对应用版本、配置、文件目录和接口状态，程序可按[日常部署说明](部署说明.md)回退。确认数据已损坏后优先评估专项备份能否只恢复受影响记录。整库替换会丢失恢复点以后相关集合中的文章、评论、用户、业务记录等变更。

整库恢复或新机初始化前，明确目标库和备份来源。先在隔离数据库验证备份可以还原。生产恢复时先停止应用及其他写入方，备份故障现场，再恢复经确认的备份。下面是当前单实例服务器的操作流程。按实际环境确认连接串和进程名。若恢复失败，保留现场并检查错误，再决定恢复操作及服务重启。

~~~bash
(
  set -eu
  umask 077
  read -r -p '输入包含 mongodb-before 的备份目录完整路径：' BACKUP_DIR
  test -s "$BACKUP_DIR/mongodb-before/personal_fullstack_blog/articles.bson"
  CURRENT_DIR="/www/personal-blog/backups/db-before-restore-$(date +%Y%m%d-%H%M%S)"
  mkdir "$CURRENT_DIR"
  pm2 stop personal-blog-api
  mongodump --uri="mongodb://127.0.0.1:27017/personal_fullstack_blog" --out="$CURRENT_DIR/mongodb-before"
  test -s "$CURRENT_DIR/mongodb-before/personal_fullstack_blog/articles.bson"
  mongorestore --uri="mongodb://127.0.0.1:27017" --nsInclude='personal_fullstack_blog.*' --drop "$BACKUP_DIR/mongodb-before"
)
~~~

`--drop` 会替换备份内包含的集合，目标库中额外出现的集合需要单独核对。若还涉及文件迁移，先从同一恢复点恢复受影响的文件并比对摘要，再启动服务。执行时保留当前完整生产 `.env` 与私有资源解密所需配置。

~~~bash
cd /www/personal-blog/backend
pm2 startOrReload ecosystem.config.cjs --update-env
pm2 status
curl -fsS http://127.0.0.1:3001/api/health
~~~

恢复后按目标核验文章详情、分类、附件、已有用户菜单以及相关联业务，保存恢复点、执行结果和对应核验记录。
