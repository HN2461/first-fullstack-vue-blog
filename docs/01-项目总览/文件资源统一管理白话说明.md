## 此前线上版本怎么找文件（2026-11-11 晚发布）

资源管理仍是一个菜单入口，里面分为“素材库、业务资源、全部资源、回收站”。分类文件夹已经恢复：先选择页签，再点“部署”等文件夹，进去后用列表看文件名、分类和使用情况。上方显示“分类文件夹 › 部署”，点击“分类文件夹”就能返回，不必靠记忆判断当前位置。

你可以把页签理解为“这次想看哪一批资料”，把分类文件夹理解为“这批资料放在哪个资料夹里”。它们都是查找同一批登记文件的方式；页面里的分类是归档标签，不等于服务器磁盘上的真实文件夹。

例如找一张以前收藏的部署图：进入“素材库” → 点“部署”文件夹 → 在列表中找到图片并打开。想跨分类搜索文件名时，点击“全部文件”或列表按钮；想看缩略图挑图片时切换图片网格；想回到分类入口时点击文件夹按钮。小屏幕无需常驻另一条分类侧栏。

文件夹按“自定义分类”和“系统分类”分组，数量只计算当前页签和账号可以看到的文件，默认隐藏空分类，可勾选显示。密码箱仍走独立验证入口。文件的真实使用位置需要打开文件的“使用位置”查看，例如某篇文章或某份简历；分类文件夹本身不代表文件只被这个分类里的一个页面使用。

这一历史版本只调整查找与查看方式，未重新上传、搬动或批量改分类，原有142份资源记录和全部原文件已核对保留。其分区和列表布局现已由下面的初代页面取代；后续开发遵守当前的“初代外观、文件夹进入、原文件网格”规则。

## 一、我到底改了什么

可以把整个网站理解成一个办公室，文章、简历、讨论、个人信息都是不同的办公桌。图片和附件就是这些桌子上使用的资料。

原先，有的桌子上传资料后会登记到“媒体资产”，有的只在自己那里留一个图片地址；各自处理保存、权限和删除。桌子越来越多，管理方式就容易分散。

这次做的是让这些办公桌共用一套文件管理办法。具体有四件事：

1. **统一接收和检查文件。** 看文件大小、是否符合这个用途、图片是否真的能打开，生成文件名并保存。头像、简历和文章仍可有不同限制。
2. **统一登记。** 每份长期保存的文件都有记录，知道它是谁上传的、存在哪里、来自哪个功能、公开还是私人文件。
3. **记录谁在使用。** 比如一张照片同时被两篇文章引用，系统能记录这两处用途。“引用”就是“某个页面或某条业务记录正在使用这份文件”。
4. **按统一规则读取和删除。** 私人文件先检查权限；删除文件前先检查还有没有地方在用；替换一处图片只解除这一处关系。

文件仍保存在目前服务器的磁盘上。数据库里保存的是文件的登记信息和使用关系。文件不需要全部搬进一个文件夹，不同页面也不需要使用完全相同的上传界面。

原有媒体资产页面承担集中查看和管理的职责；简历照片、讨论附件等私人文件即使统一登记，查看内容时仍检查对应业务权限。

## 二、我以后怎么上传

你仍在原来的页面操作：

| 你正在做什么 | 你在哪里操作 | 系统在背后做什么 |
| --- | --- | --- |
| 修改头像 | 个人信息页上传、裁剪 | 保存图片，登记上传人，关联当前头像 |
| 换简历照片 | 简历编辑页 | 登记私人照片，关联当前简历，预览和导出检查归属 |
| 写文章插图 | 文章编辑器上传或选已有素材 | 登记图片，保存文章时记录用途 |
| 发讨论附件 | 讨论页面 | 登记附件，限制可读取的讨论成员 |
| 提交反馈截图 | 反馈页面选择或粘贴 | 登记私人截图，保留反馈凭证 |
| 单纯收藏一份以后可能用到的素材 | 媒体资产页面上传 | 作为主动保留素材保存，即使暂时没有使用也保留 |

**你不需要先去媒体资产上传，再绕回来填每个表单。** 页面上传后，系统在背后完成登记。

## 三、拿一张图片说明删除规则

假设你上传一张“服务器部署示意图”，文章 A 和文章 B 都用了它：

```text
服务器部署示意图
  ├─ 文章 A 正在使用
  └─ 文章 B 正在使用
```

你把文章 A 的这张图换掉，只解除 A 的使用关系，B 仍然能显示。

你把文章 B 放进回收站，图片仍受到保护，因为恢复文章时还需要它。

你直接去媒体资产删除这张图，系统会检查并提示仍有使用方。彻底删除业务记录、解除全部用途之后，再按文件的保留规则处理。

同一篇文章的封面和正文可能分别显示一条用途，因此“引用数量”表示用途条目数，不一定等于文章篇数。列表和详情使用相同口径，不再额外重复增加一条笼统的文章用途。

简历也一样：复制简历后，两份简历可以共用同一张照片，替换第一份简历的照片不会删掉第二份仍在使用的照片。

现有分类包括默认素材、部署、软件和配置、文章原始文档、文章快照原始文档、文章正文图片、密码箱、历史未登记资源、岁时碎片和项目。它们不需要因为统一管理而全部重新分类。

这说明你的判断是对的：当前已登记资源确实由你集中上传。设计重点应放在方便你查找、复用、避免误删，以及方便朋友在各自页面上传；无需把当前系统扩展成一套复杂的多人资源运营平台。

上传人和使用人是两件事。例如你上传一张公开照片后，朋友拿来当头像，文件仍可保留你作为原上传人的信息，同时记录朋友正在使用。不能因为谁在用，就随意修改原上传人。

## 五、旧数据以后怎样接过来

已有 140 份记录已经有自己的文件编号、地址、上传人、分类和公开范围。后续主要是给这些登记卡补上“来源、保留状态、正在被哪些地方使用”，并登记两份遗漏的旧原件。

本次已按以下顺序执行：

1. 先备份数据库和永久文件目录。只备份数据库不能恢复磁盘上的图片。
2. 在生产环境运行只读预演，列出将补登记什么、哪些引用要补齐、哪里存在异常。
3. 确认报告和备份后，明确执行补录；保留已有编号、原文件位置、内容、上传人、分类和密码箱范围。
4. 再跑一次只读预演，验证重复执行不会继续生成重复记录，并核对图片、私人照片和导出。

本次已在生产环境执行补录。正式写入前暂停 API 和后台清理，完成数据库与文件一致备份，确认预演范围后执行；写入后重复预演，各项差异和异常均为 0，再恢复服务并完成公网检查。素材库原有库存无需重新上传。

已有登记素材默认按保留库存接入，即使一时没查到用途也不自动清理。头像和简历能从明确的业务记录确认使用者；遇到找不到文件、归属冲突、文章误用了密码箱文件等情况，脚本报告异常，保留原数据等待处理。

补录不是整库替换，也不需要你重新上传所有资源。脚本允许重复运行，但它不是“全部成功才写入”的整批事务：个别记录异常时，其他记录可能已完成补录，因此仍需要备份、检查报告和重复对账。

## 六、24 小时清理会不会删我的库存

不会因为“超过 24 小时没用”就删除你收藏的素材。

| 文件情况 | 怎么处理 |
| --- | --- |
| 主动上传到媒体资产的素材 | 即使没有引用也继续保留 |
| 这次接入的历史保留素材 | 继续保留，不做历史库存大扫除 |
| 已保存且被文章、简历或其他业务使用 | 受到引用保护 |
| 业务在回收站，未来还可能恢复 | 继续保护所需文件 |
| 上传到表单，但没保存，之后放弃了 | 属于待保存文件，超期后复查，确认没有使用再清理 |
| 原来绑定业务，后来解除最后一处使用的非保留文件 | 等待期限后复查，确认没有其他用途再清理 |
| 保存时网络或数据库出错，不能确定是否保存成功 | 保守保留，留待对账确认，不直接按无引用删除 |

检查任务每 15 分钟运行一批，待保存期限目前是 24 小时。到期只是获得检查资格，不代表立即删除。缩略图是可重新生成的缓存，原件是否删除仍按上面的规则判断。

## 七、公开和私人文件有什么变化

文章里的公开图片、原本主动公开的素材仍按公开资料使用。把一张公开图片选进简历，不会让原本公开的图片自动变成私人照片。

简历专门上传的照片、讨论附件、反馈截图、私人工作凭证则按相应业务检查读取权限。知道一个文件地址，不等于有权打开。媒体管理入口也不会自动赋予所有私人业务内容的读取权限。

新上传文件的读取入口会先检查文件记录和权限，服务器也会关闭相关私人目录的静态直出，避免绕过检查。密码箱继续使用原有额外授权。

## 八、以后加新页面会轻松在哪里

例如以后增加“项目资料”页面，需要上传项目图片和附件。

开发时仍要决定“谁能上传、谁能看、最多多大、页面如何保存”，这些是项目资料自己的业务规则。公共部分已经提供了保存、登记、读取、上传进度和删除保护，不需要再给新页面复制一套。

开发者需要完成：登记这个用途的规则、接入公共上传或选择组件、保存和移除时登记使用关系、补充这个业务的测试与对账入口。它不会因为增加一个上传按钮就自动完成全部业务权限。

目前头像、简历、文章、讨论、工作日志、反馈、媒体素材已接入这套公共能力。头像裁剪、编辑器插图、截图粘贴等专门交互继续保留。

没有在这次顺带引入云存储、自动合并所有同内容文件、多服务器文件共享或自动整理全部历史未知文件。当前优先解决小团体项目中实际存在的分散登记、复用和误删问题。

## 九、这次深度复查额外修好了什么

- 手动选择已登记的公开图片作为简历照片，也会补上使用关系，旧地址与完整网址都能识别。
- 简历从已有公开素材选 PNG 等有效图片时，导出需要 JPG 的模板会转换导出副本，原图片不变。
- 尚未补录新引用的旧简历、旧头像和回收站旧文章，也进入删除前的历史检查。
- 列表显示的引用数和点开后的详情保持一致；状态不确定的保存记录也显示为受保护用途。
- 私人图片使用完整网址，仍然不能绕过检查作为公开文章图片使用。
- 清理遇到应保留的文件会延后检查，避免最早的一批受保护文件长期挡住后面的废弃文件。
- 公共上传组件取消整批待上传文件，素材选择器支持初次打开时加载，搜索按提交的关键词执行。
- 旧记录缺少新状态字段时明确补成保留状态，保留素材筛选可以找到旧库存。

对应自动化回归见 `backend/tests/resource-management.test.js`。上线期间另完成 24 项公网接口和权限核查，以及全部文件内容和部署产物核对；未启动浏览器。

上线前后端 58 个测试文件、391 项测试均有完整通过结果，前端 135 项测试及构建通过。针对 44 条早期公开标记的补齐，资源专项扩充至 16 项并全部通过，累计覆盖 392 个后端用例。UTF-8 无 BOM、JavaScript 语法和差异格式检查通过。后端整批运行曾出现测试工具提前生成报告的问题，已单独补跑未完成文件。
