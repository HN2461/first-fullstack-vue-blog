# 意见反馈功能调研与方案

调研日期：2026-11-09。

## 1. 项目背景与结论

项目由超级管理员与几位注册用户共同使用，属于小规模朋友团体。当前整体使用情况可以接受，上一轮个人效率评估中的建议暂不作为近期开发优先项。本次目标是建立一个站内渠道，让用户报告问题、提出建议，并与管理员持续沟通，了解处理结果。

建议产品名称使用 **「意见反馈」**，管理员端使用 **「反馈管理」**。产品机制采用轻量工单：一条反馈对应一个问题或建议，包含后续回复、处理状态与处理记录；后续按实际需要增加小组内建议看板。

第一版应完整覆盖：**提交 → 管理员收到通知 → 双方补充沟通 → 管理员处理 → 提交者获知结果 → 必要时重新打开**。

本次交付为调研和方案，不包含功能实现、数据库写入或线上部署。市场资料通过官方网页的 HTTP 只读获取完成；未启动浏览器。官网描述用于核实产品提供的机制，不代表本轮对其效果或各套餐进行了实测。

## 2. 市场常见做法

### 2.1 反馈看板：收集需求并让用户了解进度

代表：Canny，也可参考 Featurebase 的反馈产品方向。

Canny 官方介绍包含反馈提交、需求投票、状态更新、公开路线图和更新日志。其更新日志强调向订阅用户通知已发布功能，把用户提出的需求与交付结果连接起来。

适合借鉴：一条建议可以长期跟踪；管理员说明是否采纳；功能发布后通知相关用户。投票、路线图、跨渠道自动采集和收入权重是可扩展能力，现阶段没有必要全部引入。

### 2.2 可视化 Bug 反馈：让问题更容易描述和复现

代表：Userback。

Userback 官方介绍包含站内反馈入口、带标注截图、视频、控制台信息和会话上下文等能力。核心目的在于补足「哪里出了什么问题」的上下文。

适合借鉴：反馈关联页面、用户主动提供截图、少量环境信息。第一版支持粘贴或上传截图即可；录屏、控制台采集和会话回放涉及额外实现与数据处理，不作为默认范围。

### 2.3 工单：把一次问题的所有往来留在同一条记录中

代表机制：GitLab Service Desk。

GitLab 官方文档说明，用户邮件可以生成项目中的工单，处理人员在工单中回复，外部用户继续通过邮件参与，问题处理完后关闭。这里借鉴的是「每个问题单独成条、持续回复和跟踪」的机制，并不建议本项目接入邮件工单或部署 GitLab。

适合借鉴：提交者明确、处理状态明确、回复历史保留、问题完成后有结果说明。客服排班、服务时限、复杂分派和多部门协作不适合当前规模。

### 2.4 Issue：开发侧缺陷与需求跟踪

代表：GitHub Issues。

GitHub 官方文档展示了按问题类型设置模板，以及文本、下拉框、复选框、截图等结构化表单。Bug 模板可以引导填写实际表现、预期表现、版本与浏览器信息。

适合借鉴：Bug 与建议使用不同提示，管理员用标签或关联记录整理开发工作。普通用户使用本站账号即可反馈，不应要求额外注册 GitHub、理解仓库权限或填写完整开发者缺陷报告。

### 2.5 对当前项目的取舍

| 做法 | 强项 | 本项目建议 |
| --- | --- | --- |
| 简单留言表单 | 提交方便 | 可以作为入口，但必须补齐回复和进度 |
| 私聊或群聊 | 随时交流，适合朋友 | 继续用于即时交流；需要处理的问题沉淀到反馈记录 |
| 轻量工单 | 逐条跟踪、补充沟通、结果明确 | 第一版主体 |
| 建议看板 | 大家能看到建议并表达支持 | 第二阶段按需要开放给登录小组成员 |
| 可视化 Bug 平台 | 上下文完整，利于复现 | 第一版借鉴截图和页面上下文 |
| 开发者 Issue 系统 | 连接代码和开发过程 | 由管理员按需要关联，用户端保持易用 |

腾讯兔小巢官网当前可核实的页面标题为「免费便捷的用户意见反馈服务平台」，可作为国内同类入口了解；本轮未取得足够产品文档，不据此断言其具体流程、套餐或接入能力。

## 3. 第一版用户体验

### 3.1 入口与页面

用户侧：

- 在控制台「知识库」域新增数据库菜单「意见反馈」。
- 页面提供「我的反馈」列表和「提交反馈」主操作。
- 可在用户下拉菜单增加快捷入口，显示仍以服务端菜单权限为准。
- 提交时记录用户发起反馈的来源页面，随后跳转反馈页也不丢失该上下文。

管理员侧：

- 在现有「后台管理」域新增「反馈管理」。
- 默认处理人和新反馈通知接收人为超级管理员；普通注册用户只查看自己的反馈。
- 如果以后需要朋友协助处理，再通过明确的 RBAC 角色授予管理权限。
- 不因某账号名称叫管理员，就让其自动读取全部反馈。

不增加新的顶部一级业务域。列表复用 `BlogTable` 现有能力；详情与回复使用有最大高度的抽屉或独立详情页，长内容和图片仅在受约束容器内滚动。

### 3.2 提交什么

用户先选择一种类型：

| 类型 | 引导用户描述 | 第一版必填 |
| --- | --- | --- |
| 问题 / Bug | 发生了什么；当时做了什么；原本希望出现什么 | 类型、标题、内容 |
| 功能建议 | 想解决什么事情；现在如何处理；希望怎样更方便 | 类型、标题、内容 |
| 使用咨询 / 其他 | 哪个地方不清楚，或希望管理员协助什么 | 类型、标题、内容 |

用提示帮助用户补充，不强迫其填写复杂模板。截图、复现步骤、预期表现和来源页面为可选信息；注册身份已能确定提交者，不重复要求填写邮箱、手机号或联系人。

建议支持最多 5 张截图、单张不超过 5 MB，数值在实现阶段结合现有上传限制确定。支持粘贴图片可以减少操作。只上传用户选中的图片；环境信息仅收集可预览的必要字段，如浏览器、设备类型、视口尺寸与版本标识。

来源页面只保存必要路径，移除令牌、分享提取码、搜索私密内容等敏感查询参数；不采集表单正文、密码、浏览器存储和完整网络请求。第一版无需自动截屏、录屏或采集控制台日志。

提交成功后显示反馈编号，并进入该反馈详情。网络失败保留已填内容；重复点击避免生成重复记录。

### 3.3 在哪里交流

每条反馈详情包含：问题内容、截图、处理状态、双方回复和状态变化时间线。

管理员需要更多信息时，在这条反馈下追问，用户直接补充。回复保留发言人和时间，状态变化作为系统事件显示。沟通使用异步回复，不要求双方同时在线，也不需要重做一个即时聊天系统。

如增加管理员内部备注，应与用户可见回复明确区分，绝不能将内部备注发送给用户。当前只有一个处理人，内部备注可以后置。

## 4. 状态与处理规则

建议第一版使用以下六种状态；字段名称统一，用户界面按类型显示「已解决」或「已上线」等结果文案：

| 状态 | 表达的意思 | 下一步 |
| --- | --- | --- |
| 待处理 | 系统已收到，管理员尚未决定如何处理 | 管理员查看、回复或分类 |
| 待补充 | 还需要提交者提供信息 | 用户补充后回到待处理，并通知管理员 |
| 已采纳 | 值得处理，尚未开始 | 管理员安排处理；不自动承诺日期 |
| 处理中 | 已经开始修复或实现 | 管理员更新进度或交付 |
| 已完成 | 已解决、已上线，或咨询已经答复 | 用户查看处理说明；有问题可请求重开 |
| 已关闭 | 重复、暂不处理、无法复现或用户撤回等 | 必须提供原因；可保留关联反馈 |

Bug 可以从待处理直接进入处理中，不要求机械经过所有状态。建议也可以在沟通后直接关闭。

管理员标记完成时填写简短说明；涉及代码修复或新功能时，以用户使用环境中已可用为准。只有代码写完但尚未上线时，仍显示处理中，可以在回复中告知预计安排。

用户通过「仍有问题」提交说明并重新打开已完成项，进入待处理，由管理员再判断。用户撤回采用关闭原因，保留沟通记录。关闭不等于删除，也不因为管理员看过通知就自动改变业务状态。

可以暂不提供优先级给用户填写；由管理员根据影响判断轻重。功能建议是否实现仍由管理员决定，采纳、暂缓和拒绝均有明确回复。

## 5. 消息如何到达双方

| 事件 | 接收人 | 行为 |
| --- | --- | --- |
| 注册用户提交反馈 | 超级管理员 | 小铃铛出现未读提醒，点击打开对应反馈 |
| 用户补充或回复 | 超级管理员 | 提示该反馈有新回复 |
| 管理员回复 | 提交者 | 提示管理员已回复，点击查看同一条记录 |
| 管理员改变采纳、处理、完成或关闭状态 | 提交者 | 提示进度发生变化，并显示处理说明 |
| 操作者自己的动作 | 操作者本人 | 显示操作结果，不再给自己新增未读提醒 |

第一版使用持久化站内通知：离线期间反馈仍保存在数据库，管理员下次登录后能够看到；这不等于退出网站后手机也会收到推送。若需要离站立即提醒，再接入经过配置的邮件等渠道。

在线实时性可以先沿用当前轮询方案：项目小铃铛每 60 秒刷新未读数。第一版明确这个时效，必要时缩短合理间隔。即时推送是后续增强，通知可靠落库比瞬时动画更关键。

回复和状态更新以反馈记录为准；通知携带反馈链接与事件标识，重复重试不得重复制造未读消息。通知临时写入失败时，应允许补发，不能因此丢掉已保存的反馈，也不能让用户误以为提交失败后反复提交。

## 6. 反馈可见范围

建议第一版全部采用 **「本人 + 获授权处理人」** 可见，Bug 截图和工作内容不会因为进入建议列表而被其他朋友看到。

第二阶段可新增「小组建议」看板，仅登录且有权限的小组成员可见。值得共同讨论的建议由管理员整理摘要，确认没有私人内容并取得提交者同意后发布；其他人可以支持、订阅进度。小组可见与匿名互联网公开应明确区分。

不建议第一版让所有反馈默认全员可见，或同时加入投票、匿名反馈、复杂关注规则。先跑通提交与回复，观察大家是否确实需要共同讨论的需求池。

## 7. 当前代码可以复用什么

### 7.1 定向系统通知可以复用

`backend/src/modules/notification/services/notification.service.js:22` 已有 `createSystemNotification(input, recipientId)`；通知模型支持接收人、链接、已读、时间等。权限审批也在使用这个服务，说明现有系统已具备向特定用户发送站内结果通知的基础。

`frontend/src/components/NotificationBell.vue` 已有未读数、通知列表与轮询。反馈可以在此复用提醒入口，但当前系统通知被归入「公告」列表，点击后先打开公告详情，再以链接进入目标。接入反馈时应明确标注「反馈回复 / 处理进度」，让点击直接进入该反馈；必要时增加反馈分类，不必另造一个铃铛。

通知的列表、读取和链接目标都要校验接收人权限。反馈撤回、角色变化或目标不可访问时有合理提示。

### 7.2 现有讨论适合借鉴交互，不适合直接充当反馈数据

项目讨论已有回复、附件、私聊/群组和实时连接，可以借鉴展示方式。但反馈需要独立编号、类型、状态、处理记录与稳定留存；当前讨论线程状态只有 active/archived。

讨论配置有每用户 300 条消息的保留上限，清理逻辑会移除超出部分及其附件。把反馈历史直接放进讨论消息，会把业务留存绑定到聊天清理策略。

此外，现有实时连接属于 `/discussions` 命名空间，授权依赖讨论模块权限。没有讨论权限的注册用户也应能使用自己获授权的反馈入口，不能为了收提醒被迫获得整个讨论模块权限。

结论：反馈记录和回复独立存储，复用通用视觉、通知与鉴权基础；如后续扩展通用实时通知，明确独立授权边界。

### 7.3 数据与附件建议

新后端代码按规则放入 `backend/src/modules/feedback/`：

- 主反馈：编号、类型、标题、内容、提交者、状态、关闭原因、必要页面上下文、最后活动时间。
- 回复与事件：反馈 ID、作者、文本/附件、事件类型和时间；状态历史与公开回复清楚区分。
- 截图：受控上传与下载，仅本人和授权处理人可访问。

私密反馈截图不能直接放进当前公开 `/uploads` 静态路径；优先参考工作日记私有凭证的鉴权读取方式。注册用户无需获得管理员媒体库权限。独立的内部备注若后续加入，使用单独可见范围并在服务端过滤。

菜单可考虑新增 `/console/feedback` 与 `/console/manage/feedback`，复用详情展示组件。业务权限仍来自数据库菜单和 RBAC，不在前端按用户名或固定角色名称写死。新增种子、菜单与索引时按发布迁移规则提供 dry-run、影响范围和 apply 流程。

上述名称与路径是方案建议，并非已实现接口。

## 8. 第一版范围与后续扩展

第一版必须完整包含：

1. 登录用户提交问题、建议、咨询，附截图和可选页面信息。
2. 我的反馈列表、详情、回复、状态与处理记录。
3. 超级管理员反馈管理、筛选、回复、状态更新和处理说明。
4. 提交、回复和进度变化的双向站内通知；离线后再次登录可找回。
5. 已完成问题重新打开、反馈撤回，以及必要的归属和附件权限检查。
6. 加载、空态、失败重试、表单保留和手机窄屏下的核心可用性。

后续根据真实使用再选择：小组建议看板、支持/订阅、重复反馈关联、批量整理、邮件提醒、修复版本关联、已上线更新摘要、开发任务或项目台账关联。

当前无需引入企业客服排班、SLA、复杂工作流、机器人自动回答、AI 优先级评分、自动录屏或第三方工单平台同步。对几位朋友的小项目，内置轻量功能可以复用现有账号和权限，也不用让大家切到另一套工具。直接使用第三方平台能更快开通完整产品，但会新增账号接入、外部数据存放、套餐与维护边界；本次没有做采购或接入决定。

## 9. 用一条真实情景验收

小王在手机上发现账本筛选不正常，打开意见反馈，填写标题与表现并上传截图。系统生成编号，超级管理员的小铃铛出现未读。管理员追问日期范围，小王在同一条记录补充。管理员标记处理中，修复上线后写明结果并标记已完成。小王下次登录看到结果，点击回到原反馈；仍未解决时可以补充说明并重新打开。

还需要验证：A 用户不能读 B 用户的反馈或图片；普通用户不能处理全站反馈；没有讨论权限仍可按反馈权限正常收到反馈提醒；通知已读不改变处理状态；重复提交与重复事件不生成多条；聊天历史清理不影响反馈记录。

研究阶段只新增文档，未运行构建或业务测试；实现阶段再按实际风险补齐测试与构建。浏览器验证继续遵守当前项目的授权规则。
