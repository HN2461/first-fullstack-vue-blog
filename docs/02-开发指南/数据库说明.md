# 数据库说明

本文档用于说明当前项目的数据层结构，帮助理解：

- 项目使用什么数据库
- 主要集合有哪些
- 每类数据大概存什么
- 代码发布与业务数据导入的边界
- 后续更新时，数据库通常要不要动

## 1. 当前使用的数据库

当前项目使用的是：

- 数据库：MongoDB
- ODM：Mongoose
- 后端连接配置位置：`backend/src/config/database.js`
- 运行时连接串来源：`backend/.env` 中的 `MONGODB_URI`

本机开发环境的默认数据库连接串示例：

```text
mongodb://127.0.0.1:27017/personal_fullstack_blog
```

这表示：

- 数据库服务运行在本机
- 数据库名是 `personal_fullstack_blog`

## 2. 为什么代码发布不会自动带来文章数据

项目代码发布和业务数据导入是两件独立的事。部署脚本不会把本地 MongoDB 整库覆盖到线上，也不会自动把本地 Markdown 文章写入线上数据库。文章通常通过文章导入或项目专用的文章同步流程进入数据库。

首次部署时，可能只创建了管理员和系统设置，因此文章、分类、标签、评论和媒体内容暂时为空。这是初始化数据范围的结果，不一定表示部署失败。

需要新增文章时，使用后台文章录入/导入流程或受控的文章同步工作流；不要把整库恢复当作日常文章同步方式。

初始化阶段一般会执行：

- 安装 MongoDB
- 初始化管理员账号
- 启动前后端服务

具体初始化内容以目标数据库当前数据为准，查看后台列表或使用只读统计接口，不要依赖本节假设线上数据为空。

## 3. 为什么 `.env` 有管理员信息，还要执行创建管理员脚本

`backend/.env` 中的这几项：

```text
ADMIN_USERNAME
ADMIN_EMAIL
ADMIN_PASSWORD
```

只是给管理员初始化脚本提供参数，本身不会自动把管理员写入数据库。

真正把管理员写入 MongoDB 的命令是：

```bash
npm run create:admin
```

这个脚本会：

- 如果管理员邮箱不存在：创建一个管理员账号
- 如果管理员邮箱已存在：更新成管理员，并重置为 `.env` 中的密码

所以：

- `.env` 是原料
- `create:admin` 是执行动作

## 4. 当前主要集合说明

下面这些集合来自各业务模块中的 Mongoose 模型，通常位于 `backend/src/modules/<业务模块>/models`。

### 4.1 users

来源文件：[User.js](../../backend/src/modules/user/models/User.js)

用途：

- 存储用户账号
- 包括普通用户和管理员

主要字段：

- `username`：用户名
- `email`：邮箱，唯一
- `passwordHash`：密码哈希，不存明文
- `avatar`：头像
- `bio`：简介
- `website`：个人网站
- `location`：地区
- `notificationSettings`：通知设置
- `role`：角色，普通用户或管理员
- `status`：状态，是否启用

说明：

- 注册页创建的默认是普通用户
- 管理员是通过脚本或后台权限调整产生的

### 4.2 articles

来源文件：[Article.js](../../backend/src/modules/content/models/Article.js)

用途：

- 存储文章正文和文章元数据

主要字段：

- `title`：标题
- `slug`：文章唯一标识，用于路由
- `summary`：摘要
- `contentMarkdown`：Markdown 正文
- `cover`：封面
- `resources`：附带资源
- `category`：所属分类
- `tags`：标签数组
- `status`：状态，如草稿/已发布

- `publishedAt`
- `createdBy` / `updatedBy`
- `deletedAt`

说明：

- 文章正文真正存储在 `contentMarkdown`
- 文章同步或迁移前必须先备份，并确认筛选范围，避免误改正文

### 4.12 workLogs

来源文件：[WorkLog.js](../../backend/src/modules/workJournal/models/WorkLog.js)

用途：

- 存储按工作经历和日期归档的工作日记，支持草稿、定稿、周/月汇总和 ZIP 导出。
- 图片凭证元数据内嵌在日记中；图片文件保存在私有目录，不进入公开 `/uploads` 静态目录。
- 删除采用软删除，恢复前保留正文、历史版本和图片凭证。

主要字段：

- `employment`、`workDate`、`title`、`summary`
- `accomplishments`、`blockers`、`nextPlan`、`contentMarkdown`
- `status`、`finalizedAt`、`version`、`revisions`
- `evidence`、`deletedAt`、`createdBy`

说明：

- 同一用户、同一工作经历、同一天只允许一篇日记，依赖复合唯一索引保障；软删除记录仍占用该日期，恢复时不会和新建日记冲突。
- 生产环境关闭 Mongoose 自动建索引。首次部署或模型索引有变化时，先备份 MongoDB，再在 `backend` 目录执行 `npm run work-journal:indexes` 检查；确认计划后执行 `npm run work-journal:indexes:apply` 创建缺失索引。
- 日报图片作为 `Media` 资源登记到系统分类“工作日志”，资源记录保留日报与图片关联、上传人及 SHA-256；文件存放在 `uploads/work-journal` 并设置私有访问，静态 `/uploads` 路径对该目录返回 404，图片只能通过工作日记鉴权接口读取。
- 新上传图片会同时出现在日报详情和管理员“媒体资产”页面的“工作日志”分类；媒体引用信息能定位来源日报。软删除进入媒体回收站，彻底删除会清理日报关联和磁盘文件。
- 首次启用该存储方式时，先执行 `npm run work-journal:media-migrate` 查看旧私有凭证的数量、容量和完整性；确认 MongoDB 与旧凭证目录备份后再执行 `npm run work-journal:media-migrate:apply`。迁移按 `workJournalLog + workJournalEvidence` 幂等登记，并在关联保存后移除旧文件。

### 4.13 workReports

- 创建报告时按选择日期生成对应自然周或自然月的初始 Markdown 内容，之后的编辑不再覆盖日报原文。

主要字段：

- `employment`、`period`、`fromDate`、`toDate`
- `title`、`contentMarkdown`、`sourceLogIds`

说明：

- 同一用户、同一工作经历、同一周期区间只允许保存一份周报或月报。
- 新增工作日记报告后，执行 `npm run work-journal:indexes:apply` 与 `npm run work-journal:indexes:verify` 以创建、核验报告唯一索引。

## 5. 首次部署时，数据库通常需要做什么

首次部署一般只需要做这几件事：

1. 安装并启动 MongoDB
2. 在 `.env` 中写好 `MONGODB_URI`
3. 初始化管理员账号
4. 如果项目有历史内容，再执行数据导入脚本

实际步骤取决于部署环境是否已有数据。管理员初始化、RBAC 种子和文章导入分别有各自的脚本或后台流程，执行前应查看脚本说明与 dry-run 输出。

## 6. 后续更新时，数据库通常要不要动

大多数普通前端更新：

- 不需要动数据库

普通后端接口或页面更新：

- 也不一定要动数据库

只有下面几种情况，数据库才需要额外处理：

- 新增了模型字段
- 写了数据迁移脚本
- 需要导入历史文章
- 需要初始化或修复某类数据

所以你之前感觉“前端、后端、数据库应该独立”，这个理解是对的。正常更新时，它们确实不总是一起动。

可以简单理解为：

- 前端：更新页面和交互
- 后端：更新接口和服务逻辑
- 数据库：只在数据结构或数据内容变化时处理

## 8. 当前阶段结论

数据库是否正常，应以目标环境的健康接口、后端日志和只读业务查询结果为准。本节不固定描述线上当前文章数量或部署阶段，避免把过期的阶段记录误当作实时状态。

## 9. 发布元数据不属于业务数据库

最近成功发布时间保存在服务器运行目录 `/www/personal-blog/runtime/release-meta.json`，由发布脚本在部署和公网检查全部成功后更新。该文件包含最后成功时间、发布目标和发布编号：

```json
{
  "lastSuccessfulReleaseAt": "2026-11-01T13:35:00.000Z",
  "target": "full",
  "releaseId": "20261101-213500"
}
```

它不是 MongoDB 迁移数据，不要求 frontend-only 发布连接数据库，也不应通过整库备份/恢复维护。
