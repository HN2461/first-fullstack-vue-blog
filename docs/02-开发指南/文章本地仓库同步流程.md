# 文章本地仓库同步流程

## 目录定位

`output` 是文章内容的本地权威仓库，文章正文不再长期散落在多个导出目录中。

```text
output/
├─ 线上文章/
│  ├─ manifest.json
│  ├─ README.md
│  └─ 按线上分类路径存放的文章
└─ 未导入线上/
   └─ 尚未同步数据库的本地草稿和专题
```

- `线上文章`：文章的本地唯一权威源，与本地、生产数据库中的全部未删除文章对应；目录层级必须与分类路径一致。
- `未导入线上`：只放尚未进入线上数据库的内容，可以继续在本地完善和调整分类。
- 文章是否上线以数据库和 `manifest.json` 中的 `originalId`、`originalSlug` 为准，不能仅凭文件夹名称或标题判断。
- 对线上文章进行 AI 修改时，直接编辑 `线上文章` 中的对应文件，不再额外复制一份“修改版”。
- 差异分析报告统一写入 `docs/02-开发指南/文章同步报告`，不放在 `output` 内容目录中。
- 当前基线的文章全部为 `published`；未写完的新文只放在 `未导入线上`，不以草稿状态混入权威快照。

## 本地内容优先原则

- 历史本地文件可能比线上版本更新，必须比较正文、标题、摘要、标签、封面和分类后再选择保留版本。
- `originalId`、`originalSlug` 和线上导出时间只用于确认文章身份，不能用于判断哪份正文更新。
- 本地与线上正文有差异时，默认保留本地版本并进入待同步清单；不能使用线上快照直接覆盖。
- 线上不存在但本地存在的文章默认移入 `未导入线上`。只有明确确认永久废弃后才清理，并且清理前必须保留可恢复备份。
- 旧导出文件缺少的新字段，例如 `sortOrder`，可以从当前数据库补齐；字段缺失不代表本地正文是旧版本。

## 生成权威快照

在确认本地数据库已经与线上同步后执行：

```powershell
cd backend
npm run article-repository:export -- --output=../output/article-repository-latest.zip
```

导出命令使用原 slug，不追加 `revision-日期`。目标文件已存在时默认拒绝覆盖；确需覆盖时显式增加 `--force`。

ZIP 解压并通过 `manifest.json` 完整性校验后，才可以替换 `output/线上文章`。替换前必须备份旧目录，不能直接覆盖一份尚未验证的权威快照。

## 日常维护顺序

### 已上线文章的小范围修改

1. 从 `线上文章` 中找到原文章并直接修改；`originalId` 和 `originalSlug` 是稳定身份，禁止由 AI 删除、改写或复制为新的身份。线上后台同样允许调整分类、排序、状态、标签或导入新资料，但这些操作必须进入回写流程。
2. 修改后先审阅 `git diff -- output/线上文章`，确认只包含预期文章和字段，再提交 Git。
3. 在目标数据库所在环境运行 `npm run article-authority:compare`。该命令按“上次确认基线 / 本地 / 线上”三方比较，分别输出正文待推送、线上运营信息待回写、冲突和仅线上新文章。
4. 只有报告没有冲突、没有线上运营字段待回写时，才可运行 `npm run article-authority:sync -- --slugs=文章-slug` 预览；确认仅包含预期正文后，才运行 `npm run article-authority:sync -- --apply --slugs=文章-slug`。该命令只会更新标题、摘要、封面和正文，绝不覆盖线上分类、标签、排序或发布状态。
5. 生产端必须先部署包含 `output/线上文章`、新版脚本和同一 Git 提交的发布源，再运行生产预览。写入时必须显式使用：

```bash
npm run article-authority:sync -- --apply --target=production --confirm-production-content-sync --slugs=文章-slug
```

6. 写入前脚本会备份命中文章，写入时以预览时的 `updatedAt` 为条件；若后台有人在预览后修改了同一文章，脚本会拒绝覆盖。写后再次执行 `article-authority:compare`，并保留生成的增量同步审计 JSON。

### 线上后台运营回写

1. 后台重新分类、排序、调整发布状态、标签或导入外部资料后，先运行 `npm run article-authority:compare`，不得直接执行正文同步。
2. 对于已有本地文章且仅线上运营字段变化，先预览 `npm run article-authority:pull -- --slugs=文章-slug`，再使用 `--apply` 回写本地 Front Matter 和 `manifest.json` 基线。
3. 对于报告中的“仅目标数据库存在”文章，使用目标数据库导出 ZIP 并经过三方审阅后纳入 `output/线上文章`；脚本不会把它自动删除，也不会凭标题猜测身份。
4. 同一字段被本地和线上同时修改，或旧快照缺少正文 hash 无法判断来源时，报告会阻断；必须人工合并后重新建立基线，禁止任选一端覆盖。

### 新文章发布

1. 新文章与学习专题只放在 `未导入线上`，不要手动移动到 `线上文章`，也不要手工向 `manifest.json` 追加记录。
2. 使用后台导入或经过审查的专项导入脚本创建草稿；普通导入只会新建草稿或跳过重复 slug，不会覆盖原文章。
3. 在后台补齐分类、标签、排序并发布后，从目标数据库重新导出 ZIP，校验 `manifest.json` 与文件完整性，再以备份后的方式更新 `线上文章`。
4. 更新权威快照后提交 Git；此时新文章才成为下一次增量同步可识别的既有文章。

### 全量快照重建

`article-snapshot:apply` 会删除并重建文章、分类和标签，只用于历史收敛、灾难恢复或已经明确确认本地快照是完整权威源的迁移，禁止作为日常 AI 修改文章后的发布命令。

执行全量重建前仍应遵循：

1. 运行 `npm run article-snapshot:prepare -- --publish-all` 检查发布状态、重复排序和章节顺序；只在报告确认后运行 `npm run article-snapshot:prepare:apply -- --publish-all`。
2. 运行 `npm run article-snapshot:dry-run -- --publish-all`，检查更新、新增、删除和分类变化数量。
3. 生产同步前依次执行生产 dry-run、`mongodump` 整库备份和脚本 EJSON 专项备份；生产写入必须显式传入 `--target=production --confirm-production-replace`。
4. 同步保留同 ID 或同 slug 文章的阅读量、推荐状态、附件、评论和互动；历史孤立评论和互动默认也保留，只有专项审计后显式传入 `--clean-orphans` 才允许清理。

## 目录排序规则

- 数据库和线上目录以 `sortOrder` 升序为唯一排序权威，文件管理器的名称排序不代表线上顺序。
- 每个分类内的排序值规范为 `10、20、30...`，避免 `0` 和重复值导致时间字段参与排序。
- 同级分类也按当前可见顺序固化为 `10、20、30...`，解决接口和前端在重复值下分别按创建时间、名称二次排序的差异；系统“默认分类”保留 `-9999`。
- 同一分类有两篇以上明确标注“第 N 篇 / 章 / 节”或 `01-`、`02：` 时，按章节号升序；总目录和学习导航优先。
- 无章节号的分类保留当前线上顺序；如果同一分类出现多组重复章节号，视为多套教程混放，不自动交叉重排。

## 删除规则

- `线上文章` 中删除文件不等于自动删除数据库文章；删除线上文章必须使用支持删除预览的同步脚本，并显式确认影响范围。
- 当前导入页面只会创建新草稿或跳过重复文章，不能用于覆盖更新。
- 历史导出副本、重复目录和已经从线上删除的旧文章，在确认权威快照完整并完成备份后清理。
