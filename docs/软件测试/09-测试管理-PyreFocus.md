# 09 测试管理与 PyreFocus

## 本阶段目标

理解测试管理系统中的对象关系，并把前面写在 Markdown/表格里的内容变成可跟踪的测试周期：需求或版本 → 测试计划 → 测试套件 → 用例 → 执行 → 缺陷 → 回归 → 报告。

## 先理解测试管理系统解决什么问题

如果用例只写在个人记事本里，团队很快会遇到这些问题：谁测过不知道，失败用例和缺陷对不上，修复后没有回归记录，版本结束时无法统计通过率。因此测试管理系统的价值不是“多一个表格”，而是让每条测试都有负责人、版本、执行结果和历史证据。

可以把它理解为一条链：

```text
项目 -> 版本 -> 测试周期 -> 测试套件 -> 测试用例 -> 测试执行 -> 缺陷 -> 回归结果
```

对象关系要清楚：同一条用例可以在多个版本执行；一次执行失败可以关联一个或多个缺陷；缺陷关闭后要重新执行原用例，而不是只把缺陷状态改成“已关闭”。

## 关于 PyreFocus 名称

不同团队可能使用同名、定制版或课程版工具。当前项目没有该工具的安装实例，因此本文不虚构具体按钮名称。打开你使用的 PyreFocus 后，先找到与下列通用对象对应的菜单；如果实际叫“项目”“版本”“测试集”“缺陷”或英文名称，建立同义映射并记录在 `工具字段对照.md`。

如果你说的 PyreFocus 是课程中的特定产品，请先记录产品准确名称、版本和登录地址。没有确认前，不要把别的工具菜单截图当成 PyreFocus 教程。本文先教通用方法，等工具版本确定后再把按钮名称逐一映射。

## 0. 第一次登录后的准备

1. 使用测试账号登录，不使用生产管理员账号做练习。
2. 找到个人设置，确认时区、日期格式和通知设置。
3. 找到项目列表，确认自己有创建项目、用例、执行和缺陷的权限。
4. 截一张不包含 Token、邮箱隐私和密码的首页截图。
5. 建立 `工具字段对照.md`，记录左侧菜单、创建按钮、保存按钮、状态字段的实际名称。

如果看不到某个菜单，先判断是权限不足、项目未创建还是工具版本没有该功能，不要直接认为工具不支持。

## 1. 建立项目与版本

1. 新建项目：`个人全栈博客系统-测试练习`。
2. 设置项目描述、时区、默认负责人和缺陷严重级别。
3. 新建版本：例如 `local-2026-09-18`，写入 Git 提交号和环境地址。
4. 建立模块树：认证、公开阅读、知识库、文章管理、RBAC、媒体、评论、设置、性能。
5. 建立测试周期：冒烟、功能回归、发布验收；每个周期写开始时间、结束时间和准出标准。

### 1.1 每个字段怎么填

- **项目名称**：使用稳定名称，不要每次测试都创建新项目。
- **版本**：写产品版本和 Git 提交，例如 `local-2026-09-18-abc1234`。
- **模块**：按用户理解的业务模块分组，不按开发者个人文件名分组。
- **严重级别**：提前定义阻塞、严重、一般、轻微的判断规则。
- **测试周期**：写清本次执行的是冒烟、回归还是发布验收。
- **环境**：写前端、后端、数据库地址和浏览器版本。

建立完成后重新打开版本详情，确认保存的数据没有丢失，再进入下一步。测试管理系统中“页面提示保存成功”也要抽查刷新后的数据。

## 2. 导入或新建用例

每条用例填写：模块、标题、前置条件、步骤、输入、预期、优先级、类型、标签、关联需求/版本。优先录入 P0/P1 用例，再补 P2/P3。避免把十几个动作塞到一个“验证所有功能”的大用例。

推荐标签：`smoke`、`regression`、`api`、`ui`、`db`、`permission`、`boundary`、`performance`。

### 2.1 新建一条用例的完整示例

```text
标题：普通用户不能发布其他用户的草稿
模块：RBAC/文章管理
优先级：P0
类型：接口、权限、回归
前置条件：普通用户已登录；管理员创建了一篇草稿；已知文章 ID
步骤：
  1. 使用普通用户 Token 调用文章发布接口。
  2. 请求路径中的文章 ID 使用管理员创建的草稿 ID。
预期：返回 403 或项目约定的无权限错误；文章状态仍为 draft；公开接口查不到该文章。
标签：permission, api, smoke
```

“普通用户不能发布”是业务结论，“返回 403”是接口证据，“状态仍为 draft”是数据库/副作用证据，三者都写出来，执行结果才有价值。

### 2.2 批量导入前的检查

如果工具支持 CSV/Excel 导入：

1. 先用 2 条用例做小批量试导入。
2. 确认列映射：标题、步骤、预期、优先级、标签没有错位。
3. 确认换行、中文和特殊字符显示正常。
4. 确认失败行有错误提示，成功行没有重复导入。
5. 再导入完整套件，并保存导入时间和文件版本。

## 3. 创建执行并填写结果

1. 从版本创建测试执行，选择本轮范围和环境。
2. 按用例逐条执行，填写通过、失败、阻塞、跳过，不用“未执行”代替失败。
3. 失败时关联缺陷，附上最小复现步骤和原始证据路径。
4. 修复后重新执行同一用例，写回归结果和修复版本。
5. 不要删除历史执行结果；测试管理系统的价值在于保留过程和趋势。

### 3.1 四种执行状态的区别

- **通过**：实际结果符合预期，并有证据。
- **失败**：实际结果不符合预期，通常应关联缺陷。
- **阻塞**：由于环境、依赖或前置缺失暂时无法判断，不等于功能失败。
- **跳过**：本轮明确不执行，必须写原因和后续计划。

例如后端服务未启动，登录用例应标为阻塞并记录环境问题；如果服务正常但错误密码返回 200，应标为失败并提交缺陷。

### 3.2 执行一条用例的填写顺序

1. 选择正确版本和环境。
2. 打开用例详情，先读前置条件和预期，不要只看标题。
3. 按步骤执行，每一步都记录实际观察。
4. 选择状态并填写实际结果。
5. 上传脱敏截图、响应或日志链接。
6. 失败时创建/关联缺陷，保存缺陷编号。
7. 执行清理动作，再关闭本次执行。

## 4. 练习一次完整周期

- [ ] 建立版本和三个测试周期。
- [ ] 导入 20 条文章/登录/RBAC 用例。
- [ ] 执行 10 条冒烟用例，故意制造 1 条失败。
- [ ] 从失败用例创建缺陷，关联模块、版本和证据。
- [ ] 把缺陷状态推进到修复、待回归、关闭或重新打开。
- [ ] 导出执行统计：总数、通过、失败、阻塞、跳过和通过率。

### 4.1 通过率计算练习

假设总用例 20 条：通过 15、失败 2、阻塞 1、跳过 2。明确写出：

- 执行数 = 15 + 2 + 1 = 18。
- 执行通过率 = 15 / 18 = 83.33%。
- 总计划通过率如果把跳过也算进分母，则为 15 / 20 = 75%，但这个数字必须注明口径。

不同工具可能默认不同分母，报告中一定要写公式，不要只复制一个百分比。

## 6. 工具不可用时的替代练习

如果暂时没有 PyreFocus：

1. 用 `测试记录/日期/09-PyreFocus/` 目录保存项目、版本、用例、执行和缺陷 Markdown 文件。
2. 用表格中的唯一编号关联它们，例如 `CASE-001`、`RUN-20260918-001`、`BUG-001`。
3. 按同样生命周期推进状态，并导出一份统计。
4. 工具安装后再把这些对象录入，不要因为没有工具而跳过测试管理训练。

## 7. 本阶段常见错误

1. 用例标题写成“测试文章功能”，没有可执行步骤。
2. 把阻塞写成失败，导致错误的缺陷统计。
3. 修复后新建一条相似用例，丢失原用例历史。
4. 删除失败执行记录，导致版本看起来虚假全绿。
5. 导入用例前不做小批量验证，出现整批字段错位。

## 8. 本阶段交付物

- PyreFocus 版本和字段对照表
- 一个项目、一个版本、三个测试周期
- 至少 20 条用例
- 10 条执行结果
- 1 条失败用例和关联缺陷
- 1 次回归结果
- 执行统计及计算口径

## 完成标准

你能在 PyreFocus 中从一个版本建立测试周期、录入用例、执行用例、关联缺陷、完成回归，并导出一份别人能读懂的执行统计。若工具不可用，要能用本文同样的字段在表格或 Issue 系统中完成闭环。
