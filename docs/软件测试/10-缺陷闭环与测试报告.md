# 10 缺陷闭环与测试报告

## 本阶段目标

学会把“发现问题”变成开发人员可复现、产品人员可判断、测试人员可回归的缺陷记录，并在周期结束时给出有证据、有边界的测试结论。

## 先理解什么才算缺陷

缺陷不是“我不喜欢这个页面”，而是可观察的实际结果与已确认的预期不一致。预期可以来自需求、设计、接口契约、数据规则、安全规则或团队约定。

提交前先做三件事：

1. 用最小数据确认现象仍然存在。
2. 重复执行，记录必现还是偶现。
3. 排除环境和测试数据问题，例如服务没启动、账号没有权限、浏览器缓存或数据已经被别人改过。

如果预期本身不明确，先提“需求疑问”，不要把争议直接写成缺陷。


标题写“条件 + 现象 + 影响”，例如：`普通用户携带有效 Token 调用文章发布接口返回 200，导致草稿被发布`。不要写“接口有问题”“页面不对”这种无法检索的标题。

### 1.1 最小复现原则

步骤越少越好，但不能省略必要前置。优先删除无关点击、无关数据和无关环境差异，直到另一个人可以在 3 到 8 步内复现。复现步骤中不要写“正常登录”“填写正确内容”，要写具体角色、输入和按钮。

### 1.2 缺陷单示例

```markdown
# [文章权限] 普通用户可发布管理员创建的草稿，造成公开内容越权

## 环境
- 版本/提交：abc1234
- 后端：http://127.0.0.1:3001
- 账号：普通用户（测试账号，不写密码）

## 前置条件
1. 管理员创建文章 `qa_20260918_draft`，状态为 draft。
2. 普通用户已登录并获得自己的认证信息。

## 复现步骤
1. 使用普通用户认证信息调用文章发布接口。
2. 将文章 ID 设置为管理员创建的草稿 ID。

## 预期结果
返回无权限错误，文章仍为 draft，公开端不可见。

## 实际结果
接口返回成功，文章变为 published，公开端可以访问。

## 影响
普通用户可以发布不属于自己的内容，属于核心权限风险。
```

## 2. 缺陷严重级别

| 级别 | 判断 |
| --- | --- |
| 阻塞 | 无法启动、无法登录、数据大量损坏、核心链路完全不可用 |
| 严重 | 核心功能错误、越权、数据丢失、公开内容泄露 |
| 一般 | 功能可绕过但影响正常使用，部分场景失败 |
| 轻微 | 文案、样式、非关键交互问题 |

严重级别描述影响，优先级还要考虑版本目标、用户数量、发布时间和修复成本。

### 2.1 严重级别和优先级不要混淆

严重级别回答“坏得有多严重”；优先级回答“现在多快要修”。一个只影响少数管理员的严重安全问题仍可能是高优先级；一个全站用户可见但不影响数据的错别字可能是轻微级别，但在宣传页面上线前也可能需要提高优先级。

## 3. 缺陷生命周期

```text
新建 -> 确认 -> 已分派 -> 修复中 -> 待回归 -> 已关闭
                         └-> 拒绝/重复/无法复现/延期
待回归 -> 重新打开（仍然存在或引入回归）
```

每次状态变化写清楚谁在什么版本做了什么判断。修复后先验证原步骤，再执行相邻回归：权限、重复提交、刷新、异常输入和数据查询。

### 3.1 回归记录模板

```markdown
| 缺陷 | 修复版本 | 原步骤复现 | 相邻场景 | 结果 | 证据 |
| --- | --- | --- | --- | --- | --- |
| BUG-001 | def5678 | 不再复现 | 普通用户/游客/重复发布 | 通过 |  |
```

如果原问题消失但相邻场景出现新问题，原缺陷可以关闭，同时创建新的缺陷，不要把两个问题混在一个编号里。


### 4.1 测试总结怎么写结论

- **通过**：核心范围完成，阻塞/严重风险为 0，剩余问题不影响发布且已确认。
- **有条件通过**：存在已知限制或低级别缺陷，业务负责人明确接受，必须列出条件。
- **不通过**：核心链路失败、存在越权/数据丢失/无法恢复等发布阻塞问题。

不要用“测试全部完成”代替结论。测试报告的读者最先想知道的是“能不能发布、依据是什么、还有什么风险”。

### 4.2 缺陷统计口径

统计前先定义：是按创建数量、关闭数量、当前未关闭数量，还是按严重级别统计；重复缺陷、拒绝缺陷、无法复现缺陷是否单独列出。报告中写明统计时间点，否则同一版本每天的数字都可能不同。

## 完成标准

你能提交一条最小可复现的缺陷，也能在缺陷修复后完成有范围的回归；测试报告不会只写“全部通过”，而会写清测试范围、证据、限制和剩余风险。

## 5. 本阶段常见错误

1. 标题写“系统崩了”，没有模块、条件和影响。
2. 把截图当成全部证据，没有请求、响应或日志。
3. 复现步骤依赖测试人员记忆，别人无法照做。
4. 把需求不明确当成代码缺陷。
5. 修复后只点一次成功按钮，没有验证数据库、权限和相邻流程。
6. 关闭缺陷时不写修复版本和回归证据。

## 6. 本阶段交付物

- 3 条完整缺陷报告
- 一份严重级别/优先级判断说明
- 一条缺陷生命周期记录
- 一份回归记录
- 一份填写完整的版本测试总结
