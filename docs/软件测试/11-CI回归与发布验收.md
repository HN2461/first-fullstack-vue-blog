# 11 CI、回归与发布验收

## 本阶段目标

把可重复质量检查放到提交和发布流程中，建立从代码变更到构建、测试、报告、验收、回滚准备的证据链。

## 先理解 CI 是什么

CI 是持续集成（Continuous Integration）的缩写。每次代码提交或合并时，机器自动执行固定检查，尽早发现问题。CI 不是一台神奇的测试机器：脚本写错、环境缺失或测试不稳定，也会产生错误信号。

发布验收比 CI 更靠后。CI 证明构建和自动化检查通过，发布验收还要证明实际部署后的服务、配置、数据库、权限和关键用户链路可用。

## 1. 本地质量门禁

在仓库根目录依次执行：

```powershell
Set-Location frontend
npm run build

Set-Location ..\backend
npm run test

Set-Location ..
pwsh -File scripts\check-encoding.ps1
```

根据本次变更再补充接口集合、Pytest、Playwright 和 JMeter 基线。保存完整输出，不要只记录最后一句“通过”。

### 1.1 每条命令是在检查什么

- `npm run build`：前端源码能否被打包，发现语法、依赖和构建配置问题。
- `npm run test`：后端现有自动化用例是否通过，发现接口、服务、模型和权限回归。
- `check-encoding.ps1`：源码是否出现 UTF-8 BOM 等编码问题。
- API/UI 自动化：从请求或真实浏览器角度验证关键链路。
- JMeter：在指定负载下观察性能，不代替功能和权限测试。

### 1.2 保存质量门禁日志

```powershell
New-Item -ItemType Directory -Force '测试记录\2026-09-18\11-发布验收' | Out-Null
Set-Location frontend
npm run build 2>&1 | Tee-Object '..\测试记录\2026-09-18\11-发布验收\frontend-build.log'
Set-Location ..\backend
npm run test 2>&1 | Tee-Object '..\测试记录\2026-09-18\11-发布验收\backend-test.log'
Set-Location ..
pwsh -File scripts\check-encoding.ps1 2>&1 | Tee-Object '测试记录\2026-09-18\11-发布验收\encoding.log'
```

后端测试仍在输出时不要关闭窗口。结束后检查命令退出码和报告，不要只看中途出现的绿色用例。

## 2. 回归范围选择

- **提交级**：受影响模块的单元/服务/API 测试。
- **合并级**：冒烟、核心 API、关键 UI 链路和构建。
- **发布级**：完整核心回归、权限、数据一致性、兼容性、性能基线、迁移/备份检查。
- **紧急修复**：复现用例、修复用例、相邻链路和最小冒烟。

每次选择范围都写出依据：改了什么、影响哪些依赖、为什么可以不跑其他套件。

### 2.1 变更影响分析步骤

1. 使用 `git diff` 看本次改动文件。
2. 按文件判断影响层：页面、接口、服务、模型、脚本、配置或部署。
3. 搜索被修改函数或接口的调用方。
4. 列出直接受影响的用例。
5. 再列出相邻风险：权限、数据写入、回滚、错误路径和兼容性。
6. 根据风险选择提交级、合并级或发布级回归，并把理由写入测试记录。

例如修改文章发布接口时，不能只跑成功发布，还要考虑普通用户、游客、缺少标题、重复发布、公开查询和回收站。

## 3. CI 任务顺序

```text
拉取代码
  -> 安装依赖（锁文件）
  -> 编码/格式检查
  -> 前端构建
  -> 后端测试
  -> API/UI 自动化
  -> 生成报告和构件
  -> 质量门禁判断
```

失败时必须能看到失败命令、测试名称、日志、截图/Trace 或报告链接。机密变量放 CI Secret，不写入 YAML、脚本和报告。

### 3.1 CI 失败排查顺序

1. 看失败的是哪个 job 和哪条命令。
2. 区分“没有执行到测试”和“测试断言失败”。
3. 查看 Node、Java、Python、MongoDB 版本是否符合基线。
4. 查看是否使用锁文件安装依赖。
5. 查看测试是否依赖本地文件、固定端口、真实网络或共享数据库。
6. 在相同提交的本地环境复现，再判断是产品缺陷还是测试环境问题。

不要点击“重新运行”直到成功。重复运行可以帮助判断不稳定，但每次失败都要保留记录。

## 4. 发布验收单

- [ ] 目标提交号和发布包校验值已确认。
- [ ] 前端构建和后端测试通过。
- [ ] 数据库是否有结构/枚举/权限变化已判断。
- [ ] 若需迁移，已先 dry-run、备份并记录影响数量。
- [ ] 服务器配置、上传目录、日志目录和 `.env` 不会被错误覆盖。
- [ ] 发布后健康检查、登录、权限、文章公开端和管理端冒烟通过。
- [ ] 监控日志无新增高频错误。
- [ ] 回滚包、数据库备份和负责人已明确。

### 4.1 发布前、发布中、发布后

发布前确认提交号、构建产物、环境变量、数据库备份、迁移 dry-run、回滚包和负责人。发布中按部署顺序执行，记录时间、命令、返回结果和异常处理。发布后先做健康检查和最小冒烟，再观察日志和资源；发现阻塞问题按预案回滚。

## 5. 发布后最小回归

1. 健康检查和静态资源。
2. 游客访问公开首页、文章详情和搜索。
3. 普通用户登录、查看文章、个人信息和退出。
4. 管理员登录、文章发布、菜单权限和回收站。
5. 上传/下载（若本次涉及媒体）。
6. 检查服务日志和数据库关键集合/表的写入。

### 5.1 发布后检查表

```markdown
| 检查项 | 预期 | 实际 | 证据 | 结果 |
| --- | --- | --- | --- | --- |
| 健康接口 | 200 |  | 响应 |  |
| 游客文章详情 | 可访问公开文章 |  | 截图/响应 |  |
| 普通用户权限 | 不可进入管理接口 |  | 403 响应 |  |
| 管理员发布 | 成功且公开可见 |  | ID/数据库/页面 |  |
| 日志 | 无新增高频错误 |  | 日志片段 |  |
```

## 完成标准

你能让一次提交产生可追溯的构建和测试证据，能根据变更范围选择回归集，并能在发布后用最少步骤判断系统是否达到上线门槛。

## 6. 本阶段常见错误

1. 只看 CI 页面绿色徽章，不看具体测试和报告。
2. 用普通 `npm install` 造成 CI 和本地依赖不同。
3. 把环境缺失误判为产品缺陷，或把真实失败误判为环境问题。
4. 发布后只打开首页，没有验证登录、权限、数据库写入和日志。
5. 没有备份和回滚方案就开始数据库迁移。

## 7. 本阶段交付物

- 本地质量门禁日志
- 变更影响分析
- CI 检查流程图
- 发布前/中/后验收单
- 发布后冒烟证据
- 回滚触发条件和联系人记录
