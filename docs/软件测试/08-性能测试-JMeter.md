# 08 性能测试：Apache JMeter

## 本阶段目标

学会在隔离环境设计可解释的性能测试：先定目标，再建脚本、准备数据、逐步加压、观察服务和数据库、分析结果，最后给出容量和风险结论。性能测试不是单纯追求最低响应时间。

## 先理解几个性能词

| 词 | 白话解释 |
| --- | --- |
| 响应时间 | 从发出请求到收到完整响应所用的时间 |
| 平均值 | 所有请求耗时的平均，容易被少量极慢请求掩盖 |
| P90/P95/P99 | 90%/95%/99% 请求不超过的耗时，更能体现尾部体验 |
| 吞吐量 | 单位时间处理的请求数，常见为每秒请求数 |
| 并发数 | 同一时刻正在执行或等待的请求/用户数 |
| 错误率 | 失败请求占总请求的比例 |
| 基线 | 低负载下的可比较正常结果 |
| 负载测试 | 在目标使用量下验证系统是否满足指标 |
| 压力测试 | 超过目标逐步加压，寻找拐点和失效方式 |
| 稳定性测试 | 在一段较长时间内观察资源和响应是否恶化 |

平均响应时间 100ms 不代表所有用户都快；如果 P95 是 5 秒，仍然有一部分请求很慢。报告至少同时看平均值、P95、吞吐量和错误率。

## 1. 安装与验证

JMeter 需要 Java：

```powershell
java -version
```

启动 GUI 用于建脚本：

```powershell
Set-Location '<JMeter解压目录>\bin'
.\jmeter.bat
```

正式执行优先使用命令行：

```powershell
New-Item -ItemType Directory -Force .\results | Out-Null
.\jmeter.bat -n -t .\blog-smoke.jmx -l .\results\blog-smoke.jtl -e -o .\results\html
```

`-n` 表示非 GUI 模式，`-t` 指定测试计划，`-l` 保存原始结果，`-e -o` 生成 HTML 报告。输出目录必须是不存在或为空的目录，否则 JMeter 可能拒绝生成报告。

### 1.1 安装小白步骤

1. 安装并验证 Java：`java -version`。
2. 从 Apache JMeter 官方渠道下载压缩包，不要下载来路不明的修改版。
3. 解压到没有中文空格的短路径，例如 `C:\tools\apache-jmeter`。
4. 进入 `bin` 目录运行 `jmeter.bat`。
5. GUI 打开后先关闭不需要的监听器，再创建第一个小脚本。
6. 关闭 GUI 后使用命令行跑正式结果。

如果双击窗口一闪而过，从 PowerShell 启动，这样可以看到 Java 或路径错误。

每次运行记录机器配置、服务提交号、数据库数据量、线程数、持续时间和 JMeter 版本。

## 2. 第一个测试计划

在 JMeter 中依次建立：

1. **Test Plan**：命名为 `blog-local-baseline`。
2. **HTTP Request Defaults**：协议、主机、端口、基础路径。
3. **HTTP Header Manager**：`Content-Type: application/json`。
4. **CSV Data Set Config**：准备不同账号或查询词，避免所有线程使用同一数据。
5. **Thread Group**：先 1 线程、1 次循环、无 ramp-up 做连通性验证。
6. **HTTP Request**：健康检查、公开文章列表、搜索、登录等请求。
7. **JSON JMESPath/JSON Extractor**：提取 Token、文章 ID。
8. **Assertions**：状态码、响应字段、业务成功标志和响应时间上限。
9. **Summary Report/Backend Listener**：只用于观察，不在高并发 GUI 中实时渲染大量结果。

### 2.1 第一个脚本只测健康接口

不要一开始就录制登录、发布、上传等复杂链路。先建立：

```text
Test Plan
└─ Thread Group（1 线程，1 次循环）
   ├─ HTTP Request Defaults（127.0.0.1:3001）
   ├─ HTTP Request（GET /api/health）
   ├─ Response Assertion（响应码 200）
   └─ View Results Tree（仅学习时使用）
```

点击绿色运行按钮后，在 Summary Report 中确认请求数为 1、错误数为 0。若失败，先检查 URL、端口、后端服务，再检查断言；不要直接增加线程数。

### 2.2 变量和数据文件

把主机、端口、查询词放到 User Defined Variables 或 CSV 文件中。CSV 每行一个测试值，例如：

```text
query
Vue
MongoDB
测试文章
```

线程组读取 CSV 时要明确文件到末尾怎么办：循环、停止线程还是共享读取。不同设置会影响结果，必须写进报告。

## 3. 分阶段执行

### 基线

1 线程运行 10 次，确认错误率为 0，记录平均值、P90、P95、最大值。

基线不是为了证明系统能承受生产并发，而是确认脚本、数据和服务在低负载下都正确。低负载就失败时，不应该继续加压。

### 负载

逐级增加线程，例如 5、10、25、50；每级设置 ramp-up 和稳定时间。观察吞吐量、P95、错误率、CPU、内存、MongoDB 查询和连接数。

### 压力

继续增加到出现明显错误或 P95 超过目标，记录拐点和恢复情况。压测必须提前设定停止条件。

### 稳定性

以目标并发持续 30 分钟或更久，观察内存增长、连接泄漏、错误累积和响应时间漂移。

### 3.1 逐级加压示例

| 级别 | 线程 | ramp-up | 持续时间 | 停止条件 |
| --- | ---: | ---: | ---: | --- |
| 基线 | 1 | 1 秒 | 10 次 | 错误率必须为 0 |
| 低负载 | 5 | 10 秒 | 5 分钟 | 错误率 > 1% 停止 |
| 目标负载 | 10 | 30 秒 | 10 分钟 | P95 超目标停止 |
| 压力探索 | 25/50 | 60 秒 | 5 分钟 | 服务错误、资源饱和或人工停止 |

数字只是学习示例，不能直接当成生产容量。每一级完成后先保存结果，再决定是否进入下一级。

## 4. 结果分析

报告至少回答：

- 目标并发和实际并发是多少？
- 成功率、吞吐量、平均值、P90/P95/P99 和最大值是多少？
- 哪个接口先成为瓶颈？
- 错误是连接失败、超时、HTTP 错误还是业务断言失败？
- 数据库和服务资源是否饱和？
- 测试数据、网络、缓存、日志级别是否影响结果？
- 是否达到本次版本目标？剩余风险是什么？

### 4.1 一个结果怎么解释

假设 10 分钟内发送 60,000 个请求，成功 59,400 个，失败 600 个：错误率 = 600 / 60,000 = 1%。如果 P95 为 1.8 秒，说明 95% 请求在 1.8 秒内完成，但仍有 5% 更慢。不要只说“平均 500ms，很快”，要同时写数据量、并发、持续时间、环境资源和失败类型。

### 4.2 观察服务和数据库

压测期间另开终端记录 Node 进程 CPU、内存和日志错误；MongoDB 连接数、慢查询、锁或磁盘压力；测试机自身 CPU、内存和网络。如果压测机先满载，结果不能代表服务容量；如果日志级别过高，也可能人为拖慢服务。

## 5. 安全与清理

只对本地、测试或已授权环境压测；不要把生产账号、真实个人数据或高并发脚本提交到仓库。测试结束后清理生成的草稿、评论、日志和临时报告，保留汇总结果和原始 JTL 到指定归档目录。

## 7. 本阶段常见错误

1. 在 GUI 中直接跑高并发并打开大量 View Results Tree，监听器本身可能成为瓶颈。
2. 没有基线就直接加压，无法区分脚本错误和服务瓶颈。
3. 所有线程使用同一个账号和同一个查询词，结果不代表真实使用。
4. 只看平均值，不看 P95、P99 和错误率。
5. 在没有授权的生产环境压测。
6. 没有停止条件，把服务打到不可恢复状态。

## 8. 本阶段交付物

- 一个只测健康接口的 JMX
- 一个公开文章列表或搜索的 JMX
- 基线、负载和压力结果
- JTL 与 HTML 报告
- 服务/数据库观察记录
- 性能报告和限制说明

## 完成标准

你能独立建立一个登录/查询场景，命令行跑出 JTL 和 HTML 报告，解释 P95、错误率和吞吐量，并能指出结果适用的环境边界。
