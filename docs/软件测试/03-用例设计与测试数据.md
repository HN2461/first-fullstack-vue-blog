# 03 用例设计与测试数据

## 本阶段目标

把测试点写成可重复执行的用例，掌握等价类、边界值、判定表、状态迁移和场景法，并建立不会相互污染的数据。

## 先理解一条好用例长什么样

一个刚接触测试的人常写：“测试登录功能，输入正确账号密码，检查是否成功。”这句话不能直接执行，因为没有账号、没有地址、没有明确的成功标准，也没有说明失败时要看什么。

好用例应该让一个没有参与设计的人照着执行，得到大致相同的结果。它至少回答：

1. 在什么环境、什么状态开始？
2. 使用哪个角色和哪一份数据？
3. 每一步具体点击什么、输入什么、调用什么？
4. 每一步预期看到什么？
5. 失败时保存什么证据？
6. 执行后数据怎么清理？

## 1. 用例模板

每条用例至少包含：

| 字段 | 写法 |
| --- | --- |
| 用例编号 | `ART-LOGIN-001`，稳定且唯一 |
| 标题 | 用“条件 + 操作 + 结果”描述 |
| 优先级 | P0 核心、P1 重要、P2 一般、P3 次要 |
| 前置条件 | 账号角色、数据状态、环境状态 |
| 测试数据 | 明确值、来源和清理方式 |
| 步骤 | 一步一个动作，避免“正常操作” |
| 预期结果 | 页面、接口、数据库、日志分别写清楚 |
| 实际结果 | 执行后填写，不提前复制预期 |
| 证据 | 截图、请求、响应、查询、日志路径 |
| 状态 | 未执行、通过、失败、阻塞、跳过 |

### 1.1 可直接抄写的完整用例

```markdown
## AUTH-LOGIN-001 管理员使用正确账号密码登录

- 优先级：P0
- 类型：功能、接口、冒烟
- 前置条件：后端健康接口返回 200；管理员账号处于启用状态；浏览器打开 /login
- 测试数据：账号从本地环境变量读取；密码不写入共享文档
- 步骤：
  1. 打开登录页。
  2. 在邮箱输入框输入管理员邮箱。
  3. 在密码输入框输入本地配置中的密码。
  4. 点击“登录”。
  5. 等待页面跳转到控制台。
- 预期结果：
  1. 请求返回成功状态码。
  2. 页面进入 /console 或需求指定的重定向地址。
  3. 页面显示管理员可见的后台管理入口。
  4. Network 中没有把密码作为明文 URL 参数发送。
  5. 刷新页面后登录状态仍按需求保持。
- 实际结果：
- 证据：响应、截图、控制台和登录后的菜单截图
- 清理：退出登录，删除临时截图中可能出现的 Token
```

注意“预期结果”分成多条，是为了失败时知道到底是哪一条失败，而不是只写一个模糊的“登录成功”。

## 2. 等价类与边界值

以标题长度为例，假设允许 1 至 100 个字符：

| 类别 | 数据 | 预期 |
| --- | --- | --- |
| 有效最小 | 1 个字符 | 接受 |
| 有效中间 | 50 个字符 | 接受 |
| 有效最大 | 100 个字符 | 接受 |
| 无效下界 | 空字符串/0 个字符 | 拒绝并提示 |
| 无效上界 | 101 个字符 | 拒绝并提示 |
| 特殊字符 | 表情、换行、HTML 片段 | 按需求处理且不执行脚本 |

不要只测一个正常标题。对密码、分页页码、文件大小、数组数量、日期范围、搜索关键字分别做同样分析。

### 2.1 什么时候使用等价类

当大量输入在系统看来应该得到同一种结果时，把它们分成几组，每组选择代表值。例如邮箱：

| 等价类 | 示例 | 预期 |
| --- | --- | --- |
| 合法普通邮箱 | `qa001@example.test` | 接受 |
| 缺少 @ | `qa001.example.test` | 拒绝 |
| 缺少域名 | `qa001@` | 拒绝 |
| 前后空格 | ` qa001@example.test ` | 明确是自动去空格还是拒绝 |
| 大小写 | `QA001@example.test` | 按账号规则判断 |
| 极长邮箱 | 超过字段最大长度 | 拒绝且不截断 |

### 2.2 什么时候使用边界值

当需求有“最多、最少、不超过、不早于”等数字限制时，至少测边界外一格、边界值和边界内一格。例如页码最小为 1：测 0、1、2；标题最大 100：测 99、100、101。

## 3. 判定表

以“文章是否可以发布”为例：

| 条件 | 规则 A | 规则 B | 规则 C | 规则 D |
| --- | --- | --- | --- | --- |
| 已登录 | 是 | 是 | 是 | 否 |
| 有发布权限 | 是 | 否 | 是 | - |
| 标题和正文完整 | 是 | 是 | 否 | - |
| 分类有效 | 是 | 是 | 是 | - |
| 预期 | 允许发布 | 拒绝并 403 | 拒绝并校验提示 | 跳转登录 |

### 3.1 如何从判定表生成用例

每一列至少对应一条用例。先执行规则 A 的成功场景，再分别只改变一个条件执行规则 B、C、D。这样可以知道失败究竟由权限、数据完整性还是登录状态导致。

如果条件很多，不要机械列出所有组合。先找业务上真正不同的结果，再使用风险和正交思路减少重复组合，并在测试计划中说明取舍。

## 4. 状态迁移

为文章画状态图并逐条覆盖：

```text
草稿 -> 发布 -> 下架 -> 发布
草稿 -> 回收站 -> 恢复为草稿
发布 -> 回收站 -> 永久删除
```

对每条迁移验证操作者权限、接口状态码、列表可见性、公开端可见性和数据库字段变化。

### 4.1 状态迁移用例示例

| 当前状态 | 操作 | 角色 | 预期新状态 | 不允许时的结果 |
| --- | --- | --- | --- | --- |
| 草稿 | 发布 | 管理员 | 已发布 | - |
| 草稿 | 发布 | 普通用户 | 不变 | 403/无权限 |
| 已发布 | 下架 | 管理员 | 已下架或草稿 | 按需求 |
| 回收站 | 恢复 | 管理员 | 草稿 | - |
| 回收站 | 公开访问 | 游客 | 不可见 | 404/空结果 |

测试状态时不要只看列表文字。至少再查一次详情接口或数据库字段，避免页面缓存让你误以为状态已经改变。

## 5. 测试数据规则

- 每个测试用例使用唯一后缀，例如 `qa_20260918_001`。
- 不使用生产真实个人信息；邮箱、手机号和文件内容使用虚拟数据。
- 创建数据时记录 ID，结束后按依赖顺序清理子数据再清理主数据。
- 测试之间不能依赖执行顺序；需要共享数据时写成明确前置条件。
- 并发和幂等测试使用独立账号或带批次号的数据。

### 5.1 建议的数据命名

```text
qa_20260918_admin
qa_20260918_user
qa_20260918_article_draft_001
qa_20260918_article_published_001
```

名称中包含日期和用途，查询时容易找到，清理时也不容易误删其他人的数据。

### 5.2 清理顺序

先清理依赖主数据的子数据，再清理主数据。例如文章相关测试通常按“评论/点赞/收藏 → 文章 → 测试分类/标签 → 测试账号”的方向清理。实际项目如果使用软删除或回收站，要记录“已回收”和“已永久删除”是两种不同结果。

### 5.3 测试数据清单

```markdown
| 数据名 | 类型 | ID | 创建用例 | 是否共享 | 清理方式 | 清理结果 |
| --- | --- | --- | --- | --- | --- | --- |
| qa_..._article_draft_001 | 草稿文章 |  | ART-001 | 否 | 管理接口移入回收站 |  |
```

## 6. 练习题

- [ ] 为登录写 15 条用例：正常、空值、错误、锁定、重复提交、Token 失效、权限。
- [ ] 为文章发布写 20 条用例，至少包含一张判定表和一张状态迁移表。
- [ ] 为上传写边界数据：空文件、超大文件、扩展名伪装、重复上传、同名文件。
- [ ] 把 5 条人工用例改写成另一个人能完全照抄执行的步骤。

## 7. 执行用例时的填写顺序

1. 先填执行人、时间、版本和环境。
2. 按步骤执行，不要一次执行完再凭记忆填写。
3. 每一步发现异常就暂停并保存证据；不要把异常带到后续步骤导致结果混乱。
4. 预期和实际分开写，实际不要复制预期。
5. 失败后记录复现次数，例如“连续 3 次失败 3 次”，或“5 次中失败 2 次”。
6. 结束后填写清理结果，确认没有留下脏数据。

## 8. 本阶段交付物

- 20 条登录、文章、权限和上传用例
- 一张等价类/边界值表
- 一张判定表
- 一张状态迁移表
- 测试数据清单
- 至少 3 条已经执行并附证据的用例

## 完成标准

用例不依赖“测试人员应该知道”，预期结果能被页面、接口、数据库或日志中的客观证据支持。
