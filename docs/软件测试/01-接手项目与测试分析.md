# 01 接手项目与测试分析

## 本阶段目标

学会接手一个陌生系统时先建立项目地图和风险地图，不直接凭感觉点击页面。测试人员的第一份产出是“知道系统有哪些入口、角色、状态、数据和外部依赖”。

## 先理解“接手项目”不是马上点页面

新测试人员最容易犯的错误是打开首页后凭感觉点十分钟，然后说“看起来没问题”。这样做有三个问题：不知道哪些功能是重点，不知道当前账号是什么权限，也不知道页面背后是否真的写入了数据。

接手项目要先回答：

1. 这是什么产品？解决谁的什么问题？
2. 有哪些用户和权限？
3. 哪些功能是发布阻塞点？
4. 一次操作会经过哪些页面、接口、服务和数据集合？
5. 哪些地方改坏后会造成数据丢失、越权或公开内容错误？

把这些问题写下来，再开始执行，后面的用例才不会漏掉关键链路。

## 1. 从代码和文档建立项目地图

阅读顺序：

1. `README.md` 和 `docs/README.md`。
2. `docs/01-项目总览/代码导览.md`。
3. `docs/02-开发指南/前端代码说明.md`、`后端代码说明.md`、`数据库说明.md`。
4. `frontend/src/router`，确认页面、登录守卫和角色判断。
5. `backend/src/modules/**/routes`、`services`、`models`、`middlewares`，确认请求流转；当前后端按模块组织，不是单独的 `backend/src/routes` 目录。
6. `backend/tests`，了解已有契约和边界案例。

用下面的表格抄写一份项目地图：

| 模块 | 入口 | 角色 | 主要数据 | 外部依赖 | 高风险点 |
| --- | --- | --- | --- | --- | --- |
| 登录 | `/login` | 游客 | 用户、Token | MongoDB | 密码、会话、错误提示 |
| 知识库文章 | `/console/articles` | 登录用户 | 文章、分类、标签 | MongoDB | 可见性、搜索、分页 |
| 文章管理 | `/console/manage/articles` | 管理员 | 草稿、发布、回收站 | MongoDB、上传目录 | 权限、状态转换 |
| 媒体 | `/console/manage/media` | 管理员 | 文件元数据 | 文件系统 | 类型、大小、路径 |
| 菜单与角色 | `/console/manage/menus` | 管理员 | RBAC | MongoDB | 越权、菜单可见性 |

### 1.1 实际操作：从目录开始，不要求先读懂所有代码

在项目根目录执行：

```powershell
Get-ChildItem -Directory
Get-ChildItem frontend\src\views -Directory
Get-ChildItem backend\src\modules -Directory
rg --files frontend\src\router backend\src\modules | Select-Object -First 120
```

先看文件名，不要一开始逐行阅读几万行代码。文件名通常能告诉你模块边界：`routes` 负责 URL，`services` 负责业务流程，`models` 负责数据模型，`middlewares` 负责登录/权限/错误处理。

### 1.2 页面地图写法

对每个页面填写四列：

| 页面 | 谁能进入 | 页面上能做什么 | 失败时应该怎样 |
| --- | --- | --- | --- |
| `/login` | 游客 | 输入账号密码、提交 | 显示错误，不泄露账号是否存在 |
| `/console/articles` | 已登录用户 | 查看文章、搜索、分页 | 无权限时跳登录或提示 |
| `/console/manage/articles` | 有管理菜单权限的管理员 | 创建、发布、下架、删除 | 403、校验提示或确认弹窗 |

“谁能进入”和“谁能调用接口”要分别记录。隐藏一个菜单不等于接口安全，测试时必须直接调用接口验证。

### 1.3 从前端找到接口

例如搜索 `http.get`、`http.post`、`axios`：

```powershell
rg -n "http\.(get|post|put|patch|delete)|axios" frontend\src\services frontend\src\views
```

把找到的路径复制到接口清单中。再到后端搜索相同路径或模块路由，确认方法、参数和权限中间件。若前端调用了 `/api/admin/articles`，后端应能找到对应路由和权限检查；找不到时先记为“待确认”，不要凭经验补全。

## 2. 画出一条业务链路

以“管理员发布文章”为例，写出：

```text
登录 -> 获取 Token -> 打开文章管理 -> 创建草稿 -> 填标题/正文/分类
-> 保存 -> 预览 -> 发布 -> 公开端查看 -> 搜索 -> 下架/回收站
```

每个箭头旁标出：页面、接口、数据库集合、权限、成功条件、失败条件。再补充普通用户和游客在同一链路上的预期行为。

### 2.1 用“请求追踪表”替代只画箭头

```markdown
| 步骤 | 用户动作 | 页面 | HTTP 请求 | 角色 | 数据变化 | 证据 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 输入账号密码 | /login | POST /api/auth/login | 游客 | 创建登录会话 | 响应、Cookie |
| 2 | 打开文章管理 | 管理台 | GET /api/admin/articles | 管理员 | 无 | 响应、页面 |
| 3 | 保存草稿 | 编辑页 | POST /api/admin/articles | 管理员 | 新增文章 | ID、数据库 |
| 4 | 发布 | 编辑页 | POST .../publish | 管理员 | 状态变 published | 响应、公开查询 |
```

填表时如果不知道某一格，不要留空后继续假设；写 `待查：需要查看 frontend/src/services/admin.js`，然后回到代码或 DevTools 查询。

### 2.2 页面、接口、数据库三处都要验证

以“发布成功”为例，仅看到按钮提示“发布成功”不够。至少核对：

- 接口返回状态码和文章状态。
- MongoDB 中该文章的状态、发布时间、更新时间。
- 公开端详情接口/页面是否能看到。
- 草稿列表是否不再显示为草稿，或按需求显示为已发布。

这叫做“端到端闭环”，可以避免前端提示成功但后端实际没有保存的问题。

## 3. 建立风险清单

用“影响 × 发生可能性 × 发现难度”排序：

| 风险 | 影响 | 可能性 | 发现难度 | 首轮动作 |
| --- | --- | --- | --- | --- |
| 普通用户访问管理员接口 | 高 | 中 | 中 | 先做 RBAC 接口测试 |
| 草稿出现在公开端 | 高 | 中 | 中 | 做状态和公开查询验证 |
| 上传恶意或超大文件 | 高 | 中 | 高 | 做类型、大小和路径测试 |
| 搜索分页重复/漏数据 | 中 | 中 | 中 | 做边界页和排序稳定性测试 |
| 数据库连接失败 | 高 | 低 | 低 | 启动和故障恢复检查 |

### 3.1 小白风险评分

为了不只凭感觉，可以给每一项打 1 到 5 分：

- 影响：1 表示几乎没有影响，5 表示数据丢失、越权或系统不可用。
- 可能性：1 表示极少发生，5 表示每次都可能发生。
- 发现难度：1 表示很容易发现，5 表示只有线上或长时间运行才发现。

风险分数 = 影响 × 可能性 × 发现难度。分数高的项目优先设计用例，分数低的项目可以放到后续回归。

### 3.2 风险不等于缺陷

“上传大文件可能导致磁盘满”是风险；实际上传 2GB 后服务崩溃才是缺陷。风险清单用于决定先测什么，缺陷单用于描述已经观察到的实际问题。

## 4. 接手检查单

- [ ] 版本、分支、环境和配置来源已记录。
- [ ] 页面、接口、集合、定时任务和文件目录已列出。
- [ ] 游客、普通用户、管理员的权限差异已写出。
- [ ] 关键状态流转已画出：草稿、发布、下架、删除、恢复。
- [ ] 外部依赖和不可控因素已列出。
- [ ] 现有自动化测试和已知问题已阅读。
- [ ] 首轮冒烟路径已选定，并且每一步都有通过标准。

## 5. 观察一个请求的完整过程

选择“打开文章列表”练习：

1. 打开浏览器 DevTools 的 Network 面板并勾选 Preserve log。
2. 刷新页面，使用筛选框找到文章列表请求。
3. 记下 Request URL、Request Method、Query String Parameters、Status Code、Response。
4. 在后端代码中搜索该路径，找到路由和服务函数。
5. 在 MongoDB 中找到对应查询的集合和字段。
6. 修改一个安全的查询参数，例如页码从 1 改为 2，再观察返回数据如何变化。
7. 把页面、请求、数据库和结果写入请求追踪表。

如果请求失败，先判断失败发生在哪一层：

| 现象 | 优先怀疑 |
| --- | --- |
| 页面打不开，静态资源 404 | 前端服务、构建产物或路径 |
| 请求显示 `(failed)` | 服务未启动、网络、CORS 或端口 |
| 401 | 没登录、会话失效或认证信息没有发送 |
| 403 | 权限不足或角色菜单权限不满足 |
| 404 | 路由、ID、资源状态或前端路径错误 |
| 422/400 | 参数校验失败 |
| 500 | 后端异常、数据库错误或未处理边界 |

## 5. 练习题

1. 不看实现代码，只根据页面和接口文档列出“注册→登录→查看文章”的 15 个测试点。
2. 再读代码，标出哪些测试点已有自动化覆盖，哪些只有人工覆盖。
3. 对一个高风险点写出最小复现和所需测试数据。

4. 创建三张表：页面地图、接口地图、数据库地图；同一个“发布文章”功能必须在三张表中都能找到。
5. 选一个普通用户不能做的动作，分别用页面、直接接口、数据库结果验证权限边界。
6. 给五项风险打分，并解释为什么分数最高的两项要最先测。

## 完成标准

你能把一个功能从“用户操作”追到“HTTP 请求、服务逻辑、数据库变化、最终页面”，并能说清楚最先测试哪三条链路以及原因。
