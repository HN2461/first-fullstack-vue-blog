# 02 需求、计划与测试策略

## 本阶段目标

把需求转成可验证的范围、策略、资源、时间和发布门槛。测试计划不是“把所有功能点列一遍”，而是说明在当前版本和时间内，哪些风险用什么证据验证。

## 先区分三种内容

### 功能需求

功能需求说明系统“做什么”，例如“管理员可以发布文章”“普通用户可以评论”。测试时要验证输入、处理、输出、权限和失败路径。

### 非功能需求

非功能需求说明系统“做得怎么样”，例如“搜索在 2 秒内返回”“移动端不能横向滚动”“密码不能明文出现在响应中”。它们也必须有测量方法，不能只写“体验好”。

### 约束和假设

约束是必须遵守的条件，例如“只能使用 MongoDB”“上传目录不能被发布包覆盖”；假设是暂时认为成立的条件，例如“测试环境网络稳定”。假设如果没有验证，要在风险中登记。

## 需求改写练习：从模糊句到可测句

模糊需求：

> 用户可以快速搜索文章。

可测写法：

> 已登录用户在文章搜索页输入 2 到 50 个字符的关键词并提交时，系统返回匹配的已发布文章；在基线数据量和指定并发下，P95 响应时间不超过 2 秒；草稿、回收站文章不出现在结果中；没有关键词时显示空状态而不是返回全部管理数据。

改写后的句子包含角色、输入、动作、结果、边界和质量指标，测试人员才知道怎样判断通过。

## 1. 写需求可测试性检查

对每一条需求逐项提问：

- 谁可以操作？未登录、普通用户、管理员分别怎样？
- 在什么前置状态下可以操作？
- 输入允许什么格式、长度、大小和数量？
- 成功时页面、接口和数据库各有什么结果？
- 失败时错误码、提示、回滚和重试是什么？
- 重复提交、刷新、并发、超时和网络中断如何处理？
- 操作是否留下审计、通知、日志或可恢复数据？

如果需求无法回答，登记为“需求疑问”，不要擅自把猜测当成预期结果。

### 1.1 需求疑问记录模板

```markdown
| 编号 | 原文 | 不清楚的地方 | 影响的用例 | 需要谁确认 | 状态 |
| --- | --- | --- | --- | --- | --- |
| Q-001 | 可以发布文章 | 普通用户是否允许发布？ | ART-PERM-001 | 产品/负责人 | 待确认 |
```

需求疑问没有确认前，不要把某个猜测写进“预期结果”。可以编写两个候选用例，但要标明“取决于需求确认”。

## 2. 写一页测试计划

复制以下结构到 `测试计划.md`：

```markdown
- 版本/提交：
- 测试周期：
- 业务目标：

## 测试范围
- 包含：
- 不包含：

## 测试类型
- 冒烟：
- 功能：
- 接口：
- 数据：
- 兼容性：
- 安全：
- 性能：
- 回归：

## 环境与数据
- 前端地址：
- 后端地址：
- 数据库：
- 账号角色：
- 测试数据来源与清理方式：

## 风险与应对
| 风险 | 影响 | 应对 | 负责人 |
| --- | --- | --- | --- |

## 准入标准
- 构建成功；
- 服务可启动；
- 数据库可连接；
- 核心接口可响应。

## 准出标准
- 阻塞级/严重级缺陷为 0；
- 核心链路通过；
- 已知遗留风险得到业务确认；
- 测试报告和证据已归档。
```

### 2.1 逐字段填写说明

- **版本/提交**：从 `git log -1 --oneline` 获取，不写“最新版”。
- **测试范围**：写本轮明确要验证的模块和不验证的模块，避免测试结束争议。
- **测试类型**：只选择本轮真的会执行的类型；写了性能测试却没有 JMeter 结果，属于计划未完成。
- **环境与数据**：写地址、数据库、账号角色和清理方式，不能只写“测试环境”。
- **准入标准**：测试开始前必须满足的条件，例如服务可启动、构建通过。
- **准出标准**：决定是否可以交付的条件，例如 P0/P1 缺陷为 0 或已获明确豁免。

### 2.2 一个已填写的小例子

```markdown
## 版本与目标
- 版本/提交：abc1234
- 测试周期：2026-09-18 09:00 至 18:00
- 业务目标：管理员可以创建并发布文章，普通用户只能阅读和评论

## 范围
- 包含：登录、文章草稿、发布、公开阅读、评论权限
- 不包含：账本、简历导出、JMeter 长稳测试

## 准出
- P0/P1 缺陷为 0；P2 缺陷有负责人和延期说明；主链路通过；证据归档完整
```

这个例子故意写出“不包含”项。测试范围越清楚，越不会为了赶时间假装覆盖没有执行的内容。

## 3. 制定测试策略

按风险分层：

1. **冒烟**：服务启动、登录、文章列表、文章详情、管理员入口。
2. **核心功能**：文章创建/发布/搜索、权限、评论、媒体。
3. **扩展功能**：个人备忘录、通知、项目台账、回收站。
4. **质量属性**：响应时间、并发、兼容性、可访问性、基础安全。

测试层次采用“快速反馈优先”：单元/服务测试 → API 集成测试 → 浏览器关键链路 → 少量高价值性能场景。不要等到最后一天才第一次跑完整回归。

### 3.1 为什么要分层

- 单元测试反馈最快，适合验证一个函数或规则。
- API 测试比浏览器测试快，能稳定验证状态码、权限和数据副作用。
- 浏览器测试最接近用户，但受浏览器、网络和等待时机影响，应该只保留关键链路。
- 性能测试需要独立数据、时间和资源，不能把普通功能测试的响应时间当成容量结论。

### 3.2 测试优先级

- **P0**：不通过就不能继续，例如服务不能启动、管理员无法登录、普通用户越权。
- **P1**：核心业务必须通过，例如文章创建、发布、公开阅读、搜索。
- **P2**：重要但可绕过，例如筛选、批量操作、部分兼容性。
- **P3**：低风险细节，例如不影响业务的文案或间距。

先执行 P0，再执行 P1。时间不足时，减少 P2/P3，不要跳过权限和数据一致性。

## 4. 设计准入、冒烟和准出清单

### 准入

- [ ] 需求或变更说明已冻结到可测试版本。
- [ ] 部署包、数据库、配置和测试账号可用。
- [ ] 关键接口至少有一条可调用样例。
- [ ] 测试数据不会污染生产数据。

### 冒烟

- [ ] 首页可打开，静态资源无大面积失败。
- [ ] 注册/登录/退出链路正常。
- [ ] 普通用户只能看到知识库菜单。
- [ ] 管理员能进入管理菜单。
- [ ] 文章列表、详情和搜索可用。

### 准出

- [ ] 核心用例全部通过或有明确豁免。
- [ ] 缺陷已按严重级别统计，阻塞风险已关闭。
- [ ] 自动化、接口、性能和人工测试结果均已留证。
- [ ] 数据库和上传目录无异常残留。

## 5. 做一个简单的时间计划

假设只有一天，按下面顺序安排：

| 时间 | 工作 | 必须产出 |
| --- | --- | --- |
| 09:00-09:30 | 环境检查和冒烟 | 环境记录、冒烟结果 |
| 09:30-11:00 | P0/P1 接口和权限 | 请求/响应、失败证据 |
| 11:00-12:00 | 数据库前后核对 | 查询记录 |
| 13:30-15:00 | 核心页面和异常流程 | 用例结果、截图 |
| 15:00-16:00 | 回归已修复缺陷 | 回归记录 |
| 16:00-17:00 | 总结风险和发布建议 | 测试报告 |

时间计划不是把每分钟塞满，而是确保高风险工作不会被低价值的样式巡检挤掉。

## 6. 本阶段交付物

- 需求疑问表
- 测试范围说明
- 测试计划
- 风险与优先级表
- 准入、冒烟、准出清单
- 一份按时间安排的执行计划

## 完成标准

另一名测试人员只拿到你的测试计划，就能知道测什么、在哪测、用什么数据、什么结果可以发布。
