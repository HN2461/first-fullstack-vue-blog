# 软件测试实操路线

这是一套可以逐篇抄写、逐条执行、逐项留证的测试人员训练手册。练习对象优先使用当前项目“个人全栈博客系统”，这样每一步都能和真实的 Vue 3、Express、MongoDB、认证、RBAC、文件上传、文章搜索等功能对应起来；MySQL 部分使用独立练习库，用来掌握关系型数据库测试方法。

这套资料默认你是第一次接触软件测试。你不需要先会写代码，也不需要一开始就会所有工具。每一篇都按照“先解释名词 → 再准备环境 → 再照抄操作 → 再观察结果 → 最后写下结论”的顺序学习。看到命令时，不要只复制粘贴；先看命令前面写的“目的”，执行后把输出保存下来，再用自己的话解释输出代表什么。

## 先认识测试人员到底在做什么

测试不是“随便点页面，发现报错就告诉开发”。测试人员要回答四个问题：

1. **系统应该怎样工作？** 这来自需求、原型、接口契约、数据模型和角色权限。
2. **系统现在实际上怎样工作？** 这需要亲自操作页面、发送请求、查看日志和查询数据库。
3. **实际结果和预期结果有什么差异？** 只有有明确预期，才可以判断通过或失败。
4. **这个差异是否值得修复、影响多大、如何证明已经修复？** 这就是缺陷分级、回归和测试报告。

“通过”也不是一句感觉。一次可信的通过至少要有：测试版本、测试环境、测试数据、操作步骤、预期结果、实际结果和证据。

## 小白必须先记住的 20 个词

| 词 | 白话解释 | 在本项目中的例子 |
| --- | --- | --- |
| 需求 | 产品希望系统完成的事情 | 管理员可以发布文章 |
| 功能 | 系统提供的一项能力 | 登录、搜索、上传 |
| 角色 | 一组身份和权限 | 游客、普通用户、管理员 |
| 前置条件 | 执行用例前必须先满足的状态 | 已登录且文章为草稿 |
| 用例 | 可重复执行的一组测试步骤 | 输入错误密码后应提示失败 |
| 测试点 | 一个需要确认的行为或风险 | 过期 Token 不能访问管理接口 |
| 预期结果 | 根据需求应该发生什么 | 返回 401，页面跳到登录 |
| 实际结果 | 执行后真实发生了什么 | 返回 200 并返回了文章 |
| 接口/API | 程序之间通信的入口 | `GET /api/health` |
| 请求 | 客户端发给服务器的内容 | 方法、URL、请求头、请求体 |
| 响应 | 服务器返回给客户端的内容 | 状态码、响应头、响应体 |
| 状态码 | HTTP 对结果的数字说明 | 200 成功、401 未认证、403 无权限 |
| 数据库 | 保存业务数据的地方 | MongoDB 中的文章文档 |
| 断言 | 自动化测试对结果做出的判断 | 断言状态码等于 200 |
| 冒烟测试 | 快速确认系统能不能继续测 | 能启动、能登录、能打开文章 |
| 回归测试 | 修复或改动后重新检查旧功能 | 修复发布权限后重测登录和文章 |
| 缺陷 | 实际结果不符合约定的可追踪问题 | 普通用户可以发布文章 |
| 基线 | 一次可比较的正常结果 | 1 个用户请求健康接口的响应时间 |
| 并发 | 同一时间有多个请求或用户 | 50 个线程同时搜索 |
| 证据 | 支撑结论的原始材料 | 截图、响应 JSON、日志、查询结果 |

## 每篇文档的固定学习动作

1. 把本篇标题和目标抄到自己的笔记里。
2. 创建本篇对应的证据目录，不要把截图、日志散落在桌面。
3. 先执行“准备检查”，出现环境问题时先排查，不要跳过并假装成功。
4. 每个练习先写预期，再执行操作；不要执行完才修改预期来迁就结果。
5. 遇到失败先保存现场，不要立刻刷新、删除数据或重启服务。
6. 完成后写三句话：做了什么、看到了什么、还不确定什么。
7. 只有“操作 + 证据 + 解释”都完成，才在总表打勾。

## 不知道下一步做什么时的排查顺序

1. 看命令是否在正确目录执行：`Get-Location`。
2. 看工具是否安装：`node --version`、`java -version` 等。
3. 看服务是否启动：终端日志和健康接口。
4. 看浏览器 Network 请求的实际 URL、状态码和响应体。
5. 看后端终端是否出现错误堆栈。
6. 看数据库是否真的写入或清理了数据。
7. 用最小数据重新复现一次，并记录“第一次失败”和“第二次失败”是否相同。

不要一遇到问题就执行 `npm install`、删除数据库或重装工具。先记录现象，盲目清理可能会把最有价值的证据删除。

## 使用方式

1. 按文件编号顺序学习，不要先跳到工具命令。每个阶段先写出目标、输入、预期结果，再执行操作。
2. 每次练习建立一个日期目录，例如 `测试记录/2026-09-18/`，保存测试计划、用例、请求集合、SQL、截图、日志和报告。
3. 每个阶段至少完成一轮“正常场景、异常场景、边界场景、权限场景、重复操作”验证。
4. 工具只负责提高执行效率，结论必须回到需求、接口契约、数据库状态和用户可观察结果。
5. 练习结束后填写本文末尾的阶段验收表；没有证据文件的“做过”不算完成。

## 先记住测试人员的固定动作

1. **理解对象**：确认版本、环境、角色、数据和需求范围。
2. **设计风险**：找出最可能坏、坏了影响最大、最难恢复的地方。
3. **写可执行用例**：前置条件、步骤、输入、预期结果必须让另一个人照着执行。
4. **观察证据**：记录请求、响应、日志、数据库前后状态、截图和时间。
5. **隔离问题**：判断是前端、后端、数据库、环境、数据还是需求本身。
6. **提交缺陷**：用最小复现步骤描述实际结果与预期结果。
7. **回归验证**：验证修复本身，再验证相邻功能和原有关键链路。
8. **形成结论**：说明测了什么、没测什么、剩余风险是什么，以及能否发布。

- [ ] 能完成浏览器功能、响应式、兼容性、基础安全检查。
- [ ] 能运行并维护至少一组 API 或 UI 自动化回归。

## 工具边界说明

- **Postman/Apifox**：验证 HTTP 接口契约和业务流程，不代替数据库一致性验证。
- **MySQL**：练习关系模型、SQL、事务、索引和执行计划；当前项目生产数据仍以 MongoDB 为准。
- **MongoDB Compass/mongosh**：核对当前项目集合、索引、文档和权限隔离。
- **Playwright**：验证真实浏览器中的关键用户流程；定位器应优先使用可见文本、角色或稳定属性。
- **JMeter**：测量服务在指定负载下的响应和错误，不把一次压测结果当成绝对容量。
- **PyreFocus**：用于测试管理练习。由于不同发行版的菜单和字段可能不同，文档给出的是通用对象和操作顺序，实际字段以安装版本为准。

## 给初学者的学习节奏

建议每天只完成一个小目标：

- 第一天只把项目启动并访问健康接口。
- 第二天只读懂一个模块并画出一条请求链路。
- 第三天只写登录用例，不急着学习性能测试。
- 第四天只完成一个接口集合和三个断言。
- 第五天只完成一次数据库前后核对。

如果一天不能完成整篇，不代表失败。测试工作强调可重复和可解释，慢一点但留下完整证据，比快速点完所有工具更有价值。
