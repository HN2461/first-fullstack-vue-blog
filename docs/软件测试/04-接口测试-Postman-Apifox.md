# 04 接口测试：Postman、Apifox 与 curl

## 本阶段目标

掌握 HTTP 方法、状态码、请求头、认证、参数校验、响应契约、业务流程、断言和环境变量。接口测试要同时验证“返回正确”和“副作用正确”。

## 先理解接口是什么

把浏览器想成餐厅里的服务员，把后端想成厨房。浏览器不会直接修改数据库，而是把一张“订单”发给后端；后端处理后返回“出餐结果”。这张订单就是 HTTP 请求，出餐结果就是 HTTP 响应。

一个接口请求通常由五部分组成：

1. **方法**：想做什么，例如 `GET` 查询、`POST` 创建、`PATCH` 修改、`DELETE` 删除。
2. **URL**：请求哪个资源，例如 `/api/auth/login`。
3. **请求头**：附加信息，例如 `Content-Type` 和 `Authorization`。
4. **参数**：查询参数、路径参数或 JSON 请求体。
5. **认证信息**：证明“你是谁”，例如 Cookie 或 Bearer Token。

响应通常有状态码、响应头和响应体。接口测试的基本问题不是“返回 200 就通过”，而是“它是否按约定返回了正确状态、正确字段、正确数据，并且只允许正确的角色执行”。

## 常见 HTTP 状态码

| 状态码 | 白话解释 | 在测试中关注什么 |
| --- | --- | --- |
| 200 | 请求成功并有返回 | 数据和字段是否正确 |
| 201 | 创建成功 | 是否真的新增了一条数据 |
| 204 | 成功但没有响应体 | 是否按契约不返回内容 |
| 400 | 请求格式或参数不对 | 错误字段是否可理解 |
| 401 | 没有通过身份认证 | 无 Token、过期 Token 是否被拒绝 |
| 403 | 已识别身份但没有权限 | 普通用户是否无法调用管理员动作 |
| 404 | 路径或资源不存在 | 错误 ID、已删除资源如何处理 |
| 409 | 状态冲突或重复 | 重复邮箱、重复提交如何处理 |
| 422 | 参数语义校验失败 | 长度、格式、枚举值是否校验 |
| 429 | 请求太频繁 | 限流后是否给出重试提示 |
| 500 | 服务端未正常处理 | 保存响应、后端日志和请求时间 |

## 1. 先用 curl 看清请求

当前项目示例后端端口是 3001。以实际 `backend/.env` 和启动日志为准，先设置变量：

```powershell
$apiBase = 'http://127.0.0.1:3001/api'
curl.exe -i "$apiBase/health"
curl.exe -i -X POST "$apiBase/auth/login" `
  -H 'Content-Type: application/json' `
  --data '{"email":"admin@example.com","password":"从本地环境读取"}'
```

记录：URL、方法、状态码、响应头、响应体、耗时、是否改变数据库。不要把真实 Token 提交到仓库。

### 1.1 第一次练习：健康接口

先确认后端服务正在运行，再执行：

```powershell
curl.exe -i http://127.0.0.1:3001/api/health
```

`-i` 表示把响应头和响应体都打印出来。你要抄写以下结果：

```text
HTTP/1.1 200 OK
Content-Type: application/json; ...

{ ... }
```

如果状态不是 200，不要先改测试预期。先检查后端是否启动、端口是否为 3001、请求路径是否为 `/api/health`，并保存原始输出。

### 1.2 认识三种参数

```text
/api/admin/articles/文章ID       # 路径参数
/api/admin/articles?page=1       # 查询参数
{"title":"测试文章"}            # JSON 请求体
```

路径参数通常指定某一条资源，查询参数通常指定筛选/分页，请求体通常承载创建或修改内容。测试时分别做“缺少、为空、类型错误、边界值”验证。

## 2. 在 Postman/Apifox 建立环境

建立 `local` 环境变量：

```text
baseUrl = http://127.0.0.1:3001
adminEmail = admin@example.com
adminToken = 登录后手动或脚本写入
userToken = 普通用户登录后写入
articleId = 当前测试文章 ID
```

建立集合目录：`01-健康检查`、`02-认证`、`03-公开阅读`、`04-文章管理`、`05-RBAC`、`06-媒体与评论`。每个请求填写用途、前置条件、清理方式。

### 2.1 Postman 小白操作步骤

1. 打开 Postman，点击 **Environments → Create Environment**。
2. 把环境命名为 `blog-local`。
3. 增加 `baseUrl`，初始值填写 `http://127.0.0.1:3001`；保存并在右上角选中该环境。
4. 新建 Collection，命名为 `个人博客-接口测试`。
5. 在 Collection 下建立文件夹，再新建 Request。
6. URL 写 `{{baseUrl}}/api/health`，方法选择 `GET`，点击 Send。
7. 确认状态码、响应体和响应时间，再把请求保存到集合。

右上角环境变量有“当前值”和“初始值”。Token 只写当前值，导出环境或提交文件前必须删除 Token。不要把密码写入请求示例。

### 2.2 Apifox 小白操作步骤

1. 新建项目并填写本地服务地址。
2. 新建环境 `local`，设置变量 `baseUrl`。
3. 建立“健康检查、认证、公开阅读、管理、权限”目录。
4. 新建接口时填写方法、URL、参数、请求体示例和响应示例。
5. 使用“运行/测试”发送请求，查看请求、响应、断言和数据库副作用。
6. 把能稳定执行的接口加入测试场景，再按依赖顺序串起来。

工具界面版本可能不同，菜单名称变化时，找“环境、接口、测试场景、断言、导出”这些同义功能即可。

## 3. 登录接口断言示例

Postman Tests 脚本：

```javascript
pm.test('状态码符合登录成功契约', function () {
  pm.expect(pm.response.code).to.be.oneOf([200, 201])
})

const body = pm.response.json()
pm.test('返回用户和令牌', function () {
  pm.expect(body.data || body).to.have.property('token')
})

const token = body.data?.token || body.token
if (token) pm.environment.set('adminToken', token)
```

根据项目真实响应结构调整断言，不要为了让断言通过而放宽到“响应是 2xx”。

### 3.1 断言到底是什么

断言就是自动化版的“我预期这里应该是……”。例如：状态码等于 200、响应体存在 `user`、用户对象不包含密码、登录后确实得到 Cookie 或 Token。每个断言只验证一个事实，断言失败时先保存原始响应，不要马上把断言改宽。

错误接口可以这样练习：

```javascript
pm.test('错误密码应拒绝', function () {
  pm.expect(pm.response.code).to.be.oneOf([400, 401, 422])
})

const errorBody = pm.response.json()
pm.test('错误响应包含可读信息', function () {
  pm.expect(errorBody).to.have.property('message')
})
```

实际项目的错误码以接口契约为准。不要为了适应当前实现，把所有失败都写成“400、401、422 任意一个都可以”，否则真正的状态码回归会被漏掉。

## 4. 每类接口都要测的场景

| 类别 | 最少场景 |
| --- | --- |
| 正常 | 合法参数、最小合法数据、完整数据 |
| 参数 | 缺字段、空字符串、错误类型、超长、非法枚举、未知字段 |
| 认证 | 无 Token、过期 Token、篡改 Token、错误 Token |
| 授权 | 普通用户访问管理员接口、资源所有者与非所有者 |
| 资源 | 不存在 ID、错误格式 ID、已删除资源、重复创建 |
| 幂等 | 重复提交、重复删除、重复发布、重复上传 |
| 并发 | 两次更新、同时发布/下架、分页期间新增数据 |
| 稳定性 | 超时、依赖失败、服务重启后的重试 |

### 4.1 以登录接口为例的完整清单

1. 正确邮箱 + 正确密码。
2. 正确邮箱 + 错误密码。
3. 不存在邮箱 + 任意密码。
4. 空邮箱、空密码。
5. 邮箱格式错误、密码超长。
6. 多次错误后账号锁定或限流。
7. 登录成功后访问 `/api/auth/me`。
8. 退出后使用旧 Token 访问受保护接口。
9. 普通用户使用管理员接口。
10. 重复发送登录请求，确认不会产生异常重复数据。

### 4.2 接口测试记录表

```markdown
| 编号 | 请求 | 前置 | 输入 | 预期状态 | 实际状态 | 数据副作用 | 证据 |
| --- | --- | --- | --- | ---: | ---: | --- | --- |
| API-001 | POST /api/auth/login | 账号启用 | 正确账号密码 | 200 |  | 创建会话 |  |
```

## 5. 链路测试：登录到发布

按以下顺序执行并保存每个响应：

1. 管理员登录，保存 Token。
2. 创建草稿，记录文章 ID。
3. 查询草稿，核对返回字段。
4. 更新标题、正文、分类和标签。
5. 发布文章，核对状态和时间字段。
6. 用公开接口查询，确认公开端可见。
7. 用普通用户 Token 调用管理接口，确认被拒绝。
8. 删除或移入回收站，确认公开接口不再返回。
9. 清理测试数据，并保存清理结果。

### 5.1 链路失败时如何定位

假设“发布后公开端看不到文章”：

1. 先看发布请求状态码和响应体。
2. 用文章 ID 查询管理接口，看状态是否为已发布。
3. 用 MongoDB 查询状态、删除标记和发布时间。
4. 直接调用公开详情接口，不先看页面。
5. 如果接口能返回但页面没有，检查前端路由、缓存和请求参数。
6. 如果数据库不是已发布，问题在发布接口、服务、权限或输入。

## 6. 导出与命令行回归

Postman 导出集合和环境时删除 Token、密码和个人信息。Apifox 导出接口定义时检查示例响应是否包含敏感字段。需要批量执行时使用 Newman 或 Apifox CLI，并保存 JUnit/HTML 报告。

### 6.1 Newman 基础练习

如果已经安装 Newman：

```powershell
npx newman run '.\个人博客-接口测试.postman_collection.json' `
  -e '.\blog-local.postman_environment.json' `
  --reporters cli,junit `
  --reporter-junit-export '.\测试记录\2026-09-18\04-接口\newman.xml'
```

如果命令失败，先确认集合路径、环境路径和后端服务地址。报告中的通过数不能代替失败请求的分析，要打开 XML 或终端输出查看具体请求。

## 7. 本阶段常见错误

1. 把浏览器地址栏能打开当成接口测试；地址栏通常只能方便发送 GET，无法覆盖 POST、请求体和认证。
2. 只断言状态码，不检查响应字段和数据库副作用。
3. 复制别人 Token 长期使用；Token 过期后会造成假失败。
4. 在请求体中写真实密码并导出集合。
5. 把 500 当作“接口按预期失败”；500 通常代表服务端异常，需要缺陷调查。
6. 顺序依赖没有写前置条件；别人单独执行第二个请求就会失败。

你能从一个接口样例反推出完整测试矩阵，能解释每个状态码和字段断言的理由，并能用接口证据证明数据库副作用和权限边界正确。
