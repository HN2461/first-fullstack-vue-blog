# 12 综合实战：为博客系统完成一轮测试

## 实战目标

从接手版本到发布建议，完成一次完整测试项目。最终作品集应包含：测试计划、风险清单、用例、接口集合、数据库核对、自动化结果、JMeter 报告、缺陷闭环和测试总结。

## 给小白的实战规则

这不是“五天把所有工具点一遍”的比赛，而是模拟真实版本的测试过程。每完成一个动作都要留下记录；如果某项因工具、环境或权限无法完成，写成阻塞和原因，不要伪造通过。

每天开始前写“今天要验证什么、需要什么前置、完成标准是什么”；结束时写“完成了什么、发现了什么、还有什么风险”。

## 业务范围

本轮只选可闭环的主线，避免一开始把所有页面混在一起：

```text
管理员登录 -> 创建文章草稿 -> 编辑分类/标签 -> 发布
-> 公开端查看 -> 搜索 -> 普通用户阅读/评论
-> 管理员审核评论 -> 下架或移入回收站
```

### 实战角色和数据

| 角色/数据 | 用途 |
| --- | --- |
| 游客 | 验证公开页面和未登录限制 |
| 普通用户 | 验证阅读、评论和管理接口越权 |
| 管理员 | 验证文章、分类、评论和回收站操作 |
| 草稿、已发布文章、回收站文章 | 验证状态、可见性和权限 |

所有名称增加日期后缀，例如 `qa_20260918_article_draft_001`。实战结束按依赖顺序清理，并记录软删除和永久删除的区别。

## 第 1 天：接手与计划

1. 记录提交号、环境、服务地址、数据库和账号角色。
2. 读路由、模型、现有测试，画出业务链路。
3. 建立风险清单，选出 P0/P1 场景。
4. 写测试计划、准入和准出标准。

产出：`01-项目地图.md`、`02-测试计划.md`、`03-风险清单.md`。

### 第 1 天完成标准

你应该能不看代码回答：管理员和普通用户分别能做什么；文章从草稿到公开的状态变化；公开端如何证明文章可见；至少三个最高风险是什么。

## 第 2 天：用例与数据

1. 为登录、文章、权限、评论写用例。
2. 用等价类和边界值覆盖标题、正文、分页、评论长度和文件。
3. 准备管理员、普通用户、无权限用户和隔离文章。
4. 记录所有数据 ID 和清理脚本。

产出：`用例.xlsx` 或 Markdown 表、`测试数据说明.md`。

### 第 2 天完成标准

至少有 20 条用例，其中 P0/P1 覆盖登录、文章发布、普通用户越权、公开可见性和评论审核；每条用例都有前置、步骤、预期和清理方式。

## 第 3 天：接口与数据库

1. 在 Postman/Apifox 建环境和集合。
2. 完成登录、文章、搜索、评论和 RBAC 请求。
3. 加入状态码、响应字段和业务结果断言。
4. 用 MongoDB 核对创建、发布、审核、删除前后状态。
5. 在独立 MySQL 库完成表、约束、事务、索引和恢复练习。

产出：集合导出文件（删除 Token）、接口报告、MongoDB 查询记录、MySQL SQL 文件。

### 第 3 天完成标准

至少 10 个接口请求可以按顺序执行；至少 3 个错误场景有明确状态码断言；一篇文章完成创建、发布、公开查询和回收的数据库前后核对。

## 第 4 天：Web、自动化与缺陷

1. 执行桌面/移动视口、空数据、错误、刷新、重复提交和键盘检查。
2. 把健康检查、登录或公开文章查询写成 Pytest/API 自动化。
3. 把登录到文章详情写成 Playwright 关键链路（若项目环境允许）。
4. 对发现的问题提交缺陷，并让另一人按你的步骤复现。

产出：浏览器矩阵、自动化报告、缺陷单和证据目录。

### 第 4 天完成标准

至少完成一个桌面视口和一个移动视口；一条 Pytest 或 Playwright 测试可以独立运行；至少提交一条可复现缺陷，或记录本轮未发现缺陷的覆盖证据。

## 第 5 天：性能与发布建议

1. 用 JMeter 先做 1 线程基线，再逐级增加公开文章列表和搜索负载。
2. 记录 P95、错误率、吞吐量、服务资源和 MongoDB 查询情况。
3. 在 PyreFocus 中建立版本、套件、执行和缺陷关联；若工具不可用，用表格完成同样字段。
4. 运行构建、后端测试、编码检查和发布后冒烟。
5. 写测试总结，给出“通过 / 有条件通过 / 不通过”以及剩余风险。

产出：JMeter JTL/HTML、测试管理执行统计、发布验收单、最终测试报告。

### 第 5 天完成标准

JMeter 至少有 1 线程基线和一组逐级负载结果；报告写明 P95、错误率、吞吐量和限制；发布建议明确是通过、有条件通过还是不通过。

## 验收问题

完成后不看文档回答：

1. 普通用户为什么不能发布文章？证据是什么？
2. 文章发布后，接口、数据库和公开页面分别怎样证明成功？
3. 同一个发布请求重复发送会发生什么？这是需求还是缺陷？
4. 搜索响应变慢时，如何区分服务、数据库、网络和测试数据因素？
5. 为什么本轮性能结果不能直接承诺生产容量？
6. 还有哪些没有覆盖的风险？如果只能再测一小时，优先测什么？

### 验收问题参考思路

不要背固定答案，要引用自己的证据：权限问题引用普通用户请求状态码和数据库状态；发布成功同时引用接口响应、MongoDB 字段和公开页面；重复发布要说明需求约定和实际副作用；性能问题要把服务、数据库、压测机和网络放在一起比较；剩余风险要写未覆盖原因和下一步。

## 最终作品集目录

```text
测试记录/版本-日期/
├─ 测试计划.md
├─ 风险清单.md
├─ 用例.md
├─ 接口集合.json
├─ 数据库核对.md
├─ Web兼容性矩阵.md
├─ 自动化报告/
├─ JMeter/
├─ 缺陷/
├─ 测试管理/
├─ 发布验收单.md
└─ 测试总结.md
```

完成这套目录后，你不只是“看过工具”，而是有一套能向团队解释、复现和复盘的测试证据。

## 实战结束后的复盘问题

1. 哪一条用例最容易被漏测？为什么？
2. 哪一次失败最难定位？后来找到了哪一层？
3. 哪些数据清理动作最容易污染下一轮测试？
4. 哪个自动化测试最值得长期保留？哪个应该删除或重写？
5. 如果上线后出现同类问题，监控、日志或测试应如何提前发现？

把答案写在 `复盘.md`，这份复盘比单纯增加用例数量更能帮助你形成测试思维。
