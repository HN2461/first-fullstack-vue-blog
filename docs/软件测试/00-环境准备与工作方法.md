# 00 环境准备与工作方法

## 本阶段目标

完成测试环境、项目环境和证据目录的准备，学会在执行任何测试前记录“测的是什么版本、用的什么数据、在哪里测”。本阶段不追求工具数量，先保证每次结果可重复。

## 先理解“环境”是什么

环境不是“电脑”两个字，而是一组会影响结果的条件：操作系统、代码提交号、前端地址、后端地址、数据库地址、配置文件、账号角色、浏览器版本、测试数据和依赖服务。只要其中一个条件变化，测试结果就可能变化。

例如，同一个登录用例在以下两种环境中可能得到不同结果：

- 本地 MongoDB 里有管理员账号，测试可以成功登录。
- 新数据库没有账号，测试会失败，但这不一定是产品缺陷，可能只是前置数据没有准备。

因此每次记录都要写清“在哪里、用什么版本、用什么数据”。

## 0. Windows 小白准备

下面的命令在 PowerShell 中执行。看到命令前的 `PS>` 不需要复制；代码块中的注释行以 `#` 开头，可以复制也可以不复制。

### 0.1 打开 PowerShell 并进入仓库

1. 按 `Win` 键，搜索“PowerShell”。
2. 打开普通 PowerShell，不需要管理员权限时不要使用管理员窗口。
3. 输入：

```powershell
Set-Location 'C:\Users\HN246\Desktop\个人全栈博客系统'
Get-Location
```

预期结果中的 `Path` 应该是项目根目录。如果路径不对，后面的 `npm`、`git` 和文件命令可能全部作用在错误位置。

### 0.2 检查命令是否存在

```powershell
Get-Command node, npm, git, python, java, mongosh -ErrorAction SilentlyContinue |
  Select-Object Name, Source, Version
```

如果某个工具没有输出，说明它可能没有安装、没有加入 PATH，或当前终端还没有重新打开。先重新打开 PowerShell；仍然找不到时，把完整错误复制到环境记录中，不要自己猜版本。

### 0.3 推荐版本

当前项目后端和前端的 `package.json` 要求 Node.js `>=20`。建议使用 Node.js 20 LTS 或更高 LTS；Java 用于 JMeter，建议 JDK 17 或更高 LTS；Python 建议 3.11 或更高；MongoDB 使用与本机兼容的稳定版。版本不是越新越好，团队应尽量统一。

## 1. 建立测试工作区

在仓库根目录执行：

```powershell
New-Item -ItemType Directory -Force -Path 测试记录\2026-09-18\00-环境准备 | Out-Null
Set-Location .
git status --short
git branch --show-current
git log -1 --oneline
```

把输出保存到 `测试记录/2026-09-18/00-环境准备/01-仓库状态.txt`。如果工作区有未提交修改，不要覆盖或清理，先在记录中写明来源。

可以直接把命令输出保存成文件：

```powershell
git status --short | Tee-Object '测试记录\2026-09-18\00-环境准备\01-git-status.txt'
git branch --show-current | Tee-Object '测试记录\2026-09-18\00-环境准备\02-branch.txt'
git log -1 --oneline | Tee-Object '测试记录\2026-09-18\00-环境准备\03-commit.txt'
```

`Tee-Object` 的意思是“一边在屏幕显示，一边写入文件”。如果输出为空，不代表命令没有执行，`git status --short` 为空通常表示工作区没有未提交变更。

## 2. 核对工具

逐条执行并记录版本：

```powershell
node --version
npm --version
git --version
mongosh --version
java -version
python --version
```

工具用途：

| 工具 | 先练什么 | 结果证据 |
| --- | --- | --- |
| Git | 查看版本、比较变更、定位提交 | 提交号、diff |
| PowerShell | 进入目录、运行命令、保存日志 | 命令记录 |
| Node/npm | 启动项目、构建和测试 | 构建/测试日志 |
| MongoDB | 查询文档、索引、聚合 | 查询结果 |
| Java | 启动 JMeter | `java -version` |
| Python | 运行 Pytest 辅助脚本 | `pytest --version` |
| 浏览器 | 用户行为、网络、控制台、响应式 | 截图和 HAR |

Postman、Apifox、MySQL Server/MySQL Workbench、MongoDB Compass、Apache JMeter、PyreFocus 分别打开一次，记录安装版本和登录地址。不要把密码写进仓库。

### 2.2 常见“命令找不到”处理

| 现象 | 原因方向 | 处理顺序 |
| --- | --- | --- |
| `node is not recognized` | Node 未安装或 PATH 未刷新 | 重开终端，再检查 Node 安装 |
| `mongosh is not recognized` | Shell 未安装或未加入 PATH | 用 MongoDB Compass 验证连接，随后补装 Shell |
| `java is not recognized` | JDK 未安装 | 安装 JDK 并重新打开终端 |
| `python is not recognized` | Python 未安装或 Windows 别名干扰 | 执行 `py --version`，再配置 Python |
| 版本和同事不同 | 使用不同安装方式或 LTS | 把差异写入环境基线，不要私自升级生产环境 |

## 3. 启动当前项目

先按项目文档准备 `backend/.env` 和 `frontend/.env`，再分别启动。复制配置文件时只复制示例，不要把真实生产 `.env` 带入测试记录：

```powershell
if (-not (Test-Path backend\.env)) { Copy-Item backend\.env.example backend\.env }
if (-not (Test-Path frontend\.env)) { Copy-Item frontend\.env.example frontend\.env }
```

确认 `backend/.env` 至少包含本地 MongoDB、`SERVER_PORT=3001`、`CLIENT_ORIGIN=http://127.0.0.1:5173` 等本地配置。再执行：

```powershell
Set-Location backend
npm install
npm run test

Set-Location ..\frontend
npm install
npm run build
```

这里的 `npm run test` 是后端自动化测试，`npm run build` 是前端生产构建。它们不是启动服务；启动服务要使用下面的开发命令。

开发联调时使用两个终端：

```powershell
# 终端 1
Set-Location backend
npm run dev

# 终端 2
Set-Location frontend
npm run dev
```

成功时后端终端应出现监听端口和数据库连接成功信息，前端终端应显示类似 `Local: http://127.0.0.1:5173/`。如果终端没有返回提示，不要立即关闭窗口；开发服务会持续占用终端，这是正常现象。

在第三个终端验证健康接口：

```powershell
curl.exe -i http://127.0.0.1:3001/api/health
```

预期是 HTTP `200`，响应体能够表示服务健康。若返回 `Failed to connect`，先检查后端终端是否仍在运行、端口是否被占用、`.env` 的 `SERVER_PORT` 是否不同。

检查前端时打开 `http://127.0.0.1:5173`。浏览器能看到页面不等于后端正常，还要在 Network 面板确认 API 请求没有大量 `4xx` 或 `5xx`。

记录前端地址、后端地址、MongoDB 地址、当前提交号、测试账号角色和数据是否为新库。当前本地演示管理员可使用项目约定的 `admin@example.com`，密码只从本地配置或环境变量读取，不复制到共享文档。

## 4. 建立证据规则

每一次失败至少保留：

1. 复现时间和环境版本。
2. 操作步骤和实际输入。
3. 实际结果、预期结果和影响范围。
4. 页面截图、网络请求、响应体、服务日志或数据库查询结果中的至少一种原始证据。
5. 清理方式和是否可以稳定复现。

文件名使用“日期-模块-场景-结果”，例如：`2026-09-18-登录-空密码-失败响应.json`。

### 4.1 截图不要只截结果

一张好的失败截图应同时包含页面上的关键现象和浏览器地址栏/时间信息；接口问题还要保存 Network 请求详情；数据库问题要保存查询语句和结果。不要只截一张“红色报错”而不说明是哪个请求产生的。

### 4.2 保存日志的命令

```powershell
Set-Location backend
npm run test 2>&1 | Tee-Object '..\测试记录\2026-09-18\00-环境准备\backend-test.log'
```

`2>&1` 会把错误输出也合并进日志。测试完成后用文本编辑器搜索 `FAIL`、`Error`、`failed`，再回到对应测试文件定位，不要只看最后一行。

### 4.3 证据的最小可读格式

```markdown
# 证据说明

- 时间：2026-09-18 09:30
- 版本/提交：
- 环境：本地 / 测试服务器
- 账号角色：
- 操作：
- 预期：
- 实际：
- 文件：
- 是否稳定复现：是 / 否 / 未知
```

## 6. 本阶段常见错误

1. **把 `localhost`、`127.0.0.1` 和公网 IP 混着用**：Cookie、跨域和加密能力可能因此表现不同。练习时固定使用项目配置中的 `127.0.0.1`。
2. **把前端能打开当成系统可用**：前端可能只是静态资源正常，API 请求仍然失败。
3. **把测试账号密码写入 Git**：密码只能放本地 `.env`、密码管理器或团队安全系统。
4. **直接清空数据库解决数据污染**：先导出证据并确认是本地测试库，再做有范围的清理。
5. **服务启动后立刻关闭窗口**：开发服务器需要持续运行，另开终端执行测试。
