# 06 Web、兼容性与安全基础

## 本阶段目标

从用户可观察行为验证页面功能、布局、浏览器差异和基础安全边界。安全练习只在本地或明确授权的测试环境进行，不对生产系统做攻击性操作。

## 先理解 Web 测试的三个层面

1. **功能层面**：按钮、表单、跳转、列表、弹窗是否按需求工作。
2. **表现层面**：不同浏览器、屏幕尺寸、主题和网络条件下是否仍然可用。
3. **安全层面**：未登录、普通用户和管理员是否只能看到和操作自己被允许的内容；输入和输出是否会造成信息泄露或脚本执行。

这三层要分开记录。一个按钮在桌面上能点击，不代表它在移动端没有横向溢出；页面隐藏了管理员菜单，也不代表直接调用管理员接口不会越权。

## 1. 浏览器功能检查

使用 Chrome 或 Edge 的 DevTools：

1. `Console`：确认没有未处理异常、敏感信息和持续报错。
2. `Network`：确认请求方法、状态码、缓存、失败接口、重复请求和响应时间。
3. `Application`：检查 Token、Cookie、Local Storage 的范围和退出后的清理。
4. `Elements`：确认表单标签、禁用状态、错误提示和焦点顺序。
5. `Lighthouse` 或无障碍工具：记录明显的结构、对比度和可访问性问题。

### 1.1 DevTools 小白操作顺序

1. 打开本地页面，按 `F12` 或右键选择“检查”。
2. 点击 **Network**，勾选 **Preserve log**，再刷新页面。
3. 点击一个业务按钮，找到对应请求；不要只看 `Fetch/XHR`，静态资源问题还要看 `Doc/JS/CSS`。
4. 点开请求的 **Headers**，记录 URL、方法、状态码和请求头。
5. 点开 **Payload**，确认发送的字段和类型；点开 **Response/Preview**，确认返回字段。
6. 点击 **Console**，刷新页面并执行一次业务操作，保存错误和警告。
7. 点击 **Application**，在 Cookies、Local Storage、Session Storage 中查看登录状态。

### 1.2 如何保存 HAR

Network 面板空白处右键选择 **Save all as HAR with content**，保存到当前测试记录目录。HAR 可能包含 Cookie、Token、邮箱和请求体，分享前必须脱敏。不要把包含凭据的 HAR 提交到 Git。

### 1.3 常见页面结果和下一步

| 页面现象 | 先看什么 | 不要马上做什么 |
| --- | --- | --- |
| 按钮无反应 | Console、请求是否发出、按钮是否禁用 | 不要连续点击几十次 |
| 一直加载 | Network 是否 pending、后端日志、超时 | 不要只刷新掩盖请求 |
| 页面白屏 | Console 第一条错误、构建资源 | 不要直接删除 node_modules |
| 显示成功但列表没变 | 请求响应、刷新后的查询、数据库 | 不要只相信 Toast |

## 2. 响应式与兼容性矩阵

至少执行以下矩阵：

| 浏览器 | 视口 | 重点 |
| --- | --- | --- |
| Chrome 最新版 | 1440×900 | 桌面主流程、表格、弹窗 |
| Edge 最新版 | 1366×768 | 企业环境兼容性 |
| Chrome 移动模拟 | 390×844 | 登录、列表、详情、菜单 |
| Safari 或 WebKit | 实际设备/模拟器 | 日期、上传、固定定位 |

每个视口检查：横向溢出、文字截断、弹窗滚动、表格固定列、折叠菜单、键盘操作和空数据状态。

### 2.1 视口测试步骤

1. 在 DevTools 点击设备工具栏图标，选择或自定义 390×844。
2. 刷新页面，等待所有请求完成。
3. 从登录开始走一条最短业务链路，不要只截首页。
4. 检查页面右侧是否出现横向滚动条；输入框、表格、弹窗是否能操作。
5. 在 390×844、768×1024、1366×768、1440×900 各执行一次。
6. 回到真实浏览器窗口再执行一次，避免模拟器与真实设备差异被忽略。

| --- | --- | --- | --- | --- | --- |

## 3. 表单和交互检查

- [ ] 必填、格式、长度、前后空格和中文输入均有明确行为。
- [ ] 快速连续点击不会重复提交。
- [ ] 加载、成功、失败、空数据和网络断开状态可区分。
- [ ] 返回、刷新和重新进入页面不会丢失或错误重复数据。
- [ ] 弹窗超长时只在内容区滚动，底部按钮保持可操作。
- [ ] 图标按钮有 tooltip 或上下文，键盘焦点可见。

### 3.1 键盘操作练习

不使用鼠标，按以下顺序操作登录页和一个管理弹窗：

1. 按 `Tab`，观察焦点是否按视觉顺序移动。
2. 输入框是否有可理解的标签。
3. 按 `Enter` 是否能提交，按 `Esc` 是否按需求关闭弹窗。
4. 弹窗打开后焦点是否进入弹窗，关闭后是否回到触发按钮。
5. 禁用按钮是否真的不能提交，错误提示是否能被键盘和辅助技术发现。

### 3.2 网络条件练习

在 Network 的 Throttling 中选择 Slow 3G 或 Offline，只在本地练习：页面是否显示加载状态、请求失败是否有提示、恢复网络后是否可重试、重试是否重复创建数据。完成后恢复为 No throttling。

### 3.3 空数据、错误和重复操作

对文章列表、搜索结果、评论列表和媒体列表分别制造以下状态：

| 状态 | 怎么制造 | 应观察什么 |
| --- | --- | --- |
| 有数据 | 准备 1 至 3 条测试数据 | 列表、分页、操作按钮 |
| 空数据 | 使用不会命中的关键词或空账号 | 空状态说明和返回入口 |
| 加载中 | 慢网络或临时断开 | 是否有明确加载反馈 |
| 请求失败 | 停止后端或使用无效接口 | 错误提示、重试按钮 |
| 重复操作 | 快速双击、刷新后再次提交 | 是否产生重复数据 |

每种状态都要写“用户下一步能做什么”。例如空搜索结果应该告诉用户可以修改关键词，而不是只显示一块空白。

## 4. 基础安全检查清单

仅使用无害测试字符串：

- 登录：错误账号、错误密码、过期 Token、退出后旧 Token。
- 授权：普通用户请求管理员路径、修改其他用户资源 ID。
- 输入：`<b>test</b>`、`' OR '1'='1`、超长字符串、路径片段 `../`，观察是否被安全处理。
- 文件：错误 MIME、双扩展名、超大文件、空文件、同名覆盖。
- 输出：公开页面是否泄露邮箱、角色内部字段、Token、服务器路径或堆栈。
- 会话：Cookie 的 HttpOnly/Secure/SameSite（若使用 Cookie）和退出清理。

记录“输入、位置、实际输出、是否被存储、是否执行、证据”，不要只写“安全/不安全”。

### 4.1 权限测试的三步法

以“文章发布”为例：管理员在页面操作确认成功；普通用户在页面看不到发布操作，再直接用普通用户认证信息调用相同接口确认服务端拒绝；游客不带认证信息调用接口确认未认证结果。随后修改 URL 中的文章 ID，检查普通用户是否能访问别人的草稿，这属于对象级权限。

### 4.2 输入和敏感信息检查

在本地输入以下无害字符串并观察列表、详情、错误提示和日志：

```text
<b>test</b>
' OR '1'='1
../../test.txt
超长文本（超过字段限制）
```

记录是否被安全转义、是否改变查询结果、是否导致 500。只在授权环境操作，不上传脚本文件、不扫描生产端口。再在 Network Response、页面源码、Local Storage、Cookie 和日志中搜索 `password`、`token`、`secret`、数据库连接串、服务器绝对路径；发现疑似敏感信息时先保存脱敏证据。

### 4.3 Cookie、Token 和退出登录

当前前端请求同时设置了 `withCredentials`，并兼容 Bearer Token。测试时不要假设只有一种认证方式：

1. 登录前调用 `/api/auth/me`，记录未认证结果。
2. 登录后检查 Network 请求是否带上 Cookie 或 Authorization。
3. 在 Application 面板记录认证信息的存储位置和过期时间，不保存完整值。
4. 退出登录后重新调用受保护接口，确认旧认证信息不能继续使用。
5. 关闭浏览器重新打开，按需求判断会话是否应保留。

如果使用 Cookie，观察 `HttpOnly`、`Secure`、`SameSite` 等属性是否符合部署环境；如果使用 Local Storage，关注 XSS 风险和退出时是否清理。测试人员记录现象和证据，不自行修改安全策略来“让测试通过”。

### 4.4 CORS 和跨域的初步检查

当前本地前端默认是 `http://127.0.0.1:5173`，后端会根据配置判断允许的来源。访问页面后在 Network 中查看请求失败信息：

- 浏览器 Console 出现 CORS 错误时，记录 Origin、请求 URL 和后端响应头。
- 不要只在 Postman 中判断跨域，因为 Postman 不受浏览器 CORS 限制。
- 如果前端换成 `localhost` 而后端只允许 `127.0.0.1`，这可能是配置差异，不一定是业务缺陷，但应在部署配置中明确。

## 完成标准

你能提供一份按浏览器和视口分组的结果矩阵，能通过 Network 和数据库证据解释前端现象，并能在授权本地环境完成基础权限、输入和敏感信息检查。

## 5. 无障碍小白检查

不要求一开始就掌握完整 WCAG 标准，先完成可观察的基础检查：

- 图片有能说明用途的替代文本，装饰图片不会干扰朗读。
- 输入框有可见标签或等价的可访问名称。
- 颜色不是唯一的信息来源，错误状态同时有文字或图标说明。
- 文本与背景有足够对比度，禁用态和选中态仍然能辨认。
- 键盘可以完成登录、打开菜单、提交表单和关闭弹窗。
- 焦点不会被固定头部、弹窗或抽屉遮挡。

把“人工观察结果”和自动化工具结果分开记录。自动化工具没有报错，不代表完整的键盘和语义体验一定合格。
