# 06 多表连接与集合思维

## 1. 为什么 JOIN 是关系型数据库核心

订单表只保存 `user_id`，用户信息在 `users`。要返回“订单号 + 用户名”，需要通过公共关系把两张表连接：

```sql
SELECT
  o.order_no,
  o.total_amount,
  u.username
FROM orders AS o
INNER JOIN users AS u ON u.id = o.user_id;
```

SQL 操作的是集合。理解 JOIN 的关键不是背语法，而是先回答：

1. 左侧集合是什么？
2. 右侧集合是什么？
3. 哪些列表示两者关系？
4. 没有匹配数据时是否仍要保留左侧行？
5. 一条左侧记录可能匹配多少条右侧记录？

## 2. INNER JOIN（P0）

只保留两侧能匹配的行：

```sql
SELECT
  o.id,
  o.order_no,
  u.username,
  o.status
FROM orders AS o
INNER JOIN users AS u ON u.id = o.user_id
WHERE o.status = 'paid';
```

`INNER` 可省略，但显式写出可读性更好。

## 3. LEFT JOIN（P0）

保留左表全部行，右表没有匹配时字段为 NULL：

```sql
SELECT
  u.id,
  u.username,
  COUNT(o.id) AS order_count
FROM users AS u
LEFT JOIN orders AS o ON o.user_id = u.id
GROUP BY u.id, u.username;
```

这会包含从未下单的用户，`COUNT(o.id)` 为 0。

如果改成 `COUNT(*)`，每个用户至少会统计 LEFT JOIN 产生的那一行，从未下单用户也可能得到 1，因此这里必须数右表非空主键。

## 4. LEFT JOIN 条件放 ON 还是 WHERE（P0）

查所有用户及其已支付订单数量：

```sql
SELECT
  u.id,
  u.username,
  COUNT(o.id) AS paid_order_count
FROM users AS u
LEFT JOIN orders AS o
  ON o.user_id = u.id
 AND o.status = 'paid'
GROUP BY u.id, u.username;
```

如果把 `o.status = 'paid'` 放到 WHERE：

```sql
WHERE o.status = 'paid'
```

未匹配行的 `o.status` 是 NULL，会被 WHERE 过滤，LEFT JOIN 实际上退化成 INNER JOIN。判断规则：

- ON 决定右表哪些行参与匹配。
- WHERE 过滤连接完成后的最终行。

## 5. 多表 JOIN（P0）

订单详情常连接订单、用户、明细和商品：

```sql
SELECT
  o.order_no,
  u.username,
  p.name AS product_name,
  oi.quantity,
  oi.unit_price,
  oi.quantity * oi.unit_price AS line_amount
FROM orders AS o
INNER JOIN users AS u ON u.id = o.user_id
INNER JOIN order_items AS oi ON oi.order_id = o.id
INNER JOIN products AS p ON p.id = oi.product_id
WHERE o.id = 1001
ORDER BY oi.id;
```

订单有 3 条明细，结果就有 3 行。这不是重复，而是“一对多”展开后的正确基数。

## 6. JOIN 重复行诊断（P0）

看到重复时不要立刻加 DISTINCT。依次检查：

1. JOIN 条件是否遗漏一部分联合键。
2. 被连接表是否本来就是一对多。
3. 中间表是否缺少防重复唯一约束。
4. 需求真正需要明细行、聚合结果，还是只判断存在性。

错误示例：租户系统只按 `role_code` 连接，没有带 `tenant_id`：

```sql
ON r.role_code = ur.role_code
```

正确关系可能是：

```sql
ON r.tenant_id = ur.tenant_id
AND r.role_code = ur.role_code
```

## 7. EXISTS：只关心是否存在（P0）

查询至少有一个已支付订单的用户：

```sql
SELECT u.id, u.username
FROM users AS u
WHERE EXISTS (
  SELECT 1
  FROM orders AS o
  WHERE o.user_id = u.id
    AND o.status = 'paid'
);
```

如果只判断存在性，`EXISTS` 往往比 JOIN 后 DISTINCT 更贴近业务语义。

查询从未下单的用户：

```sql
SELECT u.id, u.username
FROM users AS u
WHERE NOT EXISTS (
  SELECT 1
  FROM orders AS o
  WHERE o.user_id = u.id
);
```

相比 `NOT IN`，`NOT EXISTS` 更不容易被子查询中的 NULL 破坏语义。

## 8. 自连接（P1）

分类树中的父分类也在同一张表：

```sql
SELECT
  child.id,
  child.name,
  parent.name AS parent_name
FROM categories AS child
LEFT JOIN categories AS parent ON parent.id = child.parent_id;
```

同一张表取不同别名，分别扮演子节点和父节点。

## 9. CROSS JOIN（P2）

笛卡尔积把左表每行与右表每行组合：

```sql
SELECT s.size_name, c.color_name
FROM sizes AS s
CROSS JOIN colors AS c;
```

可用于生成规格组合，但行数是两侧数量乘积。普通 JOIN 漏写条件也可能意外产生巨大笛卡尔积，是常见事故来源。

## 10. UNION 与 UNION ALL（P1）

纵向合并两个结构兼容的结果集：

```sql
SELECT email, 'customer' AS source FROM users
UNION ALL
SELECT email, 'subscriber' AS source FROM newsletter_subscribers;
```

- `UNION`：合并并去重，通常需要额外排序/临时处理。
- `UNION ALL`：保留重复，通常更快。

业务不要求去重时优先 `UNION ALL`。参与合并的 SELECT 列数要一致，对应类型应兼容。

## 11. 常见接口查询模板

### 列表查询

```sql
SELECT
  o.id,
  o.order_no,
  o.status,
  o.total_amount,
  u.username,
  o.created_at
FROM orders AS o
INNER JOIN users AS u ON u.id = o.user_id
WHERE o.deleted_at IS NULL
  AND (? IS NULL OR o.status = ?)
ORDER BY o.created_at DESC, o.id DESC
LIMIT ? OFFSET ?;
```

实际后端更推荐按传入筛选项动态构造固定白名单条件，而不是大量使用 `? IS NULL OR`，因为 OR 可能影响索引选择。无论如何，值都必须参数化。

### 列表总数

```sql
SELECT COUNT(*) AS total
FROM orders AS o
WHERE o.deleted_at IS NULL
  AND o.status = ?;
```

总数 SQL 不要机械复制所有用于展示字段的 JOIN。只有过滤条件依赖某张表时才需要连接它。

### 一次查询一对多详情

JOIN 返回平面行，Node.js 层可把相同订单聚合成：

```json
{
  "orderNo": "ORD202607260001",
  "items": [
    { "productName": "机械键盘", "quantity": 1 },
    { "productName": "鼠标", "quantity": 2 }
  ]
}
```

也可分别查询订单头和明细。选择取决于查询复杂度和可维护性，不要强求“一条 SQL 做完所有事情”。

## 12. JOIN 性能基本原则

- 连接列类型必须一致，例如都为 `BIGINT UNSIGNED`。
- 外键/连接列通常需要索引。
- 先通过 WHERE 尽量缩小结果集。
- 避免在连接列上做函数或隐式类型转换。
- 用 `EXPLAIN` 检查访问方式和估算行数。
- 不要把大结果集全部拉回应用再手工关联。

## 13. MongoDB 对照：$lookup、populate 与 JOIN（P0）

MongoDB 中通过引用保存 `userId` 时，常使用 `$lookup` 或 Mongoose `populate()` 获取用户信息；MySQL 直接通过 JOIN 表达同一关联：

```text
MongoDB: orders.userId -> $lookup users._id
MySQL:   orders.user_id -> JOIN users ON users.id = orders.user_id
```

两者不能机械等同：

- Mongoose `populate()` 可能生成额外查询，要检查是否出现 N+1。
- `$lookup` 和 JOIN 都可能把一对多关系展开成多行/多个数组元素，必须先确认基数。
- MySQL 可用外键和唯一约束保护关系；MongoDB 引用通常需要应用或校验器额外保证。
- MongoDB 常把关联结果装进数组；SQL 返回扁平行，后端可能需要按订单 ID 重新组装嵌套 JSON。
