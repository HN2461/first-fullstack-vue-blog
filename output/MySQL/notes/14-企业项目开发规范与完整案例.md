# 14 企业项目开发规范与完整案例

## 1. 案例目标

本章把前面知识串成一个简化下单流程。需求：

- 登录用户一次购买多个商品。
- 商品必须上架且库存充足。
- 订单号全局唯一。
- 订单保存商品名称和价格快照。
- 任一步失败，订单和库存全部回滚。
- 重复请求不能重复创建订单。
- 列表支持按用户、状态和时间查询。

完整基础表位于本地实验附件 `sql/01_schema.sql`。本文已经独立说明核心表、约束和事务流程，线上阅读不依赖该附件。

## 2. API 契约

```json
POST /api/orders
{
  "idempotencyKey": "client-20260726-0001",
  "items": [
    { "productId": "1", "quantity": 2 },
    { "productId": "3", "quantity": 1 }
  ]
}
```

注意：客户端不提交可信成交价、用户 ID、订单状态或总金额。它们由认证上下文和服务端计算决定。

## 3. 数据库约束

即使应用已经校验，数据库仍应有：

```sql
UNIQUE KEY uk_orders_order_no (order_no),
UNIQUE KEY uk_orders_user_idempotency (user_id, idempotency_key),
CHECK (total_amount >= 0),
CHECK (quantity > 0),
FOREIGN KEY (user_id) REFERENCES users(id),
FOREIGN KEY (product_id) REFERENCES products(id)
```

幂等键应绑定用户，避免不同用户使用相同客户端键互相冲突。

## 4. 正确的下单顺序（P0）

1. 在事务外校验请求格式、商品数量上限和重复商品 ID。
2. 生成服务端订单号。
3. 开启事务。
4. 按商品 ID 升序读取并锁定所有商品。
5. 校验商品存在、上架、未删除和库存。
6. 使用数据库价格计算订单金额。
7. 插入订单，唯一键保证订单号和幂等键。
8. 条件扣减库存并检查每次影响行数。
9. 批量插入订单明细和库存流水。
10. 提交事务。
11. 提交后再发送消息或异步事件。

按商品 ID 固定顺序锁定能降低多个订单同时购买不同组合商品时的死锁概率。

## 5. 幂等处理（P0）

收到请求先尝试按 `(user_id, idempotency_key)` 查询已有订单。仍必须依赖唯一索引处理并发窗口：两个请求可能同时查询不到。

事务插入遇到重复键时：

1. 回滚当前事务。
2. 查询同一幂等键已有订单。
3. 如果请求摘要一致，返回已有结果。
4. 如果相同幂等键对应不同请求内容，返回冲突错误。

仅“发现重复就返回任意旧订单”可能把错误请求伪装成成功。可额外保存请求摘要哈希。

## 6. 为什么不能信任客户端金额（P0）

攻击者可把 999 元商品价格改成 0.01。服务端必须通过商品 ID 查询可信价格，结合促销、优惠、运费、税费规则计算并保存明细。

支付回调还要校验：

- 支付平台签名。
- 商户订单号。
- 支付金额和币种。
- 当前订单状态。
- 平台事件 ID 幂等性。

## 7. 库存并发方案（P0）

简单可靠的核心语句：

```sql
UPDATE products
SET stock = stock - ?
WHERE id = ?
  AND stock >= ?
  AND status = 'on_sale'
  AND deleted_at IS NULL;
```

影响 0 行就失败并回滚。若已经 `SELECT ... FOR UPDATE` 锁定，仍可保留 `stock >= ?` 作为防御性约束。

高流量秒杀不是把这条 SQL 无限并发打到主库。它需要限流、排队、库存预热、异步化和对账等专项架构，属于进阶主题。

## 8. 状态流转（P0）

支付成功：

```sql
UPDATE orders
SET
  status = 'paid',
  paid_at = CURRENT_TIMESTAMP(3)
WHERE id = ?
  AND status = 'pending';
```

影响 1 行表示本次成功推进；影响 0 行时，需要查询当前状态区分：已经 paid 的重复回调可按幂等成功处理，cancelled 则进入异常/退款流程。

## 9. 事务与外部消息（P1）

数据库 COMMIT 成功后进程可能在发送消息前崩溃，形成“订单有了但消息没发”。Outbox Pattern：

1. 在创建订单的同一数据库事务中插入 `outbox_events`。
2. 后台任务轮询未发布事件并发送消息。
3. 发送成功后标记已发布。
4. 消费方按事件 ID 幂等处理。

这样把数据库原子性与最终消息投递衔接起来。入门项目可先知道问题与模式，达到事件驱动规模时再实现成熟版本。

## 10. 订单列表查询

```sql
SELECT
  o.id,
  o.order_no,
  o.status,
  o.total_amount,
  o.created_at
FROM orders AS o
WHERE o.user_id = ?
  AND o.deleted_at IS NULL
  AND o.created_at >= ?
  AND o.created_at < ?
ORDER BY o.created_at DESC, o.id DESC
LIMIT ?;
```

候选索引：

```sql
KEY idx_orders_user_created_id (user_id, created_at, id)
```

若状态筛选几乎总存在，可评估 `(user_id, status, created_at, id)`。两个访问路径都高频时可能需要两个索引，但必须用真实负载验证写入成本。

## 11. 订单详情查询

可分两条清晰 SQL：

```sql
SELECT id, order_no, status, total_amount, created_at
FROM orders
WHERE id = ? AND user_id = ? AND deleted_at IS NULL;

SELECT
  product_id,
  product_name_snapshot,
  unit_price,
  quantity,
  line_amount
FROM order_items
WHERE order_id = ?
ORDER BY id;
```

先按 `id + user_id` 查询体现资源归属，避免 IDOR 越权。并非所有详情都必须塞进一条巨大 JOIN。

## 12. 发布迁移方案

假设为订单新增 `idempotency_key`：

1. 新增可空列和普通索引，新旧代码均兼容。
2. 发布写入该字段的新代码。
3. 对新请求开始填充并监控。
4. 历史数据是否回填由业务决定。
5. 若目标是 NOT NULL，先校验不存在 NULL，再改约束。
6. 添加联合唯一索引前先查询重复值。

创建唯一索引前的校验：

```sql
SELECT user_id, idempotency_key, COUNT(*) AS duplicate_count
FROM orders
WHERE idempotency_key IS NOT NULL
GROUP BY user_id, idempotency_key
HAVING COUNT(*) > 1;
```

## 13. Code Review 清单

- [ ] SQL 值是否全部参数化？动态列是否白名单？
- [ ] 查询是否只返回必要字段？
- [ ] 用户资源查询是否绑定当前用户/租户？
- [ ] 唯一性是否有数据库唯一索引？
- [ ] 多步写入是否需要事务？事务是否同一连接？
- [ ] 事务中是否存在 HTTP、消息或慢计算？
- [ ] 金额、BIGINT、时间是否正确映射？
- [ ] UPDATE/DELETE 是否检查 affectedRows？
- [ ] 查询条件、排序和 JOIN 是否有合理索引？
- [ ] 迁移是否兼容滚动发布并评估大表影响？
- [ ] 日志是否避免敏感数据并包含 requestId？
- [ ] 测试是否覆盖重复、并发、回滚和边界值？

## 14. MongoDB 订单文档迁移提示（P0）

如果原来的 MongoDB 订单是一份包含 `items` 数组的文档，迁移到本章模型时可按下面方式拆分：

| MongoDB 订单文档 | MySQL 订单案例 |
| --- | --- |
| 订单主文档字段 | `orders` |
| `items[]` 数组元素 | `order_items` 多行 |
| 商品当时的名称、价格 | `product_name_snapshot`、`unit_price` |
| 文档内一次更新 | `orders`、`order_items`、库存和流水的同一事务 |
| 回调事件去重字段 | 幂等键、唯一索引和状态条件更新 |

不要因为 MongoDB 中读取一份文档很方便，就在 MySQL 中把订单、商品、用户和评论全部塞进 JSON。先根据查询、约束、历史快照和并发边界设计表，再决定哪些低频扩展数据保留为 JSON。

## 15. 完成标准

你应尝试只看需求自行实现一次订单模块，然后对照本章检查。真正达到“能用于企业项目”的标准是：不仅正常路径能成功，重复请求、库存不足、并发购买、数据库异常和发布升级也有确定行为。
