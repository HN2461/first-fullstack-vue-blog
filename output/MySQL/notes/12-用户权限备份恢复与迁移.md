# 12 用户权限、备份恢复与迁移

## 1. 应用账号最小权限（P0）

生产应用不使用 root，也不应拥有任意建库、授权或删除数据库权限。

```sql
CREATE USER 'blog_app'@'10.%'
  IDENTIFIED BY 'Use-A-Secret-Manager';

GRANT SELECT, INSERT, UPDATE, DELETE
ON blog_production.*
TO 'blog_app'@'10.%';

SHOW GRANTS FOR 'blog_app'@'10.%';
```

迁移账号可单独拥有 DDL 权限，只在发布时使用。只读报表账号只授予 SELECT。这样可以缩小泄漏或误操作影响。

`'user'@'host'` 共同定义 MySQL 账号。`%` 表示更广来源，不应在没有网络隔离和必要性时无脑使用。

## 2. 密码与连接安全（P0）

- 密码保存在环境配置或密钥管理服务，不进入 Git。
- 不在命令行参数中明文写密码，避免历史和进程列表泄漏。
- 跨不可信网络使用 TLS，并验证服务端证书。
- 定期轮换凭据，应用支持平滑切换。
- 不在日志打印连接串、密码、完整敏感 SQL 参数。
- 数据库端口不直接暴露公网，使用安全组、私网和防火墙限制。

## 3. 备份类型（P0）

### 逻辑备份

导出为 SQL 等逻辑格式，便于查看和跨环境恢复。常用 `mysqldump`。适合中小数据量和结构/数据迁移，但大库速度和恢复时间有限。

### 物理备份

复制 InnoDB 数据文件和日志的一致性备份，速度通常更适合大库。常用 MySQL Enterprise Backup、Percona XtraBackup 或云数据库快照。

### 全量 + 增量 / Binlog

全量备份配合 Binlog 可做时间点恢复（PITR），把数据库恢复到误操作前。是否可恢复取决于备份、Binlog 保留和完整演练。

## 4. mysqldump 基础（P1）

学习环境导出：

```powershell
mysqldump -h 127.0.0.1 -u root -p `
  --single-transaction `
  --routines `
  --triggers `
  --events `
  mysql_learning > mysql_learning.sql
```

说明：

- `--single-transaction` 适用于 InnoDB 一致性逻辑备份，备份期间不要混入不兼容的 DDL。
- 是否导出 routines、events、triggers 要根据项目实际对象决定。
- PowerShell 重定向在不同版本下的文本编码行为需验证；生产更推荐经过验证的脚本或工具参数。
- 密码用交互输入或安全配置文件，不直接写在命令中。

仅导出结构：

```powershell
mysqldump -u root -p --no-data mysql_learning > schema.sql
```

仅导出指定表：

```powershell
mysqldump -u root -p mysql_learning users orders > core_tables.sql
```

## 5. 恢复与验证（P0）

```powershell
mysql -u root -p -e "CREATE DATABASE restore_test CHARACTER SET utf8mb4"
mysql -u root -p restore_test < mysql_learning.sql
```

在 PowerShell 中 `<` 的行为与 cmd/bash 不完全一致，最稳妥方式可使用 MySQL 客户端内部 `SOURCE`，或根据当前 Shell 选择经过验证的管道方式。

恢复不是“命令没报错”就完成。至少验证：

- 表、视图、触发器、事件等对象数量。
- 核心表行数和抽样数据。
- 字符集、时区和账号权限。
- 应用能否通过健康检查和核心业务流程。
- 备份时间、恢复耗时是否满足 RPO/RTO。

RPO：最多能接受丢失多长时间的数据。RTO：故障后最多多久恢复服务。

从未恢复验证过的备份不能被认为可靠。

## 6. Binlog 与时间点恢复（P1）

Binlog 记录数据变更，可用于复制和 PITR。概念流程：

1. 恢复最近一次全量备份。
2. 确认备份对应的 Binlog 位点或 GTID。
3. 重放之后的 Binlog。
4. 在误操作发生前停止。
5. 在隔离环境验证，再制定切换方案。

这是高风险运维操作。真实生产应按云数据库/DBA Runbook 执行，不要仅凭入门示例直接操作主库。

## 7. Schema 迁移（P0）

企业项目不靠开发者打开 GUI 手改生产表。结构变更应使用版本化迁移：

```text
migrations/
  202607260001_create_orders.sql
  202607260002_add_orders_paid_at.sql
```

可使用 Knex、Sequelize、Prisma、db-migrate、Flyway、Liquibase 等成熟工具，按项目技术栈选择。

一份迁移应具备：

- 唯一版本号和清晰名称。
- 可重复追踪的 up 变更。
- 明确回滚策略；不能回滚时写清恢复方式。
- 对现有数据的兼容处理。
- 大表 DDL 的锁和耗时评估。
- 发布顺序与新旧代码兼容窗口。

## 8. Expand and Contract 发布模式（P1）

直接重命名或删除生产列可能让旧实例报错。更稳妥的渐进方式：

1. Expand：新增可空列/新表，旧代码仍可运行。
2. 发布兼容代码，必要时双写新旧字段。
3. 回填历史数据并校验。
4. 切换读取到新结构。
5. 观察稳定后停止旧字段写入。
6. Contract：后续版本删除旧列和兼容代码。

不要在同一次发布中先删除旧列，再期待滚动发布中的旧实例正常工作。

## 9. 数据回填脚本（P0）

迁移已有数据时：

- 默认 dry-run，只统计影响范围。
- 必须显式 `--apply` 才写入。
- 按主键分批，避免超大事务。
- 可重复执行且结果幂等。
- 记录批次、最后 ID、成功/失败数和耗时。
- 写入前备份，写入后做一致性校验。
- 预估 Binlog、复制延迟和磁盘增长。

不要把不可逆的数据清洗藏在应用启动逻辑里。

## 10. 高可用与复制（P1）

常见架构是一主多从或托管数据库高可用实例：

- 主库负责写。
- 从库/只读副本承担读查询、备份或灾备。
- 复制通常存在延迟。

刚写入后立刻从副本读取，可能暂时读不到新数据。关键“写后读”应读取主库、等待复制位点，或在产品层接受最终一致性。

故障切换也不是只改连接地址：需要检测主库、选主、避免双主写入、更新路由、处理旧连接并验证数据一致性。优先使用成熟云数据库或经过验证的 HA 方案。

## 11. 日常监控（P1）

至少关注：

- 可用性、连接数和线程运行数。
- QPS/TPS、查询延迟和错误率。
- CPU、内存、磁盘空间、IOPS 和延迟。
- Buffer Pool 命中与脏页。
- 锁等待、死锁、长事务。
- 慢 SQL 和扫描行数。
- 复制延迟和复制错误。
- 备份是否成功以及最近恢复演练结果。

告警必须有责任人和处理 Runbook。没有人响应的告警只是噪声。

## 12. MongoDB 对照：权限、备份与迁移（P1）

MongoDB 常见的 `mongodump` / `mongorestore` 与 MySQL 的 `mysqldump` / `mysql` 都属于逻辑备份，但恢复可靠性不能只看命令退出码。两者都应验证：

- 对象结构、核心数据量和抽样数据。
- 索引、约束/校验器、用户权限和字符集。
- 应用健康检查、核心读写流程和恢复耗时。

MongoDB 的集合结构较灵活，MySQL 的 Schema 变更必须通过版本化迁移脚本逐步发布。把 MongoDB 数据导入 MySQL 时，除了字段转换，还要显式处理主键类型、引用关系、NULL、唯一性和历史快照。
