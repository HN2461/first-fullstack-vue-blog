# 02 关系型数据库核心概念

## 1. 从业务对象到表

以电商订单为例，业务中存在：

- 用户：姓名、邮箱、状态。
- 商品：名称、价格、库存。
- 订单：订单号、用户、金额、状态。
- 订单明细：某个订单购买了哪个商品、数量和成交价。

关系型数据库不会把整份订单对象无限嵌套保存，而是拆成具有明确职责的表：

```text
users 1 -------- N orders
orders 1 ------- N order_items
products 1 ----- N order_items
```

一对多关系通常在“多”的一方保存外键：`orders.user_id` 指向 `users.id`。

订单与商品本质上是多对多：一个订单有多个商品，一个商品可出现在多个订单。通过 `order_items` 中间表拆成两个一对多关系。

## 2. 主键（P0）

主键唯一标识一行数据：

```sql
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY
```

主键要求：

- 唯一。
- 非空。
- 尽量稳定，创建后不改变。
- 尽量短，避免所有二级索引膨胀。

企业常见主键方案：

| 方案 | 优点 | 注意点 |
| --- | --- | --- |
| 自增 BIGINT | 简单、紧凑、插入性能好 | 分布式合库可能冲突；ID 可被猜测 |
| UUID 字符串 | 全局生成方便 | 体积大、随机写入影响索引，不建议直接用 `CHAR(36)` 做聚簇主键 |
| 有序分布式 ID | 全局唯一、趋势递增 | 需要成熟生成方案，避免自行发明 |

入门项目优先使用 `BIGINT UNSIGNED AUTO_INCREMENT`。公开接口若不希望暴露递增 ID，可另设 `public_id`、订单号或 slug，不必强迫内部主键承担所有职责。

## 3. 外键（P0）

外键确保引用的数据真实存在：

```sql
CONSTRAINT fk_orders_user
  FOREIGN KEY (user_id) REFERENCES users(id)
```

它可以防止创建一个指向不存在用户的订单。

常见删除策略：

| 策略 | 行为 | 常见场景 |
| --- | --- | --- |
| `RESTRICT` | 被引用时拒绝删除 | 用户、商品等核心数据 |
| `CASCADE` | 父记录删除时自动删除子记录 | 明确从属且可一起删除的数据 |
| `SET NULL` | 父记录删除后外键置空 | 关系可选，且列允许 NULL |

不要为了“省事”到处使用 `CASCADE`，一次误删可能扩大影响。企业项目中是否使用数据库外键有团队差异：有些高并发系统在应用层维护关系。但即使项目不建物理外键，也必须理解逻辑外键、索引和数据一致性责任。

## 4. 唯一约束（P0）

唯一约束保护业务唯一性：

```sql
UNIQUE KEY uk_users_email (email)
```

“注册前先查询邮箱是否存在”不能代替唯一索引。两个并发请求可能同时查询到不存在，然后都插入。正确方案是数据库唯一约束兜底，后端捕获重复键异常并返回友好提示。

常见业务唯一键：

- 用户邮箱。
- 手机号。
- 订单号。
- 租户内的角色编码：`UNIQUE (tenant_id, role_code)`。

## 5. NULL 的真实含义（P0）

`NULL` 表示未知、缺失或不适用，不等于空字符串、0 或 false。

错误：

```sql
WHERE deleted_at = NULL
```

正确：

```sql
WHERE deleted_at IS NULL
WHERE deleted_at IS NOT NULL
```

三值逻辑是 SQL 初学高频坑：涉及 NULL 的比较结果可能是 UNKNOWN，而不是 TRUE/FALSE。因此：

- 必填字段尽量 `NOT NULL`。
- 明确默认值是否有业务含义。
- 不要用 0 或空字符串伪装“不存在”，除非业务规范明确如此。
- 唯一索引通常允许多行 NULL，因为 NULL 不被视为彼此相等；设计时要确认是否符合预期。

## 6. 约束是数据库的底线

常见约束：

```sql
email VARCHAR(255) NOT NULL,
status VARCHAR(20) NOT NULL DEFAULT 'active',
price DECIMAL(10, 2) NOT NULL,
stock INT UNSIGNED NOT NULL DEFAULT 0,
CONSTRAINT chk_products_price CHECK (price >= 0),
UNIQUE KEY uk_users_email (email)
```

接口校验负责给用户良好体验，数据库约束负责在任何写入入口下守住数据。后台脚本、迁移程序、其他服务都可能绕过某个接口。

## 7. 一对一、一对多、多对多

### 一对一

示例：`users` 与 `user_profiles`。在 `user_profiles.user_id` 上同时设置外键和唯一索引。

```sql
UNIQUE KEY uk_user_profiles_user_id (user_id)
```

只有当字段生命周期、访问频率、安全级别或体积明显不同，才值得拆成一对一表。不要机械拆表。

### 一对多

示例：一个用户有多个地址。`addresses.user_id` 指向 `users.id`，并为外键列建索引。

### 多对多

示例：文章和标签：

```text
articles <- article_tags -> tags
```

中间表通常使用联合主键或联合唯一键，防止重复关联：

```sql
PRIMARY KEY (article_id, tag_id)
```

## 8. 范式与反范式（P1）

范式的核心不是背定义，而是减少重复和更新异常。

坏例子：订单表直接保存 `product_ids = '1,5,8'`。这会导致：

- 无法可靠使用外键。
- 查询某商品所属订单困难。
- 无法保存每个商品的购买数量和成交价。
- 索引难以生效。

应拆出 `order_items`。

第三范式可粗略理解为：一个字段应描述当前表主键代表的实体，不要保存依赖于其他非主键字段的事实。

但企业项目允许有依据的冗余，例如订单明细保存 `product_name_snapshot` 和 `unit_price`。因为商品名称和现价将来会变，历史订单必须保留成交时快照。这不是随意重复，而是业务事实。

## 9. 数据库负责什么，应用负责什么

数据库适合负责：

- 类型、非空、唯一、引用关系等底线约束。
- 集合查询、关联、聚合、排序。
- 事务和并发控制。
- 数据持久化和索引。

应用适合负责：

- 复杂业务流程和状态机。
- 用户友好的校验错误。
- 调用外部服务。
- 权限判断和接口编排。
- 无法简单表达为数据库约束的跨领域规则。

不要把所有业务写成存储过程，也不要把数据库降级成没有约束的 JSON 文件仓库。

## 10. 从 MongoDB 建模迁移时的常见误区

1. 把数组用逗号拼接后塞进 `VARCHAR`。
2. 所有扩展信息都放 JSON，导致无法约束和索引。
3. 害怕 JOIN，在每张表重复大量用户信息。
4. 只在代码中判断唯一性，不建唯一索引。
5. 用业务自然键作为所有表主键，后续变更困难。
6. 认为建表后不能演进，实际应通过版本化迁移脚本演进 Schema。
