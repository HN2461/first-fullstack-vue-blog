# MySQL 阶段练习

先依次执行：

```text
sql/01_schema.sql
sql/02_seed.sql
```

除明确要求写数据的题目外，不修改示例数据。写操作练习使用事务，并在确认结果后 `ROLLBACK`。

## 第一阶段：基础 CRUD

### 1. 环境检查

写 SQL 返回 MySQL 版本、当前登录用户、当前数据库、会话时区和隔离级别。

### 2. 商品筛选

查询所有已上架、未删除、库存大于 0 且价格在 100 到 1000 元之间的商品，返回 ID、编码、名称、价格和库存，按价格降序、ID 降序排列。

### 3. 时间范围

查询 2026 年 7 月 1 日（含）至 7 月 15 日（不含）创建的订单。禁止对 `created_at` 使用 `DATE()`。

### 4. NULL 查询

查询从未登录过的用户，返回 ID、邮箱、用户名和创建时间。

### 5. 模糊匹配

查询名称以“MySQL”开头的商品。说明这种写法与 `LIKE '%MySQL%'` 对普通 B+Tree 索引的影响差异。

### 6. 批量插入

在事务中一次插入两个测试用户，列名必须明确。查询验证后回滚。

### 7. 安全更新

在事务中把 ID 为 3 的用户从 disabled 改为 active。更新前先查询，更新后检查 `ROW_COUNT()`，最后回滚。

### 8. 原子扣库存

尝试从商品 1 扣减 3 件库存，只有库存足够且商品上架时才能成功。检查影响行数并回滚。

### 9. 状态条件更新

将订单 3 从 pending 更新为 cancelled，并写入 `cancelled_at`。只有旧状态为 pending 时允许更新。回滚实验。

### 10. 聚合基础

统计商品总数、已上架商品数、平均价格、最高价和库存总量。平均价格保留两位小数。

## 第二阶段：多表与高级查询

### 11. 订单列表

查询全部订单及用户名，返回订单号、用户名、状态、金额、创建时间，按创建时间和 ID 倒序。

### 12. 用户订单统计

统计每个用户的有效订单数量和有效消费金额。有效状态是 paid、shipped、completed；必须保留从未下单用户，并让金额显示为 0。

### 13. 订单金额核对

按订单统计明细金额合计，并找出 `orders.total_amount` 与明细合计不一致的订单。

### 14. 从未下单用户

使用 `NOT EXISTS` 查询从未下单的用户。

### 15. 购买关系

查询至少购买过“无线鼠标”的用户，结果不能重复。优先使用符合“存在性”语义的写法。

### 16. 商品销量

按商品统计有效订单中的总销量与销售额，只返回销量至少为 2 的商品。

### 17. 每个用户最新订单

使用窗口函数查询每个用户的最新订单。排序必须在时间相同的情况下仍稳定。

### 18. 用户订单金额排名

对每个用户内部的有效订单按金额从高到低排名，金额相同使用相同名次且下一名不跳号。

### 19. 日销售累计

按日统计有效订单销售额，并同时返回前一日销售额和累计销售额。

### 20. 分类树

使用递归 CTE 返回分类 ID、父 ID、名称、深度和从根到当前节点的完整路径。

### 21. 每个分类销量第一

统计有效订单商品销量，返回每个商品分类销量最高的一个商品。并列时取商品 ID 较小者。

### 22. JSON 字段

查询扩展属性中颜色为“黑色”的商品，返回商品名称和颜色。

## 第三阶段：设计、索引与事务

### 23. 索引设计

接口高频执行：

```sql
SELECT id, order_no, total_amount, created_at
FROM orders
WHERE user_id = ?
  AND status = ?
  AND created_at >= ?
  AND created_at < ?
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

给出一个候选联合索引，解释列顺序。说明它是否能高效服务“只按 status 查询所有用户订单”的接口。

### 24. 索引失效改写

改写以下查询，让 `created_at` 更容易使用普通索引：

```sql
SELECT id, order_no
FROM orders
WHERE DATE(created_at) = '2026-07-20';
```

### 25. 深分页

把下面查询改成游标分页，并说明客户端需要保存哪些游标字段：

```sql
SELECT id, order_no, created_at
FROM orders
WHERE user_id = 2
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 100000;
```

### 26. 防止重复注册

解释为什么“先 SELECT 邮箱是否存在，再 INSERT”不能彻底防重复。给出数据库和 Node.js 层的完整处理原则。

### 27. 事务边界

设计下单事务，列出事务内和事务外分别执行哪些动作。必须处理库存、订单、明细和通知消息。

### 28. 死锁分析

事务 A 依次锁商品 1、2；事务 B 依次锁商品 2、1。说明为何可能死锁，提出至少四项改进。

### 29. 乐观锁

设计一张文档表的 `version` 字段更新 SQL。说明 0 行受影响时后端应如何处理。

### 30. 软删除唯一性

解释为什么 `UNIQUE(email, deleted_at)` 不能保证只存在一个 `deleted_at IS NULL` 的相同邮箱。给出至少两种可选业务方案。

## 第四阶段：Node.js 与生产工程

### 31. 参数化与动态排序

实现订单列表 SQL 构造思路：状态和用户 ID 是可选筛选值；排序字段只允许 `createdAt`、`totalAmount`；方向只允许 asc/desc。指出哪些内容可用 `?`，哪些必须使用白名单。

### 32. Node.js 事务模板

写出 `mysql2/promise` 的事务骨架，必须包含 getConnection、begin、commit、rollback 和 release，保证任何异常都释放连接。

### 33. 类型边界

说明 MySQL `BIGINT`、`DECIMAL` 和 `DATETIME` 映射到 Node.js 时的三个风险及处理方式。

### 34. 数据库错误映射

给出重复键、死锁、锁等待超时、外键引用不存在的处理策略。哪些错误可重试？重试需要什么前提？

### 35. Schema 上线

订单表需要增加最终必须为 NOT NULL 的 `channel_code`。设计一个兼容滚动发布和旧数据的上线步骤。

### 36. 备份验收

一条 `mysqldump` 命令成功退出，是否代表备份可靠？列出恢复演练至少需要验证的五项内容。

## 综合项目

独立实现一个“文章 + 分类 + 标签 + 评论”关系型模型：

- 文章属于一个分类，可有多个标签。
- 评论属于文章和用户，支持审核状态与软删除。
- 文章 slug 全局唯一，标签名称全局唯一。
- 查询公开文章列表时支持分类、标签、标题关键词、发布时间倒序分页。
- 查询文章详情时返回分类、标签和已通过评论数量。
- 设计发布文章和审核评论的状态条件更新。
- 给出核心索引、建表 SQL、三条关键查询和 Node.js 数据访问边界。
