# 11 RDB、AOF、备份与恢复

## 1. Redis 持久化不等于零丢失（P0）

Redis 主要在内存执行，持久化用于重启恢复。不同配置在性能、磁盘、恢复速度和数据丢失窗口之间权衡。

如果业务无法接受 Redis 数据丢失，就不能仅凭“开了 AOF”得出结论。还要考虑主机故障、复制延迟、文件损坏、错误操作、备份和恢复演练。

## 2. RDB 快照（P0）

RDB 在某个时间点生成紧凑快照。

优点：

- 文件紧凑。
- 适合备份和快速全量恢复。
- 主进程 Fork 后由子进程写快照。

风险/成本：

- 两次快照之间的数据可能丢失。
- Fork 和 Copy-on-Write 需要额外内存与 IO。
- 大实例生成快照可能产生延迟和磁盘压力。

常见命令：

```redis
LASTSAVE
BGSAVE
INFO persistence
```

生产不要随意执行同步 `SAVE`，它会阻塞服务。

## 3. AOF（P0）

AOF 追加记录写命令，重启时重放恢复。

常见 fsync 策略概念：

- always：每次写都 fsync，安全性高、性能成本高。
- everysec：通常每秒 fsync，常见折中，故障可能丢约秒级数据。
- no：交给操作系统决定，性能高但丢失窗口更不确定。

AOF 会重写压缩历史命令。重写同样涉及 Fork、COW、磁盘和缓冲区压力。

## 4. RDB + AOF

可以同时启用，兼顾备份与更小丢失窗口。现代 Redis 的 AOF 实现细节会随版本演进，必须以目标版本配置和官方文档为准。

同时启用不代表无需备份：实例上的 RDB/AOF 可能与机器一起损坏或被误删。

## 5. 无持久化模式

纯可重建缓存实例可以关闭持久化，减少 IO 和恢复复杂度。前提：

- Redis 全部数据可从 MySQL/其他来源重建。
- 冷启动回源不会压垮数据库。
- 有预热、限流和降级方案。

会话、限流和队列混在同一无持久化实例时，故障影响可能超出“缓存丢了”，因此应按数据职责拆实例。

## 6. 备份（P0）

备份建议：

- 复制 RDB/AOF 到独立存储和故障域。
- 文件名记录实例、时间、版本和校验和。
- 加密保存，限制读取权限。
- 配置保留周期和不可变备份。
- 监控备份结果，不只检查任务启动。
- 定期恢复到隔离环境验证。

云数据库快照仍需了解保留、跨区域、恢复粒度和账号权限。

## 7. 恢复流程（P0）

概念步骤：

1. 确认目标 Redis 版本和模块兼容。
2. 在隔离环境准备实例。
3. 校验备份文件完整性。
4. 按产品文档加载 RDB/AOF。
5. 检查启动日志和加载耗时。
6. 验证 Key 数、抽样值、TTL、数据结构和业务读取。
7. 评估恢复数据时间点与允许丢失范围。
8. 再制定流量切换，而不是直接覆盖生产。

Redis 自带检查工具如 `redis-check-rdb`、`redis-check-aof`，具体使用和修复选项需按版本文档执行；修复可能截断数据，必须先保留原文件。

## 8. 缓存恢复风暴

Redis 故障恢复后若全空：

- 大量请求同时查询 MySQL。
- 同一热 Key 并发重建。
- 应用重试进一步放大流量。

需要：请求合并、回源限速、逐步放量、热点预热、多级缓存和数据库保护。高可用恢复的不只是 Redis 进程，还包括整个数据访问链路。

## 9. RPO 与 RTO

- RPO：最多能接受丢失多长时间的数据。
- RTO：故障后多久恢复业务。

纯缓存 RPO 可以很宽，但 RTO 仍受回源能力限制。会话/Stream 实例的 RPO/RTO 要按业务重新定义。不能对所有 Redis 实例使用一个等级。
