# 07 MySQL 与 Redis 数据一致性

## 1. 为什么不能天然强一致（P0）

MySQL 事务只能原子提交 MySQL 操作，Redis 命令只能作用于 Redis。普通应用无法让下面两步天然成为一个本地 ACID 事务：

```text
UPDATE MySQL
DEL Redis Key
```

任何一步之间进程都可能崩溃、超时或网络断开。企业设计的目标通常是：根据业务确定可接受陈旧窗口，并通过重试、消息、版本和对账实现最终一致。

## 2. 为什么先更新 MySQL，再删除缓存（P0）

推荐默认顺序：

```text
1. 提交 MySQL 更新
2. 删除 Redis 缓存
```

如果先删缓存再更新数据库：

1. A 删除缓存。
2. B 缓存未命中，读到 MySQL 旧值。
3. B 把旧值写回缓存。
4. A 更新 MySQL。

缓存会长期保留旧值，直到 TTL。

先更新数据库再删缓存仍有失败窗口，但通常更容易通过删除重试和 TTL 收敛。

## 3. 为什么不默认双写缓存（P0）

更新 MySQL 后直接 SET 新缓存可能出现：

- 多个并发更新乱序，旧值后到覆盖新值。
- 不同接口只掌握部分字段，拼出不完整缓存。
- 数据库事务回滚但缓存已更新。
- 一个业务写入影响多个缓存，漏更新。

Cache-Aside 常选择删除，让下一次读取基于数据库重建完整缓存。

## 4. 删除缓存失败怎么办（P0）

至少有三层收敛：

1. 短超时内有限重试，避免无限阻塞请求。
2. 写入 Outbox/消息，异步重试删除。
3. 缓存自身有 TTL，最终自然过期。

若更新已经提交 MySQL，而 Redis 删除失败，接口不应谎报数据库写入失败后让用户盲目重试业务写。应把“业务写成功、缓存失效待重试”作为内部可观测状态处理。

## 5. 并发读写的残余竞态（P1）

即使先更新 MySQL 再删缓存，也可能：

1. 读请求缓存未命中，开始读数据库旧快照。
2. 写请求更新数据库并删除缓存。
3. 读请求把旧结果写回缓存。

这个窗口通常较短，但高一致场景可进一步采用：

- 延迟双删：提交后立即删一次，短延迟后再删一次。
- 写缓存时携带数据版本，只允许新版本覆盖旧版本。
- 逻辑过期和后台串行刷新。
- 订阅 Binlog/CDC 统一失效缓存。
- 对关键读取绕过缓存或读取主库。

延迟双删不是精确时间魔法，延迟要大于典型读查询 + 回写缓存时间，并且第二次删除必须可靠调度。

## 6. Outbox 失效缓存（P1）

在更新业务数据的同一 MySQL 事务中写事件：

```text
article.updated { articleId: 1001, version: 8 }
```

后台发布器发送事件，消费者删除：

```text
article:detail:v2:1001
article:list:category:5:...
```

消费者必须幂等；事件可能重复、延迟或乱序。删除操作天然比较容易幂等，但如果消费者更新缓存值则必须校验版本。

## 7. Binlog / CDC（P1）

通过 Debezium、Canal 或云服务 CDC 监听 MySQL 变更，再失效/更新缓存：

优点：

- 不依赖所有写入口记得删除缓存。
- 数据库变更是统一事实来源。
- 可驱动搜索索引、审计和派生视图。

成本：

- 部署和监控复杂。
- 事件存在延迟、重复、顺序和 Schema 演进问题。
- 从行变更推导哪些查询缓存受影响可能很难。

中小项目优先 Cache-Aside + TTL + 可靠删除重试，规模和多写入口明确后再引入 CDC。

## 8. 缓存 Key 粒度与失效范围

文章详情缓存容易精确删除；“分类 5 第 3 页、按热度排序”的列表缓存可能有大量组合。

方案：

- 只缓存高频固定查询。
- 使用命名空间版本：`article:list:v17:...`，更新时递增版本，旧 Key 等 TTL 回收。
- 缩短列表缓存 TTL。
- 缓存 ID 列表，再批量获取详情。
- 复杂搜索交给搜索引擎。

不要在生产用 KEYS 扫描并删除所有匹配列表缓存。

## 9. 缓存与数据库事务边界

错误：在 MySQL 事务提交前 SET 缓存。其他请求可能读到最终会回滚的数据。

正确方向：

1. 事务内只处理 MySQL 事实和 Outbox。
2. COMMIT 成功后删除缓存。
3. 删除失败进入可靠重试。

事务内也不应等待 Redis 网络调用，避免持锁时间变长。确需 Redis 做并发入口时，也要独立分析补偿和对账。

## 10. 一致性等级按业务分层

| 数据 | 可接受策略 |
| --- | --- |
| 文章浏览数 | 可异步合并，允许短暂误差 |
| 商品详情 | 短 TTL + 更新后删除，允许秒级陈旧 |
| 用户权限 | 更新后主动失效，短 TTL；关键操作可回源校验 |
| 库存展示 | Redis 可缓存，提交订单时必须原子校验权威库存 |
| 订单支付状态 | MySQL 为准，关键读绕过旧缓存或版本校验 |
| 账户余额 | 不以普通缓存值作为扣款依据 |

不能用同一缓存一致性方案处理所有数据。

## 11. 对账与修复

最终一致系统必须能发现和修复偏差：

- 缓存命中时采样对比数据库版本。
- 定时抽样或全量校验关键派生数据。
- 记录缓存失效消息积压和失败次数。
- 提供按业务 ID 重建/删除缓存的受控工具。
- 故障恢复后逐步预热，而不是全量洪峰。
