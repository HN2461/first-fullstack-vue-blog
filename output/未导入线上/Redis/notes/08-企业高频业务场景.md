# 08 会话、验证码、限流与排行榜

## 1. 登录会话（P0）

服务端 Session 常保存：

```text
Key: app:prod:auth:session:<不可预测随机ID>
Value: userId、角色摘要、创建时间、设备信息
TTL: 例如 30 分钟滑动过期，另设绝对最长生命周期
```

```redis
HSET redis-learning:session:demo userId 1001 role user createdAt 1785080000
EXPIRE redis-learning:session:demo 1800
```

安全要求：

- Session ID 使用密码学安全随机数，不能使用递增用户 ID。
- Cookie 设置 HttpOnly、Secure、SameSite，并根据架构防 CSRF。
- Redis Key 不直接包含完整 Session Token，可保存 Token 哈希降低泄漏影响。
- 登录、提权、修改密码后轮换/失效 Session。
- 滑动续期不能让会话无限存活，应有绝对到期时间。
- 权限变更需要主动清除/版本化相关 Session。

JWT 与 Redis Session 不是简单二选一。JWT 适合无状态验证，但主动吊销和权限即时变化复杂；Redis 可用于 Refresh Token、黑名单或会话版本。

## 2. 验证码（P0）

```text
Key: app:prod:verification:email:<目的>:<邮箱哈希>
Value: 验证码哈希、尝试次数、发送时间
TTL: 与验证码有效期一致
```

不要明文保存验证码或在日志打印。校验需同时限制：

- 验证码有效期。
- 单个验证码最大尝试次数。
- 单邮箱/手机号发送频率。
- 单 IP 发送频率。
- 同一账号每日总量。

“读取验证码 -> 比较 -> 删除/增加次数”应使用 Lua 保证原子，防止并发重复使用。

## 3. 固定窗口限流（P0）

例如每个 IP 每分钟最多 60 次：

```text
Key: app:rate-limit:api:<route>:<ip>:<minute>
INCR
首次创建时 EXPIRE 120
```

优点：简单、内存可控。缺点：窗口边界可能瞬间允许接近两倍流量，例如前一分钟最后一秒 60 次、下一分钟第一秒再 60 次。

计数与首次设 TTL 使用 Lua 原子执行。

## 4. 滑动窗口（P1）

用 ZSet 保存请求时间戳：

1. 删除窗口外 member。
2. 统计窗口内数量。
3. 未超限则加入当前请求。
4. 设置 TTL。

整个流程用 Lua 原子执行。member 要唯一，可用 `timestamp:randomId`。

缺点是每个请求占一个 member，高 QPS 下内存和 CPU 成本高。可采用滑动窗口计数、令牌桶，或使用成熟网关限流组件。

## 5. 令牌桶（P1）

保存剩余令牌和最后补充时间，Lua 中按经过时间补充，再尝试扣减。优点是允许可控突发并平滑限制平均速率。

实现要处理：

- Redis 服务端时间，避免应用节点时钟漂移。
- 浮点精度和最大桶容量。
- Key TTL，长期无流量的桶自动回收。
- Redis 故障时 Fail-open 还是 Fail-closed。

登录防暴力破解常倾向 Fail-closed 或本地兜底；普通内容接口可能 Fail-open 并启用网关保护。必须按风险决定。

## 6. 排行榜（P0）

```redis
ZINCRBY redis-learning:rank:daily:2026-07-26 1 article:1001
ZREVRANGE redis-learning:rank:daily:2026-07-26 0 9 WITHSCORES
ZREVRANK redis-learning:rank:daily:2026-07-26 article:1001
```

设计要明确：

- 排名周期：日、周、月还是总榜。
- 分数来源和是否允许回滚。
- 同分排序规则。
- 榜单最大成员数和历史保留时间。
- Redis 丢失后能否从事件/MySQL 重建。

ZSet 相同 score 默认按 member 字典序决定相对顺序。若产品要求同分按更早达成者优先，需要把业务规则编码进 score 或维护额外数据；double 精度边界必须验证。

## 7. 点赞与收藏（P0）

Set 可快速判断用户是否点赞：

```redis
SADD redis-learning:article:1001:liked-users user:1
SISMEMBER redis-learning:article:1001:liked-users user:1
SCARD redis-learning:article:1001:liked-users
```

但海量点赞用户会形成大 Set。核心关系通常仍写 MySQL 唯一表：`UNIQUE(article_id, user_id)`，Redis 缓存计数/状态。高并发计数可异步聚合，但要有对账。

## 8. 在线状态（P1）

可用带 TTL Key 或 ZSet 保存最后心跳：

```redis
ZADD redis-learning:online-users 1785080000000 user:1001
ZRANGEBYSCORE redis-learning:online-users 1785079700000 +inf
```

“在线”只是最近心跳近似状态，不是绝对事实。客户端断网、后台挂起、心跳延迟都会影响结果，产品文案应匹配这种语义。

## 9. 短链接/一次性 Token（P1）

```redis
SET redis-learning:one-time:download:<tokenHash> resource:1001 NX EX 300
GETDEL redis-learning:one-time:download:<tokenHash>
```

`GETDEL` 可一次取出并删除，适合一次性语义，但后续业务动作若失败，Token 已消耗。高价值流程需设计“领取、执行、确认/补偿”状态，而不是只靠 GETDEL。
