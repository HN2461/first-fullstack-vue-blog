# 12 复制、Sentinel、Cluster 与高可用

## 1. 主从复制（P0）

Redis 常用一个主节点接收写入，从节点异步复制：

```text
        -> Replica 1
Primary
        -> Replica 2
```

用途：读扩展、故障切换候选、备份分担。关键事实：复制通常异步，主节点写成功不代表从节点已经收到。

主节点在复制前宕机，故障切换后可能丢失最近写入。Redis 高可用不等于强一致。

## 2. 读副本一致性（P0）

写后立即读从节点可能读到旧值。策略：

- 关键写后读走主节点。
- 接受最终一致并在产品上明确。
- 使用版本检查或等待复制确认，但会增加延迟且仍需理解故障边界。

缓存读取本身往往允许陈旧，但会话吊销、权限更新等未必允许，需分类路由。

## 3. Sentinel（P1）

Sentinel 适合非分片主从高可用：

- 监控主从节点。
- 多 Sentinel 协商判断故障。
- 选举并提升一个从节点为新主。
- 通知客户端新主地址。

客户端必须支持 Sentinel 拓扑发现和重连。故障切换期间会有短暂不可用、连接重建和潜在数据丢失。

Sentinel 自身应部署多个独立节点/故障域，单个 Sentinel 不构成可靠仲裁。

## 4. Redis Cluster（P1）

Cluster 把 Key 分到 16384 个 Hash Slot，多主分片保存：

```text
Master A: slots 0 - 5460
Master B: slots 5461 - 10922
Master C: slots 10923 - 16383
```

每个主节点通常有副本。客户端根据 MOVED/ASK 重定向或拓扑缓存访问正确节点。

适合单机内存/吞吐不够、需要横向扩展的场景。代价：

- 多 Key 操作受 Slot 限制。
- 事务/Lua 的 Key 要同 Slot。
- 扩缩容、迁移和热点 Slot 更复杂。
- DB 选择、命令和模块可能受限。

没有容量证据时不要为了“企业级”直接上 Cluster。

## 5. Hash Tag

```text
app:order:{1001}:detail
app:order:{1001}:lock
```

相同花括号内容使 Key 进入同一 Slot，支持多 Key Lua/事务。滥用一个固定 Tag 会把所有 Key 压到同一分片，失去扩展能力。

## 6. 故障切换发生什么（P0）

应用可能看到：

- 连接断开。
- `READONLY`、`MOVED`、`ASK` 等错误。
- 请求超时或重试。
- 新主缺少最近写入。
- 旧连接指向已降级节点。
- 短时间缓存命中率下降。

客户端需支持拓扑感知、有限重试、指数退避和连接事件监控。不可重试的非幂等操作不能盲目重放。

## 7. WAIT 命令边界（P1）

`WAIT` 可等待写入被指定数量副本确认：

```redis
WAIT 1 100
```

它能降低数据未复制的概率，但不是跨故障的强一致保证，也不替代持久化或共识协议。返回确认数需要应用检查。

## 8. 脑裂与网络分区（P1）

网络分区时旧主可能仍被部分客户端写入，新主同时接收写入，恢复后旧主数据被丢弃。可通过配置限制主节点在副本数量/延迟不满足时拒绝写入，减少风险，但会牺牲可用性。

这是 CAP 取舍：不能同时承诺网络分区下绝对可用和绝不产生一致性风险。

## 9. 托管服务也需要理解拓扑

云服务负责部分运维，但应用仍要知道：

- 端点是否在切换时保持稳定。
- 是否需要 Cluster 客户端。
- 读写端点和副本延迟。
- 维护窗口和版本升级。
- 备份、跨区、TLS、ACL。
- 命令禁用和连接限制。

“用了云服务”不能替代故障演练。

## 10. 选型建议

| 规模/需求 | 常见起点 |
| --- | --- |
| 本地开发 | 单节点 |
| 中小生产、容量单机可承载 | 托管主从高可用 / Sentinel |
| 内存或吞吐超出单机 | Cluster/托管分片集群 |
| 关键强一致协调 | 不仅依赖 Redis，评估数据库/共识系统 |
