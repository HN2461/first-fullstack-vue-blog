# 09 分布式锁、幂等与原子操作

## 1. 什么时候需要分布式锁

多个应用实例可能同时执行同一个不可并发任务，例如：

- 同一订单只允许一个实例结算。
- 定时任务只允许一个节点执行。
- 同一缓存只允许一个请求重建。

但很多问题用数据库唯一约束、条件 UPDATE、消息分区或幂等键更可靠。不要看到并发就先加 Redis 锁。

## 2. 获取锁（P0）

```redis
SET redis-learning:lock:order:1001 7f9d-unique-owner NX PX 30000
```

必须在一条 SET 中同时包含：

- `NX`：不存在才成功。
- 唯一 value：标识锁持有者。
- `PX/EX`：防止持有者崩溃后永不释放。

错误写法：先 `SETNX` 再 `EXPIRE`，两条命令中间崩溃会留下永久锁。

## 3. 安全释放锁（P0）

不能直接 `DEL lockKey`：

1. A 获取锁，TTL 到期。
2. B 获取同一个锁。
3. A 执行完后 DEL，误删 B 的锁。

用 Lua 比较 value 后删除：

```redis
EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 redis-learning:lock:order:1001 7f9d-unique-owner
```

锁库应封装这一逻辑，业务代码不要散落手写 DEL。

## 4. 锁超时和续期（P0）

TTL 太短会在任务未完成时失锁；太长会让故障恢复慢。

可选方案：

- 根据临界区 P99 耗时设置有余量 TTL。
- 任务拆短，避免在锁内调用慢外部服务。
- Watchdog 定期续期，但必须只给自己的锁续期。
- 业务操作使用 fencing token，拒绝旧持有者写入。

续期也可能因 GC、网络暂停、进程卡顿而失败，不能让锁成为正确性的唯一防线。

## 5. Fencing Token（P1）

每次获取锁同时获得单调递增 token，例如 101、102。下游资源只接受大于已见 token 的写入：

```text
A 持有 token 101，暂停后锁过期
B 持有 token 102，写入成功
A 恢复并尝试写入 token 101，下游拒绝
```

这能防止旧锁持有者在暂停后继续破坏资源，但要求下游存储能够校验 token。仅靠 Redis 锁 value 不能阻止 A 对外部系统继续写。

## 6. 单实例锁与 Redlock（P1）

单 Redis 主从故障切换可能存在：主节点写锁尚未复制就宕机，新主没有该锁，另一个客户端再次获取。

Redlock 尝试在多个独立 Redis 节点多数派获取锁，但其适用性和故障模型长期有讨论。工程决策：

- 缓存重建等允许偶发重复执行的场景，单实例锁 + 幂等通常足够。
- 涉及资金、唯一领导权、不可逆外部动作时，不应只依赖简单 Redis 锁；使用数据库约束、共识系统、队列串行化或带 fencing 的成熟协调方案。

## 7. 幂等比锁更基础（P0）

锁减少并发执行，幂等保证重复执行结果可控。网络超时后客户端不知道服务端是否成功，重试无法避免。

订单创建：

```text
MySQL UNIQUE(user_id, idempotency_key)
```

支付回调：

```text
MySQL UNIQUE(provider, event_id)
UPDATE orders SET status = 'paid' WHERE id = ? AND status = 'pending'
```

Redis 可缓存幂等处理中/结果状态，但最终高价值唯一性通常由 MySQL 唯一约束兜底。

## 8. Redis 幂等记录（P1）

简单入口防重：

```redis
SET redis-learning:idempotency:user:1:req:abc processing NX EX 300
```

成功后可把 value 更新为结果摘要并延长 TTL。需要处理：

- 请求处理中进程崩溃。
- TTL 到期后重复请求。
- 相同幂等键却请求体不同。
- 结果过大不应长期缓存。
- Redis 丢失后仍不能突破数据库唯一性。

保存请求摘要哈希可以识别“同 Key 不同请求”。

## 9. 库存原子扣减

Lua 可让 Redis 库存不为负，但 Redis 中的库存与 MySQL 最终账必须同步、对账和补偿。普通电商流程优先在 MySQL 用条件 UPDATE；只有明确高并发架构才把 Redis 作为库存入口。

```redis
EVAL "local stock = tonumber(redis.call('GET', KEYS[1]) or '-1'); local amount = tonumber(ARGV[1]); if stock < amount then return 0 end; redis.call('DECRBY', KEYS[1], amount); return 1" 1 redis-learning:stock:product:1 2
```

还要处理消息投递失败、订单取消、超时释放、重复消费和对账，单个脚本不是完整库存系统。
