# 06 缓存模式与缓存三大问题

## 1. Cache-Aside（P0）

企业最常见模式，也叫旁路缓存。

读取：

1. 查询 Redis。
2. 命中则反序列化返回。
3. 未命中查询 MySQL。
4. 把结果写入 Redis，并设置 TTL。
5. 返回结果。

写入：

1. 更新 MySQL。
2. 删除 Redis Key。

通常选择删除缓存而不是直接更新缓存，因为更新逻辑可能复杂、部分接口不会使用缓存，而且删除后下一次读取可从数据库重建。但删除失败和并发窗口仍需第 7 章的一致性方案。

## 2. Read/Write Through 与 Write Behind（P1）

- Read Through：缓存组件负责未命中时加载数据。
- Write Through：写缓存组件时同步写后端存储。
- Write Behind：先写缓存，异步批量写数据库。

后两种需要成熟中间件或非常明确的数据丢失/顺序语义。普通 Node.js 业务不应自己轻率实现 Write Behind 保存订单。

## 3. 缓存穿透（P0）

请求大量查询数据库中不存在的 ID，Redis 永远未命中，压力穿透到 MySQL。

解决：

- 参数和权限校验，尽早拒绝非法请求。
- 缓存空值，并设置短 TTL。
- 布隆过滤器快速判断“肯定不存在”。
- 风控、限流和认证。

空值缓存示意：

```text
Key: app:cache:user:999999
Value: 特殊 NOT_FOUND 标记
TTL: 30~120 秒并加随机抖动
```

不要用普通 `null` 字符串而不区分“缓存缺失”和“业务不存在”。

布隆过滤器有假阳性但没有假阴性（在正确维护前提下）：它说“不存在”通常可直接拒绝；说“可能存在”仍要查库。删除和数据同步会增加复杂度。

## 4. 缓存击穿（P0）

一个极热 Key 过期，大量并发同时回源查询 MySQL。

解决：

- 请求合并/Singleflight，同一进程只允许一个回源。
- 分布式互斥重建，未获得锁的请求短暂等待或返回旧值。
- 逻辑过期：Key 不物理过期，值中保存逻辑过期时间，后台刷新。
- 热点提前刷新。
- MySQL 本身仍需合理索引和容量。

互斥重建锁必须有短 TTL 和唯一值，不能因重建失败永久阻塞。业务需要明确等待多久、能否返回旧数据。

## 5. 缓存雪崩（P0）

大量 Key 同时过期或 Redis 整体不可用，流量集中打到数据库。

解决：

- TTL 加随机抖动，分散失效时间。
- 多级缓存与热点逻辑过期。
- Redis 高可用、容量和故障演练。
- 应用超时、熔断、限流和降级。
- 回源请求合并。
- 数据库保护和只返回最小结果。

高可用只能降低 Redis 整体不可用概率，不能替代应用降级。

## 6. 缓存预热（P1）

新版本发布、扩容或 Redis 恢复后，缓存为空可能冲击数据库。预热方式：

- 根据历史热点主动加载有限 Key。
- 灰度放量，让缓存逐步建立。
- 从快照/持久化恢复，但需确认数据新鲜度。
- 对回源做并发限制。

不要把全库数据一次性加载到 Redis。缓存应只保留高价值工作集。

## 7. 序列化设计（P0）

缓存 Value 应有稳定契约：

```json
{
  "schemaVersion": 2,
  "cachedAt": "2026-07-26T15:00:00.000Z",
  "data": {
    "id": "1001",
    "title": "MySQL 索引"
  }
}
```

注意：

- 不缓存密码哈希、Token、敏感权限明细等不必要字段。
- BIGINT 用字符串，金额保留十进制字符串。
- DTO 变更时升级 Key 或 schemaVersion。
- 避免语言专属、不可跨版本的序列化格式，除非所有消费者明确兼容。
- 压缩节省网络/内存，但会增加 CPU 和实现复杂度。

## 8. 命中率不是唯一指标

```text
命中率 = hits / (hits + misses)
```

还要看：

- 被缓存接口的 P95/P99 延迟。
- 回源 QPS 和 MySQL 压力。
- Value 大小和网络带宽。
- 缓存写入/失效频率。
- 脏数据率和可接受陈旧时间。
- 热 Key 集中度。

一个 99% 命中率的大对象缓存也可能耗尽网络；一个 50% 命中率但保护昂贵查询的缓存仍可能有价值。

## 9. 什么时候不该加缓存

- 数据量小、MySQL 查询已有索引且足够快。
- 数据每次都不同，命中率很低。
- 强一致要求高且无法接受短暂旧数据。
- 更新远多于读取。
- 团队还没有 Redis 监控、容量和故障处理能力。
- 缓存只是掩盖错误 SQL 或 N+1。

缓存会引入第二份数据和更多失败模式，应该用指标证明收益。
