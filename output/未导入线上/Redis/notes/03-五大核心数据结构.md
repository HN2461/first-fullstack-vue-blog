# 03 五大核心数据结构

选择 Redis 类型时先问“我要做哪些访问”，不要先问“这个对象长什么样”。

## 1. String（P0）

String 可保存文本、数字、二进制或序列化对象，单值最大容量受 Redis 限制，但企业设计不能接近极限。

常见场景：

- JSON 缓存。
- 验证码和 Token。
- 计数器。
- 分布式锁值。
- Bitmap 底层载体。

```redis
SET redis-learning:article:1 "{\"id\":1,\"title\":\"MySQL\"}" EX 300
GET redis-learning:article:1
INCR redis-learning:article:1:view-count
INCRBYFLOAT redis-learning:metric:score 1.5
```

金额和库存的最终事实不要只保存在浮点计数中。Redis 数字命令适合计数、指标或缓存状态，财务结算仍以可靠持久化系统为准。

## 2. Hash（P0）

Hash 在一个 Key 下保存 field-value：

```redis
HSET redis-learning:user:1 name "Alice" status "active" city "上海"
HGET redis-learning:user:1 name
HMGET redis-learning:user:1 name status
HGETALL redis-learning:user:1
HINCRBY redis-learning:user:1 login_count 1
HDEL redis-learning:user:1 city
HLEN redis-learning:user:1
```

适合对象字段独立读写，例如会话属性、小型配置、聚合计数。

注意：

- TTL 主要作用于整个 Key，不是单个 field；新版本/兼容实现可能增加 field 级能力，使用前确认。
- Hash 过大仍是大 Key。
- `HGETALL` 会一次返回全部字段，大 Hash 应用 `HSCAN` 或重新建模。
- 缓存完整 DTO 时，String JSON 更容易整体失效和版本化；频繁局部更新时 Hash 更自然。

## 3. List（P0）

List 是有序序列，支持两端操作：

```redis
LPUSH redis-learning:recent:articles a1 a2 a3
RPUSH redis-learning:recent:articles a4
LRANGE redis-learning:recent:articles 0 9
LPOP redis-learning:recent:articles
RPOP redis-learning:recent:articles
LLEN redis-learning:recent:articles
LTRIM redis-learning:recent:articles 0 99
```

常见场景：

- 有固定上限的最近记录。
- 简单队列。
- 工作列表。

阻塞读取：

```redis
BLPOP redis-learning:queue:emails 5
```

List 简单队列缺少成熟确认、重试、消费组和死信能力。需要可靠消费时优先评估 Stream 或专业消息队列。

## 4. Set（P0）

Set 是无序、元素唯一的集合：

```redis
SADD redis-learning:article:1:liked-users 1001 1002 1003
SISMEMBER redis-learning:article:1:liked-users 1002
SCARD redis-learning:article:1:liked-users
SREM redis-learning:article:1:liked-users 1003
SMEMBERS redis-learning:article:1:liked-users
```

集合运算：

```redis
SINTER redis-learning:user:1:tags redis-learning:user:2:tags
SUNION redis-learning:user:1:tags redis-learning:user:2:tags
SDIFF redis-learning:user:1:tags redis-learning:user:2:tags
```

适合：标签集合、去重、权限集合、已处理 ID、小规模共同关系。

`SMEMBERS` 会返回全部元素，大集合使用 `SSCAN`。跨多个超大集合做交并差可能消耗大量 CPU 和内存，不能无边界使用。

## 5. Sorted Set（P0）

Sorted Set（ZSet）保存唯一 member 和 double 类型 score，按 score 排序：

```redis
ZADD redis-learning:rank:article-views 120 article:1 95 article:2
ZINCRBY redis-learning:rank:article-views 1 article:2
ZREVRANGE redis-learning:rank:article-views 0 9 WITHSCORES
ZRANK redis-learning:rank:article-views article:1
ZREVRANK redis-learning:rank:article-views article:1
ZSCORE redis-learning:rank:article-views article:1
ZREM redis-learning:rank:article-views article:2
```

适合：排行榜、带权重集合、时间线、延迟调度索引。

按分数范围：

```redis
ZRANGE redis-learning:scheduled-jobs -inf 1780000000000 BYSCORE LIMIT 0 100
```

调度任务要处理多个消费者竞争、任务确认、失败重试和重复执行，不能只查询后删除。Lua 或成熟任务库可帮助原子领取，业务仍需幂等。

## 6. 如何选择

| 访问需求 | 优先类型 |
| --- | --- |
| 按一个 Key 获取整个值 | String |
| 同一对象字段独立更新 | Hash |
| 两端进出、有序最近列表 | List |
| 去重、成员判断、集合关系 | Set |
| 排名、分数范围、时间调度 | Sorted Set |

同一个业务可以有多个派生 Key。例如文章详情用 String，点赞用户用 Set，浏览排行用 ZSet。它们都应能从 MySQL 或事件流重建，并有容量与失效方案。

## 7. 常见建模错误

- 把巨大 JSON 放 String，每次只改一个字段却全量读写。
- 用一个 Hash 保存系统全部用户。
- 最近记录 List 不做 `LTRIM`，无限增长。
- 用 Set 保存亿级用户且频繁 `SMEMBERS`。
- 排行榜永不分周期，ZSet 只增不减。
- 为了“一条命令拿完”把所有关系塞进一个大 Key。
