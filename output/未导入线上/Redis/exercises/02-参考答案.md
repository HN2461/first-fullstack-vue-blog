# Redis 阶段练习参考答案

答案重点是设计理由和失败边界。命令中的 TTL、限额和 Key 前缀应按真实业务调整。

## 1. Key 设计

```text
blog:prod:article:detail:v1:1001          String JSON，TTL 10 分钟 + 抖动
blog:prod:auth:session:<tokenHash>         Hash，TTL 30 分钟并有绝对到期
blog:prod:rate-limit:login:ip:<ipHash>     String，TTL 覆盖限流窗口
blog:prod:rank:article:daily:2026-07-26    ZSet，TTL 8 天
```

前缀表达应用和环境，中间表达业务和版本，末尾表达实体/周期。敏感 Token/IP 先做安全哈希。

## 2. 临时值

```redis
SET blog:prod:verification:email:<emailHash> <codeHash> NX EX 300
```

两条命令之间进程可能崩溃，留下永不过期验证码；单条 SET 原子完成条件写入和 TTL。

## 3. TTL 判断

正数是剩余秒数，`-1` 是 Key 存在但无 TTL，`-2` 是 Key 不存在。移除过期：

```redis
PERSIST key
```

## 4. JSON 还是 Hash

整对象读取且整体失效的公开资料适合 String JSON，便于版本化和一次获取。频繁只增加登录次数适合 Hash 的 `HINCRBY`。也可以把公开资料缓存和登录计数拆成两个 Key，各自有独立生命周期。

## 5. 最近浏览

```redis
LPUSH blog:prod:user:1001:recent-articles article:2001
LTRIM blog:prod:user:1001:recent-articles 0 99
LRANGE blog:prod:user:1001:recent-articles 0 19
```

若要求去重，还需 Lua 删除旧 member 后 LPUSH/LTRIM，或使用 ZSet 按最后访问时间建模。

## 6. 点赞关系

```redis
SADD blog:prod:article:1001:liked-users user:2001
SREM blog:prod:article:1001:liked-users user:2001
SISMEMBER blog:prod:article:1001:liked-users user:2001
SCARD blog:prod:article:1001:liked-users
```

海量点赞关系的最终记录仍应由 MySQL 唯一约束表或专门系统负责，避免一个无限大 Set。

## 7. 排行榜

```redis
ZINCRBY blog:prod:rank:article:daily:2026-07-26 3 article:1001
ZREVRANGE blog:prod:rank:article:daily:2026-07-26 0 9 WITHSCORES
ZREVRANK blog:prod:rank:article:daily:2026-07-26 article:1001
```

ZREVRANK 从 0 开始，展示名次通常加 1。

## 8. 扩展类型

月签到用 Bitmap，日活 UV 用 HyperLogLog，附近门店用 Geo。HyperLogLog 是近似去重计数，不适合精确财务/订单指标。

## 9. 安全遍历

KEYS 会一次遍历并返回全部匹配 Key，可能阻塞和制造大响应。

```redis
SCAN 0 MATCH app:prod:* COUNT 100
```

持续用返回游标扫描到 0。COUNT 只是提示；并发变更时结果可能重复，应用必须去重/幂等，也可能无法得到严格时间点快照。

## 10. 无边界增长

在线用户应使用带最后心跳分数的 ZSet，定期删除窗口外 member；或每用户短 TTL Key。访问日志不应无限放 List，使用专业日志系统/消息系统；Redis 只保留固定长度最近记录并 LTRIM、分日期设置 TTL。

## 11. Cache-Aside

读：查 Redis；命中返回；未命中查 MySQL；不存在写短 TTL 特殊空标记；存在写版本化 DTO 和带抖动 TTL。Redis 读取失败时记录指标并受控回源。

写：提交 MySQL 后删除缓存。DEL 失败不回滚已提交业务，写 Outbox/失效任务重试，并靠 TTL 最终收敛。

## 12. 缓存穿透

参数/权限校验、空值短缓存、布隆过滤器、限流/风控。空值 TTL 较短是因为数据稍后可能被创建，长期空值会继续返回错误的不存在结果；也避免攻击者制造大量长期空 Key。

## 13. 缓存击穿

方案一：Singleflight/分布式互斥，仅一个请求回源，其他等待或返回旧值；锁要短 TTL 且重建失败可恢复。方案二：物理不过期、Value 记录逻辑过期，过期后一个后台任务刷新，读取继续返回旧值；适合允许陈旧且热点稳定的数据。

## 14. 缓存雪崩

风险是 10 万 Key 同时失效回源。改进：TTL 加随机抖动；分批预热；多级缓存；请求合并；Redis 高可用；回源限流；数据库保护；熔断降级；热点逻辑过期。

## 15. 更新顺序

先删缓存会让并发读把 MySQL 旧值重新写回。直接 SET 新缓存可能被并发旧更新乱序覆盖、漏字段或在事务回滚时产生脏值。先提交 MySQL 再 DEL 使缓存下一次从权威库重建，失败也容易通过重复删除和 TTL 收敛。

## 16. 删除失败

MySQL 已提交，业务写应按成功处理，不能假装回滚。内部记录缓存失效失败，短时有限重试，Outbox/消息异步重试，缓存 TTL 作为最终兜底；高风险数据可暂时绕过缓存。

## 17. 旧值回写

增强方案包括：提交后立即删除并可靠延迟再删；缓存写入携带数据库 version，只允许新版本覆盖；逻辑过期并串行刷新；用 Binlog/CDC 统一失效；关键读取绕过缓存。仍应保持有限 TTL。

## 18. 缓存 DTO

```json
{
  "schemaVersion": 1,
  "cachedAt": "2026-07-26T15:00:00.000Z",
  "data": {
    "id": "9007199254740993",
    "title": "Redis",
    "price": "19.99"
  }
}
```

BIGINT 和 DECIMAL 用字符串，时间使用明确 UTC ISO 字符串。只缓存公开必要字段，不包含密码哈希、Token、后台备注和隐私信息。

## 19. 固定窗口限流

```redis
EVAL "local current = redis.call('INCR', KEYS[1]); if current == 1 then redis.call('EXPIRE', KEYS[1], 60); end; if current > 10 then return {0, current}; end; return {1, current};" 1 blog:prod:rate-limit:demo
```

生产把窗口和限额放 ARGV，脚本集中版本化；窗口 Key 应包含身份和时间桶或确保上一窗口到期。

## 20. 分布式锁

```redis
SET blog:prod:lock:order:1001 <randomOwner> NX PX 30000
```

```redis
EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]); else return 0; end;" 1 blog:prod:lock:order:1001 <randomOwner>
```

NX 防重复持有，TTL 防崩溃永久锁，唯一 owner + Lua 防止旧持有者删除新锁。

## 21. 锁过期

30 秒后 B 可获得锁，A 仍在执行，形成两个并发持有者。Watchdog 可续期但会因 GC、网络或进程暂停失效。业务必须幂等；不可逆下游写应携带 fencing token，让下游拒绝旧 token。

## 22. 幂等

MySQL 保存平台 event_id 唯一约束和订单状态条件更新，是最终正确性防线。Redis 可用 SET NX 快速挡重复、缓存处理中/完成结果，降低数据库压力。Redis 丢失或 TTL 到期仍由 MySQL 拒绝重复处理。

## 23. Pipeline

一次发送 100 条命令减少网络往返。它不保证命令原子，其他客户端命令可以穿插。批次过大会占客户端内存、Redis 输入/输出缓冲、网络带宽并造成延迟尖峰，应分批并检查每条结果。

## 24. Pub/Sub 与 Stream

在线公告允许离线错过，可用 Pub/Sub。发送邮件必须可追踪、重试和确认，至少使用 Stream + 消费组/PEL/死信/幂等；规模、保留和可靠性要求更高时使用 RabbitMQ/Kafka/云消息队列。

## 25. Stream 崩溃恢复

消息在消费组 PEL 中。其他消费者通过 XPENDING 发现，使用 XAUTOCLAIM 认领空闲过久消息，成功处理后 XACK。认领/重试造成至少一次处理，所以邮件发送需 event_id 幂等或业务发送记录。

## 26. RDB 与 AOF

RDB 是紧凑时间点快照，恢复快但快照间数据可能丢失；AOF 记录写命令，everysec 常见约秒级窗口，文件/重放和重写成本更高。二者都可能 Fork/COW。纯可重建缓存可关闭持久化，但必须验证空缓存回源、预热和降级不会压垮 MySQL。

## 27. Sentinel 与 Cluster

Sentinel 为非分片主从提供监控和自动切换；Cluster 还把 Key 分到多个主节点扩容。10 GB 且单机容量/吞吐足够，可从托管主从高可用或 Sentinel 起步，无需承担 Cluster 多 Key 和迁移复杂度。

## 28. 故障切换

异步复制未完成，新主可能没有最近写入。WAIT 可等待一定数量副本确认，降低未复制概率；但它不是共识提交，不保证网络分区、多个节点故障或持久化情况下绝不丢数据。

## 29. ioredis 连接

考虑 connectTimeout、commandTimeout、maxRetriesPerRequest、retryStrategy、ready check、TLS/ACL、error/ready/reconnecting/end 事件以及 SIGTERM 时 quit。普通 HTTP 缓存要短超时。Stream `BLOCK 5000` 本身预期长等待，应使用专用连接和匹配的命令超时，不能被普通 1 秒缓存超时提前打断。

## 30. Pipeline 结果

遍历每个 `[error, result]`，把命令索引映射回业务 ID；单条失败按命令是否幂等决定重试，并避免把部分成功当成全部失败。记录批次大小、失败数和耗时。

## 31. Redis 降级

- 文章缓存：短超时后限流回源 MySQL，可 Fail-open。
- Session：不能绕过认证；敏感操作 Fail-closed，提示重新登录/稍后重试。
- 排行榜：隐藏模块或返回持久快照，可降级为空。
- 登录限流：安全风险高，倾向 Fail-closed 或本地/网关严格兜底；普通内容限流可 Fail-open。

## 32. 大 Key 排查

先确认 Key 大小、HLEN、响应字节、调用方和频率，停止/限流 HGETALL，临时改 HSCAN/只取字段或旁路降级；使用 UNLINK 谨慎删除可重建对象；按日期/租户/ID 范围拆 Hash；给集合上限；代码审查禁止全量命令；建立 Key 大小与 P99 告警并压测。

## 33. 热 Key 排查

用应用指标、命令统计、云热 Key 工具、分片网络/CPU和采样确认具体 Key/命令。治理：进程本地短缓存；请求合并；逻辑过期后台刷新；静态内容 CDN；拆分分片计数；减少 Value；复制只读 Key 并接受一致性成本；重新设计 Hash Tag 防止集中 Slot。

## 34. 缓存命中率

可能是 Value 巨大导致网络/解析慢、热 Key 单节点过载、客户端连接池等待、跨区网络、SLOWLOG 中复杂命令、长 Lua、持久化 Fork、Redis CPU/带宽饱和、应用事件循环阻塞。命中率只描述是否找到 Key，不描述访问成本和端到端延迟。

## 35. MySQL + Redis 综合设计

可参考 [第 15 章：MySQL + Redis 企业知识库案例](/console/articles/redis-15-mysql-enterprise-case)：详情 String 10 分钟、浏览缓冲 Hash 3 天、日榜 ZSet 8 天、Session Hash 30 分钟、限流 String 2 分钟。文章/用户/最终计数以 MySQL 为准；更新后删除详情并用 Outbox 重试；浏览允许近似；Session 与安全限流故障时严格降级。

## 36. 上线评审

- Key 前缀、Value schema 和版本明确。
- 每类 Key 数量、单 Key 上限、总内存和增长已估算。
- 临时 Key 有 TTL 和抖动，永久 Key 有清理机制。
- 客户端有连接/命令超时、有限重试和优雅关闭。
- MySQL 权威来源、一致性窗口和失效重试明确。
- 淘汰、RDB/AOF、备份和恢复符合实例职责。
- 主从/Sentinel/Cluster 与客户端拓扑匹配。
- ACL、TLS、私网和 Secret 已配置。
- 延迟、内存、命中率、淘汰、复制、持久化和业务指标已告警。
- Redis 全空、超时、切换、热 Key 和回源洪峰已演练。
