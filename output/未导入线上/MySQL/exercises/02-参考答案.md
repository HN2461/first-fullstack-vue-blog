# 阶段练习参考答案

SQL 通常不止一种写法。以下答案优先展示清晰语义和企业常用边界。

## 1. 环境检查

```sql
SELECT
  VERSION() AS mysql_version,
  CURRENT_USER() AS current_user,
  DATABASE() AS current_database,
  @@session.time_zone AS session_time_zone,
  @@transaction_isolation AS isolation_level;
```

## 2. 商品筛选

```sql
SELECT id, product_code, name, price, stock
FROM products
WHERE status = 'on_sale'
  AND deleted_at IS NULL
  AND stock > 0
  AND price BETWEEN 100 AND 1000
ORDER BY price DESC, id DESC;
```

## 3. 时间范围

```sql
SELECT id, order_no, status, total_amount, created_at
FROM orders
WHERE created_at >= '2026-07-01 00:00:00.000'
  AND created_at <  '2026-07-15 00:00:00.000';
```

左闭右开不会漏掉 `23:59:59.999` 之后的更高精度时间。

## 4. NULL 查询

```sql
SELECT id, email, username, created_at
FROM users
WHERE last_login_at IS NULL;
```

## 5. 模糊匹配

```sql
SELECT id, name
FROM products
WHERE name LIKE 'MySQL%';
```

固定前缀有机会使用普通 B+Tree 索引；`%MySQL%` 无法从索引起点定位，通常需要扫描。当前 Schema 没有 name 索引，答案只是语义与访问能力说明。

## 6. 批量插入

```sql
START TRANSACTION;

INSERT INTO users (email, username, password_hash, status)
VALUES
  ('test1@example.com', 'Test 1', '$2b$test', 'active'),
  ('test2@example.com', 'Test 2', '$2b$test', 'active');

SELECT id, email FROM users WHERE email LIKE 'test%@example.com';
ROLLBACK;
```

## 7. 安全更新

```sql
START TRANSACTION;
SELECT id, email, status FROM users WHERE id = 3;
UPDATE users SET status = 'active' WHERE id = 3 AND status = 'disabled';
SELECT ROW_COUNT() AS affected_rows;
SELECT id, email, status FROM users WHERE id = 3;
ROLLBACK;
```

## 8. 原子扣库存

```sql
START TRANSACTION;
UPDATE products
SET stock = stock - 3
WHERE id = 1 AND status = 'on_sale' AND stock >= 3;
SELECT ROW_COUNT() AS affected_rows;
ROLLBACK;
```

## 9. 状态条件更新

```sql
START TRANSACTION;
UPDATE orders
SET status = 'cancelled', cancelled_at = CURRENT_TIMESTAMP(3)
WHERE id = 3 AND status = 'pending';
SELECT ROW_COUNT() AS affected_rows;
ROLLBACK;
```

## 10. 聚合基础

```sql
SELECT
  COUNT(*) AS product_count,
  SUM(CASE WHEN status = 'on_sale' THEN 1 ELSE 0 END) AS on_sale_count,
  ROUND(AVG(price), 2) AS avg_price,
  MAX(price) AS max_price,
  SUM(stock) AS total_stock
FROM products
WHERE deleted_at IS NULL;
```

## 11. 订单列表

```sql
SELECT
  o.order_no,
  u.username,
  o.status,
  o.total_amount,
  o.created_at
FROM orders AS o
INNER JOIN users AS u ON u.id = o.user_id
ORDER BY o.created_at DESC, o.id DESC;
```

## 12. 用户订单统计

```sql
SELECT
  u.id,
  u.username,
  COUNT(o.id) AS valid_order_count,
  COALESCE(SUM(o.total_amount), 0.00) AS valid_amount
FROM users AS u
LEFT JOIN orders AS o
  ON o.user_id = u.id
 AND o.status IN ('paid', 'shipped', 'completed')
GROUP BY u.id, u.username
ORDER BY valid_amount DESC, u.id;
```

有效状态条件必须放 ON，才能保留无有效订单用户。

## 13. 订单金额核对

```sql
SELECT
  o.id,
  o.order_no,
  o.total_amount,
  SUM(oi.line_amount) AS item_amount
FROM orders AS o
INNER JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY o.id, o.order_no, o.total_amount
HAVING o.total_amount <> SUM(oi.line_amount);
```

若订单允许没有明细，应改 LEFT JOIN 并用 COALESCE，根据业务决定是否也视为异常。

## 14. 从未下单用户

```sql
SELECT u.id, u.username
FROM users AS u
WHERE NOT EXISTS (
  SELECT 1 FROM orders AS o WHERE o.user_id = u.id
);
```

## 15. 购买关系

```sql
SELECT u.id, u.username
FROM users AS u
WHERE EXISTS (
  SELECT 1
  FROM orders AS o
  INNER JOIN order_items AS oi ON oi.order_id = o.id
  INNER JOIN products AS p ON p.id = oi.product_id
  WHERE o.user_id = u.id
    AND p.name = '无线鼠标'
    AND o.status IN ('paid', 'shipped', 'completed')
);
```

## 16. 商品销量

```sql
SELECT
  p.id,
  p.name,
  SUM(oi.quantity) AS sales_quantity,
  SUM(oi.line_amount) AS sales_amount
FROM products AS p
INNER JOIN order_items AS oi ON oi.product_id = p.id
INNER JOIN orders AS o ON o.id = oi.order_id
WHERE o.status IN ('paid', 'shipped', 'completed')
GROUP BY p.id, p.name
HAVING SUM(oi.quantity) >= 2
ORDER BY sales_amount DESC;
```

## 17. 每个用户最新订单

```sql
WITH ranked AS (
  SELECT
    o.*,
    ROW_NUMBER() OVER (
      PARTITION BY user_id
      ORDER BY created_at DESC, id DESC
    ) AS row_num
  FROM orders AS o
)
SELECT user_id, order_no, status, total_amount, created_at
FROM ranked
WHERE row_num = 1;
```

## 18. 用户订单金额排名

```sql
SELECT
  user_id,
  order_no,
  total_amount,
  DENSE_RANK() OVER (
    PARTITION BY user_id
    ORDER BY total_amount DESC
  ) AS amount_rank
FROM orders
WHERE status IN ('paid', 'shipped', 'completed');
```

题目要求并列且不跳号，所以使用 `DENSE_RANK()`。

## 19. 日销售累计

```sql
WITH daily AS (
  SELECT DATE(created_at) AS sale_date, SUM(total_amount) AS amount
  FROM orders
  WHERE status IN ('paid', 'shipped', 'completed')
  GROUP BY DATE(created_at)
)
SELECT
  sale_date,
  amount,
  LAG(amount) OVER (ORDER BY sale_date) AS previous_amount,
  SUM(amount) OVER (ORDER BY sale_date) AS cumulative_amount
FROM daily;
```

## 20. 分类树

```sql
WITH RECURSIVE tree AS (
  SELECT id, parent_id, name, 0 AS depth, CAST(name AS CHAR(500)) AS path
  FROM categories
  WHERE parent_id IS NULL

  UNION ALL

  SELECT
    c.id,
    c.parent_id,
    c.name,
    tree.depth + 1,
    CONCAT(tree.path, ' / ', c.name)
  FROM categories AS c
  INNER JOIN tree ON tree.id = c.parent_id
)
SELECT id, parent_id, name, depth, path
FROM tree
ORDER BY path;
```

## 21. 每个分类销量第一

```sql
WITH sales AS (
  SELECT
    p.category_id,
    p.id AS product_id,
    p.name,
    SUM(oi.quantity) AS quantity
  FROM products AS p
  INNER JOIN order_items AS oi ON oi.product_id = p.id
  INNER JOIN orders AS o ON o.id = oi.order_id
  WHERE o.status IN ('paid', 'shipped', 'completed')
  GROUP BY p.category_id, p.id, p.name
), ranked AS (
  SELECT
    sales.*,
    ROW_NUMBER() OVER (
      PARTITION BY category_id
      ORDER BY quantity DESC, product_id
    ) AS row_num
  FROM sales
)
SELECT category_id, product_id, name, quantity
FROM ranked
WHERE row_num = 1;
```

## 22. JSON 字段

```sql
SELECT name, extra_attributes->>'$.color' AS color
FROM products
WHERE extra_attributes->>'$.color' = '黑色';
```

若该条件高频，应考虑把颜色规范化为规格关系，或使用生成列索引，而不是长期扫描 JSON。

## 23. 索引设计

```sql
CREATE INDEX idx_orders_user_status_created_id
ON orders (user_id, status, created_at, id);
```

`user_id`、`status` 是等值条件，`created_at` 是范围和排序列，`id` 保证稳定排序。它不能高效承担只按 status 查所有用户的访问路径，因为跳过最左 `user_id`；该需求需评估 `(status, created_at, id)`。

示例 Schema 已包含同名访问能力的索引，无需重复执行创建。

## 24. 索引失效改写

```sql
SELECT id, order_no
FROM orders
WHERE created_at >= '2026-07-20 00:00:00.000'
  AND created_at <  '2026-07-21 00:00:00.000';
```

## 25. 深分页

```sql
SELECT id, order_no, created_at
FROM orders
WHERE user_id = 2
  AND (
    created_at < ?
    OR (created_at = ? AND id < ?)
  )
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

客户端保存上一页最后一行的 `created_at` 和 `id`。索引候选 `(user_id, created_at, id)`。

## 26. 防止重复注册

并发请求可能同时完成“查询不存在”，随后都插入。数据库必须有 `UNIQUE(email)`。Node.js 用参数化 INSERT，捕获 `ER_DUP_ENTRY` 并映射为 409；不能只检查错误消息文本。若先查用于友好提示，也只能作为体验优化。

## 27. 事务边界

事务外先做请求格式校验、鉴权、商品 ID 去重、生成订单号。事务内按 ID 顺序锁定/校验商品、读取可信价格、创建订单、条件扣库存、写明细、库存流水和 Outbox 事件，然后提交。提交后由异步发布器发消息。事务中不调用外部 HTTP。

## 28. 死锁分析

两事务分别持有对方所需锁并循环等待。改进：统一按商品 ID 升序锁定；缩短事务；补索引缩小锁范围；减少单事务商品数量；不在事务内访问网络；捕获死锁并对幂等操作有限退避重试；分析 InnoDB 死锁日志。

## 29. 乐观锁

```sql
UPDATE documents
SET content = ?, version = version + 1
WHERE id = ? AND version = ?;
```

0 行表示记录不存在或版本冲突。后端可再次查询区分，向用户返回 409，并提供刷新/合并机制；不能静默覆盖别人的更新。

## 30. 软删除唯一性

MySQL 唯一索引允许多行 NULL，所以多个相同 email、`deleted_at = NULL` 可能共存。可选：账号邮箱永久占用并使用全局唯一；软删除时改写归档 email；使用生成列只对有效记录产生非 NULL 唯一值；拆独立身份表。方案由账号恢复和复用规则决定。

## 31. 参数化与动态排序

状态、用户 ID、LIMIT/OFFSET 是值，使用 `?`。列名和方向不能由值占位符替代，使用映射：

```js
const columns = {
  createdAt: 'o.created_at',
  totalAmount: 'o.total_amount'
}

const sortColumn = columns[input.sortBy] || columns.createdAt
const sortDirection = input.sortOrder === 'asc' ? 'ASC' : 'DESC'
```

最终 SQL 只拼入白名单结果，筛选值继续进入参数数组。

## 32. Node.js 事务模板

```js
const connection = await pool.getConnection()

try {
  await connection.beginTransaction()
  await connection.execute('UPDATE ...', params)
  await connection.execute('INSERT ...', params)
  await connection.commit()
} catch (error) {
  await connection.rollback()
  throw error
} finally {
  connection.release()
}
```

所有事务 SQL 必须使用 `connection`，不能混用 `pool.execute()`。

## 33. 类型边界

- BIGINT 可能超过 JS 安全整数，按字符串返回和传输。
- DECIMAL 转 Number 会丢精度，保留字符串并用十进制库或最小单位 BigInt 计算。
- DATETIME 本身不携带时区，必须统一数据库、驱动和业务的时区策略；日期类业务值不要误转 UTC 时间戳。

## 34. 数据库错误映射

重复键通常返回 409，不重试；外键目标不存在返回业务校验错误，不重试。死锁和锁等待超时可对幂等、短事务做有限次数指数退避重试。重试前提是操作可安全重复、有最大次数、保留观测日志，且不是持续性结构问题。

## 35. Schema 上线

先新增允许 NULL 的 `channel_code`；发布能写新字段但兼容 NULL 的代码；分批回填旧数据并校验；让读取切到新字段；确认所有实例都已升级且无 NULL；再改为 NOT NULL 并添加需要的索引/约束；后续清理临时代码。大表每一步评估 DDL 方式、锁、复制延迟和回滚。

## 36. 备份验收

命令成功只说明导出进程未报告错误。应恢复到隔离实例并验证：对象数量和结构；核心表行数；抽样数据与字符编码；约束、索引、视图、触发器/事件；应用健康检查和核心流程；账号权限；恢复耗时是否满足 RTO；备份时间点和可丢数据是否满足 RPO。

## 综合项目提示

建议表：`users`、`categories`、`articles`、`tags`、`article_tags`、`comments`。`article_tags` 使用 `(article_id, tag_id)` 联合主键；评论保存 `article_id`、`user_id`、`status`、`deleted_at`；文章发布使用 `UPDATE ... WHERE status = 'draft'`。公开文章列表候选索引应结合 `status`、`category_id`、`published_at`，标签筛选还要从中间表按 `tag_id` 关联。关键词 `%keyword%` 数据量大时评估 FULLTEXT 或搜索服务。

综合项目没有唯一标准答案。重点检查实体职责、关系基数、唯一约束、状态流转、索引访问路径、参数化查询、事务边界和软删除一致性。
