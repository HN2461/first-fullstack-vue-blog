# 05 创建第一张表，学习笔记表

## 1. 本节目标：把人话需求变成 MySQL 能执行的表结构

第 04 章已经给每种数据准备好了合适的“抽屉”。这一章要把它们装进第一张真正的表：`learning_notes`。

完成后，你会在 `mysql_learning` 数据库中拥有一张空表。它还没有笔记数据，但已经清楚规定：一条笔记有哪些栏目、哪些栏目必须填、哪些由 MySQL 自动补上。

本章不会突然加入用户、分类、标签。先把一张表完全弄明白，比同时看懂十张表更重要。

## 2. 从需求到表：中间不能跳步

“创建表”不是先打开 SQL 编辑器再随手写字段。先把想保存的内容写成人话，才能判断字段是否合理。

```mermaid
flowchart LR
  A[人话需求<br/>我要保存学习笔记] --> B[列出每条笔记的信息]
  B --> C[为每项起字段名]
  C --> D[选择类型和规则]
  D --> E[写 CREATE TABLE]
  E --> F[用 DESCRIBE 检查结果]
```

### 2.1 先写清楚“每一行是什么”

本表中的一行代表：**一条学习笔记**。

这句话很重要，因为它决定了哪些信息应该放进来。下面这些内容属于一条笔记本身：

| 人话需求 | 是否属于一条笔记 | 原因 |
| --- | --- | --- |
| 笔记标题 | 是 | 每条笔记都有自己的标题 |
| 笔记正文 | 是 | 每条笔记都有自己的正文 |
| 笔记状态 | 是 | 每条笔记可以是草稿或已整理 |
| 浏览次数 | 是 | 统计的是这条笔记被看了几次 |
| 创建时间 | 是 | 每条笔记的创建时刻不同 |
| 作者的邮箱 | 暂时不放 | 目前还没建用户表，后面会通过关系处理 |
| 分类名称 | 暂时不放 | 第 08 章再用分类表处理 |

### 2.2 把人话翻译成字段名

课程使用英文小写加下划线的字段名。字段名是给程序和开发者看的，要短、明确、稳定：

| 人话 | 字段名 | 为什么不叫别的名字 |
| --- | --- | --- |
| 笔记编号 | `id` | 约定俗成，表示这行的内部标识 |
| 标题 | `title` | 一眼知道是标题 |
| 正文 | `content` | 比 `text`、`data` 更具体 |
| 状态 | `status` | 表示草稿、正常、归档等状态 |
| 浏览量 | `view_count` | 表示“次数”，而不是模糊的 `num` |
| 归档时间 | `archived_at` | `_at` 表示发生时刻 |
| 创建时间 | `created_at` | 表示记录创建时刻 |
| 更新时间 | `updated_at` | 表示最后一次被修改的时刻 |

## 3. 先确认自己在正确的数据库

在创建表之前，先运行：

```sql
SELECT DATABASE();
```

预期结果应为：

```text
mysql_learning
```

若返回 `NULL` 或其他名字，先执行：

```sql
USE mysql_learning;
```

然后再运行一次 `SELECT DATABASE();`。把这个检查养成习惯：同样叫 `learning_notes` 的表可以存在于多个数据库中，建错库以后会非常困惑。

## 4. 先预览最终表：它会长成什么样

建表语句执行成功后，脑中应该有下面这张“空白登记册”：

| 字段 | 例子 | 是否必须有 | 谁来填 |
| --- | --- | --- | --- |
| `id` | 1 | 是 | MySQL 自动生成 |
| `title` | 认识 MySQL | 是 | 写笔记的人或后端 |
| `content` | MySQL 用来管理数据 | 是 | 写笔记的人或后端 |
| `status` | draft | 是 | 不写时 MySQL 默认填 draft |
| `view_count` | 0 | 是 | 不写时 MySQL 默认填 0 |
| `archived_at` | NULL | 否 | 归档时才填写 |
| `created_at` | 2026-08-03 ... | 是 | MySQL 自动填当前时间 |
| `updated_at` | 2026-08-03 ... | 是 | MySQL 自动填，并在更新时刷新 |

这里的“必须有”不代表每次 `INSERT` 都要手写。`id`、默认值、自动时间字段仍然会有值，只是由 MySQL 负责填写。

## 5. 创建第一张表：先完整执行一次

确认当前数据库是 `mysql_learning` 后，执行：

```sql
CREATE TABLE learning_notes (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  title VARCHAR(120) NOT NULL,
  content TEXT NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'draft',
  view_count INT UNSIGNED NOT NULL DEFAULT 0,
  archived_at DATETIME(3) NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
    ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

第一次看见这样一大段 SQL 很正常会觉得密。不要试图一眼全背下来。它只是把第 02、04 章已经做过的决定，按 MySQL 规定的语法写成一份“表格设计说明”。下面会一块一块拆开。

## 6. 把 CREATE TABLE 拆成四层来读

### 6.1 外壳：告诉 MySQL 要创建什么

```sql
CREATE TABLE learning_notes (
```

| 片段 | 意思 |
| --- | --- |
| `CREATE TABLE` | 创建一张表，这是定义结构的命令 |
| `learning_notes` | 表名，表示学习笔记的集合 |
| `(` | 从这里开始列出表内部的字段和规则 |

字段之间用英文逗号 `,` 隔开。最后一条表内规则后面不要再加逗号，否则会报语法错误。最外层的 `)` 表示字段列表结束。

### 6.2 每一行的身份证：id

```sql
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
```

把它拆成一句人话：

> 有一个叫 `id` 的栏目，保存非负的大整数；每一行都必须有它；新增笔记时由 MySQL 自动给出下一个编号。

这一行末尾的逗号告诉 MySQL：“字段还没有列完，下一行还有。”

### 6.3 用户填写的内容：标题和正文

```sql
title VARCHAR(120) NOT NULL,
content TEXT NOT NULL,
```

| 字段 | 为什么选这个类型 | `NOT NULL` 为什么合理 |
| --- | --- | --- |
| `title` | 标题是长度明确的短文本，最多 120 个字符 | 没有标题很难识别一条笔记 |
| `content` | 正文可能很长，使用 `TEXT` | 空正文不是本课程认可的完整笔记 |

如果你的产品允许“只有标题、正文以后再写”的空笔记，可以把 `content` 设计为允许 `NULL` 或使用默认空字符串。但那是另一条明确的业务规则，不应因为“想先建成功”就随意放宽。

### 6.4 状态和次数：有明确的初始值

```sql
status VARCHAR(20) NOT NULL DEFAULT 'draft',
view_count INT UNSIGNED NOT NULL DEFAULT 0,
```

新建笔记时，调用方可能只提交标题和正文。这个时候 MySQL 会自动补上：

```text
status     = draft
view_count = 0
```

`DEFAULT` 不是“可有可无的偷懒设置”。它让无论来自命令行、后端接口还是导入脚本的新数据，都遵守同样的初始规则。

### 6.5 可以还没有的时间：archived_at

```sql
archived_at DATETIME(3) NULL,
```

一条刚写完的笔记并没有归档，因此“归档时间”此时不存在，使用 `NULL` 是合理表达。等以后归档时，才会用 `UPDATE` 把具体时间写入。

`DATETIME(3)` 可保存毫秒。你暂时只要知道 `(3)` 的目的是让创建、更新很接近的记录仍然有更细的时间精度。

### 6.6 自动记录创建和更新时间

```sql
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
  ON UPDATE CURRENT_TIMESTAMP(3),
```

它们的区别很容易混：

| 字段 | 新增笔记时 | 后来 UPDATE 这条笔记时 |
| --- | --- | --- |
| `created_at` | 自动填当前时间 | 保持第一次创建的时间 |
| `updated_at` | 自动填当前时间 | 自动刷新为这次修改的时间 |

`ON UPDATE CURRENT_TIMESTAMP(3)` 只属于 `updated_at` 这一列。它像“最后修改时间”的自动印章：同一行真正被更新时，MySQL 会把当前时间盖上去。

### 6.7 主键规则：给 id 加上最终身份

```sql
PRIMARY KEY (id)
```

这句不是新字段，而是一条表级规则：把 `id` 指定为主键。括号里的 `id` 表示“这条规则作用于哪一列”。

一张表只有一个主键。它的作用是确保每行都能被唯一定位，也会让 MySQL 为这个字段建立主键索引。索引的含义在第 10 章再深入，现在只需知道它有助于按 `id` 找到某一条笔记。

### 6.8 右括号后的表选项：整本登记册的规则

```sql
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

| 片段 | 为什么需要它 |
| --- | --- |
| `ENGINE=InnoDB` | 使用 InnoDB 存储引擎，它支持事务和外键，是 MySQL 默认且常用的业务表引擎 |
| `DEFAULT CHARSET=utf8mb4` | 这张表默认可保存完整 UTF-8 文本，包括中文和 emoji |
| `COLLATE=...` | 规定文本比较、排序时使用的规则 |

数据库已经在第 03 章设置为 `utf8mb4`，这里显式写出是为了让单独查看这张表时也能知道它的文字规则。

## 7. 创建后不要靠“没报错”判断：检查三次

### 7.1 确认表在当前数据库中

```sql
SHOW TABLES;
```

预期列表中出现 `learning_notes`。如果没有，先用 `SELECT DATABASE();` 确认当前是不是 `mysql_learning`。

### 7.2 用 DESCRIBE 看表头和字段规则

```sql
DESCRIBE learning_notes;
```

你会看到类似列：`Field`、`Type`、`Null`、`Key`、`Default`、`Extra`。它们可以这样看：

| DESCRIBE 列 | 你该看什么 |
| --- | --- |
| `Field` | 字段名是否是你设计的名字 |
| `Type` | 类型和长度是否正确 |
| `Null` | `YES`/`NO` 是否符合是否允许没有值 |
| `Key` | `id` 是否显示为主键 |
| `Default` | `status` 是否是 `draft`、`view_count` 是否是 `0` |
| `Extra` | `id` 是否显示 auto_increment，`updated_at` 是否有自动更新说明 |

### 7.3 用 SHOW CREATE TABLE 看 MySQL 最终保存的定义

```sql
SHOW CREATE TABLE learning_notes;
```

这会返回 MySQL 当前认为的完整建表语句。它像最终的“施工图”，比你记忆中的输入内容更可信。后面排查表结构时，优先看它。

## 8. 重复执行、改错和重新开始：不同情况不同处理

### 8.1 已经存在时为什么报错

第二次执行相同建表语句，MySQL 可能返回：

```text
Table 'learning_notes' already exists
```

这是一种保护：它不愿在没有确认的情况下把已有表覆盖掉。先运行 `SHOW CREATE TABLE learning_notes;` 看看表是否已经是你需要的结构。

### 8.2 `IF NOT EXISTS` 适合做什么

```sql
CREATE TABLE IF NOT EXISTS learning_notes (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  PRIMARY KEY (id)
);
```

它只表示“表不存在才创建，已经存在就不报错”。它**不会**检查已有表是否缺少字段，也不会把旧表自动升级为你刚写的新结构。因此它适合初始化脚本的幂等保护，不适合用来掩盖“我到底建成什么样了”。

### 8.3 练习库中确实要推倒重来时

在你确认当前是 `mysql_learning`，且这张表中的练习数据可以丢弃后，才可以执行：

```sql
DROP TABLE learning_notes;
```

这条命令会同时删除表结构和表里的数据，无法靠撤销找回。执行前先运行下面两句，确认目标：

```sql
SELECT DATABASE();
SHOW TABLES;
```

真实项目数据库中，不要把“建表失败后重来”的习惯带到生产环境。结构变更要先备份、评估已有数据，再使用迁移方案。

## 9. DELETE、TRUNCATE 和 DROP：三种删除不是同一件事

它们名字都带“删除”，危险程度和影响对象不同：

| 命令 | 删除什么 | 表结构还在吗 | 本课程什么时候用 |
| --- | --- | --- | --- |
| `DELETE FROM learning_notes WHERE ...` | 符合条件的若干行 | 在 | 第 06 章学习 |
| `TRUNCATE TABLE learning_notes` | 整张表的所有行 | 在 | 练习清空时，确认后使用 |
| `DROP TABLE learning_notes` | 表和其中所有数据 | 不在 | 只有确认要重新建表时 |

先看目标再写命令，特别是 `DROP`。从“表里删几条数据”到“表本身也没了”，只差一个关键词。
