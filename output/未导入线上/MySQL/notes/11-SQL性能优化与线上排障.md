# 11 SQL 性能优化与线上排障

## 1. 性能优化的第一原则

先测量，再优化。需要收集：

- 哪条 SQL 慢，完整结构是什么。
- 实际参数或参数分布是什么。
- P50、P95、P99 耗时和执行频率。
- 返回多少行、扫描多少行。
- 表大小、索引、数据分布和增长趋势。
- 当时 CPU、IO、内存、连接数、锁等待是否异常。

单次本地执行 10 ms 不代表线上一定快；线上可能有高并发、冷缓存、不同参数和百万级数据。

## 2. 慢查询日志（P1）

查看相关配置：

```sql
SHOW VARIABLES LIKE 'slow_query_log';
SHOW VARIABLES LIKE 'long_query_time';
SHOW VARIABLES LIKE 'log_queries_not_using_indexes';
```

慢查询日志的启用、路径和阈值应由 DBA 或运维按环境管理。不要在生产随意打开高开销选项，也不要仅根据“未使用索引”判断查询有问题，小表扫描可能很合理。

常用分析工具包括 `mysqldumpslow`、Percona Toolkit 的 `pt-query-digest`、云数据库慢 SQL 分析。入门重点是会根据频率 × 单次成本排序优化价值。

## 3. 常见慢查询原因（P0）

- 缺少合适索引或联合索引顺序不对。
- 返回大量不必要字段或行。
- 前导模糊匹配、函数、隐式转换导致无法有效使用索引。
- JOIN 条件错误造成行数膨胀。
- 深分页扫描并丢弃大量数据。
- N+1 查询造成大量数据库往返。
- 大事务、长事务和锁等待。
- 统计查询与在线交易争抢资源。
- 数据分布变化后统计信息不准确。
- Buffer Pool 太小、磁盘 IO 饱和、连接过多。

## 4. N+1 查询（P0）

错误流程：

1. 查询 100 个订单。
2. 对每个订单再查询一次用户。
3. 再对每个订单查询一次明细。

总请求数从 1 变成 201。解决方式：

- 使用 JOIN。
- 批量 `WHERE id IN (...)` 后在应用层映射。
- ORM 使用 eager loading / include，但要检查生成 SQL。
- GraphQL 场景用 DataLoader 批处理。

减少往返有时比微调单条 SQL 更有效。

## 5. 分页优化（P0）

传统页码：

```sql
LIMIT 20 OFFSET 200000
```

数据库仍需定位并跳过前面大量记录。

游标分页：

```sql
WHERE (created_at, id) < (?, ?)
ORDER BY created_at DESC, id DESC
LIMIT 20
```

MySQL 支持行值比较，但团队若担心可读性或边界，可展开成 OR 条件。必须让游标字段和排序字段完全对应，并设置联合索引。

若产品必须跳到任意页，可以继续 OFFSET，并限制最大页深、使用延迟关联、预计算或调整产品交互。不能声称 Keyset 能替代所有分页需求。

## 6. COUNT 优化要符合产品需求（P1）

InnoDB 的 `COUNT(*)` 通常不能像某些引擎一样直接读取精确行数元数据，带过滤条件更需实际计算。

优化方向：

- 为过滤条件设计覆盖索引。
- 列表不需要精确总页数时，用“是否还有下一页”。
- 对高成本统计使用汇总表或缓存。
- 允许近似值时使用监控/统计估算，但必须明确产品语义。

不要为了快而把精确值悄悄改成近似值。

## 7. 批量处理（P0）

避免一次更新几百万行并持有超大事务。按主键分批：

```sql
UPDATE orders
SET archived = 1
WHERE id > ?
  AND id <= ?
  AND created_at < ?;
```

每批记录影响行数、耗时和最后 ID，支持暂停和重跑。批量迁移应默认 dry-run、明确范围、具备幂等性，并监控复制延迟和数据库负载。

## 8. 连接池（P0）

连接池避免每次请求重新建立 TCP、认证和会话。池并非越大越好：

- 太小会让应用排队。
- 太大会让数据库同时处理过多查询，增加上下文切换和内存压力。
- 多个应用实例的池大小要相加评估。

监控：活跃连接、空闲连接、等待连接、获取连接耗时、数据库 `Threads_connected` 和 `Threads_running`。

数据库达到最大连接数时，盲目提高 `max_connections` 可能只是让崩溃来得更慢。应先找连接泄漏、慢查询和不合理并发。

## 9. Buffer Pool 基础（P1）

InnoDB Buffer Pool 缓存数据页和索引页，是性能关键。专用数据库服务器通常给它较大内存比例，但具体配置必须考虑实例上其他进程、数据集、云服务限制和故障恢复，不要照抄固定百分比。

需要理解的现象：

- 热数据命中内存比随机磁盘读取快得多。
- 重启或全量扫描可能冲掉缓存，导致暂时变慢。
- 索引膨胀会挤占缓存。
- 应结合命中率、磁盘 IO 和工作集判断，而非只看一个指标。

## 10. 锁等待与长事务排查（P0）

常用只读检查：

```sql
SHOW FULL PROCESSLIST;
SHOW ENGINE INNODB STATUS;
```

MySQL 8 还可查看 Performance Schema 中的事务、锁和语句统计。排查顺序：

1. 谁在等待？
2. 谁阻塞了它？
3. 阻塞事务从何时开始，执行了什么 SQL？
4. 是否处于 `Sleep` 但事务未提交？
5. 条件是否缺索引导致锁范围扩大？
6. 是否能让应用正常提交/回滚，而不是立即 KILL？

`KILL` 生产连接是有影响的写操作，可能触发大事务长时间回滚，应先评估和获得授权。

## 11. CPU 高、IO 高、连接高怎么区分

### CPU 高

可能是大量排序、聚合、表达式计算、扫描和并发查询。看 Top SQL、执行计划、扫描行数和线程运行数。

### IO 高

可能是缓存未命中、大范围扫描、检查点/刷盘、备份或大批量写。看磁盘延迟、Buffer Pool、读写吞吐和当时任务。

### 连接高

可能是连接泄漏、池设置过大、慢查询积压或突发流量。不要只看连接数，还要区分 running 与 sleep。

### 延迟高但资源不高

可能是锁等待、网络、DNS、连接池排队或下游调用。需要端到端 Trace 和请求 ID。

## 12. 统计信息与 ANALYZE TABLE（P1）

优化器依赖统计信息估算行数。数据分布剧烈变化时可能选错计划：

```sql
ANALYZE TABLE orders;
```

这是会影响数据库状态和资源的维护操作，生产执行前评估。MySQL 还支持直方图帮助没有合适索引列的分布估算，但属于针对性工具，不是到处创建。

## 13. 查询缓存和应用缓存

MySQL 8 已移除旧 Query Cache，不要学习依赖它的过时调优教程。

应用缓存适合：

- 读多写少。
- 可接受短暂不一致。
- 计算昂贵且重复度高。

缓存不是慢 SQL 的自动解药。必须设计 key、TTL、失效、击穿、穿透、雪崩和一致性策略。先修复明显错误 SQL 与索引，再判断缓存价值。

## 14. 优化验收

优化前后都记录：

- SQL 结果是否完全一致。
- EXPLAIN 估算/实际扫描行数。
- 冷/热缓存下耗时。
- 不同参数分布下 P95/P99。
- 并发吞吐和数据库资源。
- 新索引增加的存储和写入成本。
- 其他查询是否发生计划回归。

## 15. MongoDB 对照：从 explain 到慢 SQL（P1）

MongoDB 用户可以把排障思路迁移过来，但不要只寻找名称相同的字段：

- MongoDB `executionStats` 关注实际扫描文档数、返回数和执行时间；MySQL 要看 `EXPLAIN ANALYZE` 的实际行数、循环次数和耗时。
- MongoDB 的 N+1 常来自循环 `find` 或 `populate()`；MySQL 的 N+1 常来自循环 `SELECT`，可用 JOIN 或批量 `IN` 查询解决。
- MongoDB 深分页的 `skip` 和 MySQL 的 OFFSET 都会随着偏移量增大而浪费扫描，Keyset/游标分页是共同的改进方向。
- 两种数据库都不能把缓存当作错误查询和错误索引的替代品。
