# 03 数据类型、建库与建表

## 1. DDL 是什么

DDL（Data Definition Language）用于定义结构，常见命令：

- `CREATE`：创建数据库、表、索引。
- `ALTER`：修改表结构。
- `DROP`：删除数据库或表。
- `TRUNCATE`：清空整表数据并保留结构。

DDL 的影响通常比普通查询大。生产环境中必须通过迁移脚本、评审、备份和变更流程执行。

## 2. 创建和选择数据库（P0）

```sql
CREATE DATABASE IF NOT EXISTS mysql_learning
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

USE mysql_learning;

SELECT DATABASE();
SHOW CREATE DATABASE mysql_learning;
```

删除数据库会删除其中全部对象：

```sql
DROP DATABASE mysql_learning;
```

这只是语法展示，不要在有用数据上执行。生产删除前必须确认目标、备份和恢复方案。

## 3. 整数类型（P0）

常见类型：`TINYINT`、`SMALLINT`、`INT`、`BIGINT`。区别主要是可表示范围和占用空间。

```sql
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
stock INT UNSIGNED NOT NULL DEFAULT 0,
sort_order INT NOT NULL DEFAULT 0
```

注意：

- `INT(11)` 中的 11 不是存储长度，旧写法不要再依赖。
- `UNSIGNED` 适合确定不会为负的数量或 ID，但团队也可能为跨语言兼容统一使用有符号整数。
- 布尔值在 MySQL 常用 `TINYINT(1)` / `BOOLEAN`，实际底层仍是整数语义。
- 枚举状态不要使用神秘数字；如果用整数，要在代码和文档中维护稳定字典。

## 4. 精确金额与浮点数（P0）

```sql
price DECIMAL(10, 2) NOT NULL
```

`DECIMAL(10, 2)` 表示最多 10 位有效数字，其中 2 位小数。金额必须使用 `DECIMAL`，不要使用 `FLOAT` 或 `DOUBLE`，因为二进制浮点不能精确表示许多十进制小数。

```sql
SELECT 0.1 + 0.2;
```

金额还要明确：

- 币种是否固定。
- 精度是分、厘还是更多小数。
- 是否允许负数。
- 是在数据库中以 `DECIMAL` 保存，还是以最小货币单位整数保存。

两种方案都可行，关键是全系统统一，不能一部分按元、一部分按分。

## 5. 字符串类型（P0）

### VARCHAR

```sql
username VARCHAR(50) NOT NULL,
email VARCHAR(255) NOT NULL
```

适合长度可变的短文本。长度应基于业务边界，不要所有字段都无脑 `VARCHAR(255)`。

### CHAR

固定长度字符串，例如严格固定长度的内部编码。多数业务字段使用 `VARCHAR` 更自然。

### TEXT

适合长文本，例如文章正文、备注。`TEXT` 不能像短字符串一样随意建立完整普通索引；通常根据查询方式选择全文索引或搜索服务。

不要使用 `VARCHAR` 保存数字并期待正确的数值排序，也不要使用字符串保存日期。

## 6. 日期时间类型（P0）

```sql
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
  ON UPDATE CURRENT_TIMESTAMP(3)
```

常见类型：

| 类型 | 特点 | 常见用途 |
| --- | --- | --- |
| `DATE` | 只有日期 | 生日、账期日期 |
| `TIME` | 时间或时长语义 | 特定时间值，使用前确认业务语义 |
| `DATETIME` | 保存字面日期时间，范围大 | 业务创建时间、预约时间 |
| `TIMESTAMP` | 与会话时区转换相关，范围较小 | 明确需要其时区语义的时间戳 |

企业项目中常统一使用 `DATETIME(3)` 保存毫秒。真正关键的是团队明确时区策略：

- 推荐存 UTC，应用展示时转换。
- 不要把带 `Z` 的 UTC 字符串、服务器本地时间和数据库会话时区混用。
- 生日是日历日期，不应粗暴当成 UTC 时间戳。

## 7. JSON 类型（P1）

```sql
extra_attributes JSON NULL
```

适合：第三方回调原文、低频扩展配置、结构变化快且不参与核心关系的数据。

不适合：用户邮箱、订单状态、商品价格、外键数组等核心字段。

查询示例：

```sql
SELECT JSON_UNQUOTE(JSON_EXTRACT(extra_attributes, '$.color'))
FROM products;

SELECT extra_attributes->>'$.color'
FROM products;
```

JSON 内字段需要高频过滤时，可考虑生成列并建立索引，但这已经是有明确需求后的优化，不应成为默认设计。

## 8. ENUM 是否该用（P1）

```sql
status ENUM('pending', 'paid', 'cancelled') NOT NULL
```

`ENUM` 能限制值，但新增状态需要改表，跨数据库迁移也不够灵活。企业常见做法是 `VARCHAR` 或小整数 + CHECK + 应用常量：

```sql
status VARCHAR(20) NOT NULL,
CONSTRAINT chk_orders_status
  CHECK (status IN ('pending', 'paid', 'shipped', 'completed', 'cancelled'))
```

选择取决于团队规范。重点是状态集合必须被约束和集中维护，不能在各处散落魔法字符串。

## 9. 创建业务表（P0）

```sql
CREATE TABLE users (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  email VARCHAR(255) NOT NULL,
  username VARCHAR(50) NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'active',
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
    ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_users_email (email),
  KEY idx_users_status_created_at (status, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

查看结构：

```sql
SHOW TABLES;
DESCRIBE users;
SHOW CREATE TABLE users;
```

`SHOW CREATE TABLE` 比 `DESCRIBE` 信息更完整，能看到约束、引擎和字符集。

## 10. 修改表结构（P0）

```sql
ALTER TABLE users
  ADD COLUMN last_login_at DATETIME(3) NULL AFTER status;

ALTER TABLE users
  MODIFY COLUMN username VARCHAR(80) NOT NULL;

ALTER TABLE users
  ADD UNIQUE KEY uk_users_username (username);

ALTER TABLE users
  DROP INDEX uk_users_username;
```

修改大表可能锁表、复制大量数据或产生较高 IO。不要因为语法简单就直接在生产执行。应先确认：

- 表行数和大小。
- MySQL 版本及该 DDL 是否支持 INSTANT / INPLACE。
- 是否有长事务。
- 是否需要在线变更工具。
- 回滚方案是什么。

## 11. DROP、TRUNCATE、DELETE 区别（P0）

| 命令 | 删除内容 | 保留表结构 | 可带 WHERE | 典型用途 |
| --- | --- | --- | --- | --- |
| `DELETE` | 行数据 | 是 | 是 | 业务删除 |
| `TRUNCATE` | 全部行 | 是 | 否 | 清空测试表 |
| `DROP TABLE` | 数据和结构 | 否 | 否 | 移除整张表 |

`TRUNCATE` 不是“更快的 DELETE”这么简单，它的事务和自增计数行为不同。生产操作前必须明确影响。

## 12. 表注释与字段注释

```sql
CREATE TABLE categories (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '分类主键',
  name VARCHAR(100) NOT NULL COMMENT '分类名称',
  PRIMARY KEY (id)
) ENGINE=InnoDB COMMENT='商品分类表';
```

注释用于补充单位、枚举含义、边界或非直观业务语义，不要只把字段名翻译一遍。Schema 迁移脚本和代码常量仍应保持同步。

## 13. MongoDB 对照：动态文档如何迁移（P0）

MongoDB 文档可以让不同记录拥有不同字段；MySQL 表中的每行共享同一套列定义。迁移时不要把整个文档原样塞进 JSON，而应先分类：

| MongoDB 字段 | MySQL 建议 |
| --- | --- |
| 邮箱、状态、金额等核心字段 | 独立列，并增加类型、NOT NULL、唯一或 CHECK 约束 |
| 对象引用 ObjectId | 与目标主键类型一致的外键列，如 `user_id BIGINT UNSIGNED` |
| 低频、结构易变的附加属性 | JSON 列，但高频查询字段应规范化或使用生成列索引 |
| 文档数组 | 根据生命周期选择 JSON，或拆成一对多/多对多子表 |

MongoDB 中“字段不存在”和“字段值为 null”可以表达不同状态；MySQL 中列始终存在，是否有值由 `NULL` 表达。迁移脚本必须明确缺失字段应该变成 NULL、默认值，还是拒绝导入。
