# 08 企业表设计与数据建模

## 1. 从需求开始，不从字段开始

拿到需求后先回答：

1. 系统有哪些核心实体？
2. 每个实体的唯一身份是什么？
3. 实体之间是什么关系和基数？
4. 哪些规则必须由数据库约束？
5. 高频写入、查询、排序和统计路径是什么？
6. 数据是否需要审计、软删除、历史快照或租户隔离？
7. 数据量和增长速度大致是多少？

表设计不是把前端表单字段照抄进数据库。列表筛选、唯一性、并发和历史数据同样影响模型。

## 2. 命名规范（P0）

一套常见约定：

- 数据库、表、列：小写 `snake_case`。
- 表名使用复数或单数均可，但项目必须统一。本套使用复数。
- 主键统一 `id`。
- 外键统一 `<entity>_id`，如 `user_id`。
- 布尔语义统一 `is_enabled` 或状态字段。
- 时间统一 `created_at`、`updated_at`、`deleted_at`。
- 索引名：`pk_`、`uk_`、`idx_`、`fk_` 前缀表达用途。

避免保留字、拼音、含义模糊的 `type`、`data`、`value1`。无法避免保留字时虽可用反引号，但更好的做法是换清晰名称。

## 3. 推荐的通用字段（P0）

典型业务表：

```sql
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
  ON UPDATE CURRENT_TIMESTAMP(3),
deleted_at DATETIME(3) NULL
```

按需求增加：

- `created_by` / `updated_by`：操作人审计。
- `version`：乐观锁版本号。
- `tenant_id`：多租户隔离。
- `remark`：确有用途的备注，不是所有表必备。

不要机械给每张纯中间表加全部通用字段。字段应该服务于查询、审计或业务。

## 4. 订单模型案例（P0）

### orders

保存订单头：用户、订单号、状态、总金额、收货快照、关键时间。

### order_items

保存订单明细：商品 ID、商品名称快照、成交单价、数量、小计。

为什么既保存 `product_id` 又保存名称和价格快照？

- `product_id` 用于关联当前商品。
- 快照用于还原成交时事实。
- 商品改名、调价甚至下架后，历史订单仍必须准确。

总金额是否冗余保存？通常保存，因为它是订单结算后的业务事实，读取频繁，也可能包含优惠、税费和运费，不能简单用当前明细重新推导。但创建订单时必须在同一事务中确保明细和总额一致。

## 5. 状态设计与状态机（P0）

状态列不是任意字符串：

```text
pending -> paid -> shipped -> completed
   |         |
   +------> cancelled（具体规则由业务决定）
```

需要明确：

- 允许哪些值。
- 哪些旧状态能进入哪些新状态。
- 状态变化时同时更新哪些时间字段。
- 重复回调是否幂等。
- 谁有权限执行流转。

数据库 CHECK 保护值域；`UPDATE ... WHERE status = 'old'` 保护单次流转；完整业务状态机由服务层维护并测试。

## 6. 唯一键应表达业务边界（P0）

多租户中用户名可能只在租户内唯一：

```sql
UNIQUE KEY uk_users_tenant_username (tenant_id, username)
```

而不是全局 `UNIQUE(username)`。设计唯一键前问清“在什么范围内唯一”。

软删除与唯一键组合较复杂。MySQL 唯一索引允许多个 NULL，但 `UNIQUE(email, deleted_at)` 并不能直接保证所有未删除行只有一个相同 email，因为多行 `deleted_at = NULL` 可以共存。常见方案包括：

- 核心身份不允许复用，继续全局唯一。
- 删除时将唯一字段改写为带 ID 的归档值。
- 使用生成列将有效记录映射为可唯一约束的值。
- 由专门身份表维护唯一性。

不要未经验证就照搬组合唯一键。

## 7. 多租户设计（P1）

共享表模式常在所有业务表保存 `tenant_id`：

```sql
tenant_id BIGINT UNSIGNED NOT NULL
```

查询必须始终带租户条件：

```sql
WHERE tenant_id = ? AND id = ?
```

索引和唯一键通常也以 `tenant_id` 为前导列。仅依赖前端传租户 ID 是严重漏洞，租户身份应由认证上下文决定。

更严格隔离可使用独立数据库或实例，但运维成本更高。选型取决于规模、合规和客户隔离要求。

## 8. 密码、隐私和敏感数据（P0）

- 只保存密码哈希，例如 Argon2id 或 bcrypt 结果，不保存明文和可逆“加密密码”。
- 接口查询明确列名，避免返回 `password_hash`。
- 身份证、手机号等敏感数据需按法规和威胁模型决定加密、脱敏和审计。
- 加密字段会影响查询和唯一索引，方案必须提前设计。
- 日志、备份和只读副本同样属于敏感数据边界。

## 9. 金额与库存不只是字段类型

金额设计应明确：币种、精度、税费、折扣、四舍五入位置。库存设计应明确：可用库存、锁定库存、已售库存以及超时释放。

简单项目可原子扣减：

```sql
UPDATE products
SET stock = stock - ?
WHERE id = ? AND stock >= ?;
```

复杂交易系统通常有库存流水、预占和补偿机制。不要仅靠一个 `stock` 字段承担所有审计需求。

## 10. 审计日志与业务表（P1）

`updated_at` 只能告诉你最后修改时间，不能回答谁把什么从什么改成什么。高价值操作可写审计表：

```text
audit_logs
- actor_user_id
- action
- resource_type
- resource_id
- before_data
- after_data
- request_id
- created_at
```

审计日志应限制修改和删除权限，并注意敏感字段脱敏。是否保存 JSON 快照取决于审计要求。

## 11. 索引与表设计一起完成（P0）

根据查询反推索引：

```sql
SELECT id, order_no, total_amount, created_at
FROM orders
WHERE user_id = ?
  AND status = ?
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

候选联合索引：

```sql
KEY idx_orders_user_status_created_id
  (user_id, status, created_at, id)
```

不是每个 WHERE 字段各建一个单列索引。索引设计要结合等值条件、范围条件、排序、选择性和真实数据分布，后续用 EXPLAIN 验证。

## 12. 不要过早分库分表（P1）

先把单库设计、索引、归档和查询做好。分库分表会引入：

- 跨分片 JOIN 和聚合困难。
- 全局 ID、分页和排序复杂。
- 事务边界改变。
- 扩容、迁移和故障处理成本。

没有明确数据规模、增长和性能证据时，不要为了“企业级”而引入分片。云数据库纵向扩容、读副本和归档通常能支撑很长阶段。

## 13. Schema 评审清单

- [ ] 每张表是否只有一个清晰职责？
- [ ] 主键是否稳定、紧凑？
- [ ] 字段类型、长度、单位、时区是否明确？
- [ ] 必填字段是否 NOT NULL？默认值是否有真实语义？
- [ ] 业务唯一性是否由唯一索引兜底？
- [ ] 一对多、多对多关系是否正确表达？
- [ ] 删除策略和历史数据策略是否明确？
- [ ] 高频查询是否有候选联合索引？
- [ ] 外键两侧类型是否完全一致？
- [ ] 是否泄漏或弱保护敏感数据？
- [ ] 是否有可执行、可回滚、可追踪的迁移脚本？

## 14. MongoDB 对照：嵌入还是拆表（P0）

可以用三个问题判断 MongoDB 中的嵌入文档迁移到 MySQL 后是否应拆表：

1. 子对象是否需要独立查询、分页、权限或审计？
2. 它是否存在多对多关系，或需要被多个父对象引用？
3. 它是否有自己的生命周期，可能独立新增、修改、删除？

只要任一问题答案为“是”，就优先设计独立表和外键。订单商品在 MongoDB 中可以嵌入订单数组，但 MySQL 通常拆成 `orders` 与 `order_items`；订单明细还要保存成交快照，不能只依赖商品当前文档/当前行。
