# 04 INSERT、UPDATE、DELETE

## 1. 插入数据（P0）

明确列名是企业开发的基本习惯：

```sql
INSERT INTO users (email, username, password_hash, status)
VALUES ('alice@example.com', 'alice', '$2b$hash', 'active');
```

不推荐：

```sql
INSERT INTO users
VALUES (NULL, 'alice@example.com', 'alice', '$2b$hash', 'active', NOW(), NOW());
```

省略列名会强依赖表的列顺序，结构变更后容易报错或写错位置。

批量插入：

```sql
INSERT INTO users (email, username, password_hash, status)
VALUES
  ('bob@example.com', 'bob', '$2b$hash', 'active'),
  ('carol@example.com', 'carol', '$2b$hash', 'disabled');
```

批量写入通常比逐条请求数据库高效，但一次也不能无限大。应根据数据包大小、事务时长和错误处理要求分批。

## 2. 获取自增 ID（P0）

当前连接刚插入的 ID：

```sql
SELECT LAST_INSERT_ID();
```

在 Node.js 中通常直接读取驱动返回的 `insertId`。不要用 `SELECT MAX(id)` 获取自己的插入 ID，并发时会拿到别人的记录。

## 3. 唯一键冲突与幂等（P1）

```sql
INSERT INTO product_stocks (product_id, stock)
VALUES (1001, 20)
ON DUPLICATE KEY UPDATE
  stock = VALUES(stock),
  updated_at = CURRENT_TIMESTAMP(3);
```

这类 Upsert 只有在唯一键真实表达业务身份时才可靠。不要用它静默掩盖本应报错的数据冲突。

MySQL 8 新版本对 `VALUES(col)` 的这种引用形式有弃用演进，实际项目应根据具体版本采用官方推荐的行别名写法。入门阶段先理解 Upsert 语义，使用前查看目标版本文档。

幂等不是单靠 `ON DUPLICATE KEY UPDATE`。支付回调、消息消费通常需要业务幂等键和唯一约束，例如：

```sql
UNIQUE KEY uk_payment_events_provider_event
  (provider, provider_event_id)
```

## 4. 更新数据（P0）

```sql
UPDATE users
SET
  username = 'alice_new',
  updated_at = CURRENT_TIMESTAMP(3)
WHERE id = 1;
```

最重要的安全规则：写 UPDATE 前，先执行相同 WHERE 的 SELECT。

```sql
SELECT id, username, status
FROM users
WHERE id = 1;
```

确认命中范围后再改成 UPDATE。

对库存做原子扣减：

```sql
UPDATE products
SET stock = stock - 2
WHERE id = 10
  AND stock >= 2
  AND status = 'on_sale';
```

随后检查受影响行数：

- 1 行：扣减成功。
- 0 行：商品不存在、未上架或库存不足。

这比先 SELECT 库存再 UPDATE 更可靠，因为两个请求可能同时读到相同库存。

## 5. 条件更新与 CASE（P1）

```sql
UPDATE orders
SET status = CASE
  WHEN status = 'pending' THEN 'cancelled'
  ELSE status
END
WHERE id = 1001;
```

更常见且更清晰的状态流转写法是把旧状态直接放进 WHERE：

```sql
UPDATE orders
SET status = 'paid', paid_at = CURRENT_TIMESTAMP(3)
WHERE id = 1001
  AND status = 'pending';
```

检查受影响行数即可判断状态流转是否成功。这是一种轻量乐观并发控制。

## 6. 删除数据（P0）

物理删除：

```sql
DELETE FROM user_addresses
WHERE id = 20
  AND user_id = 3;
```

仍然要先执行相同条件的 SELECT。后端接口删除资源时，WHERE 中通常同时带资源 ID 和当前用户 ID，避免越权删除。

错误且危险：

```sql
DELETE FROM users;
```

没有 WHERE 会删除全表数据。

## 7. 软删除（P0）

核心业务数据常使用：

```sql
deleted_at DATETIME(3) NULL
```

删除时：

```sql
UPDATE articles
SET deleted_at = CURRENT_TIMESTAMP(3)
WHERE id = 100
  AND deleted_at IS NULL;
```

正常查询必须统一带：

```sql
WHERE deleted_at IS NULL
```

软删除的代价：

- 所有查询都要考虑过滤条件。
- 唯一键复用变复杂。
- 数据持续增长，需要归档或清理策略。
- 关联表如何处理必须明确。

不是所有表都要软删除。临时会话、可重建缓存、纯中间关系可以物理删除。是否软删除由审计、恢复和合规需求决定。

## 8. INSERT ... SELECT（P1）

从查询结果批量写入：

```sql
INSERT INTO archived_orders (
  id,
  order_no,
  user_id,
  total_amount,
  created_at
)
SELECT
  id,
  order_no,
  user_id,
  total_amount,
  created_at
FROM orders
WHERE status = 'completed'
  AND created_at < '2025-01-01';
```

数据归档不能只执行这一步，还需要校验行数、约束、关联数据、切换读取逻辑和回滚方案。

## 9. 受影响行数是业务结果的一部分

后端执行写操作后应检查：

- `affectedRows`：实际匹配或改变了多少行，具体语义受驱动和连接选项影响。
- `insertId`：自增主键。
- 重复键、外键、非空等数据库错误码。

不要执行完 SQL 就无条件返回“成功”。例如更新只允许当前用户自己的地址，影响 0 行意味着资源不存在或无权操作。

## 10. 禁止字符串拼接（P0）

错误：

```js
const sql = `SELECT * FROM users WHERE email = '${email}'`
```

攻击者可构造输入改变 SQL 语义。正确做法是参数化查询：

```js
const [rows] = await pool.execute(
  'SELECT id, email FROM users WHERE email = ?',
  [email]
)
```

参数只能替代值，通常不能直接替代表名、列名或排序方向。动态排序必须使用后端白名单映射，不能把用户输入直接拼入 SQL。

## 11. MongoDB 对照：CRUD 迁移（P0）

| MongoDB | MySQL | 迁移注意 |
| --- | --- | --- |
| `insertOne()` | `INSERT INTO` | 明确列名，数据库约束会校验类型和唯一性 |
| `insertMany()` | 多行 `VALUES` | 控制批次大小和事务时间 |
| `$set` | `UPDATE ... SET` | WHERE 是安全边界，不能省略 |
| `$inc: { stock: -2 }` | `SET stock = stock - 2` | 可追加 `stock >= 2` 做原子条件更新 |
| `upsert: true` | `INSERT ... ON DUPLICATE KEY UPDATE` | 必须先有表达业务身份的唯一键 |
| `deleteOne()` | `DELETE ... WHERE` | 需要恢复和审计时改用 `deleted_at` 软删除 |

MongoDB 的单文档更新天然以一个文档为原子单位；MySQL 把订单和明细拆成多表后，多步写入必须使用事务，不能认为多条 UPDATE/INSERT 会自动一起成功。
