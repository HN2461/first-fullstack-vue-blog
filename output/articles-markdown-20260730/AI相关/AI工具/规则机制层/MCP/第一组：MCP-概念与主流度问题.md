# 第一组：MCP 概念与主流度问题

复核日期：2026-05-24

## 第一题：你理解的 MCP 是什么

### 30 秒回答

MCP 是 Model Context Protocol，本质上是让大模型标准化连接外部能力的开放协议。  
它不只处理工具调用，也支持资源读取和提示模板复用。  
对工程落地的价值是让不同宿主和不同能力提供方之间更容易复用、治理和审计。

### 2 分钟展开

如果只用一句话概括，我会把 MCP 理解成 Agent 时代的“外部能力接入标准”。  
模型本身擅长理解和生成，但真实工作里还需要浏览器、文件、数据库、命令行、知识库这些外部能力。  
MCP 解决的是“这些能力如何以统一方式被发现、调用、读取和治理”。

它的价值主要有三点：

1. 标准化：不同工具不需要各写一套私有接入协议
2. 可复用：同一类 server 更容易被多个 host 复用
3. 可治理：权限、审批、隔离、审计更容易统一设计

所以我不会把 MCP 简单理解成“又一个插件市场”，而是把它看成协议层。

### 追问应对

- 如果面试官追问“是不是就是工具调用”，可以补一句：不完全是，官方语义里常见原语还有 `resources` 和 `prompts`
- 如果面试官追问“为什么叫 context”，可以回答：因为它让模型拿到执行任务所需的外部上下文，而不只是在对话窗口里猜

### 可反问面试官的问题

- 你们现在对 MCP 的使用，更偏浏览器自动化，还是偏内部知识和代码上下文接入？
- 你们更关注接入效率，还是权限治理与审计合规？

## 第二题：为什么最近 MCP 会这么火

### 30 秒回答

因为大家已经不满足于“只聊天”，而是希望模型真的参与查资料、读文档、改文件、跑命令和验证结果。  
一旦进入 Agent 场景，就需要一个更统一的外部能力接入标准，MCP 正好补上了这一层。

### 2 分钟展开

我觉得 MCP 走热，不是因为它名字新，而是因为需求成熟了。  
以前很多 AI 产品主要解决“问答”问题，现在大家开始追求“完成任务”的能力闭环。  
例如前端排障时，模型不只是解释报错，还要去读代码、看页面、查文档、执行命令、验证结果。

这时候如果每个平台都用自己私有的插件协议，会有几个问题：

1. 接入重复，生态割裂
2. 能力难复用，迁移成本高
3. 权限边界不好统一治理

MCP 提供了一个比较清晰的共识层，所以它会被越来越多宿主、工具和团队接受。

### 追问应对

- 如果被追问“它是不是唯一标准”，可以答：不一定是唯一，但它现在是非常有影响力的一套开放协议
- 如果被追问“火是不是因为营销”，可以答：更根本还是 Agent 实际落地需要统一能力层

### 可反问面试官的问题

- 你们内部现在更看重 AI 的问答能力，还是任务执行能力？
- 目前接入外部工具时，最大的阻力是技术接入还是安全审批？

## 第三题：MCP 和 function calling 有什么区别

### 30 秒回答

function calling 更像模型一次调用某个函数的能力接口，重点在“单次调用格式”。  
MCP 更像完整的外部能力接入协议，重点在“能力发现、连接管理、资源读取、工具调用和治理边界”。

### 2 分钟展开

两者不是互斥关系，但抽象层级不同。

我会这样区分：

1. function calling 关注的是：模型怎么按给定 schema 发起一次调用
2. MCP 关注的是：宿主怎么连接外部能力，能力怎么暴露，如何发现、如何读取、如何治理

也就是说，function calling 更像模型调用一个函数的机制，  
而 MCP 更像面向 Agent 场景的能力接入协议。

在工程落地里，MCP 会比单纯 function calling 多出很多上下文：

1. host / client / server 的职责划分
2. `tools`、`resources`、`prompts` 等不同能力原语
3. 权限、审批、审计、隔离这些治理要求

### 追问应对

- 如果面试官问“那 MCP 底层会不会还是函数调用”，可以答：很多时候执行动作最终也会体现成某种调用，但 MCP 讨论的是更上层的协议组织方式
- 如果面试官问“什么时候只用 function calling 就够了”，可以答：能力简单、调用单一、没有复杂治理需求时就够

### 可反问面试官的问题

- 你们现在的 AI 能力编排，更偏 API function schema，还是已经有独立的能力接入层？
- 如果未来有多个宿主要复用同一套能力，你们更倾向私有接口还是协议化管理？

## 第四题：MCP 和插件有什么区别

### 30 秒回答

插件通常是某个平台自己的扩展机制，平台差异很大。  
MCP 更强调跨宿主的开放协议和标准化能力暴露。  
所以插件偏“某个平台怎么扩展”，MCP 偏“不同平台怎么用一致方式接入能力”。

### 2 分钟展开

我会把插件和 MCP 理解成两个层面。

插件的核心问题是：

1. 某个产品怎么扩展自己
2. 生命周期、安装方式、权限模型通常都跟这个产品强绑定

而 MCP 更像公共协议层，它不要求能力一定以内嵌插件形式存在。  
能力提供方可以是本地服务、远程服务、知识库入口、浏览器能力、文件系统能力等。

所以从工程角度看：

1. 插件是产品机制
2. MCP 是能力接入协议

两者可以配合，但不应该混为一谈。

### 追问应对

- 如果被追问“那插件会不会被取代”，可以答：不会，很多产品仍然需要自己的插件体系，MCP 更像补上跨工具复用能力的那一层
- 如果被追问“哪个更重要”，可以答：要看目标，是做单产品扩展还是做跨宿主能力复用

### 可反问面试官的问题

- 你们当前更需要单产品扩展，还是多产品共享一套 AI 能力？
- 你们团队现在有没有遇到“同一能力重复接多次”的问题？
