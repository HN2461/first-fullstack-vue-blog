# 智能体编排与状态设计规范

## 1. 先把智能体画成状态机

复杂智能体不是一条长提示词，而是有明确状态的业务流程。设计时先列出：

```text
入口状态
意图识别状态
查询/检索状态
待补充状态
待选择状态
待确认状态
执行中状态
成功状态
失败与恢复状态
退出/清理状态
```

每个状态必须回答四个问题：

1. 进入条件是什么。
2. 需要读取哪些变量或真实数据。
3. 用户本轮允许做什么。
4. 完成、失败或取消后更新和清理哪些变量。

## 2. 三类输入不要混淆

### 2.1 用户输入

`基本信息 -> 用户输入` 是问答页面提供给用户填写或选择的输入项。官方 v2 文档确认可使用文本、密码、选择、日期、开关、模型、知识库和树形选择器等组件，并可通过变量被后续节点引用。

适合：

- 用户主动选择模型、知识库、业务范围或固定身份选项。
- 在进入对话前提供稳定上下文。

不适合：

- 保存对话过程中不断变化的业务状态。
- 承载服务密钥或长期敏感凭证。

### 2.2 接口传参

`基本信息 -> 接口传参` 用于公开访问 URL 或 API `form_data` 进入的参数。当前官方文档明确 `token` 是内部保留字段，不能添加为接口参数。

推荐分层：

```text
环境态：业务 API 根地址、租户标识等，由环境配置或安全中转层注入。
用户态：当前用户票据，由前端或后端按用户动态注入。
敏感服务密钥：优先放工具启动参数或服务端密钥管理，不放公开 URL。
```

### 2.3 会话变量

会话变量用于当前对话中的业务状态。每个变量都应有明确的生命周期：

| 生命周期动作 | 例子 |
| --- | --- |
| 创建 | 进入候选选择时设置 `isSelecting=true` |
| 更新 | 用户选中后写入 `selectedId` |
| 使用 | 判断器依据 `isSelecting` 和 `selectedId` 分流 |
| 清理 | 完成、取消、失败回退时赋值 `null` 或明确空值 |

不要只用“某个列表不为空”代表状态。字符串 `"[]"`、旧值残留和类型变化都可能误触发分支；优先使用显式布尔状态或稳定枚举。

## 3. 变量引用规则

```text
1. 永远优先通过 MaxKB 变量选择器复制真实变量。
2. 节点重命名后重新复制变量，不能沿用旧前缀。
3. 后置节点只能可靠引用已执行前置节点的输出。
4. 同一个值不要同时维护多套命名和多种类型。
5. JSON 字符串、JSON 对象、数组和布尔值要明确区分。
```

## 4. AI 节点的正确边界

AI 节点适合：

- 意图分类、口语化问题标准化。
- 从自然语言中抽取候选参数。
- 把结构化结果整理为用户可读说明。
- 在知识库证据范围内生成回答。

AI 节点不应独立决定：

- 当前用户是否有权限。
- 表单是否满足真实业务必填与类型规则。
- 金额、日期、库存、审批人等关键数据是否有效。
- 是否已经成功提交、支付、审批或保存。
- 是否可以访问另一用户、租户或知识库的数据。

官方 v2.10.4 高级智能体文档确认 AI 对话节点可输出：

```text
answer
reasoning_content
history_message
exception_message（启用异常捕获时）
```

生产环境通常关闭不必要的思考过程和技能执行过程展示，避免泄露提示词、工具细节、内部数据或模型推理内容。

## 5. 判断器与多入口汇合

判断器条件应优先基于：

```text
工具返回的稳定 code/ok 字段
参数提取的明确字段
显式会话状态
意图识别的 category
空值、长度、枚举和类型明确的变量
```

多前置连线的汇合节点：

| 执行条件 | 含义 | 适用场景 |
| --- | --- | --- |
| 任一 | 任意一个前置完成即可执行 | 互斥分支回到共同后续节点 |
| 所有 | 等全部前置完成才执行 | 真正并行任务全部完成后汇总 |

互斥分支错误设置为“所有”，会导致共同后续节点永远等待未执行分支。

## 6. 表单收集与自然语言补充

使用表单收集的条件：

- 字段类型固定，用户需要一次填写多项。
- 选择项、日期、开关、附件等结构化组件明显降低错误率。
- 当前客户端能够稳定展示和提交表单。

继续使用自然语言的条件：

- 用户表达高度口语化，需要模型理解。
- 字段较少，逐轮补充更自然。
- 选项来自实时业务接口，需先查询和权限过滤。

表单提交后仍要由工具或业务后端做最终校验。文件上传得到的是 MaxKB 文件对象或内部标识，不自动等于业务系统附件 ID。

## 7. 循环、子智能体与工作流工具

### 7.1 循环

循环适合数组批处理、固定次数处理和有明确 Break 条件的任务。不要使用无限循环模拟长期用户会话。

官方当前高级智能体文档同一页面对无限循环默认上限同时出现 `500` 和 `1000` 两种描述，属于官方口径冲突。实际项目中：

```text
1. 不把具体上限写入业务正确性假设。
2. 通过小规模调试确认当前环境行为。
3. 需要修改服务端上限时交由管理员处理。
4. 业务链路自身必须有 Break、超时和失败出口。
```

### 7.2 子智能体

子智能体适合复用已经发布、职责单一、输入输出稳定的能力。总智能体负责路由与上下文，不应重复复制子智能体的全部业务逻辑。

### 7.3 工作流工具

如果一组确定性节点需要被多个智能体复用，优先考虑工作流工具；如果只是一个智能体内部的一次性编排，先留在当前智能体中，避免过早拆分造成依赖追踪困难。

## 8. 异常分支是正式流程的一部分

每个外部调用至少考虑：

```text
鉴权失败：401/403
资源不存在：404
业务冲突或重复：409
字段校验失败：400/422
限流：429
服务器失败：5xx
网络超时或无响应
返回 JSON 结构变化
返回空列表但 HTTP 成功
```

异常分支要给用户可执行的下一步，同时保留追踪信息给开发者。不要把原始堆栈、密钥、完整请求头或内部 URL 直接显示给用户。

## 9. 发布前画布硬检查

- 没有孤立节点和开始节点不可达节点。
- 节点名唯一、清晰，重命名后变量已重新绑定。
- 所有模型、知识库、工具、MCP 和子智能体都可用且已授权。
- 解析节点和工具原始 JSON 的“返回内容”按需关闭。
- 每个写操作都有二次确认、权限校验和幂等策略。
- 每个状态都有成功、取消、失败和清理路径。
- 发布后重新走一次公开入口，因为编辑画布保存不等于已发布页面生效。
