# 从接手环境到发布的标准流程

## 1. 第一步不是画节点，而是建立环境基线

向公司平台管理员确认并记录：

| 项目 | 必须确认的内容 |
| --- | --- |
| MaxKB 版本 | 完整版本号，例如 `v2.10.4-lts` |
| 版本类型 | 社区版、专业版或企业版 X-Pack |
| 工作空间 | 开发者所在工作空间、资源可见范围 |
| 权限 | 智能体查看/编辑/发布、工具、知识库、模型、日志、API Key 权限 |
| 模型 | 可用模型类型、上下文长度、函数调用、多模态、费用和并发限制 |
| 网络 | MaxKB 到业务 API、MCP、外部模型、文件地址的网络可达性 |
| 接入 | 公开链接、嵌入第三方、API Key、中转后端中实际采用哪一种 |
| 管理员协作 | 谁负责升级、依赖安装、日志、域名、证书、CORS 和白名单 |

推荐建立项目环境卡：

```text
项目名称：
MaxKB 地址：
MaxKB 版本/版本类型：
工作空间：
开发智能体：
正式智能体：
公开链接域名：
业务 API 根地址：
用户身份来源：
允许使用的模型/知识库/工具：
平台管理员联系人：
最后核验日期：
```

环境卡不能记录真实密码、API Key、用户 token 或服务密钥，只记录密钥由谁维护、从哪里注入。

## 2. 把需求分成四种能力

收到需求后，先建立能力矩阵：

| 能力 | 适合承载位置 | 典型任务 |
| --- | --- | --- |
| 确定性业务 | 工具、工作流工具、业务后端 | 权限、查询、提交、计算、幂等、附件转存 |
| AI 理解 | AI 对话、意图识别、参数提取、问题优化 | 口语理解、分类、抽取、总结、改写 |
| 知识检索 | 知识库检索、标签检索、多路召回 | 制度、手册、产品知识、FAQ |
| 对话交互 | 表单收集、指定回复、快捷问题、业务前端 | 补充字段、选择、确认、只读展示 |

如果一个需求包含真实写操作，默认链路应是：

```text
AI 理解用户意图
  -> 工具读取真实业务状态
  -> 工具/判断器做硬校验
  -> 指定回复让用户确认
  -> 工具使用幂等键执行写操作
  -> 工具返回真实结果
  -> 指定回复展示结果
```

## 3. 先写数据契约，再配置工具

每个外部接口都建立契约表：

| 项目 | 说明 |
| --- | --- |
| 接口用途 | 查询还是写入，有无副作用 |
| 方法与路径 | `GET/POST/...` 和真实路径 |
| 鉴权 | 用户 token、服务密钥、签名、租户字段 |
| 输入 | 字段名、类型、是否必填、示例和来源 |
| 输出 | 成功结构、空结果、分页和错误结构 |
| 超时与重试 | 哪些请求可重试，写操作如何防重复 |
| 权限 | 当前用户能否查看或操作该资源 |
| 敏感数据 | 哪些字段禁止进入提示词、日志和前端回复 |

工具返回建议统一成稳定信封：

```json
{
  "ok": true,
  "code": "SUCCESS",
  "message": "查询成功",
  "data": {},
  "requestId": "可选追踪号"
}
```

失败时也返回同一结构，避免后续判断器同时猜 HTTP 状态、Python 异常文本和多种业务字段。

## 4. 建立依赖清单

MaxKB 官方说明：高级智能体 `.mk` 导出包含工作流节点配置和函数内容，但工作流中选择的知识库与模型信息不导出。因此只保存 `.mk` 不是完整备份。

每个智能体至少维护：

| 依赖 | 记录内容 |
| --- | --- |
| 模型 | 名称、类型、用途、关键参数、是否支持函数调用/多模态 |
| 知识库 | 名称、向量模型、检索方式、标签和文档版本 |
| 工具 | 名称、版本、输入输出、启动参数名称、外部依赖 |
| 子智能体 | 名称、发布状态、输入输出和责任边界 |
| MCP | 名称、协议、工具列表、网络和鉴权要求 |
| 接口传参 | 环境态、用户态、是否必填和注入位置 |
| 会话变量 | 名称、语义、创建/更新/清理时机 |
| 前端接入 | 公开链接、嵌入方式、API Base URL 和中转层 |

## 5. 从稳定基线开发

新功能优先复制一个已发布、已回归的智能体：

```text
正式稳定版：只修生产问题，不直接试验大改。
开发复制版：本轮需求的主要开发线。
风险试验版：验证新节点、新模型、新渲染或新内部能力。
```

每次只引入一组可解释变化，例如先改参数传递，再改分支，再改展示。不要同时更换模型、重写提示词、重构工具并修改接入方式，否则失败时无法定位原因。

## 6. 节点级开发顺序

推荐顺序：

```text
1. 开始/基本信息：输入、接口传参、会话变量。
2. 工具或知识库：先验证真实数据来源。
3. 变量拆分/参数提取：建立稳定结构。
4. 判断器：按显式字段分流。
5. AI：只承担理解和文案任务。
6. 指定回复/表单收集：完成用户交互。
7. 异常捕获和失败回复：覆盖超时、鉴权和空数据。
8. 最后再优化样式、快捷问题和多模态体验。
```

## 7. 发布交付物

一次可复用的交付不只是一条公开链接，应包含：

- 智能体 `.mk` 导出包。
- 工具 `.tool` 导出包或工具创建说明。
- 知识库导出包或文档清单、分段与检索配置说明。
- 模型、知识库、工具、MCP、子智能体依赖清单。
- 接口传参和会话变量清单，不含真实密钥。
- 测试用例、实际结果、已知限制和未覆盖场景。
- 当前发布历史名称、发布时间和回滚目标版本。
- 公司管理员需要完成的配置项。

## 8. 什么时候必须暂停开发并找管理员

出现下面情况时，不要继续靠改提示词规避：

```text
1. MaxKB 版本低于项目需要的节点或修复版本。
2. MaxKB 无法访问业务 API、MCP、模型或文件地址。
3. 需要安装 Python 第三方依赖或修改沙箱策略。
4. API Key、工作空间、资源授权或发布权限缺失。
5. 上传失败来自反向代理 413、证书、域名或 CORS。
6. 执行详情不足以定位，需要服务器日志或数据库核查。
7. 发现跨用户、跨知识库、跨工作空间访问异常。
8. 需要调整 `.env`、循环上限、日志保留期或系统级参数。
```
