# 04：意图识别节点
> 文档状态（2026-07-01）：根据空白高级智能体验证截图和官方资料，记录意图识别节点配置、输出和可优化链路。

## 1. 节点定位

`意图识别` 属于添加组件面板中的：

```text
基础组件 -> AI 能力 -> 意图识别
```

官方说明：

```text
根据输入进行意图的分类识别。
```

它本质上也是调用大模型，但目标比普通 `AI 对话` 更窄：

```text
只负责把输入归到预设意图分类，并给出判断理由。
```

适合的链路形态：

```text
当前界面优先：意图识别分类出口 -> 不同分支节点
旧版兜底：意图识别 -> 判断器 -> 不同分支节点
```

## 2. 初始配置项

| 配置项 | 初始状态 / 可见内容 | 说明 |
| --- | --- | --- |
| AI 模型 | 右侧有模型来源下拉，当前为 `自定义`；下方需要选择 AI 模型 | 必填，未选择模型时不能正常识别 |
| 输入 | 下拉占位为 `选择文本内容` | 必填，选择要识别意图的文本来源 |
| 历史聊天记录 | 数值为 `1` | 控制携带几轮历史上下文 |
| 意图分类 | 至少一组输入框，当前显示 `请输入`；右侧有 `+` 添加分类 | 必填，配置模型可选择的分类名称；每个分类右侧 `+` 可作为该分类出口接线 |
| 其他 | 默认可见一个 `其他` 分类输入框 | 默认兜底分类，不需要手动再添加一个 `其他`；用于未命中已配置分类的情况 |
| 输出参数 | `分类(category)`、`理由(reason)` | 分类出口直连时一般不用再判断 `category`；旧版兜底接判断器时使用 `category` |

## 3. 输入配置

`输入` 是意图识别节点最关键的入参。

常见输入来源：

| 场景 | 推荐输入 |
| --- | --- |
| 识别用户本轮话术 | `开始 -> 用户问题(question)` |
| 识别草稿确认动作 | `开始 -> 用户问题(question)` + 必要会话状态由前置判断保证 |
| 识别后端草稿后续意图 | `开始 -> 用户问题(question)` |
| 识别附件/组件补充意图 | `开始 -> 用户问题(question)` |
| 识别流程候选编号 | 不建议优先用意图识别，编号解析更适合工具 |

注意：

```text
1. 输入只能代表要分类的文本，不要把大段表单元数据塞进输入。
2. 如果需要结合状态判断，应先用判断器确认当前状态，再进入意图识别。
3. 对“1、2、确认、就这个”这类短句，必须明确当前状态，否则意图识别容易误分。
```

## 4. 意图分类配置

意图分类是这个节点的“候选标签”。

配置原则：

```text
1. 分类名称要短、稳定、互斥。
2. 面向中文业务用户时，优先使用清晰中文分类名，因为当前界面没有每个分类的单独说明字段。
3. 不要把分类名称写成长句。
4. `其他` 是默认兜底分类，不需要手动重复添加；如果界面允许改名，改名后文档和接线说明要同步。
5. 分类数量不要过多；超过 6 到 8 类时，应考虑拆成多个局部意图识别节点。
6. 如果后续脚本或接口必须依赖英文分类值，才使用英文固定短标识。
```

推荐命名示例：

| 业务场景 | 分类建议 |
| --- | --- |
| 草稿确认动作 | `正式提交`、`保存草稿`、`修改内容`、`确认无误`、`取消办理`，保留默认 `其他` |
| 后端草稿后续意图 | `继续提交`、`修改草稿`、`打开小程序`、`取消办理`，保留默认 `其他` |
| 快捷候选选择 | `选择候选`、`退出选择`，保留默认 `其他` |
| 附件补充意图 | `上传组件附件`、`继续普通填写`、`保存草稿`，保留默认 `其他` |
| 审核查看意图 | `查待办`、`查已办`、`查我发起或流程进度`、`选择编号`、`查看详情`、`审批动作`，保留默认 `其他` |

如果确实需要英文分类，可使用：

| 业务场景 | 英文分类建议 |
| --- | --- |
| 草稿确认动作 | `submit`、`draft`、`modify`、`confirm`、`cancel` |
| 审核查看意图 | `query_todo`、`query_done`、`query_my_started_status`、`select_task`、`view_detail`、`approve_action` |

## 5. 输出参数

当前截图中输出参数包括：

| 显示名称 | 变量名 | 用途 |
| --- | --- | --- |
| 分类 | `category` | 命中的意图分类名称 |
| 理由 | `reason` | 模型判断该分类的理由 |

常用引用写法示例：

```text
{{意图识别.category}}
{{意图识别.reason}}
```

注意：

```text
1. `意图识别` 是节点名称，重命名后变量前缀会变化。
2. 当前界面如果已经有每个分类右侧的 `+` 出口，优先直接从分类出口接后续节点。
3. 只有旧版界面不能按分类出线时，才接判断器并判断 `category`。
4. `reason` 适合调试或失败提示，不适合做稳定业务条件。
```

## 6. 分类出口接线

当前推荐接线：

```text
意图识别
  -> 分类A右侧 +：分类A分支起点
  -> 分类B右侧 +：分类B分支起点
  -> 其他右侧 +：兜底回复或兜底处理
```

接线建议：

```text
1. 每个分类右侧 `+` 都接到一个后续节点，不要空着。
2. `其他` 是默认兜底分类，也要接到兜底回复。
3. 如果某个业务分支还没做，可以先接指定回复占位，后续再替换。
4. 分类出口已经完成一次分流，不要再把所有出口统一接到同一个判断器。
```

## 7. 旧版兜底：与判断器配合

如果当前 MaxKB 版本没有分类出口，只输出 `category/reason`，再使用：

```text
意图识别
  -> 判断器
       -> category = 正式提交：正式提交分支
       -> category = 保存草稿：保存草稿分支
       -> category = 修改内容：修改字段分支
       -> ELSE：兜底提示
```

判断器配置建议：

```text
1. 优先用“等于”判断固定分类名。
2. 不要用 `reason 包含 xxx` 做业务分流。
3. 每个意图识别节点都要有默认 `其他` 出口或判断器 ELSE 兜底分支。
4. 如果 MaxKB 对布尔值判断不稳定，本节点正好可以输出字符串分类，减少布尔判断风险。
```

## 8. 对当前工作流的优化价值

适合优先评估替换或前置的地方：

| 当前场景 | 可能优化方式 | 原因 |
| --- | --- | --- |
| `识别草稿确认意图` | 改为或前置 `意图识别` | 用户只是在表达提交、保存、修改、确认、取消时，不一定需要完整 AI 对话 JSON |
| `识别后端草稿后续意图` | 改为 `意图识别分类出口 -> 对应动作分支` | 后端草稿状态下多为动作路由 |
| `是否用户要上传附件/补充材料` | 用局部意图识别识别 `upload_material` | 可减少后续工具误触发 |
| `首句是查目录还是办流程` | 用意图识别做初筛 | 先分 `query_catalog/start_workflow/chat/other`，再进入快捷匹配或首句预受理 |
| `confirm` 分支动作二次确认 | 用意图识别区分 `submit/draft/modify/other` | 避免“可以、嗯、没错”被误当成正式提交 |

不建议替换的地方：

| 场景 | 原因 |
| --- | --- |
| 字段值解析 | 需要抽取字段名、字段值、选项、时间等结构化数据，普通意图分类不够 |
| 审批人编号解析 | 编号、姓名、模糊匹配更适合工具稳定处理 |
| 提交前字段完整性检测 | 必须硬校验，不能交给意图识别 |
| 附件协议生成 | 必须工具化 |
| JSONPath 拆分 | 仍用变量拆分或工具 |

## 9. 设计建议

如果用意图识别优化现有链路，建议先做局部试验，不直接大改正式链路。

推荐第一轮试验：

```text
在空白高级智能体里创建：
开始 -> 意图识别 -> 判断器 -> 指定回复
```

意图分类先配置：

```text
正式提交
保存草稿
修改内容
确认无误
取消办理
其他保留默认即可，不要手动重复添加
```

测试输入：

```text
正式提交
保存草稿
先存一下
人员数量改成 3
可以
嗯
不要了
随便聊一句
```

验收标准：

```text
1. category 能稳定返回预设分类。
2. “可以、嗯、没错”只进入 confirm，不直接进入 submit。
3. “保存草稿”和“正式提交”能稳定区分。
4. 修改类表达能进入 modify。
5. 无关闲聊进入 other。
```

## 10. 易错点

```text
1. 忘记选择 AI 模型。
2. 输入没有绑定 `开始 -> 用户问题` 或其他真实文本来源。
3. 分类名称写得太长，导致判断器难维护。
4. 分类之间语义重叠，例如 `confirm` 和 `submit` 没区分清楚。
5. 手动重复添加 `其他`，实际界面已经默认有 `其他` 兜底。
6. 直接用 `reason` 做判断器条件。
7. 把字段抽取任务交给意图识别，导致只能知道“修改”，却不知道改哪个字段。
8. 没有先判断当前会话状态，导致用户回复 `1` 时不知道是在选流程、选审批人还是填字段。
9. 当前界面已有分类出口，却仍额外接一个判断器，导致画布节点变多、维护复杂。
10. 分类出口空着，没有接后续节点。
```

## 11. 资料依据

MaxKB 官方高级智能体文档说明，意图识别节点用于根据输入进行意图分类识别；节点设置包括 AI 模型、输入、历史聊天记录、意图分类；输出参数为分类 `category` 和理由 `reason`。

MaxKB v2.2.0 发布资料也说明，意图识别节点用于让大模型识别用户输入意图，并将不同意图流转到工作流不同分支。

当前截图补充确认：

```text
1. 意图分类区域默认存在“其他”分类输入框。
2. 每个意图分类右侧都有 `+`，可直接从该分类出口连接后续节点。
3. 因此当前版本优先使用“分类出口直连”方式。
```

## 12. 待继续核对

```text
1. 选择 AI 模型后模型参数面板有哪些字段。
2. 输入下拉可选来源有哪些。
3. 意图分类最多能配置多少个。
4. `其他` 是否可改名，是否可删除；当前使用时先保留默认。
5. 历史聊天记录设置是否与 AI 对话节点一致。
6. 异常捕获是否存在或是否在更下方配置中展示。
```
