# 第四篇：Claude Code 设置、CLAUDE.md 与个性化配置（程序员深度版）

> 这一篇的重点不是“把所有设置项都背下来”，而是让主人知道怎样配出一个长期顺手、不会越用越乱的 Claude Code。  
> 对程序员来说，好的配置不是功能越多越好，而是作用域清楚、边界明确、规则稳定、排障简单。

[[toc]]

---

## 先说最重要的原则

Claude Code 的配置，最怕的不是少，而是乱。  
真正会把体验拖垮的，往往不是缺某个开关，而是下面这几种情况：

- 共享规则和个人偏好混在一起
- 项目规则写进本地设置，别人根本拿不到
- 权限一不顺就一路开到最激进
- 模型、effort、上下文和规则问题混着排

所以这篇只围绕 5 个程序员最该先搞清楚的问题展开：

1. 配置作用域怎么分层
2. `CLAUDE.md` 应该怎样写才真正有用
3. 权限模式怎么选最省心
4. 模型、`effort`、上下文怎么摆位置
5. 装了 skill / MCP / plugin 后，哪些设置最影响它们是否好用

---

## 1. 配置层级：先分清谁属于“共享”，谁属于“个人”

按官方当前 `settings` 文档，Claude Code 的配置不是只在一个文件里堆满，而是有层级和作用域概念。

从程序员的使用习惯来看，最实用的理解方式是：

### User

面向你个人的长期偏好。  
适合放：

- 你一贯喜欢的默认行为
- 与具体仓库无关的习惯项
- 你自己的界面偏好、默认模式偏好等

### Project

面向当前仓库共享。  
适合放：

- 团队共同约定
- 与项目绑定的行为边界
- 这个仓库里都该统一遵守的设置

### Local

面向你本机、当前项目的本地覆盖。  
适合放：

- 不适合提交到仓库的临时开关
- 本地调试期特有设置
- 只对你自己有意义的覆盖项

### Managed / 命令行覆盖

更适合组织级或运行时临时控制。  
对个人程序员来说，知道它存在即可，不必第一天深挖。

### 一句话速记

- User 管你个人长期习惯
- Project 管仓库共识
- Local 管当前机器临时覆盖

这层边界一旦清楚，后面很多“为什么别人机器上没生效”的问题都会自动消失。

## 2. `CLAUDE.md` 往往比很多设置项更重要

程序员很容易天然更重视“配置文件”，而低估项目规则文档。  
但在 Claude Code 里，很多质量问题其实不是设置没配，而是规则没表达清楚。

### 一份真正有用的 `CLAUDE.md`，至少应该包含 5 类内容

1. 项目定位
2. 代码风格
3. 修改前的工作方式
4. 修改后的验证要求
5. 明确禁止或必须确认的动作

你当前仓库其实就很适合把现有 `AGENTS.md` 的工程规则通过 `CLAUDE.md` 接进来，再加一层 Claude Code 专属要求。

例如：

```md
@AGENTS.md

# Claude Code 补充说明

## 工作方式
- 先分析，再动手
- 多文件改动前先给计划
- 不要覆盖已有未提交改动

## 验证要求
- 改动 public/notes 后重新生成索引
- 改动文档时检查 frontmatter 是否完整
- 涉及渲染逻辑时至少人工验证 1 篇文章详情页
```

### 为什么 `CLAUDE.md` 比“到处写 prompt”更重要

因为它解决的是“默认工作方式”问题。  
如果你每次都靠临时聊天补规则，会遇到这些问题：

- 新会话要重复说
- 长会话里容易被稀释
- 团队成员拿不到同样规则

所以程序员最该做的不是一直埋怨 Claude“这次怎么又忘了”，而是把长期规则固定到它稳定能读到的地方。

---

## 3. 一个够用的 `CLAUDE.md`，不要写成百科全书

很多程序员一旦开始认真配，就容易过度设计。

常见误区：

- 把所有历史背景都写进去
- 把每个命令都列进去
- 把每个模块的细节全写进去
- 想一步把它写成“终极手册”

结果通常是：

- 太长
- 太难维护
- 很多内容很快过时

更好的标准是：

- 只写“长期稳定、足够高频、真的会影响行为”的规则

如果一个项目规则满足下面 3 条，基本就适合写进 `CLAUDE.md`：

1. 跨多次任务都成立
2. 不写出来就很容易反复出错
3. 团队里不止你一个人会受益

## 4. 权限模式怎么选，不是“越激进越高效”

从程序员角度，权限模式要按风险和确定性来选，而不是按“想不想少点确认弹窗”来选。

### 适合 `default` / Manual 的场景

- 第一次接手仓库
- 先分析、不急着动手
- 需求还在澄清中
- 你还在观察 Claude 的行为风格

`default` 是配置值，CLI 界面里现在更常见的显示名是 `Manual`，新版也接受 `manual` 作为别名。

### 适合 `acceptEdits` 的场景

- 已经明确要改哪些文件
- 改动范围不大，但编辑频率会比较高
- 文档重构、小范围重命名、结构整理

### 适合 `plan` 的场景

- 跨多个模块
- 你自己也还没想清楚方案
- 改错成本高
- 需要先对齐实施顺序和风险点

### 适合 `auto` 的场景

- 仓库规则很清楚
- 任务边界清楚
- 验证路径清楚
- 你已经比较了解 Claude 在这个项目里的行为

当前官方把 `auto` 定义为带后台安全检查的自动模式。它能减少大量权限确认，但可能受组织设置、模型、provider 和环境限制；不要把“我这里没有 auto”直接理解成安装坏了。

### 适合 `dontAsk` 的场景

`dontAsk` 只允许预先批准过的工具自动运行，更像 CI、脚本化和严控 allowlist 的模式。它不会进入 `Shift+Tab` 循环，需要显式指定。

### 为什么不建议新手一上来就 `bypassPermissions`

因为程序员真正想要的是“减少无意义确认”，不是“失去可控边界”。  
前者靠规则和上下文也能做到很多，后者则会直接放大误操作风险。

## 5. Sandboxing 的正确打开方式

很多人对 sandbox 的第一反应是“麻烦”。  
但工程上更准确的理解是：

- 它是在帮你把行为限制在一个可预测范围内

对程序员来说，sandbox 的价值不只是安全，也包括：

- 避免误改系统级路径
- 避免任务范围失控
- 让自动化动作更容易复现和审计

所以当你被 sandbox 拦住时，先别本能地想“关掉它”，而应该先问：

1. 这次动作是否真的需要更高权限
2. 当前任务目标是不是已经超出了原定边界
3. 有没有更小范围、更可验证的替代做法

## 6. 模型、`effort`、上下文，分别解决什么问题

这三者经常被混在一起讨论，但其实是三种完全不同的维度。

### 模型

模型决定的是底层能力特征。  
按官方当前 `model config` 文档，`default` 别名会因不同计划或平台而映射到不同模型族。当前官方命令里常见的模型别名包括：

- `best`：系统自动选择最合适模型
- `opus`：Claude Opus 4.8 级别能力
- `sonnet`：Claude Sonnet 5 级别能力
- `haiku`：轻量、低延迟任务
- `fable`：适合文档、写作、清晰沟通类任务

对程序员来说，最实用的理解是：

- 模型像发动机
- 不同计划和平台下，默认发动机不一定一样
- 看到旧教程写死某个默认模型名时，不要盲信

### `effort`

`effort` 更像本次任务愿意让 Claude 花多少推演成本。  
它不等于“回答更长”，也不等于“权限更高”。

更适合提高 `effort` 的场景：

- 多文件依赖判断
- 复杂重构
- 方案比较
- 很容易因为想漏边界而返工的任务

当前官方常见档位包括 `low`、`medium`、`high`、`xhigh`、`max`、`ultracode`。`auto` 不是“最高档”，而是恢复模型默认判断。

### 上下文

上下文决定的是“Claude 当前脑子里都装了什么”。  
它不是越长越好，真正重要的是：

- 有没有把不相关的话题堆太多
- 当前对话是否还围绕一个清晰目标
- 是否需要 `/compact` 或重开会话

### 很多人误判问题的方式

明明是上下文脏了，却怪模型。  
明明是规则没写清楚，却只改 effort。  
明明是权限边界不合适，却觉得“是不是模型不够强”。

程序员最该学会的，是先分清这是哪一层的问题。

## 7. 1M Context 和 Fast Mode 应该怎么理解

这两项都很吸引人，因为一看就像“更强”的配置。  
但对程序员来说，判断标准不该是“能不能开”，而应该是“值不值得开”。

### 更大上下文适合什么

- 仓库真的很大
- 任务链很长
- 需要同时引用很多相关文件
- 你确认当前对话本身是干净和聚焦的

### Fast Mode 适合什么

- 任务偏轻量
- 更看重交互速度
- 不需要深度方案推演

### 为什么不是所有任务都该开到最强

因为：

- 上下文更大不等于任务描述会自动变清楚
- 更快不等于更稳
- 更深不等于更适合当前任务

所以程序员的最佳实践通常不是“长期固定一个最强挡位”，而是按任务类型切换。

## 8. 状态栏、快捷键、终端观感，什么时候值得认真配

这些配置当然会影响体验，但优先级没有你想象中那么高。

### 状态栏

当你开始频繁切：

- 模式
- 项目
- 会话
- 任务阶段

状态栏就会越来越有价值，因为它能减少你对“当前状态”的猜测。

### 快捷键

适合在你已经形成稳定肌肉记忆后再微调。  
太早大改，反而容易让自己更乱。

### 终端观感

对舒适度有帮助，但对结果质量影响通常远低于：

- 规则是否清楚
- 模式是否合适
- 上下文是否干净

## 9. 装了 Skills、MCP、Plugin 以后，哪些设置最影响体验

这是你当前最需要的一节。

### 第一类：作用域配置

如果一个 skill / plugin / MCP 配在用户级，但你以为它是项目级，或者反过来，就很容易出现：

- 在这个仓库能看到，换个仓库看不到
- 只有你本机有，别人没有
- 你以为提交了，实际上没跟仓库走

### 第二类：规则写法

如果你希望 Claude 优先调用某类能力，除了装它，还应该在 `CLAUDE.md` 里写出明确偏好。

例如：

```md
## 外部资料策略
- 涉及前端框架、组件库、构建工具时，优先查官方文档
- 如需最新代码示例，优先使用已接入的文档检索或浏览器能力
```

这会显著提高它在正确时机使用相关扩展的概率。

### 第三类：命名和描述清晰度

skill 的名字、description、任务定位如果太模糊，就会直接影响匹配命中率。  
这不是“模型笨”，而是扩展定义本身在给一个很弱的触发信号。

### 第四类：模式与权限

有些扩展能力需要更实际的工具调用。  
如果当前模式太保守，它可能知道该做什么，却跨不过执行边界。

## 10. 一个程序员够用的配置落地顺序

如果主人现在要从零把 Claude Code 配顺，我推荐这个顺序：

1. 建一个简洁但高质量的 `CLAUDE.md`
2. 把共享规则和个人偏好拆开
3. 默认模式保持在 `default` / Manual 或 `acceptEdits`
4. 复杂任务时再切 `plan` 和更高 `effort`
5. 装扩展后先检查 `/skills`、`/mcp`、`/plugin`
6. 用 `/memory` 定期审计 auto memory
7. 遇到长会话混乱时优先处理上下文

这个顺序的核心优点是：

- 先稳主线
- 再加能力
- 出问题时容易定位

## 11. 程序员最常见的 6 个配置误区

### 误区一：把所有偏好都写进共享规则

结果是团队规则和个人习惯缠在一起。

### 误区二：没写规则，却一直加设置项

很多时候不是设置问题，而是 Claude 根本不知道你项目里的工作方式。

### 误区三：一不顺就开最激进权限

短期少点确认，长期更容易失控。

### 误区四：所有问题都怪模型

上下文、规则、作用域、权限任何一层都可能才是根因。

### 误区五：装了扩展却不检查是否被发现

正确顺序应该是：先装成功，再看可见性，再谈调用命中率。

### 误区六：太早沉迷 UI 和快捷键微调

真正决定质量的还是规则、模式、上下文和验证路径。

---

## 12. 读完这篇后最推荐做什么

对你当前这个仓库，我最推荐马上做 3 件事：

1. 新建或整理一份项目级 `CLAUDE.md`，通过 `@AGENTS.md` 复用现有规则
2. 把“改 notes 后重建索引、先分析再动手、不要覆盖未提交改动”写成稳定规则
3. 再去看第六篇，把你已经装的前端 skill / MCP / plugin 真正调起来
