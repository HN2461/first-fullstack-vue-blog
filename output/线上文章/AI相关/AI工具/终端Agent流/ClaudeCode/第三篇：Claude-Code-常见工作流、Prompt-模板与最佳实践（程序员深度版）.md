# 第三篇：Claude Code 常见工作流、Prompt 模板与最佳实践（程序员深度版）

> 如果第一篇解决的是“怎么装、怎么开工”，第二篇和第四篇解决的是“规则和配置别配乱”，那这篇解决的就是程序员每天最真实的问题：  
> 我拿到一个仓库、一个 bug、一个重构需求、一份文档任务，Claude Code 到底该怎么带着它一步步做，才不容易返工。

---

## 先给一条主线

主人以后只要记住这一条工作流主线，Claude Code 的稳定性就会一下子高很多：

1. Explore：先读上下文，确认问题边界
2. Plan：先说会改哪里、风险是什么、怎么验证
3. Implement：按小步改动推进
4. Verify：用命令、页面、日志、测试去验
5. Recap：收尾说明已做什么、没做什么、还剩什么风险

很多人觉得 Claude Code “有时神、有时飘”，本质上不是模型突然忽高忽低，而是这 5 步经常被省掉了两三步。

---

## 1. 程序员为什么一定要把任务分阶段

因为 Claude Code 不是只在生成文本，它是在：

- 读文件
- 找引用
- 分析依赖
- 跑命令
- 改文件
- 管理当前会话上下文

如果你一句话直接说：

```text
帮我把这个模块优化一下
```

那你等于把下面这些判断全留给它自己猜：

- 你说的“优化”是性能、结构、命名、样式还是交互
- 能不能大改
- 哪些目录不能碰
- 是否需要跑测试
- 你最终怎么验收

所以真正高质量的协作，不是“会不会写 prompt 花活”，而是把任务拆成 Claude 最容易稳定执行的阶段。

---

## 2. 一套程序员通用的任务骨架

以后主人几乎所有任务都可以用这套骨架发给 Claude：

```text
任务目标：
[一句话说清目标]

上下文：
[给出文件、模块、现象、背景]

限制：
1. [不能改什么]
2. [哪些行为必须保持不变]
3. [是否先分析不改]

输出要求：
1. [先解释 / 先计划 / 直接改]
2. [改完说明涉及文件]
3. [给出验证方式]
```

为什么这套骨架有效？

- 它把“任务目标”和“行为边界”拆开了
- 它强制你说清楚“先分析还是先动手”
- 它把“验证要求”提前到了任务开始前

## 3. 场景一：第一次读陌生仓库，怎么问最稳

这是 Claude Code 最适合帮程序员提速的场景之一。

### 最小可用 prompt

```text
先不要修改任何文件。
请先阅读这个仓库，然后告诉我：
1. 这是个什么项目
2. 主要目录怎么分工
3. 入口文件和主流程在哪
4. 如果我是第一次接手，应该先看哪几个文件
5. 哪些地方最可能定义了项目级规则或约束
```

### 更适合程序员的加强版 prompt

```text
先不要修改任何文件。
请从以下角度帮我理解这个仓库：
1. 项目结构
2. 关键页面或模块
3. 主要数据流
4. 构建与运行方式
5. 测试入口
6. 代码风格和潜在项目规则来源

如果有你不确定的地方，请明确标出来，不要猜。
最后给我一份“第一次接手应该优先读哪些文件”的清单。
```

### 这一步为什么特别重要

因为这一步做得好，后面会直接减少：

- 改错文件
- 误判架构
- 误解数据流
- 一上来就重构错方向

### 这时适合搭配哪些能力

- `@文件路径`：强制把关键文件直接带入上下文
- `/status`：确认当前模式和状态
- `plan mode`：如果你明确不想它立即动手
- subagent：如果仓库很大，想让研究在独立上下文里完成
- `/batch`：如果是大规模跨代码库任务，可以让 Claude 先拆分成多个独立单元，再按 worktree 并行推进

## 4. 场景二：修 bug，怎么让 Claude 不跑偏

修 bug 最怕的不是“Claude 不会写”，而是“Claude 还没搞清根因就开始修”。

### 最稳的修 bug 提法

```text
这是一个 bug 现象：
[现象描述]

复现步骤：
1. ...
2. ...
3. ...

预期结果：
[应该发生什么]

实际结果：
[实际发生什么]

先不要修改。
请先分析最可能的原因，并告诉我：
1. 你打算检查哪些文件
2. 你打算看哪些状态、日志或调用链
3. 哪几种原因最值得优先排查
等我确认后再修。
```

### 如果你已经有报错输出

直接把错误文本、堆栈、复现命令一起给它：

```text
我在运行 `npm test` 时看到下面这个报错：
[贴错误]

请先分析根因，不要立刻修改。
告诉我这是更像环境问题、数据问题、逻辑问题还是测试本身的问题。
```

### 修 bug 时一定要补的两类信息

1. 可复现步骤
2. 验证通过标准

没有这两样，Claude 很容易写出“像修了”的改动，但你最后还是得自己重新定义问题。

### 修 bug 最值得补的一句

```text
如果你不确定根因，请先列假设和验证顺序，不要直接拍脑袋修改。
```

## 5. 场景三：重构，怎么避免“一口气重写”

Claude Code 很擅长做重构，但前提是你不能把“重构”说成一个无限目标。

### 程序员最常犯的模糊说法

- 优化一下结构
- 顺手整理一下这块
- 写得更优雅一点
- 帮我现代化一下

这些说法对人类同事都不够清楚，对 Claude 更不够。

### 更稳的重构 prompt

```text
目标：提升这个模块的可读性和可维护性，但不要改变功能行为。

限制：
1. 不改接口输入输出
2. 不改目录结构
3. 不顺手重构无关模块
4. 优先减少重复逻辑
5. 先给出重构计划，再开始修改

验证要求：
1. 说明每一步改动目的
2. 改完后运行相关测试
3. 列出仍然存在的风险点
```

### 为什么重构特别适合 `plan + 高 effort`

因为重构最怕的不是写不出来，而是：

- 想漏依赖
- 抽错边界
- 改出行为回归

所以重构场景非常适合：

1. 先切 `plan`
2. 再提高 `effort`
3. 最后按小步落实

## 6. 场景四：补测试，怎么让它别只写样板

Claude 补测试时，最容易出现的低质量结果是：

- 只补 happy path
- 只凑结构
- 断言很弱
- 没跟现有测试风格对齐

### 更好的测试 prompt

```text
请先阅读现有测试文件，理解当前项目测试风格。
然后找到这个模块还没有覆盖的关键行为和边界情况。
先不要修改，先告诉我：
1. 哪些行为缺测试
2. 哪些边界最值得补
3. 你建议新增哪些测试用例
```

确认后再让它落代码：

```text
现在开始补测试：
1. 保持和现有测试风格一致
2. 优先覆盖边界条件和错误分支
3. 改完后运行相关测试并汇报结果
```

### 一个很有价值的追问

```text
除了我已经想到的场景，你再帮我找 3 个容易被遗漏的边界测试。
```

## 7. 场景五：文档、笔记、README，怎么让它写得像程序员文档

主人这次让重构 Claude Code 笔记，本质上就是这个场景。

### 最糟的文档指令

```text
帮我润色一下
```

这会导致 Claude 很容易只做表层顺滑，而不解决结构、读者对象和信息深度问题。

### 更好的文档重构 prompt

```text
请把这份文档改写成更适合程序员深入理解的文章。

要求：
1. 不要只做表层润色，要重排结构
2. 先说程序员真正关心的问题
3. 给出可执行命令、配置、验证、排障思路
4. 区分“概念层”“实操层”“排障层”
5. 高级内容放在主线跑通之后讲
```

### 如果你希望它更像教程而不是百科

补一句：

```text
请按“先跑通，再理解，再扩展”的学习顺序组织内容。
```

## 8. 场景六：多任务并行，什么时候该用 worktree、subagent、后台任务

这部分是程序员进阶后非常有价值的能力。

### Subagent 适合什么

当你不想让主会话被大量探索过程塞满时，适合让 subagent 去做研究型任务，比如：

- 调查认证链路
- 找跨模块引用
- 汇总一个大目录的结构

这样主上下文只收结论，不收所有中间读取噪音。

注意一个当前命令变化：从 Claude Code `v2.1.198` 起，`/agents` 不再打开旧版交互管理界面，而是提示你直接让 Claude 创建、管理 subagents，或者手动编辑 `.claude/agents/`、`~/.claude/agents/`。如果你看到旧教程里说 `/agents` 会弹出配置界面，要先看自己的版本。

### Worktree 适合什么

当你想并行推进多个真实改动任务，又不想改动互相打架时，worktree 非常有用。

例如：

- 一个终端让 Claude 修 bug
- 另一个终端让 Claude 做新功能实验

两边在不同工作树里，不会互相污染。

如果任务足够大，也可以直接考虑 `/batch <instruction>`。它是官方 bundled skill，会先研究代码库、拆成多个独立单元，得到你确认后再用隔离 worktree 和后台 subagent 并行实现。

### 后台任务适合什么

适合：

- 长时间命令
- 长时间分析
- 你不想当前交互被阻塞的操作

程序员应把这些能力理解成“并行工程组织手段”，不是炫技功能。

当前更完整的并行入口可以这样记：

- `/fork`：把一个侧线任务交给后台 subagent，完成后结果回到当前会话
- `/background`：把整个会话转后台，用 `claude agents` 观察
- `/tasks`：看当前会话里的后台任务
- `/batch`：面向大规模改造的官方并行工作流

## 9. 会话管理：什么时候该 `/resume`、什么时候该 `/compact`、什么时候该重开

这是很多人忽略但非常影响质量的一块。

### 适合 `/resume`

- 你就是要继续同一个任务
- 先前上下文仍然有效
- 你不想重新解释项目背景

### 适合 `/compact`

- 任务主线没变
- 但会话太长、上下文太臃肿
- 想减少噪音继续推进

如果只是想知道当前上下文到底被什么占满，先用 `/context` 看分布，再决定要不要 `/compact`，会比盲目压缩更稳。

### 适合直接重开

- 任务已经换题
- 之前讨论里混进很多无关分支
- 当前会话开始明显“脏”

程序员要学会接受一件事：

- 有时候新开一个聚焦会话，比在旧会话里硬救更省时间

## 10. 程序员最值得直接收藏的 Prompt 模板

### 模板一：先研究，不要修改

```text
先不要修改任何文件。
请先阅读相关代码，告诉我：
1. 当前实现在哪里
2. 相关依赖和调用链是什么
3. 可能的风险点是什么
4. 如果要改，应该先改哪一层
```

### 模板二：先给计划，再动手

```text
先不要立刻修改。
请先给我一个实施计划，说明会改哪些文件、每一步目的、风险点和验证方式。
等我确认后再开始。
```

### 模板三：限制改动范围

```text
只修改和这个需求直接相关的文件。
不要顺手重构其他模块。
如果你觉得必须扩大范围，请先说明原因，再等我确认。
```

### 模板四：收尾验证

```text
请列出：
1. 你已经验证过的内容
2. 你还没有验证的内容
3. 我作为人工还应该补看的地方
4. 当前改动仍然存在的风险点
```

### 模板五：要求它承认不确定性

```text
如果你有不确定的地方，请明确标出来，不要把猜测写成结论。
```

## 11. 程序员最常见的 8 个工作流误区

### 误区一：一上来就大改

这不是效率，是把返工风险前置。

### 误区二：把模糊目标直接丢给 Claude

Claude 不会自动知道你最在乎的是性能、结构、样式还是交互。

### 误区三：不写验证要求

没有验收标准，最后只会得到“看起来像完成了”的结果。

### 误区四：长会话里不停切题

会话越脏，表现越飘。

### 误区五：把模式当作“聪明程度切换”

模式主要影响行为边界，不是单纯“更强”。

### 误区六：修 bug 时让它直接开修

很多 bug 更需要先排查、先缩小范围。

### 误区七：补测试时只让它“加几个测试”

这样最容易得到样板测试。

### 误区八：不会用并行能力

大仓库研究、并发任务、长命令如果全塞进一个会话，体验会越来越差。

## 12. 主人今天就能照着练的一条完整工作流

如果主人现在想马上练一次，最推荐这样做：

1. 找一个真实仓库
2. 用“先不要修改”让 Claude 给你做项目结构分析
3. 选一个很小的问题或重构点
4. 让它先给计划，不要直接开改
5. 让它按小步实施
6. 让它输出验证清单
7. 你自己再补一轮人工验证

只要把这条流程真的跑顺，Claude Code 对你来说就不再是“看过教程的工具”，而会开始变成日常可控的开发搭档。
