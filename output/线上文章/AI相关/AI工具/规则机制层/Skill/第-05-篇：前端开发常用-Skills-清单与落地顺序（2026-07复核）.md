# 第 05 篇：前端开发常用 Skills 清单与落地顺序（2026-11复核）


> 2026-11 复核结论：前端 skills 的落地顺序仍然成立；Codex、Cursor、Claude Code、Kiro 都已经有明确的 skills / agent skills 入口，但各自目录、触发、安装和 marketplace 机制不同。跨工具复用时先写最小 `SKILL.md`，再按具体工具补充专属层。

这篇只解决一个实际问题：

**前端团队应该先沉淀哪些 skills，才能让 agent 不只会写代码，还能稳定交付页面。**

先给一句话结论：

1. 先把“页面实现 + 与风险匹配的验收 + 响应式排障”三件事跑通
2. 再做“组件规范 + 无障碍审查 + 性能复查”
3. 最后按团队项目特性补“设计协作”和“业务域模板”

## 一、前端常用 skills 矩阵

| Skill | 类型 | 最适合场景 | 推荐级别 | 是否建议先做 |
| --- | --- | --- | --- | --- |
| `frontend-design` | 官方实例与能力方向 | 页面实现、视觉优化、组件落地 | S | 是 |
| `browser` | 能力方向，按宿主选择实际工具 | 真实浏览器验收、交互复现、截图核对 | S | 是 |
| `responsive-debug` | 建议自定义 | 移动端错位、溢出、层级遮挡 | S | 是 |
| `component-patterns` | 建议自定义 | 组件库规范、命名与边界统一 | A | 是 |
| `accessibility-audit` | 建议自定义 | 键盘可达、焦点管理、语义审查 | A | 次优先 |
| `performance-audit` | 建议自定义 | 首屏慢、卡顿、包体膨胀 | A | 次优先 |
| `figma-handoff` | 建议自定义 | 设计稿信息转代码任务清单 | B | 按需 |

表中名称是能力分类与示例命名，不能当成每个客户端都存在的可安装包。尤其 `browser` 不是跨工具统一的 Skill 名称，真实浏览器也不同于移动设备真机。

当前可核对的官方实例：

| 来源 | 真实条目 | 适用边界 |
| --- | --- | --- |
| Anthropic 官方插件仓库 | `frontend-design` 插件内同名 Skill | 视觉设计与页面实现；仍须遵守项目已有设计系统 |
| OpenAI `build-web-apps` | `frontend-app-builder`、`frontend-testing-debugging` | 新页面与前端排障分开组织 |
| 同一 OpenAI 插件 | `react-best-practices`、`shadcn-best-practices` | 仅在使用对应技术时启用，不能套到所有 Vue 项目 |
| 同一 OpenAI 插件 | `stripe-best-practices`、`supabase-best-practices` | 仅在接入相应支付或数据库技术时使用 |

官方目录会变化，安装前核对插件 catalog、技能文件和客户端支持。不要执行网上未注明来源的同名安装命令。

## 二、优先级为什么这样排

## 2.1 先保交付

`frontend-design` + `browser` + `responsive-debug` 是最短交付路径：

1. 能把页面做出来
2. 能先完成构建、静态检查和必要测试；依赖 DOM/交互的问题再按授权进行浏览器验证
3. 能修掉最常见的移动端和布局问题

## 2.2 再保可维护

`component-patterns` + `accessibility-audit` + `performance-audit` 决定后续扩展成本：

1. 组件风格是否可复用
2. 无障碍是否持续合规
3. 性能是否随业务增长而失控

## 三、7 个前端 skills 的落地建议

## 3.1 `frontend-design`

- 适合：
  1. 新页面从 0 到 1
  2. 老页面视觉与信息层级重构
- 使用要点：
  1. 把项目现有设计系统约束写进 references
  2. 把禁用写法写清楚，避免“看起来好看但不合规”

## 3.2 `browser`

- 适合：
  1. 点击路径复现
  2. 弹层、表单、列表交互验证
  3. 回归截图留档
- 使用要点：
  1. 固定“复现路径 -> 期望 -> 实际”的输出模板
  2. 要求给出最小复现步骤、实际观察和证据
  3. 遵守当前项目的浏览器授权约束；无需截图的问题不强制生成截图
  4. 真实浏览器、移动端模拟和真实设备测试分别说明

## 3.3 `responsive-debug`

- 适合：
  1. 小屏布局错位
  2. 内容溢出
  3. fixed/sticky/transform 叠层冲突
- 使用要点：
  1. 固定排查顺序：断点 -> 父布局链 -> 尺寸约束 -> 定位与层级
  2. 强制输出“根因 + 可回归检查点”

## 3.4 `component-patterns`

- 适合：
  1. 组件库建设
  2. 团队风格统一
- 使用要点：
  1. 把 `props / emits / slots` 命名规则固化
  2. 明确哪些组件必须包含空态、加载态、错误态

## 3.5 `accessibility-audit`

- 适合：
  1. 表单重交互
  2. 弹窗、抽屉、多层浮层
- 使用要点：
  1. 固定检查语义、焦点、键盘操作、ARIA
  2. 输出风险等级，避免“看起来都行”的模糊结论

## 3.6 `performance-audit`

- 适合：
  1. 首屏加载慢
  2. 列表卡顿
  3. 交互延迟明显
- 使用要点：
  1. 拆成资源、渲染、交互三层给建议
  2. 每条建议都要附“预期收益”和“验证指标”

## 3.7 `figma-handoff`

- 适合：
  1. 设计稿还原误差大
  2. 设计改动频繁
- 使用要点：
  1. 只抽取“实现决策有用”的信息
  2. 不把它当自动生成代码工具，而是信息对齐工具

## 四、skills、rules、mcp 的边界

这部分是前端团队最容易混淆的地方，建议固定这样分：

1. `Skills`：按需触发的任务流程
2. `Rules / AGENTS.md / CLAUDE.md`：持续生效的长期规范
3. `MCP`：让 agent 获得外部能力接口

可直接套用一句话：

**规则定义底线，skills 编排流程，MCP 提供工具。**

## 五、建议的 30 天落地节奏

1. 第 1 周：落地 `frontend-design`、`browser`
2. 第 2 周：落地 `responsive-debug`、`component-patterns`
3. 第 3 周：补 `accessibility-audit`
4. 第 4 周：补 `performance-audit`，并回看前三周产出

这个节奏的优点是：

1. 第一周就有明显交付收益
2. 第二周开始降低团队分歧
3. 第三、四周把质量和性能补齐

## 六、触发词建议（可直接放到 skill 描述里）

1. `frontend-design`：实现新页面、重构视觉、统一布局
2. `browser`：复现交互、检查 DOM、抓取截图
3. `responsive-debug`：修复移动端布局、处理溢出、修弹层遮挡
4. `component-patterns`：新建通用组件、统一 props 命名
5. `accessibility-audit`：审查键盘可达、焦点、ARIA
6. `performance-audit`：定位首屏慢、卡顿、资源过大

## 七、前端 UI 设计资料专项 Skill

如果你现在的重点是“先把 UI 设计资料搜准，再稳定落地”，建议加一个专项 skill：

1. `ui-research-to-implementation`

建议定位：

1. 输入：页面目标、目标用户、设备端、业务限制
2. 输出：参考资料清单、可复用组件建议、交互状态清单、实现优先级

建议流程：

1. 先用可用的官方文档、搜索工具或检索类 MCP 收集与当前页面相关的参考；无需为了查资料额外接入 MCP
2. 按信息密度和可实现性筛成 3 条候选
3. 抽取布局、层级、交互状态，不抄配色和装饰
4. 生成当前项目可落地的组件清单和任务拆分
5. 输出“必须保留”和“可裁剪”两组建议

建议触发词：

1. `检索并整理这个页面的 UI 设计参考，输出可落地方案`
2. `把这组设计灵感转换成我们的组件与交互任务`
3. `基于当前项目约束，给出 UI 实现优先级与风险点`

## 八、收口建议

如果只选 4 个先上线，我建议固定为：

1. `frontend-design`
2. `browser`
3. `responsive-debug`
4. `component-patterns`

原因很直接：这 4 个覆盖了页面交付中常见的实现、验收、布局和组件一致性问题；实际收益需要结合团队缺陷数据衡量。


## 技能落地的结果指标

每个 Skill 固定输入、输出和验证边界：页面实现输出可运行变更；响应式排障输出复现尺寸和根因；无障碍审查区分自动检查与人工键盘检查；性能审查记录同一环境下的测量前提、优化前后结果。不要把模型生成的建议写成已经实际测得的性能收益。

规则文件维护长期组件规范，Skill 维护任务流程，MCP/浏览器工具负责读取或交互。需要多人统一安装时，再使用 Codex、Claude Code 或 Cursor 的插件分发能力。
