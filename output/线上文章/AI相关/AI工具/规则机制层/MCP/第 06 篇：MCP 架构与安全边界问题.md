# 第 06 篇：MCP 架构与安全边界问题

复核日期：2026-07-04

> 时效说明：本文的 host / client / server、tools / resources / prompts、安全治理等基础回答仍按 MCP 当前正式规范复习。官方 draft 中的协议状态、授权和弃用策略变化属于进阶趋势；讲架构时可以补充“协议层可能减少会话状态依赖，但应用层仍然可能有自己的业务状态”。

## 第一题：MCP 架构里的 Host、Client、Server 分别是什么

### 30 秒回答

Host 是用户实际使用的 AI 应用，Client 是 Host 内部负责连接某个 MCP server 的协议组件，Server 是对外暴露能力的提供方。  
我会把它理解成“宿主负责体验，client 负责连接，server 负责供能”。

### 2 分钟展开

这三个角色最好分开讲，不然很容易把概念混在一起。

1. Host：例如桌面端、IDE、聊天工作台，它负责承接用户任务和整体交互体验
2. Client：它存在于 host 内部，负责与某个 MCP server 建立连接、发现能力、发起请求
3. Server：真正提供能力，例如浏览器、文件系统、搜索、数据库、知识库等

这个划分的好处是职责清晰：

1. Host 可以专注用户体验和任务编排
2. Server 可以专注能力暴露和边界控制
3. 中间用协议连接，降低平台和能力之间的耦合

### 追问应对

- 如果面试官问“一个 host 能不能连多个 server”，可以答：可以，而且这是常见形态
- 如果面试官问“client 是不是独立产品”，可以答：不一定，很多时候它是 host 内部的一层连接组件

### 可反问面试官的问题

- 你们更倾向在宿主里内建少量能力，还是通过 MCP 外挂更多能力？
- 现在是单 host 场景，还是会有 IDE、桌面端、Web 多宿主并存？

## 第二题：tools、resources、prompts 有什么区别

### 30 秒回答

`tools` 偏执行动作，`resources` 偏读取已有内容，`prompts` 偏复用任务模板。  
它们都属于 MCP server 能暴露的能力原语，但使用方式和治理重点不一样。

### 2 分钟展开

我一般会这样区分：

1. `tools`：主动做事，比如搜索、点击、运行查询、执行命令
2. `resources`：提供内容给模型读取，比如文档、文件、数据快照
3. `prompts`：提供可复用的任务模板，帮助把常见任务标准化

这三个东西很容易被混成“都是工具”，但实际落地里差异很大。

例如“搜索资料”和“阅读内容”就是两个不同动作：

1. 搜索资料通常偏 `tool`，因为它需要主动发起查询
2. 阅读内容通常偏 `resource`，因为它是在消费已有材料

所以我在做选型时，会先看这个能力本质上更像执行、读取还是模板化复用。

### 追问应对

- 如果被问“一个 server 能不能同时有三者”，可以答：完全可以，而且很多实用 server 本来就是组合暴露
- 如果被问“面试里一定要背术语吗”，可以答：不用硬背，但最好能用实际场景解释出来

### 可反问面试官的问题

- 你们实际接入的能力，更偏执行型还是阅读型？
- 你们有没有把常见排障流程做成固定 prompt 或模板入口？

## 第三题：MCP 的安全风险主要有哪些

### 30 秒回答

我会重点看四类风险：权限过大、来源不可信、执行不可审计、结果被误信。  
所以真正落地时，MCP 不是先追求“能不能接”，而是先设计最小权限、审批、隔离和审计。

### 2 分钟展开

MCP 一旦连到真实环境，就不再只是一个问答功能，而是外部能力入口，所以安全一定要前置。

我通常会按这几类风险看：

1. 权限过大：比如文件系统全盘读写、数据库写权限、危险命令直通
2. 来源不可信：server 本身来源不明，或者能力说明与实际行为不一致
3. 执行不可审计：出了问题后不知道是谁在什么上下文里触发了什么动作
4. 结果被误信：模型可能把外部结果当成绝对正确，导致错误传播

对应治理策略也比较明确：

1. 最小权限和白名单
2. 高风险动作审批或人工确认
3. 环境隔离，优先沙箱和测试环境
4. 完整日志和审计链路

### 追问应对

- 如果面试官问“最大的风险是什么”，可以答：在真实团队里，通常不是模型说错话，而是能力边界失控
- 如果被问“知识检索也有风险吗”，可以答：有，尤其是时效性错误、脏数据和来源可信度问题

### 可反问面试官的问题

- 你们对 MCP 的风险更担心读数据泄露，还是写操作与执行操作失控？
- 现在是否已经有统一审批、日志和回放机制？

## 第四题：为什么说接了 MCP 不等于就能安全自动化

### 30 秒回答

因为 MCP 只是连接协议，不会自动替你解决权限、审批、环境隔离和业务兜底。  
它能把能力接进来，但“什么时候能执行、执行到什么边界、失败后谁兜底”还是工程治理问题。

### 2 分钟展开

很多人会误以为，接上 MCP 后模型就能自然变成可靠 Agent。  
但现实里协议只解决“怎么连”，并不自动解决“怎么管”。

真正要做到安全自动化，至少还需要这些配套：

1. 场景分级，区分只读、低风险、高风险
2. 人机协同，关键动作加确认
3. 环境隔离，优先测试环境先跑通
4. 回退策略，失败时能恢复或中止
5. 观测审计，知道它调用了什么、结果是什么

所以我会把 MCP 看成自动化能力的基础设施，而不是自动化本身。

### 追问应对

- 如果被问“那它价值是不是被高估了”，可以答：不是，它价值很大，但需要配套治理才能兑现
- 如果被问“有没有适合直接自动化的场景”，可以答：只读检索、低风险查询、测试环境验证通常更适合先落地

### 可反问面试官的问题

- 你们现在更希望 AI 帮忙读和查，还是已经希望它改和执行？
- 如果进入生产场景，哪些动作在你们团队里一定需要人工确认？
