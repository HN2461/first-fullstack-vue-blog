# 第五篇：CC Switch 跨机同步后绝对路径污染排障手册（2026-05-30复核）

> 资料核对时间：2026-05-30  
> 这篇的目标不是泛泛而谈“路径可能有问题”，而是把主人这次已经真实踩到的坑整理成一篇**能复用的排障手册**。  
> 先给结论：**如果你是通过 CC Switch 做跨机导出 / 导入、云同步或 provider 切换，结果目标机器上只有 MCP、`npx`、浏览器相关工具、Codex / Claude 某些能力异常，那就优先怀疑“旧机器绝对路径污染”。**

[[toc]]

---

## 1. 先说结论：这不是“小概率玄学”，而是 CC Switch 这类配置中控台的自然风险点

主人这次踩中的问题，本质不是：

- Codex 坏了
- Claude 坏了
- Chrome DevTools MCP 坏了
- Node / npm 本体坏了

而是：

- 你在 A 机器里通过 `CC Switch` 管理过 Provider / MCP / 配置片段
- 又把这套配置导出到 B 机器，或者通过云同步同步到了 B 机器
- 结果某些配置值里混进了 A 机器的绝对路径
- CC Switch 后续再把这些旧路径写回 live 配置文件，于是目标机器开始报错

这类问题的高发位置通常不是“模型 ID 填错”这种浅层配置，而是：

- `npm_config_cache`
- 浏览器路径
- 本地缓存目录
- 项目信任路径
- 某些 CLI 自定义配置目录

---

## 2. 先把官方能确认的 5 件事讲清楚

这篇文章里有一部分结论是**官方文档可以直接确认**的，主人可以放心把它当“文档事实”。

### 2.1 CC Switch 自己的数据根目录默认就在 `~/.cc-switch/`

官方 FAQ 明确写了：

- 默认存储目录是 `~/.cc-switch/`
- 这个目录位置可以在设置里自定义

而且同一页还列出了关键文件结构：

```text
~/.cc-switch/
├── cc-switch.db      # SQLite database (SSOT)
├── settings.json     # Device-level settings
├── skills/           # Skill SSOT directory
└── db_backup_*.db    # Database backups
```

这意味着主人以后排查跨机问题时，不能只盯着 `.codex/config.toml`、`.claude.json` 这些“结果文件”，还要回头看 `~/.cc-switch/` 这个“源头目录”。

### 2.2 `cc-switch.db` 才是官方定义的 SSOT

官方 FAQ 对配置优先级写得很直白：

1. `CC Switch Database` 是 `Single source of truth (SSOT)`
2. `Live Configuration Files` 是切换 provider 时写出的结果文件
3. `Backfill Mechanism` 会在编辑当前 provider 时，从 live 文件读回变化

这条非常关键。  
它直接解释了为什么主人这次**只修当前 `.codex/config.toml` 或 `.claude.json` 不够**：

- 你修的是第 2 层结果文件
- 真正的源头却可能还停留在第 1 层 `cc-switch.db`
- 下一次切 provider、导入配置或做同步时，坏数据又能重新写回来

### 2.3 官方确实支持跨机迁移，但导入本身就是覆盖动作

官方 Settings 手册明确支持：

- `导出配置`
- `导入配置`
- `WebDAV 云同步`

同时也明确写了：

- 导出文件包含：Provider、MCP、Prompts、应用设置
- 导入时会覆盖现有配置
- WebDAV 下载覆盖本地数据库前，会先自动创建安全备份

所以“通过 CC Switch 把配置从一台机带到另一台机”这个思路本身没有问题。  
真正的问题是：**如果导出源里已经混进了机器相关绝对路径，覆盖式导入就会把这类坏数据完整带过去。**

### 2.4 设备级设置本来就不是跨设备同步字段

官方 FAQ 还单独说了：

- `settings.json` 里保存的是设备级设置
- 这些设置 `not synced across devices`

里面包括：

- 语言
- 主题
- 窗口行为
- 开机自启
- 各 CLI 工具的自定义配置目录

这条给主人一个很重要的提醒：

- **跨设备可迁的是配置体系，不是所有机器相关路径都该被照搬**
- 只要配置里混进了旧机器用户名目录、浏览器绝对路径、缓存目录，目标机器就有机会炸

### 2.5 导出本来就不包含 usage logs 和 device-level settings

官方 FAQ 还明确给了 export 边界：

- export file includes：Provider、MCP、Prompts、app settings
- not included in export：`usage logs`、`device-level settings`

这条很适合给主人拿来区分两类情况：

- 如果是旧机器绝对路径被带过来，那是“坏数据被同步了”
- 如果只是语言、窗口行为、某些本机偏好没跟过来，那可能只是“官方本来就没打算跨设备同步”

## 3. 这篇里的“绝对路径污染”判断，哪些是官方事实，哪些是这次实战结论

这一步我特意拆开说，因为程序员最怕“把经验话术误当官方规则”。

### 3.1 官方能直接确认的

- CC Switch 使用 `cc-switch.db` 作为 SSOT
- 切 provider 时会把配置写到 live 配置文件
- 手动改 live 文件后，重新编辑当前 provider 时，改动会 backfill 回数据库
- 导出 / 导入 / WebDAV 都是正式支持能力

### 3.2 这次排障得出的实战结论

下面这些不是官方手册逐字列出的“固定规则”，而是**结合官方配置优先级 + 主人这次真实故障链推出来的结论**：

1. 如果导出源或云同步源里已经保存了旧机器绝对路径，目标机器上极容易出现“表面是 MCP / Node / 浏览器报错，实质是路径污染”的问题。
2. 绝对路径污染不一定只在 live 配置文件里，往往会同时存在于 `cc-switch.db` 的源数据里。
3. 如果你只修了 `.codex/config.toml`、`.claude.json` 等结果文件，而没有把数据库源头修干净，后面切换 provider 或再次同步时，旧路径仍然可能复发。

换句话说：

- **“SSOT + 覆盖写回”是官方机制**
- **“旧机器绝对路径因此复发”是这次真实场景下的工程结论**

这个结论我认为是稳的，而且很值得主人保留。

## 4. 这类问题最常见的症状长什么样

如果你看到下面这些现象，优先怀疑是跨机同步后的绝对路径污染：

- `/mcp` 里能看到某个 server，但 `Tools: (none)`
- 一台电脑上能用的 MCP，另一台电脑不能用
- `npx`、`node`、浏览器相关 MCP 启动失败
- 日志里出现 `EPERM`、`ENOENT`、`operation not permitted`、`path not found`
- 配置里出现旧电脑用户名路径，比如：
  - `C:\Users\Administrator\...`
  - `C:\Users\HN246\...`
  - 其他历史用户名目录

主人这次最典型的真实命中点，就是：

- `chrome-devtools` MCP 的 `npm_config_cache`
- 被写成了另一台电脑上的目录
- 结果 `npx` 尝试往错误用户目录写缓存，最终报 `EPERM`

---

## 5. 这次真实踩中的根因，为什么值得单独记一篇

这次问题的直接根因是：

- `chrome-devtools` MCP 的 `npm_config_cache`
- 被写成了另一台机器上的路径：

```text
C:\Users\Administrator\.codex\npm-cache
```

而当前机器真实用户目录其实是：

```text
C:\Users\HN246\...
```

于是结果就是：

1. `npx` 启动 `chrome-devtools-mcp` 时，试图写入错误目录
2. 当前机器对那个目录不存在或无权限
3. MCP 启动失败，或者 `tools/list` 失败

这件事为什么值得记一篇？

因为它不只是一个单点字段写错，而是说明了：

- **机器相关路径一旦进入 CC Switch 的配置体系，后果不会只停留在一个字段**
- 它可能在 provider、MCP、settings、live 配置文件几层之间反复传播

## 6. 高风险文件到底有哪些

跨机同步后，主人优先检查这几类位置。

### 6.1 当前 live 配置

- `C:\Users\<当前用户>\.codex\config.toml`
- `C:\Users\<当前用户>\.claude.json`
- `C:\Users\<当前用户>\.gemini\...`
- 其他 AI 工具自己的主配置文件

### 6.2 真正的源头目录

- `C:\Users\<当前用户>\.cc-switch\cc-switch.db`
- `C:\Users\<当前用户>\.cc-switch\settings.json`

这里要注意一个边界：

- 官方 FAQ 明确写了**可以手工编辑**：CLI 工具配置文件、CC Switch 的 `settings.json`
- 官方 FAQ 也明确写了**不推荐手工编辑**：`cc-switch.db`、backup files
- 但如果你已经确认坏数据就在 SSOT 层，而 UI 又无法把它彻底覆盖掉，那数据库修复就会变成**最后兜底手段**

我的建议是：

1. 能先通过 CC Switch UI 重填并保存当前 provider，就先走 UI
2. UI 修不掉、坏路径还在、而且复发明显时，再备份后做数据库层修复

### 6.3 这次最值得优先搜的字段

- `C:\Users\旧用户名\`
- `npm_config_cache`
- `CHROME_PATH`
- `PROGRAMFILES`
- `SystemRoot`
- `TEMP`
- `TMP`
- `source = '\\?\C:\Users\旧用户名\.codex\.tmp\bundled-marketplaces\...'`
- `projects.'c:\users\旧用户名\...'`

---

## 7. 为什么“只修结果文件”往往不够

这部分是很多人第一次遇到时最容易误判的点。

### 7.1 只修 `.codex/config.toml` 看起来会暂时恢复

比如你把：

- 错误的 `npm_config_cache`
- 旧用户名项目路径
- 错误的浏览器缓存路径

都在当前机器 live 文件里改好了，重启之后也许就能临时工作。

### 7.2 但 SSOT 可能还没变

如果 `cc-switch.db` 里仍然保留：

- 旧 provider 快照
- 旧 MCP server 配置
- 旧 settings 值

那后面下面这些动作都可能让问题复发：

- 再切一次 provider
- 再导入一次备份
- 从 WebDAV 下载一次
- 在 UI 里重新保存当前 provider

### 7.3 更稳的理解方式

把 CC Switch 想成：

```text
数据库源数据 -> 写回 live 配置 -> 工具运行
```

所以修复顺序更稳的做法应该是：

```text
先修源头 -> 再修结果文件 -> 再做功能验证
```

## 8. 快速排查清单

下面这套是主人以后自己排查时最省时间的顺序。

### 8.1 第一步：先确认当前机器真实用户目录

例如：

```text
C:\Users\HN246
```

之后把所有指向旧用户名的路径都视为异常候选。

### 8.2 第二步：先扫 live 配置

PowerShell 示例：

```powershell
rg -n --hidden "C:\\Users\\Administrator\\|C:\\Users\\旧用户名\\" `
  C:\Users\HN246\.codex\config.toml `
  C:\Users\HN246\.claude.json `
  C:\Users\HN246\.gemini 2>$null
```

### 8.3 第三步：再扫 `.cc-switch` 目录

如果只是扫文本文件：

```powershell
rg -n --hidden "C:\\Users\\Administrator\\|C:\\Users\\旧用户名\\" `
  C:\Users\HN246\.cc-switch 2>$null
```

### 8.4 第四步：必要时进数据库层

这一步属于**偏程序员手段**，不是官方手册教普通用户的常规路径，所以我建议只在下面两种情况下上：

1. live 文件已经修了，但一切换又复发
2. 你已经确认 CC Switch 仍在写回旧值

如果你这次本机数据库结构和主人这次排查到的一样，可以优先查这些表：

- `mcp_servers`
- `settings`
- `providers`

如果对应列名也一致，可以优先检查：

- `mcp_servers.server_config`
- `settings.value`
- `providers.settings_config`

> 这一层“列名”属于这次实机排障看到的结构，不是我从官方手册里抄出来的公开 schema 文档，所以主人以后如果升级版本、数据库结构不同，要以自己本机实际表结构为准。

## 9. 最稳的修复顺序是什么

### 9.1 先备份

先备份：

- `C:\Users\<当前用户>\.cc-switch\cc-switch.db`
- 当前 `.codex/config.toml`
- 当前 `.claude.json`

### 9.2 先修源头

优先顺序建议这样理解：

1. 先尝试通过 CC Switch UI 重填当前 provider / MCP / 相关设置并保存
2. 再检查数据库源数据是否已被正确覆盖
3. UI 无法覆盖时，再考虑数据库层修复

### 9.3 再修当前机器上已经落地的 live 文件

至少检查这些项目：

- `.codex/config.toml` 里的 `npm_config_cache`
- `.claude.json` 里的 `npm_config_cache`
- `.codex/config.toml` 里的旧 `projects.'c:\users\旧用户名\...'`
- `.codex/config.toml` 里的旧 `bundled-marketplaces` 路径

### 9.4 最后重启并验证

修完后建议这样验证：

1. 重启 `Codex`
2. 重启 `Claude`
3. 在 `/mcp` 里重连目标 server
4. 验证：
   - MCP 是否不再显示 `Tools: (none)`
   - `npx -y chrome-devtools-mcp@latest --version` 是否能正常返回

## 10. 官方“不推荐手改数据库”，那这类问题该怎么拿捏

这一条我想单独讲，因为程序员看到这里通常会问：

> 你前面说根因可能在 `cc-switch.db`，可官方 FAQ 又说不推荐手工编辑数据库，那到底该怎么办？

我的建议是这样分层：

### 10.1 优先方案：通过 UI 覆盖 SSOT

如果当前 provider / MCP 在 UI 层可以完整打开、重填、保存，那优先这样做。  
因为官方 FAQ 已经说明：

- live 文件的改动会 backfill
- 保存后会同步回数据库

这条路径最稳，也最符合产品设计。

### 10.2 次优方案：删掉明显只属于旧机器的配置片段，再让 UI 重写

比如：

- 旧项目路径
- 旧浏览器路径
- 错误缓存目录

如果这些字段 live 层删掉后，重新编辑当前 provider 能被正确吸收回数据库，这也是比较稳的修法。

### 10.3 最后兜底：备份后直接修数据库

只有当下面几条同时成立时，我才建议你直接动库：

1. 你已经确认 `cc-switch.db` 是复发源头
2. UI 无法覆盖或无法暴露那个坏值
3. 你已经先做了完整备份
4. 你知道自己改的是“路径污染”，不是业务字段

也就是说：

- **官方推荐的是“不要手改数据库”**
- **工程实践允许的最后兜底是“先备份，再最小改动修库”**

## 11. 以后每次跨机同步后的推荐 SOP

我建议主人以后把这套动作当成固定流程。

### 11.1 导入后先别急着直接开工

先做一次“路径审计”。

### 11.2 优先查 3 个地方

1. `C:\Users\<当前用户>\.cc-switch\cc-switch.db`
2. `C:\Users\<当前用户>\.codex\config.toml`
3. `C:\Users\<当前用户>\.claude.json`

### 11.3 重点搜 4 类内容

1. 旧用户名路径
2. `npm_config_cache`
3. 浏览器可执行文件路径
4. 项目信任路径 / 本地缓存路径

### 11.4 修完后优先验证这些能力

- `chrome-devtools` MCP
- 所有依赖 `npx` 的 MCP
- 依赖浏览器路径的 MCP
- 依赖本地缓存目录的工具

## 12. 哪些字段天生就该被当成“机器相关风险字段”

这些字段在跨机同步时要特别小心：

- 用户目录：`C:\Users\<用户名>\...`
- 浏览器路径：`chrome.exe`、`msedge.exe`
- `npm_config_cache`
- `TEMP` / `TMP`
- `CHROME_PATH`
- `PROGRAMFILES`
- `LOCALAPPDATA`
- `APPDATA`
- 工具绝对路径：
  - `node.exe`
  - `python.exe`
  - 自定义 CLI 路径

只要它们写死到另一台机器的目录里，目标机器就很容易出问题。

## 13. 可直接丢给 AI 的标准提示词

下面这段保留得很好，主人以后可以直接复用：

```text
你现在在 Windows 环境，帮我排查并修复一个“CC switch 跨机同步后绝对路径污染”的问题。

背景：
1. 我把一台电脑上的 CC switch 配置导出后，导入到了另一台电脑。
2. 现在目标机器上的部分 MCP 或 AI 工具配置可能还带着源机器的绝对路径。
3. 已知这类问题会导致 /mcp 里 server 存在但 tools 为 0，或者 npx / chrome-devtools-mcp 启动失败。

你的任务：
1. 先确认当前机器的实际用户目录。
2. 检查这些位置里是否存在旧机器的绝对路径：
   - C:\Users\<当前用户>\.cc-switch\cc-switch.db
   - C:\Users\<当前用户>\.codex\config.toml
   - C:\Users\<当前用户>\.claude.json
   - 其他相关 AI 工具配置目录
3. 重点检查：
   - C:\Users\旧用户名\
   - npm_config_cache
   - CHROME_PATH
   - bundled-marketplaces source
   - projects.'c:\users\旧用户名\...'
4. 如果发现问题，不要只修当前落地配置文件，还要修 CC switch 的源数据库记录，避免下次切换再次写回旧路径。
5. 修复前先备份数据库或配置文件。
6. 修复后重新验证：
   - /mcp 中对应 server 是否恢复正常
   - npx -y chrome-devtools-mcp@latest --version 或 --help 是否能正常运行
7. 只做最小必要修改，不改业务逻辑，不改无关配置。

请你先做扫描和定位，再执行修复，并把“源头文件、实际命中的旧路径、修改项、验证结果”清晰列出来。
```

## 16. 最终判断

这次已经确认：

- 问题确实是跨机同步导致的旧机器绝对路径污染
- live 配置和 CC Switch 的源数据层都可能带着旧路径
- 只修当前配置文件不够，必须同时考虑 SSOT 层是否干净
- export 本来就不包含 `usage logs` 与 `device-level settings`，所以有些“没同步过来”其实是产品边界，不是故障
- 以后凡是公司电脑和自己电脑来回同步 CC Switch 配置，都应该先跑一次“旧用户名路径扫描”

如果主人下次再遇到类似问题，这篇就不是“复盘文章”，而是可以直接按步骤执行的排障手册。
