# 第 05 篇：CC Switch 跨电脑导出导入与云同步实战（2026-10复核）

> 资料核对时间：2026-10-11
> 结论先说：**有这个功能，但 4.0 已经把“迁移配置”和“备份整个数据库”分成不同操作。**CC Switch 官方支持配置导入、SQL 数据库备份、应用配置目录、WebDAV 和 S3 兼容云同步。
> 适合人群：像主人这样会在家里电脑、公司电脑、其他设备之间来回切换，而且手里有多家中转 Provider，不想每次都重新手配的人。

[[toc]]

---

## 1. 先给结论：主人的思路是可行的

如果主人的目标是：

- 在一台电脑上维护一份最新配置
- 需要时把这份配置带到其他电脑
- 尽量避免手改 Claude Code、Codex、Gemini CLI 等工具的配置文件

那 CC Switch 官方提供的 **手动导出 / 导入** 就是合适方案。

4.0 的官方手册在 `设置 -> 数据 -> 数据管理` 里区分了两类操作：

- 配置导入：用于跨设备迁移 Provider、MCP、Prompt 等配置
- `Export SQL Backup`：用于完整数据库备份
- 云同步：上传或下载数据库快照
- 导入、恢复和下载覆盖前会自动创建安全备份

所以从产品能力上说，主人的方案不是“曲线救国”，而是 **CC Switch 本来就支持的正式用法**。

---

## 2. 官方到底支持哪些跨设备方式

按官方资料，CC Switch 目前至少有 3 种相关能力：

| 方式 | 适合谁 | 特点 |
|------|--------|------|
| 配置导入 | 想把 Provider、MCP、Prompt 等配置带到另一台机器 | 迁移配置，不等于合并，也不带设备状态 |
| SQL 数据库备份 | 想完整留存配置、用量和应用设置 | 适合备份恢复；目标机器版本和数据边界要先核对 |
| 自定义配置目录 | 想把 CC Switch 数据放进同步盘 | 共享数据库风险高，必须避免多机同时写入 |
| WebDAV / S3 云同步 | 想让多设备维护一个远程数据库快照 | 下载会覆盖本地，先核对远程快照并保留备份 |

如果只看主人的需求，我更推荐先用 **手动导出 / 导入**，因为它最贴近“我只保留最新一份，然后其他电脑直接导入”这个思路。

---

## 3. 配置导入、SQL 备份和云同步分别带走什么

根据当前 FAQ，配置数据库的 SSOT 是 `~/.cc-switch/cc-switch.db`。应用内的配置导入适合迁移配置；`Export SQL Backup` 才是完整数据库备份。不要再把旧版 JSON 导出清单当作 4.0 的完整数据库备份说明。

### 3.1 配置导入

用于跨设备迁移时，重点是：

- Provider 配置
- MCP 服务器配置
- Prompt 预设
- 应用层配置

配置导入不是数据库文件复制，也不是多机合并。导入目标机前先备份当前数据库，并把它当作覆盖操作处理。

### 3.2 SQL 数据库备份

官方 FAQ 把 `Export SQL Backup` 定义为完整数据库备份，包含：

- Provider、MCP、Prompt
- 用量日志
- 应用设置

但仍不包含设备级 `settings.json`。它更适合恢复同一套 CC Switch 数据，不应直接当作“把所有设备文件复制到另一台机器”。

### 3.3 设备级数据和云同步边界

官方 FAQ 明确：

- `settings.json`、`live-state.json`、`codex-login-stash.json` 和 `backups/live-first-write/` 只属于本机，不随 CC Switch 配置目录迁移，也不参与云同步
- 云同步不上传只对本机有意义的数据，例如用量日志；SQL 备份则可以包含用量日志
- `cc-switch.db` 是配置和部分统计数据的 SSOT，`live-state.json` 负责本机当前直连/路由/聚合状态和最近写入内容

这意味着：

- 你配置过的中转站列表
- 各 Provider 的地址、Key、模型相关配置
- MCP
- 提示词预设

这些核心 Provider、MCP 和 Prompt 内容可以通过配置导入迁移；如果需要连同用量记录一起留存，应另行导出 SQL 备份。

如果导入后发现语言、窗口行为、配置目录、开机自启、当前模式或登录账号没有跟过去，不要判定为同步失败，这些属于设备级边界。

---

## 4. 但有两个限制，主人一定要先知道

这两条很关键，很多人以为“导入”就是“自动合并”，或者以为“所有设置都会一模一样跟过去”，实际不是。

### 4.1 导入是覆盖，不是合并

官方手册明确提示：

- 导入时会覆盖现有配置
- 建议导入前先导出当前配置做备份

所以如果主人现在多台电脑上的配置并不完全一样，最稳的做法不是直接选一台覆盖全部，而是：

1. 先把每台电脑都各自导出一份留底
2. 选一台作为“主配置机”
3. 把别的机器里独有的 Provider / MCP / Prompt 补齐到这台主配置机
4. 最后只从这台机器导出一份“最终最新版”

换句话说，**CC Switch 导入适合做“统一版本下发”，不适合做“多机自动合并”**。

### 4.2 设备级设置不会跨设备同步

官方 FAQ 明确写了：

- `~/.cc-switch/settings.json` 存的是设备级设置
- `~/.cc-switch/live-state.json` 记录每个应用当前是直连、路由还是聚合，以及 CC Switch 最近写入的配置状态
- `~/.cc-switch/codex-login-stash.json` 用于本机暂存 Codex 官方登录，不参与云同步
- 这些设置 **not synced across devices**

它举的内容包括：

- 语言
- 主题
- 窗口行为
- 开机自启
- 各 CLI 工具的自定义配置目录

所以主人要理解成：

- **核心 Provider / MCP / Prompt 配置可以迁移**
- **这台电脑自己的界面偏好、目录路径之类，不保证跟着一起过去**

这里和上面导出的“应用设置”不要机械画等号。更稳的理解是：

- 导出 JSON 主要面向 Provider / MCP / Prompts / 应用层配置
- `settings.json` 这类明确写进 FAQ 的 device-level settings 仍然按设备各自保存

如果你在不同电脑上把 Claude / Codex / Gemini 的配置目录改到了非默认位置，那目标机器上仍然要再检查一次。

## 5. 主人最该用的操作流程

下面这套是我结合官方文档后，给主人的 **最稳方案**。

### 5.1 第一次整理时，不要急着只留一份

先在每一台旧电脑上都做一次导出备份，命名可以像这样：

- `cc-switch-home-2026-05-01.json`
- `cc-switch-office-2026-05-01.json`
- `cc-switch-laptop-2026-05-01.json`

这样做的目的很简单：

- 防止后面发现某台机器上有独有 Provider，却已经被覆盖掉
- 给自己留回滚空间

### 5.2 选一台主配置机，整理成最终版本

建议选“配置最全、最新”的那台电脑做主配置机。  
如果别的机器上还有它没有的中转，就先补到主配置机里。

等确认无误后，再导出一份最终版，例如：

- `cc-switch-master-2026-05-01.json`

以后主人只维护这一个“主版本”就行。

### 5.3 把主版本放到你常用的同步位置

例如：

- OneDrive
- Dropbox
- iCloud Drive
- NAS 同步目录
- 加密 U 盘

这样你到其他电脑时，只要拿到这一个 JSON 就够了。

## 6. 具体怎么导出

### 6.1 在主配置机上操作

1. 打开 CC Switch
2. 点击左上角 `⚙️` 进入设置
3. 进入 `数据` -> `数据管理`
4. 选择配置导出/导入入口，生成一份配置迁移文件
5. 如果还要保存用量日志和完整数据库，另行点击 `Export SQL Backup`
6. 分别记录文件用途，不要把 SQL 备份当作普通配置迁移文件

配置迁移文件和 SQL 备份的格式、用途以当前界面标识为准；升级到 4.0 后不要根据旧文章默认它一定是 JSON。

### 6.2 导出前建议主人多做一步

如果你刚刚改过很多 Provider，建议在导出前快速检查一下：

- 当前常用 Provider 是否都还在
- Base URL、API Key、模型 ID 是否是最新值
- MCP / Prompt 是否齐全

因为你之后分发给其他电脑的，其实就是这一份“标准答案”。

---

## 7. 具体怎么导入

### 7.1 在目标电脑上操作

1. 先安装好 CC Switch
2. 打开 CC Switch
3. 进入 `设置 -> 数据 -> 数据管理`
4. 选择配置导入或数据库恢复入口
5. 选中对应的配置迁移文件或 SQL 备份
6. 点击 `导入`
7. 确认覆盖现有配置

这一段是官方手册明确给出的导入流程。

### 7.2 导入后怎么验证

建议主人至少做 3 件事：

1. 看 Provider 列表是否已经完整出现
2. 随机切换一个你常用的中转 Provider
3. 打开对应 CLI 工具做一次最小验证

例如：

- Claude Code：进项目后看 `/status`
- Codex / Gemini CLI / OpenCode：重开终端后跑一次最小请求

官方 4.0 发布说明还特别说明了一条：

- 大多数 CLI 工具切换 Provider 后需要重启终端或重启该 CLI
- 路由内切换通常无需重启；直连与路由切换后，Codex、Gemini CLI、Grok Build 等可能需要重启，按提示处理
- Claude Code 的聚合模型变化无需重启，但聚合需要 Claude Code 2.1.243+

## 8. 为什么我更推荐主人先用“手动导出 / 导入”

因为主人的核心诉求不是“所有机器永远自动同步”，而是：

- 我想维护一份最新配置
- 我去别的电脑时能快速恢复

这类场景下，手动导出 / 导入有 4 个优点：

1. 你永远知道“哪一份是主版本”
2. 不会因为自动同步把错误配置立即传播到所有设备
3. 迁移路径清晰，出问题容易回滚
4. 很适合多中转、多模型、多机器但不一定天天同步的人

所以主人说的“只保留最新的一份，然后其他电脑直接导入”，从方法论上是对的。

---

## 9. 如果你后面嫌手动麻烦，可以升级成官方云同步

CC Switch 官方 README 和设置手册都明确提到两类云同步方向。

### 9.1 方案一：自定义 CC Switch 配置目录

官方说明里写到，CC Switch 自身数据默认放在：

```text
~/.cc-switch/
```

并且这个应用配置目录可以在设置里自定义；修改后需要重启，CC Switch 不会自动把旧目录内容搬到新目录，需先手工复制。
README 还明确举了这些典型场景：

- Dropbox
- OneDrive
- iCloud
- NAS

这意味着你可以把数据库放进同步盘，但多台电脑同时写入同一个 SQLite 数据库存在冲突风险。更稳的做法是单写入、其他设备按需导入或下载。

不过这里主人要注意：

- 配置目录路径本身属于设备级设置
- `settings.json` 不会因为目录迁移自动同步
- 每台电脑第一次仍然要手动指向同步盘路径，并确认没有同时打开写入

### 9.2 方案二：WebDAV 云同步

如果你想让 CC Switch 直接通过应用内同步，官方还提供：

- WebDAV 服务器地址
- 用户名 / 密码
- 远程目录
- 配置名称
- 自动同步

而且按最新 Settings 手册，WebDAV 同步已经明确写成：

- 使用 **v2 协议**
- 带双层版本控制，提高同步可靠性
- 下载前先展示远程快照信息：协议版本、数据库版本、时间戳、大小

并支持：

- 测试连接
- 上传
- 下载
- 自动同步

官方手册也写得很清楚：

- 上传会覆盖远程数据
- 下载会覆盖本地数据
- 下载前会自动创建安全备份
- 自动同步会在数据库变更后把数据库推到 WebDAV

4.0 还支持 S3 兼容服务，包括 AWS S3、MinIO、Cloudflare R2、阿里云 OSS、腾讯云 COS 和华为云 OBS；可以测试连接、上传、下载和开启自动同步。上传会覆盖远程快照，下载会覆盖本地快照，先核对协议版本、数据库版本、时间戳和文件大小。

所以 WebDAV 更像“数据库级同步”，适合长期多设备协作使用。

## 10. 哪种方式更适合主人

我给主人的建议很直接：

### 如果你只是偶尔换电脑

优先用：

- **手动导出 / 导入**

这是最稳、最不容易误操作的方案。

### 如果你经常多机切换

可以考虑：

- **主版本 JSON + 云盘保存**

也就是：

1. 仍然用手动导出生成“主版本”
2. 把主版本放在 OneDrive / Dropbox
3. 到别的电脑时直接导入

这样已经能覆盖大部分需求，而且风险比自动同步更低。

### 如果你几乎每天多设备来回切

再考虑：

- **自定义应用配置目录**
- **WebDAV 自动同步**

但这两种方案更适合你已经把配置体系稳定下来之后再上。

## 11. 4.0 后不要再把 Shared Config Snippet 当成迁移核心

4.0 的升级说明明确：共享设置直接留在客户端配置文件里，旧的“通用配置片段”功能已经移除。切换 Provider 时，CC Switch 只替换地址、凭据、模型、协议等关键字段；MCP、Hooks、权限、插件、项目设置和注释留在各工具配置文件中。v4.0.8 另在 `设置 -> 数据 -> 应用诊断日志` 增加「打开日志」按钮，迁移或同步后出现模型发现、路由或写入异常时，可以直接定位 `cc-switch.log`。

因此迁移时应做两件事：

1. 用配置导入或 SQL 备份迁移 Provider、MCP、Prompt 等 CC Switch 数据
2. 在目标机检查工具自己的全局配置文件；需要迁移的 Hooks、插件、权限和项目设置，由工具原生配置或版本控制单独管理

如果升级后发现旧的 Shared Config Snippet 入口不见了，这是 4.0 的产品变化，不是导入失败。已有工具配置中的环境变量不会因为移除入口而自动删除。

## 12. 我给主人的最终推荐方案

如果让我按“稳、简单、少踩坑”来排序，我会建议主人这样做：

1. 先在每台旧电脑各导出一份备份
2. 选一台电脑作为主配置机
3. 把所有常用中转、MCP、Prompts 整理齐
4. 导出一份 `cc-switch-master-日期.json`
5. 把它放进 OneDrive / Dropbox 之类的位置
6. 在其他电脑安装 CC Switch 后直接导入这份主配置
7. 后续只维护这一份主配置，需要同步时重新导出覆盖旧文件

这套流程最符合主人现在的实际需求。

## 13. 两个额外提醒

### 13.1 如果你有自装 Skills，最好额外留意

FAQ 当前把 `skills/` 列为独立目录，并把 Skills 安装状态记录在数据库中。具体 Skill 文件是否已经同步到目标应用，仍要看 Skills 页的同步方式（自动、仅符号链接、仅复制）和目标应用目录。

所以更稳妥的理解是：

- 如果主人非常依赖本地安装的 Skills，迁移后应在 Skills 页检查“已安装”状态和目标应用目录
- 需要保留实际文件时，额外备份 `~/.cc-switch/skills/` 和目标应用的 `skills/` 目录
- 不要仅凭 Provider 配置导入成功，就假设所有 Skill 文件已经落地

这条是我根据官方导出清单和存储结构做出的**保守建议**，目的是避免你以为“所有 Skills 文件一定被装进 JSON 里”。

### 13.2 导入前、WebDAV 下载前，CC Switch 本身会做安全备份

官方 FAQ 写到：

- 每次配置导入、数据库恢复和云端下载覆盖本地数据库前会自动创建备份
- 默认保留最近 10 个备份

所以主人即使导错一份，也不是完全没有回头路。
