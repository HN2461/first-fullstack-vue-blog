# 第六篇：Kiro 工作流实战与最佳实践（2026-07）

> 本文基于 Kiro 官方文档和截至 2026-07-27 的 Changelog 整理。它是本系列的实践篇，重点不是罗列功能，而是说明 IDE 1.0 中这些能力如何组合。

[[toc]]

---

## 当前工作流全景

早期介绍常把 Kiro 概括成 Spec、Steering、Hooks、MCP 四件套。IDE 1.0 之后，更完整的工作流是：

1. **Steering / AGENTS.md** 提供项目长期规则
2. **Permissions** 先定义 Agent 的可操作边界
3. **Feature、Bugfix 或 Quick Spec** 把目标变成结构化产物
4. **Analyze Requirements** 发现跨需求矛盾和遗漏
5. **任务依赖图与子代理** 负责安全并行
6. **Autopilot / Supervised** 决定文件变更的审查节奏
7. **Hooks** 把确定性检查嵌入事件生命周期
8. **MCP / Powers** 只在确实需要外部能力时扩展工具
9. **测试、diff、checkpoint 与 Git** 共同完成验证和回退

其中最重要的原则是：先定义边界和验收标准，再提高自治程度。Autopilot、并行任务和自动批准都只能放大已有流程；如果规格模糊或权限过宽，它们也会更快放大错误。

## 实战场景：为博客增加全文检索

假设已有一个前后端分离博客，现在要增加全文检索：

- 公开文章按标题、摘要、正文检索
- 支持分类、标签和发布时间筛选
- 搜索结果高亮关键词并保留上下文片段
- 普通用户不能搜索草稿或私有文章
- 响应时间、分页和空查询行为需要明确

这个功能同时涉及需求边界、查询设计、权限过滤和前端交互，适合标准 Requirements-First Feature Spec，而不是直接 Vibe，也不建议为了省几次确认使用 Quick Spec。

### 第一步：先准备 Steering

最低限度保留三个基础文件：

```text
.kiro/
└── steering/
    ├── product.md
    ├── tech.md
    ├── structure.md
    ├── api-rules.md
    └── vue-rules.md
```

`product.md` 写公开/登录/管理员三类角色和文章可见性；`tech.md` 写 Vue、Node、MongoDB 及测试命令；`structure.md` 写目录与模块边界。API 和 Vue 规则使用 `fileMatch`，减少无关上下文：

```yaml
---
inclusion: fileMatch
fileMatchPattern: ["backend/src/**/*.js", "backend/tests/**/*.js"]
---
```

Steering 应记录稳定规则，不要把本次“全文检索”需求重复写进去。本次目标属于 Spec。

### 第二步：建立权限基线

在开始 Agent 会话前先处理高风险边界：

- 拒绝读取 `.env`、私钥和生产凭证
- 数据库迁移、删除命令、发布命令保持 `ask` 或 `deny`
- 允许项目内常用的构建、lint、只读 Git 命令
- MCP 数据库工具默认不自动批准写操作
- 子代理只授予完成专项任务所需的工具

IDE 1.0 的权限规则由 `capability`、`match`、`exclude`、`effect` 构成，限制强度为 `deny > ask > allow`。因此即使存在宽泛的 allow，也不能覆盖更具体的 deny。这比把安全希望全部寄托在 Prompt 上可靠。

### 第三步：创建 Requirements-First Spec

在 Kiro 面板点击 Specs 的 `+`，选择 Feature 与 Requirements-First，输入：

```text
为现有博客增加全文检索。请先只生成 requirements.md，不修改代码。

已知约束：
- 只能返回当前用户有权查看的文章
- 支持关键词、分类、标签、发布时间和分页
- 空关键词与特殊字符必须有明确行为
- 需要可测试的性能目标、错误行为和无结果状态
- 沿用现有 Vue 3、Express、MongoDB 架构
```

好的起始 Prompt 同时给出目标、不可破坏的行为、非功能约束和当前技术边界，但不替 Agent 提前决定所有实现细节。

### 第四步：运行 Analyze Requirements

需求生成后，不要只逐条阅读。选择 **Analyze Requirements**，让 Kiro 跨整份需求寻找：

- “全文”是否包含 Markdown、附件或评论
- 权限过滤是在检索前还是结果返回前生效
- 分类与标签筛选是 AND 还是 OR
- 空关键词配合筛选条件时是否允许
- “快速”究竟是 P95 还是平均响应时间
- 更新文章后索引何时可见
- 并发写入和翻页期间结果变化如何处理

分析会以澄清问题流式返回，选择建议答案或输入自定义答案后，Kiro 更新 `requirements.md`。复杂分析花费数分钟是正常现象，不要因为等待而跳过。

### 第五步：审查设计和属性

进入 `design.md` 后重点检查：

- 查询和索引方案是否符合现有 MongoDB 部署能力
- 权限条件是否进入同一查询，而不是取回后在内存过滤
- 高亮、分页和排序的数据流是否明确
- 索引变更是否需要迁移脚本和回滚策略
- 错误处理、观测指标和测试策略是否完整
- 设计中提取的 Property-Based Testing 属性是否真的来自需求

属性测试不是形式化证明，但能把 EARS 要求转成跨输入空间的可执行性质，例如：“对任意未授权用户和任意私有文章，搜索结果都不得包含该文章”。它适合权限、排序、序列化和边界输入，不需要替代所有例子测试。

### 第六步：生成可并行的 tasks.md

任务需要写清依赖和验证结果，例如：

```markdown
- [ ] 1. 建立检索查询与权限过滤
  - [ ] 1.1 新增查询参数校验及单元测试
  - [ ] 1.2 实现可见性过滤并验证私有文章不会泄漏
- [ ] 2. 建立索引迁移脚本（依赖 1.1 的字段定义）
- [ ] 3. 新增搜索 API 集成测试（依赖 1 和 2）
- [ ] 4. 实现前端筛选栏（依赖 1.1 的接口契约）
- [ ] 5. 接入搜索结果与高亮（依赖 3 和 4）
- [ ] 6. 执行构建、测试和回归检查（依赖全部实现任务）
```

点击 **Run all Tasks** 时，Kiro 会建立依赖图，按 wave 执行：无依赖任务并行，下一 wave 等前置任务完成后再开始。为了避免并发冲突，不要把会同时改同一个核心文件或共享数据库状态的任务描述成互不依赖。

### 第七步：选择 Autopilot 或 Supervised

**Supervised** 更适合第一次实现、权限敏感代码和迁移脚本。每个包含文件编辑的 Agent 回合结束后，可以按文件或 hunk 接受、拒绝或继续对话。

**Autopilot** 更适合规格已经充分审查、任务清晰且测试可靠的阶段。它可以跨文件修改、运行命令并持续推进，但仍应使用 checkpoint、View All Changes、Revert 和 Permissions 控制风险。

模式可以在会话中切换。实践上，设计和高风险任务使用 Supervised，重复实现和测试修复切到 Autopilot，通常比全程固定一种模式更合理。

### 第八步：谨慎使用子代理

适合并行委派的工作：

- 一个子代理核对后端查询与权限风险
- 一个子代理检查前端筛选交互与可访问性
- 一个子代理搜集现有测试模式和验证命令

子代理拥有独立上下文，完成后把结果返回主 Agent，能减少主会话污染。需要记住两个边界：子代理不会访问 Specs，Hooks 也不会在子代理中触发。关键验收标准应由主 Agent明确传入任务，不要假定子代理会自动读到 Spec。

专项自定义 Agent 可放在 `.kiro/agents/` 或 `~/.kiro/agents/`，frontmatter 中限制 `tools`、指定模型并写明职责。工具权限遵循最小授权：代码审查 Agent 通常只需要 `read` 和必要的文档 MCP，不需要 `write` 与生产工具。

## Hooks 如何嵌入工作流

Hooks 应自动化确定性检查，而不是替代任务规划。

### 保存后 lint

```json
{
  "version": "v1",
  "hooks": [
    {
      "name": "lint-source-files",
      "trigger": "PostFileSave",
      "matcher": "^(frontend|backend)/.*\\.(js|vue)$",
      "action": {
        "type": "command",
        "command": "npm run lint"
      },
      "timeout": 60,
      "enabled": true
    }
  ]
}
```

真实仓库前后端若各有独立 `package.json`，应调用仓库内统一脚本，或拆成两个范围明确的 Hook。不要假设根目录一定能运行 `npm run lint`。

### Spec 任务前后检查

- `PreTaskExec`：验证依赖服务、工作区状态或必要环境；需要阻断时 Shell 以 `2` 退出
- `PostTaskExec`：运行与该任务相关的测试或生成摘要
- `Stop`：在 Agent 回合结束后做安全检查，但要避免再次无条件触发 Agent 形成循环

Agent Prompt 动作会消耗额度；lint、类型检查和格式化应优先使用 Shell。Hooks 也不是安全边界的替代品，高风险文件和命令仍要由 Permissions 拒绝。

## MCP 与 Powers 的接入策略

### 先问“是否真的需要外部能力”

内置文件、Shell 和 Web 工具能完成的任务，不需要额外 MCP。接入每个服务器都会扩大数据边界和工具选择空间。

直接 MCP 适合单一、稳定的外部系统；Power 适合同时包含专业文档、工作流和大量 MCP 工具的技术。Power 会按关键词动态激活，避免几十个工具始终占用上下文。

### 配置基线

- 工作区 MCP：`.kiro/settings/mcp.json`
- 用户 MCP：`~/.kiro/settings/mcp.json`
- 两级配置合并，工作区优先
- 远程服务器优先使用 OAuth/PKCE，不硬编码 token
- 环境变量必须经 **Mcp Approved Env Vars** 明确批准
- 只读工具才考虑加入 `autoApprove`
- 用 `disabledTools` 隐藏删除、强推和生产写入能力
- 优先从官方 Server Directory 找当前维护的实现

全文检索示例通常只需要文档 MCP；若要让 Agent读取产品工单，可加 Jira/GitHub MCP，但创建或修改工单应保留确认。

## 模型与成本策略

Kiro 当前支持 Auto 路由和多个 OpenAI、Anthropic、开源权重模型。具体清单、地区和 credit multiplier 变化很快，不应把工作流绑定到某个永久默认模型。

实用分配方式：

| 工作 | 模型策略 |
| --- | --- |
| 日常实现和不确定任务 | 先使用 Auto |
| 跨模块重构、复杂终端操作 | 选择当前高可靠、长上下文的旗舰模型 |
| 搜索、分类、格式化、子代理搜集 | 选择更快、更低倍率的模型 |
| 合规要求只允许批准模型 | 禁用 Auto，并显式选择治理允许的模型 |

Auto 在管理员治理中是独立选项；启用 Auto 后，其内部路由不一定只落到管理员逐个批准的模型。对模型处理边界有硬性要求的组织，应阻止 Auto 并设置明确默认模型。

## IDE 与 CLI v3 的边界

Kiro CLI v3 已包含内置 Spec Agent、Steering、Hooks、Permissions、MCP、Skills、自定义 Agent、可信工作区和 Knowledge。它适合终端、远程环境、脚本化或无界面工作流。

迁移时不要把 IDE 配置机械照搬到 CLI：CLI v3 的自定义 Agent 使用 tags 替代旧工具列表方式，权限替代 trust flags，Hooks 使用新的 JSON schema；CLI v2 的 Supervised mode 也由权限模型取代。应按 [CLI v3 Feature Comparison](https://kiro.dev/docs/cli/v3/feature-overview/) 逐项迁移。

## 常见失败模式

### Spec 与代码脱节

需求变化先更新 `requirements.md` 或 `bugfix.md`，再同步设计与任务。Quick Spec 产物修改后使用 Sync Files，避免任务仍按旧需求执行。

### Steering 全部 always

只把所有任务都需要的规则设为 `always`。技术领域规范用 `fileMatch`，长流程用 `manual`。当前官方 IDE 文档没有 `inclusion: auto` 模式。

### 并行任务写同一处

Run all Tasks 能发现显式依赖，但无法替你消除含糊任务。任务必须明确共享文件、数据结构和迁移顺序。

### Hook 过于智能

高频保存事件触发 Agent 会产生延迟和额度消耗。确定性操作用 Shell，且测试返回码 `0`、`2` 和异常路径。

### MCP 权限过宽

`autoApprove: ["*"]` 只为省一次点击，却会把第三方写操作变成无确认执行。把服务器、工具、Permissions 和外部账号 scope 四层都收窄。

### 把 Autopilot 当成无人值守发布

Autopilot 代表连续执行，不代表可以绕过测试、代码审查、数据库备份和发布审批。生产变更仍应由现有工程流程控制。

### 忽略子代理的上下文边界

子代理看不到 Spec、不会触发 Hooks。委派 Prompt 必须带上验收标准、允许工具、输出格式和禁止事项。

## 一套可复用的完成清单

开始前：

- Steering/AGENTS.md 是否与当前项目一致
- Permissions 是否保护敏感文件和高风险命令
- 当前任务应使用 Vibe、Quick Spec、Feature Spec 还是 Bugfix Spec
- 是否需要 MCP/Power，数据会流向哪里

规划后：

- 需求是否可测试，是否运行 Analyze Requirements
- 设计是否覆盖权限、失败、观测、迁移和回滚
- 任务是否足够小，依赖关系是否明确
- 可测试属性是否与需求一一对应

执行后：

- 查看完整 diff，不只读 Agent 摘要
- 运行构建、单元测试、集成测试和编码检查
- 核对 Spec 任务状态与实际结果
- 对敏感变更做人工审查
- 更新项目文档与变更记录
- 使用 Git 提交形成可恢复边界
