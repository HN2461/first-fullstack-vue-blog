## 小白先看

节点测速不是“数字越小就一定越好”。更准确地说，不同测速方式测的是不同路段。

可以把一次访问网站想成一次外卖配送：

- 从你家到小区门口是一段路。
- 从小区门口到城市中转站是一段路。
- 从中转站到商家又是一段路。
- 商家打包和骑手取餐也要时间。

有些测速只测“你家到小区门口”，数字当然很好看；有些测速会把整条路都算进去，数字看起来就更高，但更接近真实体验。

常见测速方式大致可以这样记：

- **ICMP Ping**：测网络层往返，但很多服务器会限制 ICMP。
- **TCPing / RTT**：测到某个 TCP 服务或节点入口的连接往返。
- **URL Test / Connect**：通过代理访问测试网址，更接近完整代理链路。
- **下载测速**：看吞吐和拥塞，不等同于延迟。

日常判断节点体感时，不要只看最小延迟。更重要的是稳定性、丢包、抖动、晚高峰表现和目标服务是否可用。

## 这篇要解决的问题

很多客户端会给节点显示一个延迟数字，比如 20ms、80ms、300ms。新手最容易误解的是：只看这个数字选节点。

这篇的目标是帮你看懂：

1. 每种测速方式到底测了什么。
2. 为什么同一个节点在不同软件里数字差很多。
3. 什么情况下应该看延迟，什么情况下应该看真实播放、下载和网页打开速度。

## 为什么同一个节点测速结果差很多

因为“延迟”不是单一概念。

从你的设备访问一个网页，可能经过这些阶段：

1. 本机到代理客户端。
2. 代理客户端到入口节点。
3. 入口节点到落地节点或目标服务器。
4. DNS 查询、TCP 握手、TLS 握手。
5. 目标网站响应首字节。

不同工具可能只测其中一段，也可能把多个阶段都算进去。所以同一节点出现 20ms、100ms、300ms 都不稀奇，关键要知道它测的是什么。

一句话：**低延迟只说明某一段路快，不一定说明整条路都快。**

## 常见测速方式

### ICMP Ping

ICMP Ping 通过 ICMP Echo 报文测往返时间。它适合粗略判断网络是否连通，但不一定能代表代理体验。

小白可以这样理解：Ping 像是向对方喊一声“在吗”，看多久能听到回声。

局限很明显：

- 目标服务器可能禁用或限速 ICMP。
- ICMP 可达不代表 TCP/UDP 服务可用。
- ICMP 超时不一定代表节点不可用。

### TCPing

TCPing 通常尝试建立 TCP 连接，再用连接耗时估算延迟。它比 ICMP 更贴近 TCP 服务可用性，但依然可能只测到入口。

小白可以这样理解：TCPing 像是拨通一个电话，看电话接通要多久。

对于中转节点，如果 TCPing 测的是国内入口，数值会很好看，但它没有覆盖入口到海外落地、落地到目标网站这一段。这个数字适合判断你到入口的距离，不适合判断完整访问链路。

### RTT

很多客户端里的 RTT 本质上也是某种往返时间测量，通常用于衡量到节点或代理连接的响应速度。它适合快速排序节点，但不能替代真实访问测试。

小白可以这样理解：RTT 是“发出去再回来”的来回时间。

RTT 数字低，说明连接建立或探测响应快；但如果后续链路拥塞、丢包或落地质量差，实际体验仍可能很差。

### URL Test / Connect

URL Test 会通过代理节点访问一个测试 URL，例如 `generate_204`、静态小文件或指定网页，再根据响应耗时判断节点表现。

小白可以这样理解：URL Test 不是只问“在吗”，而是真的让节点去打开一个网页，看整个过程花多久。

它更接近用户实际访问，因为它覆盖了代理出站、目标访问、TLS 或 HTTP 响应等步骤。但它也会受测试 URL、目标 CDN、DNS 策略和握手开销影响。

对于中转链路，URL Test 往往比 TCPing 更有参考价值；对于直连节点，URL Test 可能把 TLS 握手、目标网站响应等成本也算进去，数字看起来偏高。

## 中转节点和直连节点要分开看

### 中转节点

中转链路通常是：

```text
用户设备 -> 国内或近端入口 -> 中转隧道 -> 海外落地 -> 目标网站
```

如果只测入口，数字可能非常低，但完整链路未必快。判断中转节点更适合看 URL Test、实际网页打开速度、视频缓冲速度和晚高峰稳定性。

### 直连节点

直连链路通常是：

```text
用户设备 -> 海外服务器 -> 目标网站
```

直连节点没有入口和落地拆分，TCPing / RTT 更能反映你到服务器的基础网络距离。URL Test 也有价值，但要知道它包含目标站点响应和握手成本。

## 延迟、带宽、丢包不是一回事

| 指标 | 代表什么 | 影响什么 |
| --- | --- | --- |
| 延迟 | 单次往返耗时 | 打开首屏、交互、游戏、会议 |
| 带宽 | 单位时间可传输数据量 | 下载、视频码率、大文件同步 |
| 丢包 | 报文未成功到达比例 | 卡顿、重传、语音视频抖动 |
| 抖动 | 延迟波动幅度 | 实时通信、游戏稳定性 |

看视频时，200ms 延迟未必不能用；但丢包高、带宽低、抖动大，会更直接地造成卡顿。反过来，游戏和视频会议更敏感的是延迟和抖动。

## 推荐判断流程

1. 先用客户端自带测速排除明显不可用节点。
2. 中转链路优先看 URL Test，直连链路可参考 TCPing / RTT。
3. 同一节点连续测 3 次，不要只看一次最低值。
4. 晚高峰再测一次，避开“白天很好、晚上拥塞”的误判。
5. 用真实目标服务验证，例如打开网页、播放视频、登录工作平台。
6. 对异常节点看日志：DNS 失败、TLS 失败、连接超时、目标拒绝，原因完全不同。

## 小白选节点口诀

- 中转节点：更看 URL Test，不要只看 TCPing。
- 直连节点：TCPing / RTT 有参考价值，但仍要真实打开网页试。
- 看视频：带宽和稳定性比 20ms 还是 100ms 更重要。
- 打游戏、开会议：延迟、丢包、抖动都重要。
- 晚上再测一次：白天快不代表晚高峰也快。

## 常见误区

### “10ms 节点一定比 100ms 节点快”

不一定。10ms 可能只是到入口的延迟，100ms 可能是完整链路延迟。测速对象不同，不能直接比较。

### “Connect 数字高就是节点差”

不一定。Connect / URL Test 可能包含 TCP、TLS、代理转发、目标响应等多段耗时。直连节点上这个数值天然可能比 TCPing 高。

### “ICMP 超时就是节点不可用”

不一定。很多服务器会禁 ICMP，但 TCP 或 UDP 服务仍正常。

### “测速软件排名第一就是实际最好”

不一定。测速 URL、规则、DNS、目标平台都可能影响结果。最终还是要以真实使用场景验证。
