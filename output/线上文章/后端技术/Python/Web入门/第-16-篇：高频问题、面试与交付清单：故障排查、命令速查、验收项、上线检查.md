# 第 16 篇：高频问题、面试与交付清单：故障排查、命令速查、验收项、上线检查

## 核心概念速答

### FastAPI 为什么快

FastAPI 基于 ASGI、Starlette 和 Pydantic，能高效处理 I/O 并发和数据校验。但框架基准不等于业务服务性能；SQL、外部接口、序列化、日志和部署配置通常更决定真实延迟。

### ASGI 和 WSGI 的区别

WSGI 主要面向同步请求响应；ASGI 支持异步调用、WebSocket 和生命周期事件。ASGI 并不会让同步阻塞库自动变成异步。

### `def` 和 `async def` 怎么选

异步库使用 `async def` + `await`；同步阻塞库可用普通 `def` 或受控线程池；CPU 密集任务交给进程/任务队列。核心是调用链是否真正非阻塞。

### Pydantic Model 和 ORM Model 的区别

Pydantic 表达接口输入输出并做校验序列化；ORM Model 表达数据库映射、关系和约束。二者生命周期、暴露字段和职责不同。

### `response_model` 有什么价值

验证输出、过滤未声明字段、生成 OpenAPI，降低内部字段泄露风险。它不能代替业务权限和敏感数据审查。

### `Depends` 的价值

声明并复用数据库 Session、当前用户、权限和基础设施客户端，形成可缓存的依赖树；测试可以通过 dependency_overrides 替换。

### Middleware 和 Dependency 怎么选

中间件适合所有请求的协议级横切能力，如 request ID、耗时、CORS。依赖适合路由可声明、可组合并能返回对象的业务前置，如认证、权限、Session。

### 为什么 Repository 不随意 commit

事务属于完整业务用例。若每个数据访问函数都提交，上层无法保证多表更新全成功或全失败。

### 为什么预检查不能保证唯一

两个并发事务可以同时查询“不存在”后同时插入。数据库唯一约束是最终保证，应用捕获约束冲突返回 409。

### 401 和 403 区别

401 表示未认证或凭证无效，Bearer 场景通常带 `WWW-Authenticate`；403 表示身份已确认但权限不足。

### JWT 为什么不是完整会话系统

JWT 自包含且签名有效不代表用户仍启用、权限未变或未主动退出。仍需 token_version、jti 撤销、刷新令牌记录或服务端会话等状态机制。

### 为什么 AsyncSession 不能并发共享

Session 维护事务和 ORM 状态，不是并发安全对象。同一 Session 同时执行多个 task 会导致连接和事务状态冲突。

### Offset 和 Cursor 分页怎么选

后台表格需要跳页和总数时用 Offset；大数据量、连续信息流和频繁变动数据用 Cursor。二者都要稳定排序和 page size 上限。

### BackgroundTasks 和任务队列的区别

BackgroundTasks 与 Web 进程同生共死，没有持久化重试和跨实例协调；任务队列适合重要、耗时、可重试和需要进度的工作。

### 缓存一致性怎么处理

常用 Cache Aside：读时未命中查库并写缓存，写时先提交数据库再失效缓存。还需考虑并发、击穿、雪崩、删除失败和权限范围。

### 为什么迁移不能由每个实例启动时自动跑

多个副本并发迁移会竞争，迁移失败也会把应用启动和结构变更绑死。生产用单次受控 Job，先备份和审查兼容性。

## 常见故障排查

### 422 Validation Error

检查：

1. 参数来源是 Path、Query、Body 还是 Form。
2. Content-Type 是否正确。
3. JSON 字段名、必填和 null 是否符合模型。
4. Pydantic 约束和验证器错误位置。
5. 前端是否把数字、布尔和数组序列化成预期格式。

### 401 但 token 看起来存在

检查：

1. Header 是否为 `Authorization: Bearer <token>`。
2. token 是否过期、类型是否 access。
3. issuer、audience、算法和密钥是否一致。
4. 用户是否禁用，token_version 是否变化。
5. 服务器时间是否严重漂移。

### 响应序列化报错

检查：

1. response_model 是否与实际返回结构一致。
2. ORM Schema 是否启用 `from_attributes=True`。
3. 关联是否预加载。
4. Session 是否已关闭或对象已过期。
5. datetime、Decimal、自定义类型是否可序列化。

### MissingGreenlet 或异步懒加载错误

通常是响应序列化时触发未显式等待的 ORM 懒加载。通过 `selectinload`/`joinedload` 预加载，或 `lazy='raise'` 提前暴露问题。

### 数据库连接耗尽

检查：

1. Session 是否在依赖 finally 中关闭。
2. 是否存在长事务和外部调用持锁。
3. 实例数 x worker 数 x pool_size 总量。
4. 数据库慢查询和锁等待。
5. 后台 worker 是否也占连接。

### 接口偶发卡顿

检查同步阻塞调用、事件循环延迟、连接池等待、DNS/外部 HTTP 超时、Redis 慢命令、大响应序列化和垃圾回收。用追踪拆分耗时，不靠猜。

### 更新后仍返回旧数据

检查缓存 key、失效顺序、CDN/浏览器缓存、读副本延迟、事务是否提交、ORM identity map 是否仍持旧对象。

### Alembic autogenerate 没发现模型

检查模型是否被 import、target_metadata 是否指向正确 Base、应用是否存在多个 Base、数据库 URL 是否连到预期环境。

### CORS 报错

检查浏览器 Origin 是否精确匹配、OPTIONS 预检、允许方法/请求头、credentials 与通配符冲突。CORS 只影响浏览器，curl 成功不代表浏览器配置正确。

## API 设计清单

- 资源路径、方法和版本一致。
- 请求和响应都有明确 Schema。
- 创建 201、删除 204、冲突 409、校验 422。
- 分页上限、稳定排序和筛选白名单。
- 错误 code 稳定，message 不作为程序判断依据。
- OpenAPI 记录权限、状态转换和异常条件。
- 非幂等关键写操作支持幂等键。
- 批量接口明确全成全败或部分成功。

## 数据库清单

- 非空、唯一、外键、CHECK 落库。
- 外键删除策略明确。
- 高频查询有经验证的索引。
- Session 请求级，事务由 Service 控制。
- 无 N+1 和意外懒加载。
- 并发唯一、乐观锁、行锁按场景设计。
- 迁移人工审查，能从空库升级。
- 破坏性变更使用 expand/contract。

## 认证授权清单

- 密码专用哈希，日志无敏感值。
- JWT 固定算法、issuer、audience、type、exp。
- 用户禁用、改密和退出能使旧会话失效。
- 功能权限、对象范围、状态规则均在后端检查。
- 登录、注册、重置限流。
- Cookie 方案有 CSRF；Bearer 方案重点防 XSS。
- 管理操作写不可篡改审计。

## 外部资源清单

- 上传限制大小、类型、内容签名和路径。
- 对象 key 绑定所有者，下载 URL 短时有效。
- HTTPX 复用客户端并设置分阶段超时。
- 重试只用于可安全重试操作。
- Redis key 有版本、TTL 和范围。
- 缓存更新有失效与故障降级。
- 关键任务持久化、幂等、有限重试和死信处理。

## 测试清单

- 单元、Service、API、集成层次合理。
- 测试数据库独立并执行真实迁移。
- 401、403、404、409、422、429、500 覆盖。
- 事务失败后验证没有部分提交。
- 并发冲突有真实数据库测试。
- 外部服务、时间、随机数可控。
- 测试无顺序依赖和 sleep。
- CI 从干净环境执行全部检查。

## 上线清单

- 生产关闭 debug 和 reload。
- Secret 不在仓库、镜像和日志。
- HTTPS、CORS、代理信任范围正确。
- liveness/readiness 和优雅关闭可用。
- worker、数据库池和外部连接总量已计算。
- 日志、指标、追踪和告警可定位问题。
- 数据库已备份并完成恢复演练。
- 迁移、发布、验证、回滚步骤明确。
- 发布后观察错误率、p95/p99、连接池和队列。

## 面试表达模板

回答项目题不要只罗列技术名词，按“问题、约束、方案、权衡、验证”表达：

```text
问题：文章发布同时要改状态、写审核记录并通知订阅者。
约束：数据库必须一致，外部通知可能超时且会重复投递。
方案：状态、审核记录和 outbox 在一个事务提交；worker 读取 outbox 发送，任务按 event_id 幂等。
权衡：通知变为最终一致，但避免在数据库事务中等待外部服务。
验证：测试中模拟 outbox 写入失败检查事务回滚，并模拟消息重复验证只产生一次业务效果。
```

这种表达能说明你理解工程边界，而不是只背过 FastAPI API。

## Express 对照速查

| FastAPI 概念 | Express 5 常见实现 | 验收重点 |
| --- | --- | --- |
| `APIRouter` | `express.Router()` | 路径前缀和业务模块边界清楚 |
| Pydantic | Zod | 输入和输出都校验，PATCH 区分未传与 `null` |
| `Depends` | 中间件 + `req` 上下文 | 认证、权限和数据范围不能漏挂 |
| Exception Handler | 四参数错误中间件 | 统一状态码、错误码，不泄露堆栈 |
| SQLAlchemy Session | Mongoose Model / ClientSession | 普通查询与事务会话边界分清 |
| Alembic | 版本化迁移脚本 | 默认 dry-run，显式 `--apply`，可幂等 |
| pytest + HTTPX | Vitest + Supertest | 不监听真实端口，测试库独立 |
| lifespan | bootstrap + shutdown hooks | 连接只创建一次，关闭顺序可控 |

真正掌握一个知识点的标准，不是能解释 FastAPI 写法，而是能在 Express 中实现同一 HTTP 契约，并说明为什么状态码、权限、事务和错误语义不能因为框架变化而变化。
